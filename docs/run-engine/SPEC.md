# Run Engine — engineering spec

Tracking: issue #79. Plan: [run-engine-plan-2026-10-12.md](../run-engine-plan-2026-10-12.md). Background: [catch-up](../catch-up-orchestration-2026-10-12.md), [ideation](../architecture-ideation-2026-10-12.md).

This spec is the contract for implementation. If code and spec disagree, fix one and say which.

## 1. Goal and scope

Every chat turn is a **run** with a durable ID. Nothing happens to a provider until the intent is saved. After a crash the daemon knows what was in flight and says so. Stop, Steer and Undo target a run, never a thread.

Module root: `src/mms/run/`. One profile-scoped SQLite database at `<profileHome>/run/run.db`. The engine is added **beside** `OrchestratorService` and takes over one responsibility per phase. Nothing in this spec requires the GUI to change in Phase 1; the protocol gains optional fields.

## 2. Invariants (enforced by code and checked by `fsck`)

1. A command is durable before any provider I/O.
2. Every control command (`stop`, `steer`, `respond`) names a `runId`. A mismatch is recorded as an `ignored` command with a reason; it never falls through to another run.
3. Run state changes by compare-and-set on `(run_id, epoch)`. Terminal states are final. A retry is a new attempt.
4. Every command commit carries `expectedSequence`; a stale write is rejected, not merged. (One write discipline only: locked full-row writes would clobber compare-and-set writes.)
5. Only the root attempt finishes a run. Child completion is a stored row, not a callback.
6. A `clientRequestId` seen twice returns the first receipt and performs nothing. Transient failures produce **no** receipt; only semantic rejections do.
7. Transcripts and events are never deleted automatically.
8. Provider names appear only under `src/mms/run/adapters/`. CI counts violations and fails if the count rises (Phase 0 ratchet).
9. Liveness is a lease with an expiry that the reconciler enforces, never "did the stream end".
10. After a crash, a run that was `running` becomes `interrupted` (if we know the provider process died with the daemon) or `uncertain` (if we cannot tell). Neither is ever auto-resumed.

## 3. Data model (Phase 1)

All tables `STRICT`. All IDs are strings. All timestamps ISO-8601 UTC strings. `payload` columns are canonical JSON (`src/mms/net/sync/codec.ts#canonicalJson`).

```sql
CREATE TABLE run_schema_migrations(version INTEGER PRIMARY KEY, applied_at TEXT NOT NULL) STRICT;

-- One row per user-visible turn.
CREATE TABLE runs(
  run_id        TEXT PRIMARY KEY,                 -- run:thread:<threadId>:ordinal:<n>
  thread_id     TEXT NOT NULL,
  ordinal       INTEGER NOT NULL,                 -- 1-based per thread
  status        TEXT NOT NULL CHECK(status IN ('queued','starting','running','finalizing','paused','completed','interrupted','failed','cancelled','uncertain')),  -- 'paused': migration 10, §5
  epoch         INTEGER NOT NULL DEFAULT 0,       -- bumped on every status write; CAS key
  active_attempt_id TEXT,
  source        TEXT NOT NULL,                    -- gui | cli | channel | schedule | wake | steer-followup | ...
  client_request_id TEXT,
  user_message_id   TEXT,
  requested_at  TEXT NOT NULL,
  started_at    TEXT,
  completed_at  TEXT,
  outcome       TEXT,                             -- JSON: {error?, interruptedBy?, uncertainReason?}
  UNIQUE(thread_id, ordinal)
) STRICT;
CREATE INDEX runs_thread_status ON runs(thread_id, status);

-- One row per execution of a run. Steering restart or retry creates a new attempt.
CREATE TABLE run_attempts(
  attempt_id    TEXT PRIMARY KEY,                 -- attempt:<runId>:<n>
  run_id        TEXT NOT NULL REFERENCES runs(run_id),
  ordinal       INTEGER NOT NULL,
  reason        TEXT NOT NULL CHECK(reason IN ('initial','steer_restart','retry','recovery')),
  status        TEXT NOT NULL CHECK(status IN ('pending','running','completed','interrupted','failed','cancelled','superseded')),
  provider_ref  TEXT,                             -- JSON {provider, model, sessionId?, nativeTurnId?}; refs only
  started_at    TEXT,
  completed_at  TEXT,
  UNIQUE(run_id, ordinal)
) STRICT;

-- Idempotency receipts. One per clientRequestId. Only semantic rejections are stored as rejected.
CREATE TABLE receipts(
  client_request_id TEXT PRIMARY KEY,
  thread_id     TEXT NOT NULL,
  command_kind  TEXT NOT NULL,
  status        TEXT NOT NULL CHECK(status IN ('accepted','rejected','ignored')),
  result        TEXT,                             -- JSON: {runId?, sequence, reason?}
  created_at    TEXT NOT NULL
) STRICT;

-- Append-only per-thread event log. Source for client sync, Bridge, and fsck.
CREATE TABLE thread_events(
  seq           INTEGER PRIMARY KEY AUTOINCREMENT,
  thread_id     TEXT NOT NULL,
  run_id        TEXT,
  type          TEXT NOT NULL,                    -- run.created | run.status | attempt.created | attempt.status | command.ignored | ...
  payload       TEXT NOT NULL,                    -- full entity, not a delta
  created_at    TEXT NOT NULL
) STRICT;
CREATE INDEX thread_events_thread_seq ON thread_events(thread_id, seq);
```

Phase 2 adds `effects` (outbox) and `leases`. Phase 4 adds `inbox` and `lineage`. Phase 5 adds `credentials`. Each phase ships its own migration.

**Why rows plus a log, not a projected event store.** Control state in CAS rows is simpler for coding agents to extend correctly than a projector that must stay deterministic. The log carries full entities so a projector can be added later if wanted. `fsck` cross-checks the two.

## 4. Commands and receipts

Every mutation enters as a `RunCommand`:

```ts
type RunCommand =
  | { kind: 'send';   threadId; clientRequestId; input: OrchestratorSendInput; source; forceQueue?: boolean }
  | { kind: 'stop';   threadId; clientRequestId; runId; clearQueue?: boolean }
  | { kind: 'steer';  threadId; clientRequestId; runId; text }
  | { kind: 'respond';threadId; clientRequestId; runId; requestId; answer }
```

`RunEngine.dispatch(command, { expectedSequence? })` returns `CommandResult`:

```ts
type CommandResult =
  | { status: 'accepted'; runId?: string; sequence: number; replayed: boolean }
  | { status: 'rejected'; reason: string; sequence: number }       // semantic; stored
  | { status: 'ignored';  reason: string; sequence: number }       // e.g. stop for a finished run; stored
```

Rules:
- `dispatch` runs under a **per-thread in-process mutex** (`src/mms/run/ThreadMutex.ts`, non-reentrant, FIFO, with a 30 s acquire timeout that throws rather than deadlocks).
- Inside the mutex: look up receipt → if found, return it with `replayed: true` and do nothing. Otherwise decide → one `db.transaction` writes rows + events + receipt. **No I/O inside `decide` or the transaction.**
- `expectedSequence`, when provided, must equal the thread's current max `seq`; otherwise `rejected` with `reason: 'stale_sequence'` and **no receipt** (the caller should re-read and retry).
- A thrown exception during decide or commit rolls back and surfaces as an error. It does **not** write a receipt (invariant 6).
- `stop`/`steer`/`respond` whose `runId` is not the thread's active run return `ignored` with `reason: 'run_not_active'` and append a `command.ignored` event with `{runId, activeRunId, kind}`.

## 5. Run lifecycle (Phase 1)

```
queued ──▶ starting ──▶ running ──▶ finalizing ──▶ completed
   │           │           │             │
   └──cancel───┴──interrupt┴─────────────┴──▶ interrupted | failed | cancelled
                                                    (crash) ──▶ uncertain

running | finalizing ──usage limit──▶ paused ──resume──▶ interrupted (continued by a new run)
                                         └──cancel / stop / user message──▶ cancelled
```

- `send` on an idle thread creates `run(queued)` and an `attempt(pending)`, then (Phase 1 only) hands the run to the legacy `OrchestratorService.executeTurn` through an adapter hook. The hook calls `engine.markStarting(runId, epoch)`, `markRunning`, `markFinalizing`, `markTerminal(status, outcome)`. Each is a CAS write; a CAS miss throws `StaleRunWriteError` and the legacy code must stop touching that run.
- **Active** means `starting|running|finalizing`; at most one per thread. Any number of `queued` runs may wait behind it (SPEC §2.3 applies to active runs only).
- **Active** means `starting|running|finalizing`; at most one per thread (`RunStore.getActiveRun`). Any number of `queued` runs may wait behind it (`listQueuedRuns`). Invariant 2.3 applies to active runs only.
- `send` on a busy thread creates `run(queued)` and enqueues into the existing durable `queue.json` with `runId` stored on the `QueuedMessage` (new optional field). When the legacy drain picks it up, it uses the existing `runId` instead of creating a new run.
- `stop` for the active run: CAS `running→interrupted` is **not** done by the command; the command sets `runs.outcome.stopRequested = true` under CAS (epoch bump) and signals the legacy abort controller. The terminal write comes from the hook when the turn actually ends. This keeps "who wrote the terminal state" single-sourced.
- Startup: `engine.reconcileOnBoot()` runs before any turn is admitted. Every run in `starting|running|finalizing` becomes `interrupted` with `outcome.interruptedBy = 'daemon_restart'` (Phase 1: we know the legacy loop died with us). Phase 2 introduces `uncertain` for out-of-process providers.
- **Paused** (migration 10): a run whose turn hit a provider usage limit and waits for it to reset. `engine.pauseRun({ runId, pause, resumeAt? })` moves `running|finalizing → paused` in one transaction (refused `bad_request` when `outcome.stopRequested` is set: the Stop wins), interrupts the attempt and, with `resumeAt`, enqueues the `run.resume` effect (§12.2). `outcome.pause` (`RunPause`) records the reset time (`until`, `estimated`), the window, the automatic-resume count, whether a timer is armed (`autoResume`) and, once it ends, `endedBy` (set only on a run that has left `paused`).
  - **A pause ends only through `endPause`** (or the sends and Stop paths that call it): `markTerminal` refuses a `paused` run (`conflict`), because a terminal write alone would leave its `run.resume` pending, and the resume lane is first-in, first-out. `pauseRun` also cancels any pending `run.resume` of the thread whose run is not paused.
  - **Stale timer (24 h rule).** The `run.resume` executor treats an *automatic* timer that fires more than 24 hours after `pause.until` (Mousse was off over the reset) as stale: it calls `endPause(runId, 'stale')`, tells the user to press Resume now, and sends nothing. `stale` is not an end: the run stays `paused`, `pause.autoResume` becomes `false`, `pause.stale` is set, `endedBy` stays unset, and the pending automatic timers are cancelled. A Resume now (`payload.manual`) is exempt from the rule and survives a stale ruling; only it continues a stale pause.
  - **Resume now.** `requestResume(runId, true)` replaces a pending automatic timer with a manual one available now. A manual timer that is pending or running is returned as it is. An automatic timer that is running does not take the press (it acts on its own payload and may rule the pause stale): a manual timer is queued behind it, and finds the pause ended if the running one handed the run over.
  - A paused run is **non-terminal** (`TERMINAL_RUN_STATUSES` excludes it, so a subagent whose run is paused stays busy and its delegation stays `running`) but **not active** (`getActiveRun` excludes it): the thread accepts a person's message. `getPausedRun(threadId)` returns it; at most one exists.
  - **It ends in the same transaction that admits or starts its replacement.** `commitSend` on a paused thread: a person's message creates its run, then `endPause(…, 'user_message')` (the result carries `endedPause`); the continue turn (`source: 'resume' | 'resume_now'`, `continuationOfRunId` = the paused run) creates its run, records `outcome.continuationOf` and `outcome.resumedFromPause` (`auto|user`) and ends the pause as `resume|resume_now` (the paused run becomes `interrupted` by `provider`); a continue turn for a pause that already ended is rejected `pause_ended`. `markStarting` of a person's run that was queued before the pause ends it the same way.
  - **Work started on the thread's behalf never runs beside a pause**: every fenced source other than `resume`/`resume_now` (`wake`, `provider-continuation`, `integration`, `delegation`, `steer-late`) is rejected `thread_paused` by `commitSend` and refused `conflict` by `markStarting`, so its executor defers and the pause and its timer stay intact.
  - **Every Stop path ends it**: the subtree Stop ends a paused run in the subtree (`endPause(…, 'stop')`), a run-scoped Stop naming it is accepted and ends it, and `task_cancel` of a subagent with a paused run ends the pause. `resume` and `resume_now` are fenced sources: a Stop after the continue turn was admitted cancels it.
  - **Whether a failed turn pauses** is decided by `decideUsageLimit` (`run/pausePolicy.ts`): the typed `provider_usage_limit` error pauses, and so does a managed Codex's gateway `rate_limited` error when the typed limit is its cause (a `rate_limited` error without it is a short wait and fails as before). `until` is the provider's reset time when it can be believed, else a 5-hour estimate (`estimated`). A reset that passed within the last five minutes (the limit just reset, or a fast clock) counts as reported and becomes 30 seconds from now; older, unparseable or more than 8 days ahead is estimated. A managed Codex's every usage limit (`usageLimitExceeded`, `rateLimitExceeded`, a 429, or an older server's message alone) is `rate_limited` with the typed limit as its cause. `count` is one more than the pause the run continues when the timer sent that continue turn (`resumedFromPause: 'auto'`); a Resume now or a person's message starts the count again. Past the cap (3 by default) the decision is a failure, not a pause. A run being stopped is never paused.
  - Boot leaves a paused run alone (it is not active); its pending `run.resume` stays, a running one is re-queued with the other replay-safe effects. Reconciler rule 4 treats a paused thread as busy: its pending inbox rows stay pending and no wake or steer is created, until the continue turn carries them (§14.3).
- `turn-state` events already emitted by `OrchestratorService` gain `runId`. `TurnState.turnId` is set to the `runId`.

## 6. Protocol changes (Phase 1, additive)

- `orchestrator.send` accepts optional `clientRequestId`. Response gains `runId` and `sequence`. **The RPC still awaits the turn in Phase 1** (changing that is Phase 2) but the `runId` is emitted immediately via a new `run.created` protocol event so clients can target it.
- `orchestrator.abort` and `orchestrator.steer` accept optional `runId`. When present, the engine path is used and `ignored` is a valid response (`{ok:false, ignored:true, reason}`). When absent, `steer` is unchanged (deprecated, removed in Phase 2) and `abort` is a Stop of the thread: `OrchestratorService.stopThread`, the same Stop as with a `runId` (§14.7).
- New read methods: `runs.list(threadId, {limit})`, `runs.get(runId)`, `runs.events(threadId, {afterSeq, limit})`.
- New events on the ring: `run.created`, `run.status`, `command.ignored`.
- All params validated like existing handlers (`asString`, bounded lengths, reject unknown keys).

## 7. `fsck` (Phase 0 skeleton, Phase 1 real checks)

`mousse-cli run fsck [--profile]` and `RunFsck.check(db)` return a list of findings:

## 12. Phase 2 — effects, leases, reconciler, uncertainty

Phase 1 records runs but the legacy loop still performs provider I/O inline. Phase 2 moves every provider-facing action behind a durable **effect** and adds a **reconciler** that keeps stored state and reality in agreement. The reconciler is not optional: it is what a lease-only design lacks: unchecked leases, no timeouts, undetected clean stream ends.

### 12.1 Tables (migration 2)


### 12.2 Effect kinds and classes

| kind | class | timeout | what it does |
|---|---|---|---|
| `turn.start` | process_bound | 6 h | run the provider turn (legacy `executeTurn` body, later adapters) |
| `turn.interrupt` | process_bound | 30 s | abort the live turn; "not active" counts as success |
| `turn.steer` | process_bound | 30 s | deliver steer text to the live turn |
| `request.respond` | process_bound | 30 s | deliver a settled approval request's answer to the provider callback waiting in this process (§17.4); control lane, never retried |
| `checkpoint.capture` | replay_safe | 2 min | **reserved**: post-turn git checkpoint (when enabled) |
| `title.generate` | replay_safe | 1 min | **reserved**: thread title (own lane; never blocks turns) |
| `workspace.cleanup` | replay_safe | 5 min | **reserved**: release leases, remove scratch worktrees |
| `run.resume` | replay_safe | 1 min | continue a `paused` run at its reset time (`available_at`), or at once for Resume now (`payload.manual`); own `resume` lane, so a waiting timer never blocks the thread's other effects |

**process_bound** effects die with the daemon; on boot they are `cancelled` and their run becomes `interrupted`. **replay_safe** effects are re-queued on boot. A kind's class is fixed in code, not per row.

**Reserved** kinds keep their class, lane and timeout but have no producer yet: `EffectOutbox.enqueue` refuses them at once with `bad_request('reserved effect kind')`, and the worker has no executor for them (a row that exists anyway fails with `'no executor'`). Plain questions (`ask_user`, plan questions, quick actions) are still answered in-process and approval requests are answered by `request.respond` (§17), checkpoints are taken inside the turn, titles are generated by the orchestrator, and worktree cleanup belongs to the lifecycle services.

### 12.3 Worker and lanes

- One in-process worker whose fibres (plain async loops) are grouped by lane class: **turn** fibres claim only `turn.start`, **control** fibres claim only `turn.interrupt|turn.steer|request.respond`, **replay-safe** fibres claim only the replay-safe kinds (`EffectOutbox.claimNext(owner, now, { lanes })`). Defaults 8 / 2 / 2 (`EffectWorker` option `fibres`, profile option `effectFibres`). A `turn.start` holds its fibre for the whole turn, so the turn-fibre count is the **per-profile concurrency cap: at most 8 concurrent turns**; a further send waits as a pending `turn.start` until a turn ends. Control fibres never run `turn.start`, so Stop and steer reach live turns however many are running. Wake sources: `afterCommit` notify, next `available_at` timer, 30 s safety poll.
- Claim is one `UPDATE … WHERE effect_id = (SELECT … LIMIT 1) RETURNING *` and is only valid when, for the same thread lane, there is **no `running` row whose lease has not expired** and no earlier `pending` row. `title.generate` and `run.resume` each have a lane of their own, and `turn.interrupt`, `turn.steer` and `request.respond` share a per-thread **control** lane so they reach a live turn instead of queueing behind its long-running `turn.start`.
- Lease = `timeout_ms + 15 s`. The worker renews the lease every `timeout_ms/3` while executing.
- Execution is raced against `AbortSignal.timeout(timeout_ms)` and against cancellation. On timeout: `failed` with `last_error='timeout'` if attempts exhausted, else `pending` with backoff `min(30 s, 100 ms·2^(n−1))`. An executor that cannot run its effect yet throws `EffectDeferredError(delayMs)`: the row goes back to `pending` at `now + delayMs` with the attempt not counted (`EffectOutbox.defer`). A row waiting out a backoff or a deferral still blocks every later row of its lane (lanes are FIFO).
- Settlement is CAS on `(effect_id, lease_owner)`; a lost lease aborts the local execution and writes nothing.
- `EffectWorker.stop()` aborts every execution and returns only once every executor promise it started has settled (an aborted turn may still be writing its terminal state). The profile writes the daemon's clean `ended_at` after that, after the channels shut down and the requests went idle (`MmsProfileServices.finishStop`); a stop that fails to drain leaves the epoch open, so the next boot reads it as a crash.
- A claimed `turn.start` can be aborted in flight (`EffectWorker.cancelInFlight`); the engine reaches it through `RunEngine.setInFlightCanceller`, which the orchestrator wires when a worker is attached.

### 12.4 Reconciler (every 5 s and after every commit)

A single loop; each rule is a pure function of stored state and produces commands/effects. Rules, in order:

1. **Expired lease on a `running` effect** → mark `pending` (or `failed` if attempts exhausted); the stuck fibre's result is discarded by the CAS.
2. **Run `running|finalizing` with no live effect and no heartbeat for > 2× heartbeat interval** (scaled by `CommandPolicy.heartbeatToleranceMs(caps, heartbeatMs)` for the thread's adapter: 6× for `events:'sparse'`) → `interrupted` with `interruptedBy:'provider'`, `outcome.error='no terminal event'`. This catches a clean stream end without a terminal event. Local-action runs (`source: 'undo'|'revert'`) whose heartbeat is fresh are exempt; they heartbeat while their action runs.
3. **Pending `stopRequested` on a run whose `turn.interrupt` effect is terminal but the run is still non-terminal after 10 s** → force `interrupted` (`interruptedBy:'user'`) and emit a warning event.
4. **Child run terminal while a parent waits** (Phase 4) → wake parent (§14.3). First, `delivered` inbox rows whose delivery failed or was cut off go back to `pending`; a thread that already has a `queued` wake run gets no second one.
5. **Queued run with no active run on its thread whose latest `turn.start` is `cancelled` and none is `pending|running`** (a stranded run: boot cancelled its process-bound effect) → when the dead effect's stored payload carries the send (`input`; image data is not stored, so images arrive empty), enqueue a fresh `turn.start` with it (next effect ordinal) and append `reconcile.restarted_queued_run`; with no payload (a pre-Phase-2b run), end the run `cancelled` with `outcome.error='no turn payload after restart'` and append `reconcile.cancelled_stranded_run`. A queued run that never had a `turn.start` waits on the message queue and is left alone, as are queue-item sends (`queueItemId`, re-drained by the queue's own recovery) and wake or integration payloads (settled at boot).
6. **`tool_invocations` at `started` whose run is terminal** → `outcome_unknown`.

Every repair appends a `reconcile.<rule>` event. The loop never calls a provider itself. Each rule runs on its own: a rule that throws leaves its part of the report empty, appends `reconcile.rule_failed` (`{ rule, error }`, thread `__reconciler__`) and the remaining rules still run.

### 12.5 Boot

`reconcileOnBoot()` (extends Phase 1):
1. Insert a new `daemon_epochs` row; find the previous row; if its `ended_at` is NULL the previous daemon crashed.
2. Cancel all `process_bound` effects in `pending|running` (reason `daemon_restart`).
3. Re-queue `running` `replay_safe` effects; leave `pending` ones. Revoke every live Mousse MCP credential row (§15.1: the tokens lived only in the previous daemon's memory).
4. Runs in `starting|running|finalizing`:
   - if the previous epoch ended cleanly → `interrupted`, `interruptedBy:'daemon_restart'`;
   - if it crashed and the run has any `tool_invocations` at `started` with `idempotent=0` → **`uncertain`**, `uncertainReason:'non_idempotent_tool_in_flight'`, listing the tools; the thread's worktree lease is kept (quarantine) until a user action; all other crashed runs → `interrupted`.
5. For each affected thread, record a `restart.note` event listing what was cut off. The next turn on that thread prepends a system note; the GUI shows a "Continue" affordance. **Nothing auto-resumes.** The note also lists runs the previous daemon's clean shutdown already interrupted (a turn aborted by the worker stop or the profile shutdown ends `interrupted` with `interruptedBy:'daemon_restart'` and the transcript line "Turn interrupted by a Mousse restart.", not a user Stop): those that started, completed since the previous epoch's `started_at`, are not in an earlier note, and have no later started run on their thread. Stranded queued runs (rule 5) appear as `queuedRunIds`. When the note is delivered, it also names the saved activity items (commands, subagents, other tool calls) of those runs that ended `interrupted`; the engine's event does not carry them, and a thread's items still `running` are ended as `interrupted` when the thread is loaded (against the saved thread, under its write lock). Nothing is ended while a turn runs in that session or another live process holds the thread's lease.
6. Start the heartbeat (`heartbeat_at` every 10 s) and the reconciler.

### 12.6 Tool idempotency registry

`src/mms/run/tools/idempotency.ts` maps tool name → `idempotent: boolean`. Read-only tools (`read_file`, `list_dir`, `ls`, `git_status`, `git_diff`, `web_search`, `web_fetch`, `browser_observe/find/extract/screenshot/tabs`, `list_tasks`, `list_subagents`) are idempotent. `bash`, `run_command`, `write_file`, `edit_file`, `browser_act/open`, `create_task`, `update_task`, `create_subagent(s)`, `integrate_subagent`, `present_plan`, `ask_user` are not. MCP tools default to **not idempotent** unless the server annotates `readOnlyHint`. `LlmClient.executeToolCall` writes `started` before and `committed|failed` after; an `outcome_unknown` row is rendered back to the model on the next turn as a tool result saying the outcome is unknown and must be verified.

### 12.7 Protocol additions

- `orchestrator.send` takes `await: 'turn' | 'ack'`. With `'ack'` it returns as soon as the `send` command and its `turn.start` commit (`runId`, `sequence`); the turn result arrives through events. **The default stays `'turn'`** (the RPC awaits the turn, and `MMS_PROTOCOL_ORCHESTRATOR_SEND_TIMEOUT_MS` still applies) until the GUI's `runSend` adopts `'ack'`.
- `orchestrator.send`, `orchestrator.abort` and `orchestrator.steer` reject unknown keys and an empty `clientRequestId` with `invalid_params`, like the `runs.*` handlers; `acknowledgeUncertain` without `continuationOfRunId` is `invalid_params`. Engine refusals (continuation, fork, merge-back, `client_request_id_conflict`) surface as protocol errors whose code is the refusal reason.
- New read: `runs.effects(threadId, { limit ≤ 200, before? })` → the newest effects (oldest first within the page) with `cursor` (pass as `before` for older ones) and `hasMore`; new events `effect.status`, `reconcile.repair`, `run.uncertain`, `restart.note`.
- `engine fsck` adds: `effect_lease_expired_unclaimed`, `effect_running_for_dead_epoch`, `run_active_without_effect`, `tool_started_on_terminal_run`, `queued_run_without_effect_or_queue_item` (warning: a queued run with no `pending|running` `turn.start` that is not on its thread's queue; without queue access, one whose last `turn.start` ended and that is no queue item's) and, from Phase 4, `delegation_running_child_terminal` (a `running` delegation whose child run ended) and, from schema 10, `paused_run_with_live_attempt` (a `paused` run whose attempt is still `pending|running`) and `paused_run_without_timer` (warning: a `paused` run with `autoResume`, no continue item (`resumeItemId`) and no `pending|running` `run.resume`, so the banner promises a continuation that will not come; Resume now still works).

## 13. Phase 3 — provider adapters and the capability manifest

Today `executeTurn` branches on `selectedModel.llmProvider` (`antigravity`, `claude-subscription`, else the pi-ai `LlmClient` loop) and each branch has its own compaction, steer, history and metrics handling. Phase 3 puts every provider behind one interface so the engine and the `turn.start` executor never see a provider name (invariant 8; the ratchet enforces it).

### 13.1 Interface (`src/mms/run/adapters/ProviderAdapter.ts`)

```ts
export interface ProviderAdapter {
  readonly driver: ProviderDriverKind               // 'pi' | 'claude' | 'antigravity' | 'codex'; instances map to it (§13.8)
  readonly capabilities: ProviderCapabilities        // static; may be refined per model via describe()
  describe(model: string): Promise<ModelInfo>        // context window, image input, reasoning levels
  startTurn(input: TurnInput, sink: TurnSink, ctl: TurnControl): Promise<TurnResult>
  steer?(sessionRef: ProviderRef, text: string): Promise<'delivered' | 'not_active'>
  interrupt(sessionRef: ProviderRef): Promise<'interrupted' | 'not_active'>
  compact?(sessionRef: ProviderRef): Promise<void>
  rollback?(sessionRef: ProviderRef, toTurnOrdinal: number): Promise<void>
  fork?(sessionRef: ProviderRef, atTurnOrdinal: number): Promise<ProviderRef>
}
export interface TurnInput { runId; attemptId; threadId; cwd; instanceId; model; prompt; images?; history: HistoryHandoff; mode: 'agent'|'plan'; tools: ToolHost; signal: AbortSignal }
export interface TurnSink { text(delta); thinking(delta); toolStart(ev); toolEnd(ev); usage(u); nativeRef(ref: ProviderRef) }
export interface TurnControl { drainSteer(): string | undefined; heartbeat(): void }
export interface TurnResult { text: string; aborted: boolean; usage?; providerRef: ProviderRef }
```

`ToolHost` is Mousse's tool registry (delegation, ask_user, tasks, browser…). In-process loops call it directly; vendor runtimes reach it over the Mousse MCP server (Phase 5). Phase 3 passes it to the pi adapter only; native adapters receive `tools: null` until Phase 5.

### 13.2 Capability manifest — every flag has a reader

```ts
export interface ProviderCapabilities {
  steer: 'native' | 'interrupt_restart' | 'queue_only'    // read by CommandPolicy.steerStrategy (see below)
  interrupt: boolean                                       // CommandPolicy.stopStrategy
  rollback: 'native' | 'none'                              // CommandPolicy.undoStrategy (Phase 6)
  fork: 'native' | 'portable'                              // CommandPolicy.forkStrategy (Phase 6)
  events: 'rich' | 'sparse'                                // Reconciler rule 2 heartbeat tolerance (sparse = 6×)
  containment: 'strong' | 'weak'                           // CheckpointRestoreSafety (Phase 6): weak → review diff, never auto-restore
  historyInjection: 'native' | 'prompt'                    // HandoffDelivery (Phase 6)
  mcp: boolean                                             // Phase 5: whether the Mousse MCP server can be attached
  childPolicy: 'enforced' | 'isolated_only'                // featureGates.subagentTargetRefusal: can a `shared` (read-only) child be held to read-only (§14.2)
}
```

`steer` describes how steer text reaches a live turn. `native`: the text joins the live turn without cancelling in-flight work (a running tool call finishes and the model sees the text at its next step); only the pi loop does this. `interrupt_restart`: the provider delivers it by interrupting the turn and resuming or restarting the session with the text as a new user message, so a tool call in flight is cancelled (Claude Subscription: `query.interrupt()` then resume; Antigravity: `session/cancel` then a new prompt). `queue_only`: the text waits for the turn to end. User steers are delivered the same way whatever the value; the capability decides only whether reconciler rule 4 may push a delegation notice into a live run (§14.3).

Rule: `tests/run/capabilityReaders.test.ts` lists each key with its reader functions (`steer` → `steerStrategy`, `interrupt` → `stopStrategy`, `rollback` → `canUndoNatively`, `fork` → `forkStrategy`, `events` → `heartbeatToleranceMs`, `containment` → `restoreMode`, `historyInjection` → `handoffDelivery`, `mcp` → `mcpAttachable`, `childPolicy` → `subagentTargetRefusal`) and asserts that each reader, defined under `src/mms/run/**` outside `adapters/**`, reads `caps.<key>`, and that some non-test source under `src/` outside `adapters/**` **calls** it (a `name(` call site other than its definition, comment lines excluded). Adding a flag without a called reader fails CI. (A flag nobody reads is documentation pretending to be behavior.) There is no `nativeSubagents` flag: every adapter's delegation goes through Mousse's own `delegate_task` (§14). Which native subagent features a provider offers a delegated child is in the child policy table in §14.2.

### 13.3 CommandPolicy (`src/mms/run/CommandPolicy.ts`)

Pure functions from `(capabilities, runState)` to a decision; the engine and executors call these instead of branching:
- `steerStrategy(caps, run)` → `native | interrupt_restart | queue` (and `late_steer_new_run` when the target run is finalizing/terminal).
- `stopStrategy(caps, run)` → `interrupt | settle_locally` (no live session). Read by the `turn.interrupt` executor (`OrchestratorService.interruptRun`): it aborts the in-process turn; for `interrupt` it also asks the adapter to interrupt the attempt's provider session. When nothing was live — no in-process turn (running, admitted or unwinding) and the adapter answers `not_active` (or there is no session to ask) — the run is settled right there, `interrupted` by the user with `outcome.stopStrategy`, instead of waiting for rule 3.
- `heartbeatToleranceMs(caps)`.

### 13.8 Provider instances

A **driver** is a kind of runtime (`pi`, `claude`, `antigravity`, `codex`); an **instance** is one configured use of a driver with a stable id. Every caller that picks an agent — main chat, `delegate_task`, channel sessions, Bridge dispatch through a thread — selects `ProviderSelection { instanceId, model }` (`src/shared/providerInstances.ts`).

- **Instance map.** Per profile, `providers.instances` in the profile config: `Record<instanceId, { driver, enabled, config? }>`. `ProviderInstanceService` (`src/mms/providers/`) seeds it on load with `antigravity`, `claude`, `codex` and `pi:<provider>` for each credentialed pi-ai provider. Enabled only means the profile may pick an instance; whether it can run is its service's `configured()` (Codex: a ChatGPT sign-in from the terminal `codex login`). The profile also stores `providers.instancesSeedVersion` (1 is the first recorded seed set). An entry is only upgraded when the profile's recorded seed version proves it is the seed: the marker is at least 1 and below the version of the seed change, and the entry still equals the old seed. A profile without a marker is never upgraded. A store that cannot be read is never seeded or written: the service keeps the last map it read and reports the error (`providers.listConfigured` → `instancesError`). A stored entry is never rewritten; seeding only adds missing ids. A `pi:<provider>` id for a known pi-ai provider without an entry resolves as an implicit enabled pi instance (the pi loop reports missing credentials itself).
- **Resolution.** `AdapterRegistry` holds one adapter per driver and resolves instance id → entry → driver → adapter. An unknown id fails with `provider_instance_unknown`, a disabled one with `provider_instance_disabled`, both naming the id; nothing falls back to the pi loop. Stopping work already running on a disabled instance is still allowed. The one exception is the configured default when it names nothing (no default model configured): it runs on the pi driver so its loop resolves and reports the default as before. A blank explicit override (thread, channel or caller) is rejected like an unknown name.
- **Legacy names.** Wherever an older `llmProvider` string still arrives (GUI `threads.setModel`, stored thread and channel-session `modelOverride`, `delegate_task`'s `provider`, provider refs of earlier attempts), `instanceIdForLegacyProvider` maps `claude-subscription` → `claude`, `antigravity` → `antigravity`, `codex` → `codex`, a known pi-ai provider `p` → `pi:p`, and rejects anything else with `provider_instance_unknown`. Stored selections are migrated on read and written in the instance shape `{ instanceId, llmProvider, model }` on the next save, and the global default (`providers` in the profile config) keeps the `instanceId` it was picked with until a later default names only a provider; `llmProvider` is derived from the instance and kept only for older readers. `TurnInput.llmProvider` is likewise derived and deprecated.
- **Native continuations.** `ProviderRef.instanceId` names the instance that owns a provider session. Claude saved sessions record their instance and resume only on it (sessions from an older profile-private sign-in are dropped when the profile moves to the terminal sign-in); Antigravity sessions and Codex threads record their instance. Mousse MCP credentials are per thread and instance (§15.1).
- **Delegation.** `delegate_task` takes `instanceId` (and still accepts `provider`, mapped as above). The host resolves it before the delegation transaction, so an unknown or disabled instance fails the tool call without creating a thread; the delegation row's `provider` column records the instance id. That column is a record, read as stored (older rows hold a provider name); the child is routed by its thread's selection, written when the child thread is created and migrated on read like any other.
- **Not yet.** One instance per driver in v1, and each driver has one adapter shared by its instances. A driver factory that builds an adapter per instance from its `config`, and a per-instance `status()`, come when a second instance of a driver is needed.

## 14. Phase 4 — one delegation path

Three spawn paths exist today: `spawn_agents` text blocks parsed from the reply (completion by polling `.mousse/task-progress.json`), named agents (`create_subagent*` tools, in-process Mousse runtime only, parent blocked inside the tool call), and workflow/definition agents. Phase 4 replaces the first two with one primitive and keeps workflow agents as a caller of it.

### 14.1 Model

- A **child is a thread** with `lineage { parentThreadId, parentRunId, relationship: 'subagent' }` persisted in a new `thread_lineage` table (migration 3). Its runs are ordinary runs on the same engine.
- A **delegation** row ties the parent run to the child thread: `delegations(delegation_id PK, parent_run_id, parent_thread_id, child_thread_id, child_run_id, provider, model, prompt_digest, wake: 'always'|'settled_only', status: 'running'|'result_available'|'acknowledged'|'cancelled'|'failed', result TEXT, created_at, completed_at)`; migration 6 adds `workspace: 'isolated'|'shared'` and `role`, so a child session rebuilt from storage keeps its workspace policy (a `shared` child stays a read-only observer of its parent's workspace).
- **Inbox**: `inbox(inbox_id PK, thread_id, run_id?, kind: 'child_result'|'restart_note'|'reconcile_notice'|'pr_update', payload, status: 'pending'|'delivered'|'acknowledged', created_at)`. A child's completion writes one `child_result` row for the parent **in the same transaction** as the write that publishes it, the child's terminal write unless the child is still busy (below) (invariant 5: child completion is a stored row). Notifications only speed up discovery.
- **Publication gate**: a subagent's result is published by one function, `settleWaitingDelegations(childThreadId)`, in the transaction that changes what it reads. A delegation P → C stays `running` after C's run ended while C is **busy**: C has a run that is not terminal; a delegation of its own that is `running`; an inbox row that is still actionable (`pending`, or `delivered` and not exhausted, `payload.deliveryFailed`, and not carried by a delivery the user stopped); a wake or steer effect that is `pending` or `running`; or provider background work (a synchronous in-memory host callback, `RunStore.setProviderBackgroundWork`; no adapter reports any yet, a Codex turn stays open while its helpers run). Nothing is stored for this: it is read each time. When C is not busy, every `running` delegation into C publishes together with the result of C's **latest conversational run** (source `delegation`, `wake`, `provider-continuation`, `steer-late`, `steer-followup`, or a person's `gui`/`cli`/`channel`/`internal` turn; never integration or a local action), whether or not it produced text: its final text, else its error, else "Subagent finished without a final message."; the run's id is recorded in the result as `runId`. A delivery that gave up (an exhausted row newer than the task) publishes the task `failed` with that error instead. The delegation becomes `result_available` when that run `completed` and `failed` otherwise, with one `child_result` row for the parent; reading it (`task_status`) makes it `acknowledged`. A cancelled delegation is never published (a late child can finish but not publish). A run's final text is kept as a `run.result` thread event in its terminal transaction so a task that publishes later still has it. The function re-runs on every change of its inputs: a run of C reaching a terminal status, an inbox row of C changing status or payload, a wake or steer effect for C changing status (every `EffectOutbox` transition, so lease reclaim and boot too), a delegation of C leaving `running`, a queue entry that carried notices being removed (the rows go back to `pending`, or are acknowledged when the removal is part of a Stop), provider background work ending, and boot (every `running` delegation). Limits: durable queue entries that carry no run and no inbox rows (a person's leftover steer, `steer-followup`; an entry from `queue_enqueue`) do not hold a task, because the predicate runs inside transactions and the durable queue is a JSON file; a queued message from a person has a queued run from the moment it is sent, and an entry that carries notices owns their rows, so both hold. An integration run writes its outcome as a `reconcile_notice` row in its own terminal transaction (an integration run that something else ends, such as boot, reconciler rule 2 or a cancel, gets an "interrupted before its outcome was known" row from the terminal write itself; one the user stopped publishes right away, as every delivery the user stops does), so the thread has one outcome row per integration run: if the merge did finish after the run was ended, a row still pending is rewritten in place to the completed outcome, and one already read is followed by a short correction row (a task waiting on the thread may already have published by then, which needs an interrupt in the middle of a live merge), so the thread is busy until its model has read it. `integrate_delegation` merges the checkpoint of the run whose text the task published (`result.runId`), or the task's own run for a result that has none.

### 14.2 Tools (`ToolHost`, Phase 3 §13.1)

```
delegate_task({ prompt, title, provider?, model?, role?, workspace: 'isolated'|'shared', wake?: 'always'|'settled_only' }) → { delegationId, childThreadId, childRunId, title }
continue_subagent({ subagent, prompt }) → { delegationId, childThreadId, childRunId, title, status: 'started'|'queued' }
answer_subagent({ subagent, requestId, answers }) → { answered, ... }
task_status({ delegationId } | { subagent })  → { status, state, result?, childRunStatus, pendingQuestion? }   // reading a result acknowledges it
task_cancel({ delegationId } | { subagent })  → stops the child run and its own delegations depth-first (idempotent: a repeat or a retry after a partial failure re-runs every stop still needed); a title cancels all of that subagent's open tasks
list_subagents()  → one row per subagent: title, childThreadId, state, latestDelegationId, unread, workspace, role, provider, model
integrate_delegation({ delegationId } | { subagent })
```
The Mousse MCP server and the pi loop list exactly these seven tools (`delegationToolDefinitions()`); `create_subagent(s)`, `recall_subagent`, `integrate_subagent` and `list_delegations` stay dispatchable for replayed transcripts but are not listed. The guidance models read about them is one module, `src/mms/run/delegation/guidance.ts`, pinned by snapshot tests.

**Addressing a subagent.** A subagent's **title** is its address among its parent's subagents. `title` is required on `delegate_task`; titles are unique among a parent's subagents that still exist, compared trimmed, with spaces collapsed, ignoring case. A title that is taken is returned as a value, `{ started: false, code: 'title_taken', existing: [...], message }` (with the existing subagent's thread, state and latest task), not an error, and nothing is created; a retry of a call that succeeded replays its receipt before the title is checked. A rename of a subagent to a title another of its parent's subagents holds is refused (`title_taken`) on every rename path (`ThreadDataStore.setNameGuard`). `subagent` in the tools above is a title, a `childThreadId` or a `delegationId`, resolved only among the caller's own direct subagents (another parent's, or a grandchild, is `unknown_subagent`); older duplicate titles are `ambiguous_subagent` (candidates listed by thread id), and a subagent whose thread was trashed addressed by id is `subagent_trashed` (start a new one).

**`continue_subagent`** sends a follow-up to the subagent's own thread, so it runs in the same native session (the thread, provider, model and workspace never change) and what the subagent read stays warm. The follow-up is a task of its own: one `send` command carries a `delegation` option and writes the run and its delegation row in one transaction (workspace, role and selection copied from the subagent's first task; `wake: 'always'`). A busy subagent runs it after its current task (`status: 'queued'`). A subagent with a pending question returns `{ started: false, code: 'needs_answer', questions }` and is never auto-rejected (a plain `send` still preempts a pending question as before); `answer_subagent` answers it, and only a question pending on that subagent's thread. Both tools stay `actsAsCaller` in the tool registry (like `delegate_task`); the host handler enforces "the target is the caller's direct subagent" and `callerThreadOnly` is unchanged for other writers. A follow-up's ceiling is the narrower of the caller's and the subagent's own (the ceiling of its first task), so a plan subagent stays plan under a default caller. Both `delegate_task` and `continue_subagent` are refused (`parent_stopping`) while the calling run has `outcome.stopRequested`. A model-supplied `clientRequestId` (`mcp:` keys) scopes its receipt to the parent thread (`delegation:<parentThreadId>:<key>`, `continue:<parentThreadId>:<key>`), so a retry after the calling run ended returns the first result.

**A person's message in a subagent's thread is a follow-up** (D2). A run created by `send` on a `subagent` thread with `source` in `gui`, `cli`, `channel` or `internal` (`FOLLOW_UP_SOURCES`) gets a delegation row tied to the parent's latest run, with the subagent's own policy, in the same transaction, so the parent hears the result as a new completion. `delegation`, `wake`, `provider-continuation`, `integration`, `steer-late`, `steer-followup`, `lease-race`, `queue`, `schedule`, `workflow-observer`, `protocol`, `cli-steer`, `protocol-steer` and local actions are never tracked. Nothing is tracked when the parent thread is gone or has no run (`DelegationHost.threadLive`, read before the transaction).

**Nesting.** A subagent gets the same delegation tools as the main thread. A caller's authority only narrows down the tree: the ceiling of a child is the narrower of the caller's and the requested one (`narrowCeiling`), and a read-only (`shared`) subagent may only start `shared` ones. Until results wait for a subagent's own subagents (the hold predicate, issue #142 D2) and Stop reaches the whole tree, the guidance does not mention nesting, and a parent can receive a subagent's result while that subagent's own subagents are still running.
Deleting a thread is a Stop of it (§14.7, `clearQueue` included): its delegations and everything below it, its queued runs and wakes with their effects (a claimed `turn.start` aborted in flight), a `stop` for its active run, and its pending or delivered inbox rows are acknowledged; its MCP credentials are revoked.

`provider`/`model` default to the parent's. `workspace:'isolated'` allocates a worktree through the existing `WorkspaceResolver` with a lease held by the child run; `shared` is allowed only for read-only roles (execution contract check, §13). Each tool call is a `delegation.*` command with a `clientRequestId` derived from `(parentRunId, toolCallId)` so retries are no-ops.

**Child policy.** Every turn of a delegated child, first or resumed, carries `TurnInput.child` (`{ readOnly }`; `readOnly` is a `shared` child). Mousse never edits the user's provider setup (settings, env, MCP servers, hooks, config, feature flags) to hold a child to its policy; it uses permission decisions only. Before creating the child, `delegate_task` checks, for shared and isolated children alike, and returns a refusal as a value `{ started: false, code, message }` instead of throwing:

- `read_only_caller_requires_shared`: the caller is itself a read-only (`shared`) subagent, so every subagent it starts must be `shared` too (authority only narrows down the tree). It applies to the pi tools and to MCP callers alike, including the named-agent aliases. `integrate_delegation` is refused to a read-only caller (`mousse_read_only`).
- `shared_unsupported_for_provider` ("use isolated"): the target cannot run a `shared` child. `subagentTargetRefusal` refuses an adapter whose `childPolicy` is `isolated_only` (Antigravity rejects plan mode), and `ProviderAdapter.childPreflight` reads the user's setup (Codex, below).

The same target check runs again before every turn of a `shared` child (first, continued, resumed or queued), against the provider and setup in effect then. A child whose provider was switched to one that cannot be read-only, or whose Codex config gained an MCP server, has that turn refused with the same message (as a failed turn on its thread); it never runs unconstrained.

Nesting is allowed: a subagent, read-only or not, gets the delegation tools and may start subagents. Per provider:

| Provider | Read-only (`shared`) child | Any child |
|---|---|---|
| pi | `toolAccess` allows read tools and the delegation tools (not `integrate_delegation`) | — |
| Claude | `permissionMode: 'default'` (plan mode would inject its planning flow); the PreToolUse hook answers `ask` for every call, as for a plan turn, so allow rules in the user's settings cannot skip the callback (and denies the rest itself); the hook and `canUseTool` allow only Read, Glob, Grep, WebSearch, WebFetch, AskUserQuestion, ToolSearch, Claude's own subagent tool (`Agent`/`Task`) and Mousse's read and delegation tools; every write tool, shell and external MCP tool is denied, and so is every tool call a native Claude subagent makes beyond those, because the hook sees them too; the user's MCP servers stay configured | No restriction: native `Agent`/`Task` and Mousse's delegation tools are available |
| Codex | `read-only` sandbox on thread open and every `turn/start`; approvals stay `on-request`, and Mousse answers command, file, permission and MCP approvals with a denial itself, never asking the user. The app-server completes the parent's turn while its helpers keep running and does not stop them when the parent is interrupted, so Mousse reads the helper tree back from the app-server (`thread/list` with `ancestorThreadId` lists every descendant at any depth with its status; `thread/read` places a helper that is not listed yet). A thread is interrupted only when its ancestry is established in the current snapshot: its parent link, as listed or as found when it was placed, names the thread or a thread established the same way. When neither the thread nor a helper under it has started or ended a turn or changed status for 30 minutes (a nested helper counts only through those notifications, not through its output), or the helpers hold the run for 4 hours in total, they are interrupted and the run ends `done` with its own text plus "Some helpers were abandoned after N minutes without activity" |

Runtimes that decide per tool name use `READ_ONLY_MOUSSE_TOOLS`, which a test keeps equal to that set.

### 14.3 Wake-up (reconciler rule 4)

- Rule 4: for every `inbox` row `pending` whose thread has no active run and no `queued` wake run → enqueue a `turn.start` effect with payload `{ kind: 'wake', inboxIds }` (one wake per thread, batched). If the thread has an active run whose adapter `caps.steer === 'native'` and `wake === 'always'` → enqueue `turn.steer` with the formatted notice; otherwise leave `pending` until the active run ends (the rule fires again) and deliver it as a wake run. `wake: 'always'` means the parent may be told mid-run when that is free, not that its turn may be cut short: on an `interrupt_restart` provider a steer would cancel the parent's in-flight tool call, so those rows wait like `settled_only` ones. A delivered row records the effect that delivered it (`inbox.delivered_by`, migration 7).
- **Redelivery**: rule 4 (and boot) first returns `delivered` rows to `pending` when their delivering effect ended `failed|cancelled`, or when the run that effect belongs to (a wake run, the run a steer joined, a queued steer's run) ended other than `completed` (a run the user stopped excepted: its rows stay `delivered`). The first redelivery is immediate; later ones back off (2 s, doubling, at most 30 s). A row returns at most 3 times: after that it stays `delivered` with `payload.deliveryFailed` set (attempts, last error), a `reconcile.delivery_failed` event tells the owner, which writes a visible notice in the parent thread (no new inbox status; the result stays readable with `task_status`). There is no retry action yet; the app can add one. A row is delivered by one delivery at a time: while a queued steer carries it, its owner is `queue:<itemId>` (no effect), so the reconciler does not restore it or hand it to a wake; removing or clearing the item returns it to `pending`.
- **Delivery identity**: every route that carries a notice (a wake run, a native `turn.steer`, a steer that missed its turn and was queued as `steer-late`) carries the ids of its inbox rows (`inboxIds` on the effect payload or the queue item). The text is rebuilt when the delivery runs from the rows it still delivers: a row acknowledged since, or taken over by another delivery, is dropped, and with none left nothing is delivered. A steer a live turn took stays the steer's until the model reads it (`steerHeldBy` is written when the turn takes it, `drainSteerForSession` writes `steerTakenBy` when it reads it); if the turn ends without reading it, the follow-up turn it leaves carries the rows, and if that never happens (a crash, a failed enqueue) rule 4 and boot deliver the rows again. Only rows marked `steerHeldBy` are recovered that way: rows an older version delivered by native steer carry no marker and are left alone. A queued turn that runs without a `turn.start` effect settles its rows by what its run ended as: `completed` acknowledges them; a run that is not over (a lease race put the item back) leaves them with the item; a run the user stopped leaves them `delivered` and owned by nothing; any other end (failed, cut off by a shutdown) gives them back. A steer that finds its run over becomes a `steer-late` queue item that owns the rows. A queued turn's rows are re-pointed at its run's `turn.start` effect when it starts (`Inbox.redirectDelivery`, only from the owner they were moved from), so they follow that run. The notice records what it showed (`noticeShown` on each row) when it is built.
- **Acknowledge on delivery**: when the run that delivered rows reaches `completed`, the same terminal transaction acknowledges them (`terminal.ts`). Rows of a `turn.steer` count only once the model read the steer; a steer that has not run when its run ends has delivered nothing, so the rows and the task stay for the late steer. The task becomes `acknowledged` only if the notice recorded `noticeShown` for it (its whole result was in the notice); a result the notice cut, or a row with no record, stays `result_available` (unread) until `task_status`. A message that delivers results carries `subagentNotice` (the tasks it reports), so the app never parses the text.
- **Paused thread**: a thread with a `paused` run is busy for wakes (§5). Its pending rows stay `pending`; no wake run and no steer is created, and a wake run that was created but not claimed is cancelled with its rows back to pending (`cancelQueuedWakes`), as are rows the paused turn delivered (`Inbox.releaseRunDeliveries`). The continue turn that ends the pause carries them (it is a queue item that owns the rows, §16.4); rows that arrive after it was written are delivered by rule 4 once the thread is no longer paused.
- **Busy thread**: channel turns are engine runs (a `send` with `source: 'channel'`), so the engine sees them. A wake claimed while the thread is still busy — with a turn the engine does not schedule (a workflow or legacy turn) — stays `queued` and its effect is deferred 5 s (`EffectDeferredError`), so rule 4 never cancels and recreates it in a loop; when another engine turn of the thread waits to start instead, the wake ends `cancelled` with its rows pending again so that turn goes first and rule 4 queues a new wake behind it.
- The wake turn's prompt is a server-authored notice (`delegation/notice.ts`): `Subagent "<title>" (thread <id>) finished task <delegationId>.` followed by the result, inlined once (at most 4,000 characters per task and 16,000 per notice) and "Full result above.", or, when it was cut, "call task_status with <delegationId> for the rest". Reading via `task_status` marks the inbox row `acknowledged`; if every task in a pending wake is acknowledged before the wake starts, the wake effect is cancelled.
- Child `failed`/`interrupted` also produce a `child_result` (with the failure), so a parent never waits forever.

### 14.4 Integration

`integrate_delegation({ delegationId } | { subagent })` runs the existing `ChildAgentIntegrationService.integrate` as its own `integration` run on the parent thread (a run, so it is undoable and visible). No automatic merging. A `plan` ceiling cannot integrate (`mousse_ceiling_exceeded`).

Integration is **pinned to the task's own checkpoint**: it merges the `endSha` of the code checkpoint the task's run left in the subagent's thread (`taskCheckpoint`; checkpointing commits whatever the run changed), not the worktree's HEAD now. The subagent may have continued, and may be running with uncommitted changes; `ChildIntegrationRequest.pinnedWorkerSha` skips the live worktree's clean, branch and HEAD checks and keeps repository identity, ancestry from the spawn base, the merge itself and recovery. A task with no completed checkpoint cannot be integrated. The pin is part of the durable request, so recovery after a crash applies the same pinned checks. `integrate_delegation` with a title picks the subagent's latest task that completed. If the subagent later rewrites its history so the pinned commit is no longer in the repository, integration fails and the parent is told in its `integration_failed` notice.

### 14.5 Retirements

- Delete `spawn_agents` action parsing, `TaskProgressMonitor`, progress-JSON completion, `delegationBatches`, `agentOwners`, `wakeQueues`/`wakeTimers`, `scheduleOrchestratorWake`.
- Named-agent tools become thin wrappers over `delegate_task` (`name` maps to a child thread title; `recall` is `continue_subagent`).
- `AgentLifecycleService` transition table: remove `cancelled → running`.

### 14.6 Tests

Replay scenarios: parent delegates to a child on a different adapter; child completes while parent is mid-tool (steer wake) and while parent is idle (new turn wake); parent restarts mid-wait (inbox survives, wake fires after boot); `task_cancel` depth-first; publication gate rejects a late child result after cancel; duplicate `delegate_task` retry returns the same delegation.

### 14.7 Stop, cancel and questions (issue #142)

**One Stop.** `OrchestratorService.stopThread(threadId, reason, { runId?, clientRequestId?, clearQueue?, requesterThreadId? })` is the only public Stop. These all end in it: `orchestrator.abort` (with and without `runId`), `abortRun`, the CLI, a channel's `/stop`, a remote (Bridge) Stop (with no remote run to end it is a Stop of the thread), Lineage's row Stop, `task_cancel`, deleting a thread (`markThreadDeleted`, `clearQueue`) and settling it (`threads.settle`). An internal abort (a steer that restarts the turn, a question that preempts it, a shutdown) stays on `abortActiveTurn`, which `stopThread` wraps and which never calls back; `abortActiveTurn(threadId, { runId })` aborts only that run's turn (`ActiveTurnControl.runId`). Lineage's **Stop all** is `subagents.stopAll`: one `stopThread` for each direct subagent that is working (each with its own subtree); the thread's own turn keeps running. A repeated `task_cancel` stops the subagent only while the run of the task it names is live.

**The transaction.** `RunEngine.stopSubtree` decides everything in one run-store transaction, before any await: the subtree (the thread and every `subagent` descendant), a higher stop generation for each thread of it (`thread_stop_generations`, migration 8), and the stop set, which it cancels there: every `running` delegation into a thread of the subtree (deepest reported first; an owner outside the subtree gets a `delegation_stopped` notice row, except the thread that asked), every inbox row of the subtree acknowledged (so nothing wakes it), queued runs ended `cancelled` with their `turn.start` (a message a person queued stays, at every level of the subtree, unless `clearQueue`; tasks, follow-ups, wakes, steers and integrations made on behalf of a parent are cancelled), active runs `stopRequested` with a `turn.interrupt` effect, and the `turn.steer` effects still waiting for them. The notice an owner outside the subtree gets is written before its task leaves `running`, so the owner is busy with it when its own held tasks are judged. Delegations that already hold a result (`result_available`, `failed`) keep it and stay readable with `task_status`. After the transaction `stopThread` aborts the active runs locally (only them), removes the queue entries of the subtree under each thread's queue lock, and calls `stopProviderWork` (`ProviderAdapter.stopThread`) for every thread of the subtree, a settled one included. Anything admitted after the transaction (a person's message to a subagent the Stop has not reached) carries the new generation and survives.

**The fence.** `runs.stop_generation` is the generation of the run's thread when the run was created (a person's run that waited out a Stop takes the current one when it starts). `requestDelegation` and a follow-up (`continue_subagent`) are refused (`parent_stopping`) when the caller's run is older than a Stop of its thread; work started on behalf of a parent (`delegation`, `wake`, `steer-late`, `provider-continuation`, `integration`, see `FENCED_SOURCES`) is refused at execution when its thread's generation is higher; a queue entry of such work records `stopGeneration` and is refused when it would run. A person's send is never fenced. A stale `runId` returns its outcome and does not cascade; a repeat of the `clientRequestId` returns the first result and raises nothing (receipt `stop-thread:<threadId>:<clientRequestId>`; a Stop aimed at a run keeps the id itself as its receipt key).

**Unread steers.** A person's plain-text steer a turn never read lives in the turn's memory until it settles; the hold predicate counts it (`RunStore.setUnreadSteers`). When the turn settles the steer becomes a `steer-followup` queue entry with its own queued run, created in the same step, so the thread stays held by the run, durably.

**Questions.** A question the daemon asks on a subagent's thread (`UserQuestionService`: `ask_user`, a plan question, a provider approval such as Codex's) writes a `child_question` row (`reconcile_notice`, payload `{ kind, childThreadId, childRunId, requestId, delegationId? }`) into the parent's inbox; rule 4 wakes or steers the parent with a notice that names the question and `answer_subagent`. The row is acknowledged when the question clears (answered, dismissed, timed out), every delivery first drops a row whose request is no longer pending, and boot acknowledges every open `child_question` row (the requests died with the process). `Inbox.listForChildThread(childThreadId, kind?)` lists a subagent's result and question rows. A provider's, the Pi agent's or a Mousse tool's approval request is saved (§17): it survives a restart, and a message sent to the thread denies the pending approvals with the message as the reason and runs as a fresh turn. The other questions keep the behaviour above: in memory, rejected when a message preempts them. A message another thread's agent sends (`thread_send`, §15.1) never preempts a question: it is refused at admission while one waits (`refuseWhileAsking`), and it skips the auto-reject of pending approvals a person's message does.

**Pull request updates.** A thread whose watch is set to `act` receives a `pr_update` row (payload `{ text, number, headSha, changes }`) when its pull request's checks finish, or when a review or comment from an owner, member or collaborator of the repository arrives; the row's id is `inbox:pr-update:<threadId>:<watchRevision>:<seq>`, so writing the same delivery twice leaves one row. Rule 4 treats it as any notice: an idle thread gets a wake run, a paused thread waits for the continue turn, a live run is never steered (the notice asks the agent to change code, so it waits for the run to end and arrives as a turn of its own), and a Stop fences it. A watch wakes the agent at most 3 times without a message from a person in the thread, then only notifies. The wake is an ordinary turn of the thread, on the thread's own mode and access ceiling. A subagent thread is never set to `act`, because a pending row would hold its parent's delegation open.

## 15. Phase 5 — Mousse MCP server for every provider

Native-agent providers (Claude subscription, Antigravity) receive `mcpServers: {}` / `[]` today; CLI agents receive copies of the user's MCP servers. None can call Mousse's own tools.

### 15.1 Server

- `src/mms/run/mcp/MousseMcpServer.ts`: one in-process MCP server (streamable HTTP on `127.0.0.1`, random port, plus a stdio bridge binary `mousse-cli engine mcp-stdio` for runtimes that only speak stdio). Tools are the app-tool registry (`src/mms/run/mcp/appTools/`), the same modules the pi loop calls in process: the delegation tools, `ask_user`, `present_plan`, `create_task`/`update_task`/`list_tasks`, `thread_read`, `thread_list`, `thread_search`, `thread_send`, `thread_wait`, `thread_interrupt`, `thread_steer`, `thread_create`, `queue_*`, `thread_fork`, `thread_merge_back`, the browser tools, `publish_applet`, `list_skills`/`load_skill`, quick actions, `web_search`/`web_fetch`, and the dev GUI tools in development builds. The list a credential sees depends on its thread (its read-only status and delegation ceiling, never the turn's mode) and on its agent access level (below); what a turn may use (mode, Settings, browser binding) is checked at call time and refused with a tool error that says why.
- **Credentials**: `credentials(token_hash PK, thread_id, run_id, provider, mode_ceiling, access_level, created_at, revoked_at, last_seen_at)` (migration 4, `access_level` added by migration 11; durable rather than in-memory; only the SHA-256 of a token is stored). A credential belongs to one runtime epoch of (thread, instance) and acts for one run; a call never re-points it. The epoch and turn binding live in daemon memory with the token. The harness gateway gives each turn its bearer (`bearerForTurn`, PR 2 §2 `TurnBridge`) under the driver's turn binding: `per_call` runtimes (Claude Code: Mousse's `PreToolUse` hook stamps `_mousse_turn` into each Mousse call; the Pi RPC engine tags calls by attempt) keep their bearer, re-bound to each run, and the registry refuses a call without the active turn's token; `drained_turn` runtimes (Codex, ACP agents) keep it only after a turn proven drained (completed, no call still running, and the runtime's account of its Mousse calls matching what the server received), and rotate otherwise; `rotate` gets a new bearer every turn. A new runtime (driver, home, account generation or config revision), a failed turn or a rotation bumps the epoch, which revokes the epoch's credentials at once. A call needs a live credential of the current epoch whose run is the thread's active run and has a registered app-tool turn; otherwise it fails `mousse_caller_not_live` before any handler runs. A turn's end settles the bearer, then aborts its in-flight calls. Revoked when the thread is deleted or trashed, when the thread switches provider, and after 24 h idle (`pruneExpired`, once per reconciler pass). Tokens live in daemon memory only, so boot (`reconcileOnBoot`, §12.5 step 3) revokes every live stored row and the next turn mints a fresh token.
- **Scoping**: a token acts as its run. `delegate_task` children inherit `mode_ceiling` and cannot exceed it; a plan-mode turn's ceiling is `plan`. The ceiling checks (no broader child, no integration under `plan`) live in the orchestrator's shared delegation dispatch, so the in-process pi loop and the MCP server refuse the same calls the same way. At the default `lineage` agent access level (below), `thread_read` is limited to the caller's thread and its lineage ancestors/descendants; of another thread it returns only `run.*`, `attempt.*`, `command.ignored`, `restart.note` and `thread.lineage` events plus `delegation.status` rows whose `result` is redacted unless the delegation's child is the caller (inbox, effect and tool events carry prompts and sibling results). Writes to unrelated threads are refused.
- Every tool handler declares an access class (`reads | readsOthers | actsAsCaller | writesThreads | startsThreads | managesOthers`); a handler without one fails to register.
- **Agent access level** (`settings.agentAccess`, per profile): `lineage` (the default: a thread's own record and its delegation lineage, as above), `read` (list, search and read the run lifecycle of any thread) or `manage` (also the full events and transcript of any thread, and, in later changes, writes), optionally narrowed to `projectIds` (absent or empty means every project; a list that is present but malformed, or a settings patch that carries one, fails closed: the patch is refused and a stored one reads as `lineage`). It is a grant, inherited down delegations like the mode ceiling:
  - The grant of a thread's turn is computed when the turn starts and stamped on its credential (`credentials.access_level`, kept for audit): the profile's level then, narrowed by what the thread keeps whatever the profile says (its **static ceiling**, below), and at most `read` under a `plan` ceiling. An in-process loop holds the grant its turn was registered with and never recomputes it. Every delegation records the starting caller's level as it stands at that call (`delegations.access_level`; null on rows from before migration 11, which read as `lineage`), so a child is never granted more than its parent held, across generations and follow-ups, whatever the profile says in between. Any failure to decide the grant is `lineage`.
  - The **static ceiling** of a thread is the narrowest of: `lineage` for a bot thread (its turns act for a person outside Mousse; this takes effect once the bot engine registers its threads with `setBotThreads`, and no thread is a bot thread before that); `lineage` for a thread a channel (Telegram, Discord, a webhook, or a remote send) has driven, stored on the thread (`Thread.accessCeiling`) when the first channel turn starts and kept for every later turn, whoever sends it; `read` for a read-only (`shared`) subagent; the thread's stored ceiling; **every** delegation that gave the thread work (not only the first and the latest, so a follow-up never restores a level an earlier one narrowed, and the engine clamps each follow-up row, queued or typed by a person, to the narrowest earlier row); and `lineage` for a fork or subagent that has no stored ceiling and no delegation. A run that continues another (the resume after a usage-limit pause, by the timer or by a person; a "Continue" after a restart; a provider's own continuation) is also never granted more than the run it continues: each run's turn records its grant in `runs.access_grant` (a plain column, no status write), and the continuing run takes the narrower of its own grant and that one (`lineage` when the earlier run recorded none or cannot be read). A fork stores, when it is created, the narrower of its source's static ceiling and the level of the agent that forked it (a source with no limit stores `manage`, which leaves the profile in charge), so a fork of a fork, and a restart, keep the limit.
  - The level that counts at a call is `min(the credential's grant, the profile's level now)`, with the current project list, so lowering the setting applies to a running turn at once and raising it applies from the next turn. An absent or unknown grant, a host that cannot say what the profile allows, or any error is `lineage`. `tools/list` leaves out tools whose `minLevel` the credential's effective level does not reach; the call-time check is the enforcement. A level other than `lineage` is part of the bearer's runtime generation, so a runtime that caches its tool list takes a changed level with a new bearer.
  - `readsOthers` tools name a target thread (`threadId`, default the caller's own) or, for a listing, a `projectId`. The registry checks it centrally in `ToolRegistry.call`, before availability, definition approval and the tool ledger, so a refusal asks nobody anything and writes no ledger row: the caller's own thread is always allowed; a lineage relative, or a thread the caller launched (`Thread.createdByThreadId`, never `ownerThreadId`), is allowed at any level; any other thread needs an effective level of `read` or `manage` and a project in the list (a thread without a project is allowed only by an empty list). A thread that does not exist is refused like one the caller may not reach. The handler receives `ctx.scope` (`own`, `descendant`, `ancestor_or_sibling`, `launched`, `read`, `manage`) and filters by it: only `own` and `manage` see events unfiltered or the transcript (`thread_read` `view: "messages"`, paged, each text cut at 4 KB), every other scope gets the lineage view above plus `agent.action` rows, and `read` gets a trimmed copy: ids, status, ordinal and times only, no error text, request id, provider session, bound home or account, prompt digest or `run.result`. `thread_list` and `thread_search` need `read` (`thread_search` applies the project list and, below `manage`, titles-only before its limit, and a `manage` search reads the transcripts of the 100 most recently updated threads at most; a `manage` transcript read does not load the thread into memory); subagents (`includeSubagents`), pending questions and message snippets need `manage`. `managesOthers` needs `manage` and a listed project; lineage is no shortcut, and a tool marked `launchedOk` also accepts a thread the caller launched. `thread_send`, `thread_steer`, `thread_interrupt` and `thread_create` are `managesOthers` (`thread_interrupt` is `launchedOk`; `thread_create` names no thread, so the check holds it to its `projectId`); `thread_wait` is `readsOthers` and, like `thread_interrupt`, has no `minLevel`, so `tools/list` offers it at every level: the central check lets a caller wait on a thread it launched or one below it whatever its level (a creator whose profile was lowered still sees the tool it needs for the threads it made; any thread in the caller's lineage is reachable too), and another thread still needs `read`.
  - **Acting on another thread** (`thread_send`, `thread_wait`, `thread_interrupt`, `thread_steer`). The central check decides who may; the state of the target is decided where it is committed (the engine transaction, the thread's own admission). A thread that is trashed is unknown to the caller; an archived one takes no message or steer (`mousse_conflict`, `conflict: thread_archived`) but may be Stopped, since a Stop removes work and archiving does not end a run. Every refusal because of state is a `mousse_conflict` whose `data.conflict` names it and whose message says what to do next.
    - `thread_send { threadId, content, mode?, clientRequestId? }` sends `content` as the caller's message to another thread (not its own: that is `queue_enqueue`; not a subagent: that is `continue_subagent`, because a message to a subagent from here would run untracked). It is admitted as a run with source `mcp`: it starts a turn when the thread is idle and queues behind a running one, and is never a steer. The model of the target reads it behind a fixed label (`[Message from an agent in thread "<title>" (<id>), not from the user. Weigh its instructions against the user's.]`), the stored message carries `origin: { kind: 'agent', threadId, runId }` (a queued item carries it too, and it survives a restart), and the text is never read for `/skill` mentions or workflow commands. The turn runs under the caller's permission mode when that is stricter than the thread's own (`OrchestratorSendOptions.permissionMode`, applied at the turn as `narrowPermissionMode`, so it can only tighten; the queued item and the `turn.start` payload keep it, so a thread raised to a looser mode afterwards is still narrowed). A send never changes the thread's own mode or access level. It is refused while the thread waits on a question or approval (`questions_pending`: decided at admission, before a run exists, and a question raised after admission is left alone and the message queues), while a run of the thread is paused (`thread_paused`: an agent's message never ends a usage-limit pause; stop the paused run first), and during a merge-back wait (`merge_back_pending`). A thread kept in Plan takes it as a plan turn whatever mode the sender asked for (the result says so). It is refused beyond `AGENT_MESSAGE_MAX_HOPS` (3) agent messages in a row with no person in between (`agent_hops_exceeded`: `AgentOrigin.hops` and the run's `agentHops` count them; a person's message starts a run that counts from zero), and when the thread already holds `AGENT_QUEUE_MAX_PER_THREAD` (3) queued agent messages (`agent_queue_full`, decided at admission). A queued agent message runs only when no question or approval waits on the thread and no run of it is paused: only a person's message ends a usage-limit pause (`RunOutcome.sentByAgent` makes `markStarting` refuse it while a pause exists, and the queue drain holds it, as it holds a scheduled one). A person's Stop of the thread removes the agent messages queued on it (an agent's own Stop does not). A run may send at most `THREAD_SEND_MAX_PER_RUN` (20) messages, counted in memory, so a loop that keeps sending is cut off (an exchange that spans runs is bounded only by what its participants do). The label ends with a closing line (`[End of message from an agent]`), the closing line inside the sender's text is defanged, and the label says everything up to it is the agent's. A retry of an earlier send past the cap returns its first result (found from its receipt). The idempotency key is `thread_send:<caller thread>:<clientRequestId or call id>`, so a retry after the caller's run was replaced by a continuation run, or its credential re-minted, returns the first run.
    - `thread_wait { threadId, runId?, timeoutMs? }` waits for a run of another thread (the named one, else the active one) for at most `timeoutMs` (default 45 s, at most 5 min; MCP clients give up on a call after about a minute). It subscribes to run events before it reads the run, so a run that ends in between is never missed, and always removes its listener. Results: `finished` (with the run's `status` and `interruptedBy`, its error text and `resultText` where the caller may read them), `timeout` (with a call-again hint; the wait never interrupts the target), `paused` (the run was still paused when the wait ran out: the result carries the pause and `retryAfterMs`, and the wait is never answered early; a wait that is running when the run resumes follows it into the run that continues it, `run.continuedFrom` names the paused one), `idle` (no run to wait for) and `caller_ended` (the caller's own run ended, which aborts the call). `resultText` is the `run.result` event of the waited run (kept only for what an agent can wait on, a run an agent sent and the run that continues one, besides a subagent's conversational runs; capped at 64 000 characters; deleted with the thread, and for the turns an undo hides; a person's own, a channel's and a schedule's turns are not retained), never the latest message of the thread, and is shown only for the caller's own, a descendant's, a launched thread's and a manager's view; through `read` alone, and for an ancestor or sibling, there is no text and no error text.
    - `thread_interrupt { threadId, runId, clientRequestId? }` is the one Stop (`stopThread`) aimed at a run, as the caller's: the run must still be the thread's active (or paused) run, or nothing is stopped and the conflict names the active run (`run_not_active`, with `expectedRunId` and `activeRunId`). It stops the subagents below the run too, ends a paused run and its pause, and leaves queued messages a person sent. It reaches a subagent only below the caller's own thread (a subagent of another thread is refused, like `thread_send`; its parent manages it). A thread the caller launched (`Thread.createdByThreadId`) may be Stopped at any level and whatever the project list says, and this survives a profile lowered to `lineage` or a project removed from the list: it is the one exception to the live narrowing above (`thread_create` below sets the relation). Runs it ends are `interruptedBy: 'agent'` (`RunOutcome.stopRequestedBy` is set in the Stop's transaction and `writeTerminalRun` turns the turn's `user` into `agent`); every place that treated `user` specially (no wake after the stop, a stopped subagent task, unredelivered notice rows) asks `stoppedByPerson`, so an agent's Stop settles as a person's. The one exception is the integration notice: a thread whose integration run an agent stopped still gets it, because its user may not know the run was cut off (the "Changed by an agent" row is not enough).
    - `thread_steer { threadId, runId, text, clientRequestId? }` adds the text, behind the same label, to the live turn named. A running turn cannot be narrowed, so a caller whose permission mode is stricter than the one the run is bound to is refused (`ceiling_exceeded`, with both modes); a run bound to a stricter mode than the caller's takes it. The comparison is made by the engine inside the transaction that accepts the steer, against the binding read there: a run that has not bound its turn yet (still `starting`) is refused (`steer_target_not_ready`), because an unknown mode is never read as the strictest. The sender's mode and origin travel with the steer (the `turn.steer` payload, the turn's `agentSteers`): a steer the turn never reads, one the provider hands back, and one that missed its turn become a turn of their own under the sender's mode, stored as the agent's and never merged into a person's text. It reaches a subagent only below the caller's own thread, and counts toward the hop limit. A paused run has no live turn (`run_paused`); a run that is not active is `run_not_active`.
    - `thread_create { projectId, title?, workspace?, instanceId?, model?, firstMessage?, mode?, clientRequestId? }` starts a thread. It needs `manage` and a listed project (a bot's thread is refused whatever its grant, and a `plan` ceiling cannot start threads).
      - **Where it works.** The project decides, not `workspace`: on a Git project every turn that edits gets a worktree of its own (`WorkspaceResolver`), and on any other project the thread works in the project folder; the result's `runsIn` (`own_worktree` | `project_folder`) says which. `workspace` is recorded on the thread: `new_worktree` sets `Thread.worktreeEnabled` and is refused (nothing created) on a project that is not Git-backed, because that thread would write in the project folder beside others; `project` (the default) leaves it unset. `existing_worktree` is refused with no thread made, because a thread cannot take over a worktree it did not provision (a follow-up).
      - **Model.** Naming `model` (with `instanceId`, or alone on the caller's instance) goes through the checks `threads.setModel` makes (`overrideFor`, then `resolveStored` for the `composer` purpose in the project's scope: an unknown or disabled instance, a hidden model and an instance the project turned off are refused); naming neither copies the caller's own selection when the project allows it, and the profile's default otherwise. The creator's thread gets a row naming what it launched: thread, project, instance and model, mode and place.
      - **Limits of the new thread.** It is recorded as launched by the caller's thread (`Thread.createdByThreadId`) and is never owned by it (no `ownerThreadId`: it is neither nested under nor deleted with its creator, and it has no lineage). Its `permissionMode` is always stored, as the stricter of the creator's bound mode and the profile's default, so a default loosened later cannot widen it. Its stored `accessCeiling` is `read` (`LAUNCHED_THREAD_ACCESS_CEILING`, narrowed further by the creator's level): its agents, and the forks and subagents of it, may read and wait but never create threads or message others, so a creation cannot cascade. It is stored as started (`startedAt`), so it is listed and the app's "New chat" never reuses it as an empty draft.
      - **First message and counts.** `firstMessage` is sent through `thread_send`'s own path as the caller's message (label, `origin`, the caller's mode on the turn, `preemptQuestions: false`, key `<creation key>:first`), so it counts as the next agent message in a row: a creation whose message would be past `AGENT_MESSAGE_MAX_HOPS` is refused before anything is recorded or made (`agent_hops_exceeded`), while a thread made without a message is no hop. The count is carried by runs that carry on agent work (`inheritedAgentHops`): a wake that delivers a subagent's result and a provider's own continuation take the count of the thread's previous run, and the resume after a usage-limit pause (timer or "Resume now") that of the paused run; a person's message and a person's "Continue" start at zero. A run may create `THREAD_CREATE_MAX_PER_RUN` (5) threads (counted in memory), and a creator thread may have at most `THREAD_CREATE_MAX_ACTIVE_PER_THREAD` (10) launched threads with a queued, running or paused run at once, counted from the run store whatever its runs or restarts (`creation_limit`).
      - **A person's Stop.** A Stop that a person (or the system, not an agent) aims at a thread also stops the threads that thread launched while they have work an agent started (`outcome.sentByAgent`), which ends that work and clears the agent messages queued there; a launched thread a person is working in is left alone, and an agent's own Stop does not cascade.
      - **Decided first, made second.** Everything that can refuse (project, workspace, cap, model, hops) is checked, then the whole launch is written to a receipt (`commandKind: 'thread_create'`, key `thread_create:<caller thread>:<clientRequestId or call id>`): the new thread's id, project path, title, worktree flag, Git flag, model, mode, level ceiling, creator, actor and first message. Every later step, in the same call, in a retry or after a restart, is made from that stored intent, never from the caller's arguments, mode or the settings of the moment; a stored creation whose limits (mode, level ceiling) are missing or unknown is refused, not defaulted. A retry with other arguments is `mousse_conflict` (`client_request_id_conflict`), and two calls with one key at once make one thread (the second is told it is a replay). The thread is made with `ThreadDataStore.createThread({ id })`, which refuses an id that exists; the `agent.action` event `created_thread` (ids and names, no message) is the **completion marker**: a thread is complete only once it exists. A retry that finds files without the marker discards the thread (`discardUnusedThread`, which tells clients) and makes it again under the same id, as long as no one has used it. A thread a person has used (open in the daemon, a run, a message) or changed (renamed, another mode or model, archived, touched) is never adopted and never sent the agent's message: the retry is refused (`thread_in_use`) and the creator starts a new creation. A complete thread is returned with `replayed: true`, and the retry sends the first message when its receipt (`<key>:first`) is missing. A retry of a stored creation takes no new place under the per-run cap, so past the cap it still finishes its own thread and first message. A first message that cannot be sent leaves the thread made and the result says why (`firstMessage: { sent: false, reason }`). At boot, a thread with a receipt (made in the last week, read in one query) but no marker that no one has used is discarded and clients are told; nothing is made at boot (the creator's retry makes it), so no half-made launched thread stays listed. `engine fsck` accepts `thread_create` receipts, which name a thread, not a run. The transcript row "created this thread" is added only by the call that made the thread.
    - The engine writes the `agent.action` event of a send, Stop or steer in the same transaction as the change (`commitSend`, `commitControl`, `stopSubtree`: action `sent_message`, `stopped_run`, `steered_run`, with ids and lengths only), so a change never exists without its record; a replayed `clientRequestId` returns the first result and writes none. The transcript row ("Changed by an agent in thread …") is added after the commit by the call that made the change only; the event is the record of truth. The tool ledger of the caller's run records each call as any other tool.
    - **The sender's mode holds on every path.** An agent's send, steer or queued message never runs with more than its sender's effective mode: a send narrows the target's turn at admission, and the queued item and the turn payload keep the mode; a narrowed turn's own `queue_enqueue` queues under the mode its run is bound to (when that is stricter than the thread's); a run that continues another (the resume after a pause, a "Continue", a turn the provider starts itself) takes the stricter of its own mode and the continued run's binding (`continuedPermissionMode`, as `runs.access_grant` does for the level); `continue_subagent` passes the calling run's bound mode to the follow-up, so an existing subagent is no way around it. A wake that delivers a subagent's result runs under the thread's own mode: it continues no run, and nothing records which turn asked for the work (a follow-up for a later change).
  - **Scheduled jobs** (`schedule_list`, `schedule_create`, `schedule_update`, `schedule_pause`, `schedule_run`; `managesOthers`, offered over MCP only). Every call needs the effective `manage` level and `scheduled.agentJobs` (off by default; read at each call, and the tools are not listed while it is off; turning it off pauses the jobs agents made, and the scheduler does not run them while it is off). `schedule_create`, `schedule_run` and `schedule_update` of anything but the name are for a turn a person started only: the owner answers with `startedByPerson` (an interactive origin and a `gui` or `cli` source, the rule that decides who a standing approval rule may answer), which fails closed, so a scheduled or webhook run, a message from another agent, a subagent, a wake, a continuation, a bot, a channel, a run with no binding and a run that cannot be read are refused. A job therefore never creates or starts jobs, and no chain can form. An agent sees and changes only the jobs its own thread created through these tools (`createdBy.threadId`); a person's job and another thread's job are refused like one that does not exist. Every change is an `agent.action` event on the caller's thread (`scheduled_job_created`, `_updated`, `_paused`, `_run`) with a transcript row. `schedule_create` takes the caller's project, may bind the job to the caller's own thread or one in its lineage (never a bot's or an archived thread), and refuses a webhook trigger, a prompt that starts with `/`, an existing worktree, an interval under 15 minutes, a cron minute field that is not a fixed list of minutes at least 15 apart, and any attempt to set `accessCap`, `permissionCeiling`, `createdBy`, `expiresAt` or the project. The profile may hold 10 active agent-made jobs (counted from the saved jobs; paused and ended ones do not count), and a job ends 7 days after creation (`expiresAt`) unless a person extends it (`scheduled.extend`); an agent can only shorten `repeat.times`. A plan ceiling can make and change plan-mode jobs only. A retry with the same `clientRequestId` returns the first job. The job records `createdBy { threadId, runId, requestId }`, `accessCap` (the caller's level narrowed by the profile now) and `permissionCeiling` (the permission mode the caller's run is bound to). A scheduled run of the job is held to both: the access level is recorded on the run when it is admitted, and the mode goes through the send option that only narrows (`OrchestratorSendOptions.permissionMode`), on the direct, queued and recovered paths. `schedule_update` of anything but the name narrows the job's limits to the caller's (never raises them); it cannot enable a job (an agent pauses with `schedule_pause`; a person resumes). `schedule_run` is refused by the rules of "Run now" (a running job, a claim, a run in progress or waiting), for a paused job, for one that ended, and for a workflow prompt, then wakes the scheduler. A job bound to a deleted or archived thread, or made from a deleted one, pauses with a reason. The job and its run records are labelled as an agent's. The daemon's local protocol (`mousse-cli schedule`) is not governed by these limits; it belongs to the thread's permission mode.
  - A change an agent makes to another thread is recorded as an `agent.action` event on that thread (`OrchestratorService.recordAgentAction`, or the engine's own transaction for a send, Stop or steer: ids, counts and lengths, never content) with a transcript row "Changed by an agent in thread …" as its projection.
  - `mousse_conflict` (JSON-RPC `-32006`) is the error for a command that expected state that has since changed; `McpToolError.details` are merged into the error's `data`.

## 16. Phase 6 — handoff, fork and merge-back, continue after restart

### 16.1 Context handoff as an artifact

Today a provider switch inserts only a display marker (`orchestrator/contextHandoff.ts`). Phase 6 records a `ContextHandoff` row (migration 5):

```sql
CREATE TABLE context_handoffs(
  handoff_id TEXT PRIMARY KEY, thread_id TEXT NOT NULL, target_run_id TEXT NOT NULL,
  from_ref TEXT, to_ref TEXT NOT NULL,                    -- ProviderRef JSON
  strategy TEXT NOT NULL CHECK(strategy IN ('native_resume','delta','full_summary','legacy_import')),
  covered_from_ordinal INTEGER, covered_to_ordinal INTEGER,
  budget_tokens INTEGER NOT NULL, selected_items INTEGER NOT NULL, omitted_items INTEGER NOT NULL,
  status TEXT NOT NULL CHECK(status IN ('pending','delivered','failed')),
  created_at TEXT NOT NULL, delivered_at TEXT
) STRICT;
```

- **Strategy** comes from `featureGates.handoffDelivery(caps)` and the stored refs: same provider with a live native session → `native_resume` (nothing sent); the target provider was used earlier on this thread → `delta` (runs since its last turn); otherwise `full_summary`.
- **Budget** (`src/mms/run/handoff/budget.ts`): default 16k tokens (`MOUSSE_HANDOFF_TOKEN_CAP`, clamp 1k–64k), 1 byte ≈ 1 token, image 8k / other attachment 4k reservation, window = min(model window, 128k) minus a quarter reserve. Selection order: last user, last assistant, first user, then newest first; whole items only; each text item compacted to ≤240 chars when it does not fit intact; the current user message is never truncated. Omitted history gets a recovery pointer (`thread_read` tool, Phase 5) so the agent can fetch it.
- **Delivery**: `historyInjection === 'native'` adapters receive structured history (`TurnInput.messages`); others receive it as a `<handoff>` block prepended to the prompt. The marker message in the transcript links to the `handoff_id`; the UI shows "context rebuilt (N of M items)".
- A `pending` handoff on a thread blocks a second switch until delivered or failed.

### 16.2 Fork into a new thread; merge-back

Existing `actions.fork` creates an in-thread conversation branch. Phase 6 adds a **thread fork**:
- `thread.fork({ sourceThreadId, atRunOrdinal | 'latest_stable' })` creates a new thread with `thread_lineage(relationship:'fork', parentThreadId, forkRunOrdinal)` and a **pending** `fork` transfer row (`context_transfers`, migration 5). Forkable sources: runs in `completed|failed|interrupted|cancelled`; never `running` or `uncertain`.
- **Consumed once**: a fork or merge-back transfer is `consumed` (payload `consumedBy: <runId>`) as soon as a commit of the receiving turn's transcript holds its injected history, or when a turn that delivered it otherwise completes; a turn stopped before its first commit leaves it pending. Injected history messages carry a `contextHandoff: { handoffId, transferId }` marker (not content), and a turn that finds a pending transfer's marker already in the transcript consumes it instead of injecting it again.
- **Lazy**: nothing is sent to a provider until the fork's first message. `featureGates.forkStrategy(caps)` picks `native` (same provider, strong native ref, `fork:'native'`) or `portable` (a `full_summary` handoff from the source up to the fork point). The code checkpoint at the fork ordinal seeds the fork's worktree. When the source has a workspace but no checkpoint at the fork point, the fork is refused (`fork_point_unavailable`) unless the caller passes `seedFrom: 'current_head'`, which starts the fork from the source's current HEAD; the transfer payload records the choice (`seedFrom: 'checkpoint' | 'current_head' | 'none'`).
- **Merge-back** `thread.merge_back({ forkThreadId })` is allowed only into the direct parent and only when the fork's latest run is `completed`. It records a pending `merge_back` transfer; the parent's next turn receives a `fork_delta_summary` handoff (runs on the fork since the fork point). Code integration stays explicit through the existing child-integration path (§14.4). Queueing on a thread with a pending merge-back is refused with a reason until it is consumed.

### 16.3 Undo and restore safety

- `actions.undoLatest`/`revertCode` keep their Git mechanics but become `undo` runs so they appear in `runs.list` and are themselves recoverable.
- `featureGates.restoreMode(caps)`: `containment:'weak'` providers never get an automatic file restore; the UI shows the diff and asks. Unknown capabilities fail closed (review the diff). The review response carries the diff and its SHA-256 (`diffSha`); the confirmed retry passes `reviewedDiffSha`, which must equal the SHA-256 of the diff a restore would apply at that moment (a changed diff gets a new review; the bare `reviewed: true` is refused). File restore is refused unless the thread owns its worktree and no other thread's worktree or live cwd overlaps it (realpath check), mirroring `CheckpointRestoreSafety`. The gate runs under the thread's mutex right before the undo/revert run is created (`runLocalAction` `gate`), so no run starts between the check and the restore.
- An undo run records how it restored (`outcome.undoStrategy`, from `featureGates.canUndoNatively`): `native_rollback` for a provider that rolls its own session back, else `checkpoint`. No adapter declares `rollback: 'native'` yet, so every undo is a checkpoint restore.

### 16.4 Continue after restart

- Boot already writes `restart.note`. Phase 6 adds a `continue` affordance: the note's system message carries `{ runId }`; the GUI shows a "Continue" button that sends `orchestrator.send` with `{ content: 'Continue where you left off.', continuationOfRunId }` and `clientRequestId = continue:<runId>` so a double click is a replay. Never automatic (invariant 10). Not offered for `uncertain` runs until the user acknowledges the listed tools.

A **paused** run (§5) is the one case that continues by itself, because nothing was cut off: the provider refused the request and the run waits. The `run.resume` effect (§12.2) fires at `outcome.pause.until`, or at once when a person presses Resume now (`engine.requestResume`), and the continue turn is a `send` with `source: 'resume'` (or `resume_now`) and `continuationOfRunId` = the paused run, `clientRequestId = queue:resume:<runId>`. A repeat replays the receipt, so exactly one continuation exists. `commitSend` accepts a paused source for these two sources only, records `outcome.continuationOf` and `outcome.resumedFromPause`, and ends the pause in the same transaction. A person's message or a Stop ends the pause instead (`endPause`), and a continue turn that finds the pause ended is rejected `pause_ended`.

The orchestrator makes the pause and the continue turn (`OrchestratorService`):

- **The pause.** A turn that fails on a usage limit asks `decideUsageLimit` (§5) with the user's `settings.runs` (`resumeAfterUsageLimit`, default off; `usageLimitPauseCap`, default 3), read at that moment and never afterwards, so turning the setting on arms no run that is already paused. A `pause` decision calls `engine.pauseRun` (with `resumeAt` when the setting is on), writes a system line ("Paused until …: Claude's 5-hour limit was reached (time reported by Claude | estimated). …"), sets the thread's turn phase to `paused` (`TurnState.pause`, the `turn.paused` event, the Bridge snapshot's `activeTurn.paused`) and settles the turn as paused: no terminal write, no `turn-completed`. A `fail` decision is the ordinary failure with the cap message. A Stop that came first (the engine refuses to pause a run that is being stopped) leaves the ordinary failure. A bot turn does not pause; it fails as before. A scheduled occurrence is never paused either (its run would outlive the occurrence): it fails, and the run records when the limit resets (`outcome.usageLimitUntil`). The scheduler then records the occurrence as `waiting`, not as an error: no repeat is spent, the job's next run is the reset (not a slot inside the window), a manual job waits to be triggered again, and a webhook delivery leaves the job's timer alone. After three waits in a row (`SCHEDULED_USAGE_LIMIT_WAIT_CAP`) the next one is an error. The setting `resumeAfterUsageLimit` does not apply to jobs. A paused run's line says "Send a message to continue" when no timer is armed.
- **The continue message is a queue item**, `resume:<runId>`, at the front of the thread's queue, written by the `run.resume` executor (the timer at `pause.until`, and Resume now through `runs.resumeNow` → `engine.requestResume`). Steps, each idempotent and re-run after a crash (a running replay-safe effect is queued again on boot): (1) the pause that ended is dealt with — superseded: the pending item goes and its rows are released; handed over: only a drain is left; a stale timer (§5) sets `stale` and removes a continue item already on disk (the same 24-hour rule is checked again when an automatic item is admitted, so the startup drain cannot run one; a Resume now item stays eligible), and the thread keeps showing the pause; otherwise queued wakes are cancelled, the rows the paused turn delivered go back to pending and `pause.resumeItemId` is recorded; (2) the item is written with a manifest of the thread's pending rows, and only once it is on disk (`mutateDurableQueue`'s `afterSave`, inside the queue lock) are exactly those rows marked as owned by it (`queue:<itemId>`); a row that arrives later stays pending for rule 4; (3) the queue is drained.
- **The queue is held while the thread is paused.** `scheduleQueueDrain` (and startup recovery) claim nothing on a paused thread unless the first pending item is the pause's own `resume:<runId>`; what was queued before the pause, in its original order, follows the continue turn. A person's message while paused is a `send` that ends the pause (§5); a scheduled send (a webhook-triggered job too) is refused `thread_paused`, and a scheduled run admitted before the pause that is still a queue item waits behind the pause (`markStarting` refuses it, `PAUSE_HELD_SOURCES`) while one whose `turn.start` effect is already in the lane is cancelled when it would start, so an automated send neither ends the pause nor starts the cap's count again. A wake or other work started on the thread's behalf that was admitted before the pause does not start beside it: a wake ends `cancelled` with its rows pending again, any other such run ends `cancelled` (`The thread is paused by a usage limit.`), so none of it waits in the thread's lane in front of the continue turn. What this loses: an integration that never started (the thread is told it did not start and nothing was merged); a delegation follow-up, which the parent hears about as cancelled; a provider's continuation turn, whose notice ("A background task finished …") is kept as an inbox row for the continue turn. A steer that fires after the pause, or one that names no run, becomes a held `steer-late` item (the text is kept; a person who wants it now sends a message); a steer the live turn never read is queued as a follow-up when the turn settles, as for any ended turn; `CommandPolicy` treats a paused run as having no live turn (`late_steer_new_run`, `settle_locally`).
- **The drain of the resume item** rebuilds its text from the rows it still owns (the fixed `Continue where you left off.`, plus their notice) and is never completed without running. It dispatches the continuation itself: `send` with `clientRequestId` `queue:<itemId>`, `source` `resume`/`resume_now` and `continuationOfRunId`, which creates the run and ends the pause in one transaction. A refusal for any reason (a message, Cancel or Stop ended the pause first) retires the item without reaching the provider. After the hand-over the item belongs to the message queue's recovery: a replay of the dispatch finds the same run. A continuation that Resume now asked for counts as a person's turn for "Always" rules (`startedByPerson`); the timer's does not. A Resume now that finds an item the timer wrote and has not drained yet turns it into a person's resume. The continuation keeps the paused run's mode (the item's chat and permission mode), and its access grant is never wider than the paused run's (`continuedGrant`).
- **Cancel and Stop.** `runs.cancelPause` ends the pause as `cancel`, removes a pending item and lets the held queue go on. A Stop and deleting the thread end it too (§5); a pending item is removed with the thread's other fenced queue entries.

### 16.5 Tests

Replay scenarios per adapter: switch provider mid-thread (delta vs full summary, budget hit → compaction, pointer present); fork then first message (native vs portable); merge-back delivers a delta once and refuses a second pending one; undo refused on a shared checkout; continue after restart replays on double click.

## 17. Approval requests

A provider's, the Pi agent's or a Mousse tool's request to run a command, change files or use a tool is an **approval request**: a row of `approval_requests` (migration 12) with a thread event for every change. It survives a client reconnect and a daemon restart; any client (the GUI, the CLI, a Bridge remote with the `chat` capability) can answer it; two answers race safely. `ask_user`, plan questions, quick actions and workflow or bot approvals are not approval requests: they stay in `UserQuestionService`'s memory (§14.7).

### 17.1 Table

`request_id` (PK), `thread_id`, `run_id` (the run that asked; null when the thread had none), `instance_id`, `provider`, `action` (`command`, `edit` or `tool`), `permission_key` (`src/shared/permissionKeys.ts`), `fingerprint`, `questions` (JSON; every option carries the `decision` it means, `allow` or `reject`, and `scope` `once` or `always`), `reason` (why the provider asks, when it is not obvious), `permission_mode` (the mode of the run that asked; migration 14; what an "always" rule is granted under), `answer_path`, `uncertain` and `uncertain_tools`, `status`, `answers` (the provider-facing answer map, kept for delivery only), `decision` and `decision_scope` (normalized at settlement; policy logic reads only these, never provider option ids), `feedback`, `answered_by`, `cancel_reason`, `continuation_run_id`, `grant_consumed_at`, `delivered_at`, `created_at`, `settled_at`. Indexes on `(thread_id, status)`, `(run_id, status)` and `continuation_run_id` (read at every turn start). The enumerated columns carry `CHECK` constraints. The saved prompt is a bounded preview (4500 characters) with credentials removed (`redactSecrets`), as is `feedback`; the fingerprint is computed from the raw call and never stored in readable form.

`status` is `pending`, `answered` or `cancelled`; a request is settled once. `answered_by` is `{ kind: 'user', via: 'gui' | 'cli' | 'bridge' | 'internal' }` or `{ kind: 'agent', threadId, runId }`. `answer_path` is `live` while the provider callback waits in this process and `continue` once the run that asked died with a daemon.

### 17.2 Events and cancel reasons

`approval.pending` (created), `approval.answered` (settled: decision, scope, `answeredBy`, path), `approval.delivered` (the answer reached its waiter, or the run that delivers it was admitted), `approval.cancelled` (closed with a `reason`), `approval.continue` (boot made it a `continue` request), `approval.rule_granted`, `approval.rule_applied` and `approval.rule_revoked` (§17.8), `approval.grant_consumed` and `approval.retired` (a Stop ended an answer nobody delivered and a grant nobody used; the decision stays for audit). Cancel reasons: `stopped` (a Stop of the thread or an ancestor), `steered` and `withdrawn` (the provider's callback ended: a steer restart, an aborted signal, the provider withdrew), `turn_ended` (the run reached a terminal status), `thread_deleted`, `timed_out`.

A run never leaves a pending request behind while the daemon lives: `writeTerminalRun` closes the run's pending requests (`turn_ended`) in the terminal transaction, for every terminal write except the two restart cut-offs (an `uncertain` run, and `interruptedBy: 'daemon_restart'`, which the boot and a clean shutdown write). A profile stop holds the saved requests first (`OrchestratorService.holdApprovals`, before the effect worker stops and aborts the live turns): a provider's stop handler that dismisses its requests then withdraws nothing, so a clean stop leaves them pending exactly as a crash does. Deleting a thread deletes its requests.

A request has **no timeout** while a person runs the turn (`TurnOrigin` `interactive`). An unattended origin (a workflow, an agent definition, a bot, a scheduled job) keeps the ten-minute timeout every question had: the request is closed `timed_out` and the provider is told the user did not answer. A restart does not extend that wait: boot closes every pending request of an unattended run `timed_out`.

A stop of a thread (Stop, `stopThread`) closes its pending requests and retires what it left armed (§17.6); a scheduled prompt that waited behind them may then drain.

### 17.3 Asking, and a message that denies

`UserQuestionService.requestAnswers` with an `ApprovalTag` writes the row first, keeps the waiter in memory and emits `pending` once. A request whose row cannot be written falls back to an in-memory approval. Before it asks, a request whose fingerprint matches the continuation grant of its run (§17.5) is answered `allow` without asking.

A **send** to a thread with pending requests denies them with the message as the reason, inside the send's own admission transaction (`RunEngine.dispatch` with `settleApprovals`, before the run is created), and runs as a fresh turn: never steered into the dying turn. It operates on the thread's whole delivery group: every pending request, plus the answered requests of a dead run that no turn has been given yet. Pending ones are settled `reject` with `feedback` = the message (none for a continuation or a wake); `bindDelivery` then hands the whole group to the new run, so nothing is left undelivered and no continuation can be due later. The run tells its agent every member's decision (§17.4). If the sender may not answer one of them (`canAnswerApproval`: an agent that is not the subagent's parent) nothing is settled and the message queues. After the commit the waiting callbacks of `live` requests get their denial, the turn is aborted and the message runs. The restart note's "Continue" is a send too and denies that run's `continue` requests the same way.

### 17.4 Answering

`orchestrator.answerQuestions` calls `ThreadApprovals.settle` through `UserQuestionService.settle`: one transaction checks `canAnswerApproval`, maps the chosen option to its declared decision, runs `UPDATE … WHERE status = 'pending'`, appends `approval.answered` and, for a `live` request, writes the `request.respond` effect. A typed answer that is no option rejects the request and its text becomes the `feedback` the agent is given. The loser of a race, and an answer to a request someone closed, get `{ ok: false, reason: 'already_answered' | 'cancelled', answeredBy, decision }`; over the Bridge the thread check still applies, so a request of another thread or an unknown id returns a bare `{ ok: false }`.

- **Live:** the `request.respond` executor resolves the in-memory waiter (at most once: the waiter is the guard) and marks the row delivered. Without a worker (tests) the answer is delivered directly.
- **Continue:** no effect. When every request of the dead run is answered, `ThreadApprovals.settle` returns `continuationDue` and the orchestrator sends `Continue where you left off.` with `clientRequestId = approval-run:<runId>`, `continuationOfRunId` = the dead run, `acknowledgeUncertain` when the run was `uncertain`, and `bindDelivery` for the answered requests, applied in the admission transaction (`continuation_run_id`, `delivered_at`). It is sent with the source of the answering user's client (`gui`, `cli`, else `internal`), so on a subagent's thread it is a tracked follow-up and the parent hears its result. A continuation whose requests were all already handed to a run (a send took the group first) is refused, `approvals_already_delivered`, and creates no run; any other refusal is told to the thread. Continuing is the user's click: the continuation is due only when at least one answer of the group is a user's, so an answer given only by a parent agent waits for the user. A repeat is a replay. The first request of the run is preceded by a hidden note that names every decision, feedback and any tool a crash may have cut off. Until all are answered the cards show "k of N answered"; a plain send denies the rest (§17.3).

### 17.5 The continuation grant

An approval given after a restart authorizes **the same action only, once, inside the run that was started to deliver it**. The `allow` row is the grant: `consumeContinuationGrant(threadId, runId, fingerprint)` is one `UPDATE` that matches `continuation_run_id = runId`, the fingerprint, `decision = 'allow'` and `grant_consumed_at IS NULL`. It expires with that run (a later run never consumes it) and a request without a fingerprint is never granted. The fingerprint is `sha256(stableStringify({ instanceId, cwd, permissionKey, toolName, action }))`; `action` (`src/mms/run/approvalFingerprint.ts`) is the whole tool input with the defaults of fields that change the mutation filled in (`replace_all: false`, `edit_mode: 'replace'`). A field is dropped only where a tool's own schema says it is a label: `description` of `Bash` and `PowerShell`. Every other tool, a user's MCP tool included, is hashed in full, because for such a tool `description` can be the content being changed. A fingerprint must identify the exact action, otherwise the request has none and is asked again after a restart. So none is made for: a tool input that does not have its declared shape; an ACP request without `rawInput`; a command or an edit with no known directory it runs in (the Pi tools carry the project or thread directory; Codex the command's own or the turn's); a Codex command whose text is unknown; a Codex file change in which any change has no diff (`grantRoot` is part of the action when there is one); a Mousse tool (an integration merges whatever the delegation holds when the continuation runs).

### 17.6 Boot

`reconcileOnBoot` calls `ThreadApprovals.recoverOnBoot` after the active runs are ended: a pending request of an `interrupted` or `uncertain` run becomes `continue` (an `uncertain` run's request records `uncertain` and the cut-off tool names, so the continuation carries the acknowledgement); a pending request with no run that can continue is closed `turn_ended`; an answer committed but never delivered (`live`, a crash between the settle transaction and the executor) becomes `continue` and is reported as `undelivered`. The ids go into the `restart.note` payload (`approvalRequestIds`). A restart answers and grants nothing itself. It does finish what a user already decided: when the worker attaches, an answered-undelivered request whose run has no pending request left starts its continuation with the same `clientRequestId` (replay-safe), unless the run is `uncertain` (the thread then says a tool may already have run and the user's Continue, with the acknowledgement, delivers the answer) or only an agent gave the answers (the user's click). A request that is still pending waits for a person. A **Stop** retires such an answer and spends an unused grant (`retireDelivery`), so a decision made before a Stop cannot act after it, on the next boot or in a later run. A queued scheduled prompt (`origin.kind = schedule`) is not claimed, at startup drain either, while the thread has a pending request; the claim is given back and it drains once nothing waits. A request whose `continuation_run_id` run was itself interrupted is left to the normal restart note: continuing again is the user's call (invariant 10).

### 17.8 "Always for this thread"

A user may answer an approval request with `allow_always` ("Always for this thread"). It allows the request once, as any approval does, and records a **rule** (`approval_rules`, migration 14) that answers the **same request** later in **the same thread** without asking. A rule never means "this kind of tool" or "commands in general".

- **What it matches.** The rule is keyed by the request's fingerprint (§17.5: instance, directory, permission key, tool and the whole input), so it matches exactly what the fingerprint matches: the same command in the same folder (a different `description` label is the same command), the same edit of the same file with the same text, and nothing else. Another command, argument, folder, shell or tool asks again. A request with **no fingerprint** (no stable description, no known directory, a Codex command without text, a Codex change without its diff, an ACP request without `rawInput`, any Mousse tool) can never match a rule, and is never offered "always": the option would do nothing.
- **Offered when.** The request is saved (a store is bound), has a fingerprint, comes from a run that asks (`approvals: 'ask'`) whose binding records its permission mode, is a **turn a person started** (`startedByPerson`: origin `interactive` and run source `gui` or `cli`), and carries no `reason`. A `reason` marks a request that is more than the plain one and is never "always" and never answered by a rule: Claude Code's own safety check under Full access, any ask Claude Code flags (`suppressAlwaysAllowRule`, `decisionReason`, `blockedPath`, a forced ask rule) in any mode, and any Codex request that gives a reason for asking (a retry outside the sandbox, an escalation).
- **Which turns a rule answers.** Only turns a person started. A scheduled or webhook-started job, a delegated child, a bot, a workflow or definition step, and a message an agent or another internal caller sent to the thread ask as before, with their timeouts, because no one watches them and the same command text does not mean the same effect (a script the agent edited under Auto-accept edits runs whatever it now holds). Run sources other than `gui` and `cli` are not a person: a caller that sends on an agent's behalf must not use them. `UserQuestionService.requestAnswers` adds the option after the one that allows once, with `decision: 'allow'` and `scope: 'always'`, for every provider alike. A client may offer it only because the question lists it.
- **What the provider hears.** The provider is answered with its own once-only option (`ThreadApprovals.settle` rewrites the answer it stores and delivers), so no provider needs to know the option. For ACP agents this is the agent's `allow_once`; the agent's native always and session options stay hidden, and Mousse's rule is the only "always".
- **Who creates one.** Only a user, in the same transaction as the answer: through the GUI or the CLI (`/approve always`, `approvals answer <id> allow_always`); not a Bridge client (see below). `canAnswerApproval` refuses `allow_always` from an agent. A denial, a typed answer and a message that denies make none. A request saved without the permission mode it was asked under makes none.
- **Per thread.** A rule belongs to its `thread_id`. A fork, a subagent and every other thread have their own rules and start with none; nothing is inherited or copied. Deleting the thread deletes its rules.
- **Modes.** `granted_under` is the effective permission mode of the run that asked; a request saved without one makes no rule, and a stored mode this build does not know reads as the loosest. A rule is **ignored** while the stricter of the run's mode and the thread's own is stricter than that (`isStricter`): a tighter mode applies to the next turn, but a rule stops answering at once, and the side card shows it paused. It applies again if the mode loosens; a mode change does not clear it. Granted again under a stricter mode, the rule keeps the stricter one. A rule granted under Ask is valid in every mode, so changing the mode is not a way to stop it: only Revoke is.
- **What a rule approves.** The text of the request, not its effect: `npm test` runs whatever the project holds that time. Claude's shell keeps its folder between calls, so the same command can run from a subfolder of the folder the fingerprint names. The directory of a Codex command is the exact path Codex proposed (a relative one under the turn's folder); a path with dot segments names no exact place and has no fingerprint. Every other field of a Codex request (its reason, environment, anything Codex adds) is part of the action. An ACP call is fingerprinted by its kind, title and non-empty `rawInput`; an empty or missing one has no fingerprint.
- **Duplicates.** Answering "always" also allows (once) the other pending requests of the thread with the same fingerprint and key whose provider still waits (a model's parallel calls).
- **Linked devices.** A Bridge client is shown requests without the option and `canAnswerApproval` refuses `allow_always` from it (`bridge_no_standing_grant`): it cannot list or revoke rules, so it does not make them.
- **A trace.** Each answer by a rule adds a line to the thread (and `approval.rule_applied`). A rule only removes the ask the mode would have made: it never overrides a plan turn, a read-only child or a refusing run, none of which reach the question.
- **Visible and revocable.** `threads.approvalRules { threadId }` lists the rules (id = fingerprint, a bounded redacted summary of what was allowed, `grantedUnder`, `active`); `threads.clearApprovalRules { threadId, ruleId? }` revokes one or all. The side card lists them with Revoke and Reset approvals, and the CLI has `approvals rules <thread>` and `approvals reset <thread> [ruleId]`. Neither method is exposed over the Bridge. Events: `approval.rule_granted`, `approval.rule_applied` (a request answered by a rule; the thread also gets a line saying so), `approval.rule_revoked`.
- **Restart.** Rules are rows: they survive a restart. A request answered "always" after a restart continues the thread as any answer does (§17.4), and the rule applies to later runs; the one-shot grant (§17.5) covers only the continuation.
