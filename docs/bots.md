# Bots

How personal bots work as of Bot Mode Phase 1, for developers. The design and its reasons are in the plans: [`plans/bot-architecture.md`](plans/bot-architecture.md) (engine, runtime, daemon API), [`plans/bot-ui.md`](plans/bot-ui.md) (the screens, with mockups in [`plans/mockups/bot-ui/`](plans/mockups/bot-ui/)) and [`plans/bot-context.md`](plans/bot-context.md) (memory). Memory as built is in [`bot-memory.md`](bot-memory.md). Terms are in the [glossary](GLOSSARY.md). Space bots are a separate system (`src/mms/bots/space/`) and are not covered here.

## What a bot is

A bot is an agent a person makes from a **look** and one sentence ("What should it do?"). It lives in the Chats tab, in the Bots section. Its owner talks to it in its **bot chat**, and it also works on its own schedules. Everything else is set by asking it: permissions, schedules, its name, how much time it takes. The UI never shows a tool row or a form, and names a model only on the Runs on pickers, in the one chat line about a picked model it can't use, and on the line and chip of work the owner asked to run on a model that is not its usual one (see "Model and depth" below). New bot is three short steps, shown like Add provider's: Look, What it does (an optional name and the sentence) and Runs on (this computer, and a model for Talk and for Work), where Create bot is. The draft and its step survive moving between steps and closing; a refused create returns to the step that can fix it.

- The definition is format 2 (`src/shared/bots/personal/definition.ts`): name, description, look, role, the main thread spec with its model choice and model rows (see Model and depth), and the grant (`permissions`). `owner` and `placement` are reserved for Teams and bot servers. Format 1 files are upgraded on read.
- `bots.create` names the bot with one short model call (5 seconds at most). When that fails, a name made from the description is used, and the bot picks its own in its first turn. The bot's first message is produced at once, as a chat activation.
- **The starter grant** (approved by pressing Create bot): read, list, search, edit and write in the bot's files folder only, the web (`web_search`, `web_fetch`), the bot's own tools, and an hour of work per activation. A bot whose grant still holds the earlier default of 15 minutes is moved to the hour when the profile opens (`BotEngine.upgradeWorkTime`, the same publish-and-approve as Allow); a grant the owner raised stays. The browser is asked for separately (see Use the browser).

## Lanes

Each bot has two lanes. The chat lane runs one activation at a time; the run lane runs up to three side by side (`MAX_RUN_SLOTS_PER_BOT`), and a profile runs at most six run activations at once across its bots (`MAX_RUN_SLOTS_PER_PROFILE`). Each activation keeps its own spend ledger, counts, deadline and supervisor. The chat is the bot's front desk and the run lane does its work, so the owner can always talk to it (see "The chat and its work").

- **Slots.** An activation that runs (waiting for the internet included) or waits at a wall holds a slot of its lane (`holding`, `slotFree`). `pump` fills free run slots across all the profile's bots in one order (`nextRun`): work that waited and may go on first (more room was allowed, or its usage limit reset), then the queue in its order (`runOrder`): work the owner asked for in the chat (or by hand), then a reminder's work, then scheduled runs, oldest first in each, whichever bot it is of. Each slot is taken in its own `bots.db` transaction, so two pumps never overfill them.
- **A slot kept for the owner** (`runSlotFree`). Scheduled runs and reminders' work together hold at most 2 of a bot's 3 slots (`MAX_BACKGROUND_SLOTS_PER_BOT`) and at most 4 of the profile's 6 (`MAX_BACKGROUND_SLOTS_PER_PROFILE`); they also leave a bot's last free slot to the owner's work that is allowed to go on and still letting go of its last turn (`ownerWorkWaits`). Work the owner asks for may take any free slot. So it starts at once whenever its bot has a free slot and the profile's 6 are not all held, and a bot's schedules alone never fill its 3. Work already running keeps its slot when the rule holds it back (after a restart, say): the rule only decides what starts.
- **The profile's slots.** What does not fit in the profile waits in its bot's queue, and `work_start` says it waits behind "your other bots' work". When a run slot frees, the next piece is chosen across all the profile's bots in the order above, so no bot's owner work waits behind another bot's scheduled runs.
- **The queue of 20** (`MAX_QUEUED_ACTIVATIONS`) counts a bot's running work too: queued, waiting and running together are at most 20, and the oldest that waits is dropped (never a running one). A dropped scheduled run says why on its automation (`dropped_queue_full`, as a skipped occurrence does), and the chat says at most once a day that scheduled runs are being dropped (`bm_<botId>_sched_dropped_<day>`).

| | Chat lane | Run lane |
|---|---|---|
| Started by | the owner's message (`bots.chat.send`), or the bot's creation | work the chat hands off (`work_start`), a reminder's work, a schedule, or by hand (`bots.activate`, internal) |
| Thread | the home thread, execution key `bot:<id>` | a new child thread, `bot:<id>:act:<activationId>` |
| Context | cleared at each activation's first dispatch (`clearConversationContext`), then the chat pack | the run brief, keyed by the schedule id |
| Missing permission | a wall: the turn ends with an ask card, and the answer continues it | refused; the run carries on (see Asks) |
| Tools | the grant without what takes long (the web, the browser, `shell`, the owner's MCP tools), plus the work and reminder tools | the whole grant, no work tools |
| Ends with | a reply (`text` row) | a run report (`run_report` row), also the notification |

- Clearing the home context keeps the transcript but sends no thread history, so no bot turn depends on a runtime session surviving. Claude Code and Codex resume their native session only while the history Mousse sends is the one saved after the last turn, so a cleared context starts a new one. Continuations inside one activation (a wall answer, a reload) keep the activation's own turns and may resume.
- A message sent while the chat lane is busy queues behind it. A message sent while the chat waits at a wall counts as Not now for its asks, and the turn continues with that message.
- Ordinary sends, steers and queue writes to a bot's threads are still refused (`bot_thread_read_only`). The owner's chat goes through `bots.chat.*`, so every turn keeps the bot's grant and lock.
- **The bot chat is `bot_messages`** in `bots.db`: owner messages, replies, run reports, notices with ask cards, error lines, and the chips of each message. The renderer reads only this table, never transcripts, so tool rows and model names can't leak.
- Each activation has a scratch folder, deleted when it ends. Documents the bot keeps go to its **files folder**, `<profile>/bots/files/<botId>/`, which every bot may write and which About never lists. Both lanes read and change it under the starter grant, so lists and plans the owner keeps with the bot live there as files, one each, with a short memory note naming each one's path (the instructions say so; a memory entry holds 400 characters, and work saves only run notes).
- **The bot chat's composer** is the thread composer (`ChatComposer`) without a thread's run settings: no model picker, reasoning level, permission mode, context ring, `/` commands or skills, since a bot picks its own model. It keeps the same box, attach (the button, dropping files and pasting images), dictation, Up for the last message, and Send or Stop.
- **Attached files** are copied into the bot's files folder, under `attachments/<date>/`, and the message and the bot's input name the copies (`copyBotAttachments`). The starter grant reads them, so the bot never needs the folder the owner keeps them in, and its edits never touch the originals. A pasted file has no path: it waits in a temporary folder until it is copied. At most 10 files of 50 MB each per message. Images reach the bot as files it reads, not as pictures in the message.

## The chat and its work

A person who works for you keeps talking to you while they work. A bot does the same (`docs/plans/bot-always-free.md`):

- **The chat answers in moments.** A chat turn is compiled with `frontDesk` (`compileBotThread`, `frontDeskManifest`): it is not offered `web_search`, `web_fetch`, the browser, `shell` or the owner's MCP tools, even when the grant holds them, and it gets the work and reminder tools (`BOT_WORK_TOOLS`), which are always on and never grantable, like memory. So a chat turn is a model call and a few local tool calls, and the queue behind it is seconds long. The grant and its digest do not change.
- **Work runs beside it.** `work_start({ title, brief, level?, model? })` inserts a run-lane activation with the trigger `{ kind: 'work', input, title, replyTo, from, level?, model? }` and returns at once (`level`, light, medium or hard, picks its Work row; `model` is a model the owner named for this work alone; see Model and depth); the chat then says it is on it. The brief stands on its own: a run sees the bot's memory, not the chat. Up to three pieces run at once (see Lanes), so a quick lookup starts beside an hour-long job; the chat's instructions tell it to start one rather than tell the owner to wait. Work that does not fit waits, and `work_start` says what it waits behind (`waitsBehind`). Its report is posted as a `run_report` that answers the owner's message that asked (`replyTo`).
- **While it runs.** The chat pack's situation lists the work in progress with its live activity ("Your work now: …"), so "how's it going?" needs no tool. `work_list` gives the same with ids and the last three that ended; `work_stop` stops one, and the others carry on; `work_note` keeps a note in `bot_work_notes`. Waiting work gets its notes with its request. Notes go only to work that waits or runs, never to paused or blocked work. Each note keeps the owner's message it came from, so forgetting that message removes the note and its copies in the dispatch prompts. What Forget cannot reach: a note (or a brief) that running work already read is also in that work's own thread, in its transcript and in the context Mousse keeps for it, which a continuation of the same work sends again, and in the runtime's session, until the work ends. A run's thread is never given to a model after its work ends; like every thread transcript and runtime session file, it is outside Forget ([`bot-memory.md`](bot-memory.md)).
- **A note reaches running work while it works.** Each main dispatch carries a steer (`PreparedBotTurn.steer`, `steerFor`), which the orchestrator offers the runtime as the turn's own steer source (`botSteerSource`): an agent's steer, so it waits for a running tool and goes in at the runtime's next step. The note goes in framed as the owner's addition to the job (`noteSteerText`), and the work's report leads with what changed. It is marked read in `bots.db` only when the runtime reports the model read it (`accepted`). Delivery is at least once, usually once: a note the runtime hands back waits for the dispatch's end and goes on as before (`advance` posts what it had and continues the thread with it); a note it took but never reported read (a Stop, a crash, or a result that came first) goes the same way, marked "(may be a repeat)" with a line telling the work not to redo what it already did (`offeredNotes`, `NOTE_REPEAT_LINE`); after a restart every unread note is marked so, since what the earlier process knew is gone. Nothing goes in once the activation no longer runs (Stop wins), with under 30 seconds of the dispatch left, or into the thread's queue: the steer adds text and never widens the grant (a permission allowed meanwhile still comes with the next dispatch). While the runtime compacts the turn's context a note waits for it, at most 3 minutes (`BOT_COMPACTION_HOLD_MS`, `SteerHold.compactionLimitMs`): one whose end is never reported holds it no longer. Per runtime: Claude Code (a bot's turn is one query) interrupts the query between tool calls and resumes the same session under the same lock with the note as its prompt; a call its grant gate already let start holds the cut until it ends, and a call made once the cut is decided is refused before it runs (`ClaudeLockedGate.cut`), so no call is cut mid-run. Codex adds it to the turn with `turn/steer`; Pi takes it at its next step. A runtime that takes no steers (`steer: 'queue_only'`) keeps the earlier way. `work_note` tells the chat which (`noteReach`): "it has it now", "it gets it in a few minutes" (while a compaction runs), "it gets it when this step ends", or "when it starts".
- **Asks.** An ask for the web, the browser or commands that the bot's grant holds is answered "your work already has this" with no card, in `escalate` and at the gate (`grantHolds`, read from the active grant at call time); anything else allowed since the chat turn started comes to it once its reply ends (see Asks below). When work needs a permission the bot lacks, the chat asks for it first, as before, and hands the work off once the owner answered; a run that meets one carries on and asks, as any run.
- **What the owner sees.** The status line and the composer's Stop follow the chat's own turn only (`BotSummary.chat`). Work is a line each above the composer (`BotSummary.work`), one per running or waiting piece: its title, what it is doing (the live chip of that activation), how long it has run, and Stop (`bots.work.stop`). The Recent line reads "Working on <title>" while one piece runs, and "Working on 3 things" with more.
- **Failures.** Failed work never counts toward pausing the schedules (`countFailure`), and done work doesn't reset the count. Work dropped from a full queue says so in the chat, and scheduled runs dropped so say it once a day (see Lanes).

## What a compaction cannot remove

When a model's context fills inside one long dispatch, the runtime compacts it by itself. What must never be lost is the bot's system text (`sessionInstructions` for a bot turn: `botInstructions`, its role, its lane's rules and "What your owner allows now"), which the runtime keeps through a compaction; its memory pack and its request stay in the turn's message (`turnPreamble`), and are given again after one.

- **The system text.** Claude Code's system prompt is replaced by it (`ClaudeLockedTurn.systemPrompt`, a custom prompt rendered fresh each request, `snapshot: false`, so a turn after an Allow resumes the session with the wider permissions in it); Codex takes it as developer instructions, which a Codex thread keeps from when it was opened, so a bot's dispatch whose system text differs from its thread's (after an Allow or a Remove) starts a new Codex thread under the new text, with the history in its prompt (`SavedThread.instructionsHash`): what survives Codex's own compaction is never the old permissions; Pi adds it to its own system prompt. None of the owner's own settings files, plugins or MCP servers are loaded for it. It holds nothing per turn (no time, no counts), so it is the same on every turn of an activation and the prompt cache holds across them; it changes only when the permissions or the bot's name change.
- **After a compaction.** Claude Code reports one inside the turn (its `compacting` status, then its `compact_boundary`, `TurnFrames`), and Pi reports its own (`compaction_start`, `compaction_end`). The orchestrator passes the end on (`BotTurnSteer.compacted`), and at the next safe point the turn gets one framed message with its memory pack and its request again, and the notes the owner added since (`regiveText`), read from `bots.db` then, so a message the owner forgot since is not given back. Once per compaction: several in a row before it went in are given once; it is no note, posts nothing in the chat and starts no dispatch. One the turn never read is dropped at its end, as the next dispatch carries the pack anyway.
- **Codex** reports no compaction inside a turn that Mousse reads, so after its own compaction a bot on Codex keeps its system text (developer instructions) but has its pack and request only as Codex's summary, until its next dispatch.

## Long work

Work that takes long is held to the bot's own budget, its work time per activation (an hour in the starter grant) and its turn budget when the grant has one, never to a runtime's limits on one turn.

- **The cap on model turns in one dispatch.** Claude Code ends one query after 300 model turns (`CLAUDE_LOCKED_MAX_TURNS`, only a bot's turn sets it; it was 100). That result is `provider_turn_cap`, not a failure: the activation carries on in the same thread, as after a restart, with "You reached the most steps one turn may take; what you did so far is kept. Continue." (`continueWith`, `turnCap`). The continuation runs on the time the activation has left; with under 15 seconds left, or its turn budget used up, it ends at that limit as any run or chat does (see Asks). What the capped turn did is not lost: the orchestrator hands back what it said last (`OrchestratorResponse.partial`, the open reply, else the one it finished last), and its words and chips go into the activation's next message (`carried`), so a continuation that runs out at once still posts them with its ask. Codex has no such cap, and Pi has none of its own (it counts against the grant's turn budget). The continuations are counted in total per activation, not in a row (a note or an Allow in between does not start the count again): after 10 (`MAX_TURN_CAP_CONTINUATIONS`), work ends as out of room, never as a failure: done (`end_reason` `turn_cap_repeated`), with a report that answers the owner's message, "I ran out of room before finishing, so I stopped here. Here is what I have so far:" and what it had (`endAtTurnCap`). Any other activation fails as before ("I kept going without finishing, so I stopped here.").
- **Work that runs out of room.** Work the owner asked for (trigger `work`: `work_start` and a reminder's work) that uses up its work time, turns or tool calls waits instead of failing (`budgetEnd`). It is `blocked` with `end_reason` `budget_exhausted` (`workWaits`, `BOT_WORK_WAIT_REASONS`), so it no longer holds a run slot and other work goes on; no new column, so older builds still read `bots.db`. Its chat gets one notice, a reply to the owner's message that asked: "I ran out of room before finishing. Allow more and I'll carry on. Here is what I have so far:", the turn's last words (the reply it finished last when it was cut right after a call: its turn is cut with `BotRoomAbort`, and only that cut hands back a finished reply, `stoppedReplyText`; a chat's wall, a reload or a Stop hands back only the reply still open) and its chips, with the card of the limit ask (posted by the dispatch's reply when its turn ends, `postReply`, else at once, `postRoom`; once per dispatch). The bot's one open ask for that limit is the one it waits on: a scheduled run's ask is taken over (`moveAsk`), else one is written; the ask caps are unchanged. When a chat waits at a wall for the same limit, the work waits on that wall's card, and its notice carries it (`roomAskOf`). Which limit the work waits on is kept in memory until its notice is posted, then read from its own ask or the card on its notice (`waitingOn`); spend limits are known only that way. The work shows as held in the work line and `work_list`, with Stop, and takes notes.
  - **Every answer settles the work that waits on that limit**, in the answer's own transaction (`settleRoomInTx`): Allow and Not now on any card for it, a message the owner sends instead of answering a chat's wall for it (it counts as Not now), and `respond`. Which limit each piece waits on is read before the answer widens the grant.
  - **Allow** widens the grant as for any ask. It carries on only work that waits on that same limit (an Allow of work time never wakes work that waits on a spend limit), that has room now under the wider grant (no limit used up, spend limits included), and that has waited at most a day (`MAX_ROOM_WAIT_MS`); work that waited longer ends with one line, ""…" waited too long, so I stopped it. Ask me again if you still want it." (`waited_too_long`). Work it carries on moves to `room_allowed`; when a run slot is free, before anything queued, it goes on in the same thread with "You have more room now; what you had so far was already sent to the owner. Carry on where you left off." (`pump`, `resumeWork`); its report answers the owner's message as before. Work that still has no room (an "allow this time" for a chat gives it none) ends with one line that says so. The card reads "Allowed: … It carries on with this now." ("… 3 pieces of work carry on now." when it carried on more than one, `BotAskCard.carried`) only when this answer carried work on: work that waited on it (owning it, or showing its card) waits its turn now or has gone on since (`BotAskCard.carriesOn`, `limitOutcome`). Work that ended without going on, or failed with its ask under an older build, carries nothing on, so its card reads as a run's ("It uses it from the next run.").
  - **Not now** ends it (`failed`, `budget_denied`) with what it posted; nothing new is posted, as the card says Not now. Stop ends it at any time, and stopped work never goes on.
  - **Waiting work counts toward the run lane's queue of 20** (`dropOverQueue`, running work counted too): when more is queued, the oldest of the queued and the waiting is dropped, waiting work with "I had too much waiting, so I dropped "…". Ask me again when I'm less busy."
  - **Nothing waits forever.** Each tick (`maintain`) and the startup pass end work that has waited more than a week, whatever it waits for (`MAX_WORK_WAIT_MS`, the same "waited too long" line), and waiting work that nothing would wake: work that waits for room with no open ask for its limit, or for a usage limit with no reset time to wait for. It fails (`nothing_to_wait_for`) with one line, a reply to the owner's message: "I stopped "…": nothing could let it carry on any more. Ask me again if you still want it." (`settleStrandedWork`).
  - **Continue** (the owner's, `continueActivation`) refuses waiting work, with a plain message (`bot_work_waiting`: "This work ran out of room. Answer its ask to let it carry on, or stop it.", or for a usage limit "… press Resume to try now."), so it never holds a run slot at a wall of its own. Its summary's `canContinue` is false.
  - **Grant changes.** About → Remove moves waiting work to the narrower grant with queued work (`narrowGrant`, a dispatch it has not sent included), so it goes on under what is approved now, never the wider grant. Revoking the grant, or approving one that replaces it, ends waiting work with queued and running work (`cancelled`, `endUnderGrant`), withdraws its own asks so no card brings it back, and posts one line: "I stopped "…": my permissions changed."
  - A start of Mousse posts a notice the earlier process never wrote (`repostRoom`), and work allowed before it stopped goes on once (`waitingBots`). While it waits it lets go of the bot's browser; its next turn opens tabs of its own.
  - A scheduled run and a run started by hand end as before: failed, with an ask that offers the higher limit for later runs. Work that runs out within a day of a Not now to that limit ends at once too ("I ran out of room on this run, so I stopped.", no ask, as the ask caps say), and its turn's last words are still posted after that line.
- **Work a usage limit stopped.** When every model is at its usage limit, work the owner asked for waits (`blocked`, `end_reason` `usage_limit`, `usagePause`) instead of ending; a scheduled run ends as before. The chat's one line says so: "Paused until 14:00 (your Claude usage limit). I'll carry on with this then." A provider that gives no reset time pauses the bot for 30 minutes at a time (`USAGE_RECHECK_MS`), and the line says that instead: "Paused (your Claude usage limit, with no reset time given). I'll try this again every 30 minutes until it goes through." (a scheduled run's: "I'll try again at 14:30."). When the pause ends (`maintain` at the first tick past the reset, or the owner's Resume), the work goes on in the same thread when a run slot is free, before anything queued, on a model chosen again: "A usage limit stopped you while you were working; it has reset now. Continue where you left off." A first dispatch that never went out (no model was free) is sent as it was. Under the owner's own pause (or one after failed runs) there is no usage pause to end, so the work waits for the reset time itself (kept in memory; after a restart it tries once at the start). It shows as held, never counts as a failed run, and Stop ends it.
- **A restart charges only the work done.** A dispatch is charged the whole time it may take when it starts and refunded when it ends. The last moment it is known to have been working is kept in `bot_dispatches.checkpoint_at`, at most once a second (`BOT_CHECKPOINT_EVERY_MS`): when a call is checked (any tool call, its consults' included, or a counted model request), when a call finishes (`tool.status` in the run log, `toolCallEnded`), and at each look at the live dispatch every 20 seconds (`BOT_OFFLINE_WATCH_MS`, the same look that checks the internet), unless it made no call for a minute and the internet is gone. After a crash the startup pass charges it up to that moment and no further, on every runtime (P3, whatever the supervisor's `exit_at` says, since that includes the time Mousse was down), so a long command in flight is charged, and a crash under-charges by one look at most. As the profile closes (`close`, or the in-process end of a turn the shutdown cut), it is charged up to the shutdown itself, unless it was waiting for the internet then (up to its last working moment). Such a turn never fails its activation: the startup pass carries it on once with "Mousse restarted while you were working." (rows 11 and 12, as before), with the time it has left. With under 15 seconds left it is a time wall, as at a deadline. The boot's own end of such a run (`settleRun`) is left to the startup pass.

## Replies

Every bot message can name the message it answers (`bot_messages.reply_to`, bots.db v6): a chat reply the owner's message its turn holds (`ownerMessageOf`), a work report and a reminder the message that asked for them. The chat shows a short quote of it (who wrote it and its first line, `BotChatQuote`) when it is not the message right above; clicking it scrolls there. The owner can reply to any message (Reply on hover): `bots.chat.send` carries `replyTo`, a message of the same bot only, and the bot's input starts with `(Replying to your message: "…")` (`messageInput`, which also rebuilds the input from the row after a restart).

## Reminders

`remind({ text, inMinutes | at, work? })` keeps a one-off reminder in `bot_reminders` (v6); `reminder_list` and `reminder_cancel` manage them, at most 50 waiting per bot, at most a year ahead. `at` is a local date and time on this computer. One engine timer waits for the soonest (`armReminders`, re-armed at most every 6 hours), and each scheduler tick checks again (`maintain`). When one is due (`deliverDueReminders`):

- a text reminder is posted as a `run_report` answering the message that asked, in the same transaction that marks it delivered, with no model run;
- a reminder with `work` starts that work (`reminder:<id>`), whose report answers the same message; when the bot can't run then (its permissions wait for approval, its thread is in the trash), the reminder is said with why;
- one that fails to be said (a full disk) is tried again a minute later, never in a loop;
- one that fell due while Mousse was off is said at the next start, prefixed with its time ("(For 14:30) …").

A deleted bot's reminders are cancelled at once and purged with it. Forgetting the owner's message that asked for a reminder or work (`memory_forget`, Forget in About) cancels the reminder and removes its words, and the work's brief and notes. Repeating reminders are schedules.

## Asks

An ask is a request for one permission, shown as a card with Allow and Not now (`bot_escalations`, `mode` `wall` or `ask`).

- **In a chat turn** the bot's authority check returns a wall: the dispatch ends, the reply carries the card, and the answer continues the turn ("The owner allowed …" or "The owner said not now …"). Several `escalate` calls in one turn put all their cards on that one message. At most 5 walls per activation (`MAX_BOT_WALLS`).
- **In a run** the check returns a third outcome, `refused`: the call fails with "The owner has not allowed this yet. You asked them; carry on without it and say in your report what you skipped." and the dispatch goes on. One open ask is kept per permission (by fingerprint), across every piece of work that runs at once; later runs, and other pieces running beside it, get the same refusal and write no new ask. Each piece refused it remembers so (`refusedAsks`), so an Allow reaches every one of them when its turn ends (see the next bullets). A run writes at most 5 new asks, a bot at most 10 a day. An ask that waits never blocks a run or skips a schedule.
- **Budgets** are different: work the owner asked for that runs out of time or turns waits for the answer to an ask for more room, with what it had posted, and Allow carries it on (see Long work); any other run ends as failed, with an ask for more room. Only work is charged: time spent waiting for the internet is not (see No internet), and a run that made no call at all in its whole time, with the internet there, ends failed with no ask (`no_progress`, "I couldn't get anything done on this run, so I stopped.").
- **Allow** publishes and approves the widened grant. A run that is no longer running when the owner allows its ask gets it from the next run, with no follow-up activation; one still running continues with it (next bullet), and work that waits on a limit goes on (see Long work). A run's answered card says which: "It carries on with this now." while the run that asked still runs or waits, or once it went on after the answer (`BotAskCard.carriesOn`); "It uses it from the next run." when it had ended and other runs were going; "Nothing is running now; it has this from now on." when nothing of the bot ran or waited at the answer (`idle`). **Not now** closes the ask; a run may ask again for it after 24 hours, and an Allow of the same permission from any other card still counts. Asks never expire.
- **No card for what the grant holds.** A turn keeps the permissions it started with (its tools, sandbox and browser are set up for them), so a turn that was already running when the owner pressed Allow still lacks the new permission. Its `escalate`, its gate refusal and its call of a browser tool (answered by the app-tool registry, `BotAuthority.held`) are answered at once, with no card and no count against the caps (`grantHolds`, read from the active grant at call time):
  - A chat turn is told to hand commands, the web and the browser to work (`BOT_WORK_HAS_TEXT`); the chat is never offered them.
  - For anything else, a chat turn is told it gets it once its reply ends (`BOT_ASK_HELD_CHAT_TEXT`), and a run-lane turn (work or a scheduled run) once its turn ends (`BOT_ASK_HELD_NEXT_TEXT`). The refusal is kept (in memory) and, when the turn completes, the reply or what the run has so far is posted (a run's as a `notice`) and the activation continues in the same thread with a new dispatch under the wider grant (`continueWith`, as for notes), if it has 30 seconds of work time left; a run's report then leads with what changed. Without the time, the run reports what it has and ends.
  - A consult is told it can't use it and to say what needs it (`BOT_ASK_HELD_CONSULT_TEXT`).
  - When the turn started with it but still can't use it (a narrower thread), or the runtime would not offer it to the next turn (Claude Code locked for bots withholds commands without a proven sandbox, `botWithheldTools`), the turn is told it can't be used on this turn and to say in its report what it skipped (`BOT_ASK_HELD_UNAVAILABLE_TEXT`), and nothing continues for it.
  - A refusal is forgotten once a dispatch of the activation starts with the permission (a reload, a usage-limit retry or a restart after the Allow), so that dispatch's report is the report and no further turn follows. After a restart the kept refusals are gone, and the continuation runs under the current grant anyway.
  - The running dispatch's permissions are never widened in place: a new dispatch compiles the tools, sandbox and browser from the approved grant together. A permission removed in About is not in the active grant, so it is asked for again as before.
- About lists what the bot can use, each with Remove (`bots.permissions.revoke`). Narrowing needs no approval.
- Card wording comes from `askText` (`src/shared/bots/personal/askText.ts`).
- The bot asks straight away: when the owner wants something it has no permission for, its instructions (`src/mms/bots/instructions.ts`) tell it to call `escalate` at once, with one plain sentence on why, and then say it has asked. It never asks the owner whether it should ask.
- Nothing this computer has switched off is asked for: no card, and the bot is told it is not on this computer (see What bots may do here).

## Run commands

"Run commands" (the neutral tool `shell`) is one permission for any command. The bot asks for it once (a card reading "run commands"); after Allow it is in the grant like any other tool, and no command is asked about again, even by work that was already running (see Asks). Commands run in the bot's work: a chat turn hands them off. Not now, the ask caps and About → Remove work as for every other permission. The authority allows every `shell` call once the grant holds it, whatever command or folder the call names (`botAuthority.ts`); without it, a command is a wall in the chat and a refusal with an ask in a run. Commands start in the bot's files folder. A computer can switch commands off for every bot (see What bots may do here). How far a command reaches depends on the runtime:

- **Claude Code** (owner's entry): Bash is offered only when the grant holds `shell`. Where Claude Code's own sandbox can run (bubblewrap and socat on Linux, Seatbelt on macOS), Bash runs in it: writable are the bot's files folder and its scratch folder. Without file access, on Linux every top folder but the system's own (`LINUX_SYSTEM_FOLDERS`: `/usr`, `/bin`, `/lib`, `/etc`, `/proc`, `/dev`, `/sys`, `/tmp`, …) and the home folder are unreadable, so `/home`, `/mnt` (on WSL, the Windows drives), `/media`, `/opt`, `/srv`, `/var`, `/root` and `/run` are closed. `/run` holds removable drives (`/run/media/<user>`) and the user's runtime folder (`/run/user/<uid>`: network mounts, sign-in sockets); the sandbox needs nothing there (checked on Ubuntu 24.04: commands, Python and the bot's own folders work with all of `/run` closed). On NixOS the system's programs and the setuid wrappers live under `/run` (`/run/current-system/sw/bin` on the PATH, `/run/wrappers`), so those two stay readable when they exist, and nothing else under `/run` (`LINUX_RUN_KEPT_OPEN`); they lead into `/nix`, which is open. Not checked on a real NixOS. The top folders are the ones there when the turn starts: a drive mounted later at a new top folder stays readable until the next turn. When `/` can't be listed, every command of the turn is refused with a plain reason (`claudeCommandsRefusal`) rather than run with only the home folder closed. On macOS only the home folder is unreadable. The bot's own folders and Claude Code's own storage stay readable. With file access commands read and write the whole file system but Mousse's own data (see File access). The network is closed; `dangerouslyDisableSandbox` is refused (`claudeLockedSandbox`). Where the sandbox can't run (Windows, or Linux without bubblewrap or socat), Bash still runs, outside any sandbox, because the owner allowed commands as a whole.
  - **`/tmp` on Linux.** It stays readable (writing is denied with the other temporary folders): Claude Code's sandbox keeps its own sockets there, and other programs keep theirs. The start-up pipe of the owner's MCP servers is made in Mousse's own data, for every thread (`CLAUDE_MCP_START_FOLDER`); a start folder a killed service left there is removed when the service next starts, unless a start of this process holds it or it changed in the last five minutes, the longest a start keeps its pipe (`sweepClaudeMcpStartFolders`).
    - **What Mousse still keeps in `/tmp`.** Each folder is private to the user (mode 700), but a bot's command runs as that user, so it can read them: the ChatGPT token broker's socket folder (the socket itself can't be used: the sandbox refuses every connect to a Unix socket), and for the seconds a task runs, `mousse-pr-*` (the title and text of a pull request the owner opens), `mousse-pathspec-*` (the paths of files the owner stages or discards), `mousse-trace-*` (Git's trace of the hooks of the owner's commit or push) and `mousse-acp-*` (the working folder of an ACP agent's check). A command can't change or add anything there. These are open: moving them into Mousse's data needs the same clean-up after a crash as the start folders, and the Git code would then write into the real data folder from its tests.
    - **Claude Code's own temporary folder.** Claude Code keeps every session's command output in `/tmp/claude-<uid>`, the owner's own sessions included, and its sandbox opens that folder, read and write, to the session's commands. So a bot's turn without file access keeps its own in a private folder of the user's runtime folder (`$XDG_RUNTIME_DIR/mb<hash>`, `CLAUDE_CODE_TMPDIR`; at most 30 bytes, since Claude Code gives a longer one only to itself and not to the commands it runs), and `/tmp/claude-<uid>` is closed to its commands, read and write (`claudeBotTemp`). The folder is the bot's (named after its files folder): it is emptied when the last of the bot's turns running ends (`holdClaudeBotTemp`) and removed when the bot is deleted (`removeClaudeBotTemp`). Without a private runtime folder under `/run` (`$XDG_RUNTIME_DIR` unset, elsewhere, not the user's, open to others, or a path too long, as with a user id of eight digits or more), the turn keeps Claude Code's shared folder, and its commands can read and change other sessions' command output there; the service log says so once, with why.
- **Codex**: with `shell` and without file access, on Linux and macOS the thread runs under Mousse's own permission profile (`mousse-bot`, `CODEX_BOT_PROFILE`, defined in the thread's config): commands read Codex's `:minimal` (the system's own programs, libraries and settings: `/usr`, `/etc`, `/dev`, `/proc`; on Linux no `/tmp` and nothing of `/run` but what WSL mounts there), the Codex package that runs them and the bot's folders, and write only the bot's folders, with no network. Every command asks under it, so the grant answers each one. It wins over a sandbox the owner's own Codex config names. On Windows, and with file access everywhere, the thread runs in the `workspace-write` sandbox: writes go only to the bot's folders (with file access, every entry beside Mousse's own data too), with no network and no temporary folder, but commands read every file, and Codex runs the read-only commands it trusts without asking (`codexTurnPolicy`, `codexBotSandbox`). Approvals stay `untrusted`, and the grant answers every command approval with accept. A retry outside the sandbox ("retry without sandbox?") is always declined. Without `shell` the thread starts with Codex's command tools off (`features.shell_tool`, `features.unified_exec`: `CODEX_COMMAND_FEATURES`), so it has no command tool at all, read-only ones included.
  - **Codex's other tools.** Every bot turn starts with the features that add a tool no bot may have switched off in its thread config, whatever the owner's Codex config says (`CODEX_BOT_FEATURES_OFF`): `view_image` (opens any image by its path, unasked and outside the sandbox), image generation, subagents (`multi_agent`, `multi_agent_v2`), apps, plugins and their MCP servers, hooks, Codex's own browser and computer use, memories, code mode, the sandbox-permission ask, messages and questions to a person, goals, sleep and suggestions. What the pinned Codex (0.162.1) still offers, checked on the real binary with every one of those features on in the owner's config (`tests/harness/codexBotTools.test.ts`): `request_user_input` (answered with an error for a bot: nobody is asked), OpenAI's hosted `web_search` (no file of this computer), `apply_patch` (each change asks and the authority decides by path), the command tools with `shell`, and, on models whose catalog entry says so, code mode's `exec` and `wait` (JavaScript with no file system or network, calling only those tools, the MCP resources of Mousse's own server, which has none, and the time) and the subagent tools of `collaboration` (`spawn_agent` and the rest), which no config removes. A subagent inherits the thread's features and sandbox (it has no command tool when the bot has none), and Mousse answers none of its approvals: they are cancelled, so a child runs no command or file change that asks, and under the bot's profile every command asks. So without `shell` and without file access, a bot on Codex opens no file by its path.
  - **Only a checked Codex runs a bot.** Codex ignores a feature name it doesn't know, so on a newer Codex a tool added or renamed there would reach a bot. Mousse can't see the tools Codex offers a turn (Codex sends them straight to the model provider), so it reads the version Codex reports when its process starts (the user agent of `initialize`, `codexVersionOf`), and a bot's turn runs only on a version in `CODEX_BOT_CHECKED_VERSIONS` (the pinned one). On any other, the turn does not start and the bot's chat says "This version of Codex is newer than Mousse knows, so my work can't run on it yet." (or, for an older or unreadable version, "Mousse doesn't know this version of Codex, so my work can't run on it."). The owner's own threads on that entry run as before. A Codex entry Mousse manages runs the pinned version, so this reaches only bots on the owner's own Codex. When Codex updates there, bots on that entry wait for a Mousse that has checked the new version: `tests/harness/codexBotTools.test.ts` is run on it, any new tool is accounted for, and its version is added. Meanwhile the owner can move a bot to another entry.
- **Pi**: with `shell` the turn offers Pi's `bash` tool; it runs in the locked environment, from the bot's files folder, with no sandbox.

So, without file access, a command is held to the system's folders (`/usr`, `/etc`, …, and `/tmp` with Claude Code) and the bot's folders only by Claude Code's sandbox on Linux and by Codex on Linux and macOS. Elsewhere it can read files outside the bot's folders (on macOS with Claude Code, everything but the home folder), and on Pi or an unsandboxed Claude Code it can change them too. The card's note says so, and so does the Run commands switch of What bots may do here.

## File access

"Use files on this computer" is one permission for every file and folder, read and write (`docs/plans/bot-architecture.md` §3.7). Without it a bot's file tools reach only its files folder and its scratch folder. The first time a file call names anything else, or the bot asks with `escalate` for any folder, there is one ask (`filesAsk()`, the same card whatever the folder); after Allow, no file or folder is asked about again. Not now, About → Remove and the ask caps work as for every other permission. A computer can switch file access off for every bot (see What bots may do here).

- **Stored form.** The grant's `workspace`: any non-null workspace is file access. Allow writes `{roots: ['/'], access: 'write'}` (the system drive on Windows). A grant an older build wrote for some folders keeps its form and digest and counts as file access; About lists it as one line.
- **Older asks.** When bots open (`BotEngine.upgradeFileAsks`), open folder asks are worded as the file ask. A bot that already has file access gets them settled as allowed, and a chat waiting at one continues. Otherwise one stays open (the chat's wall, else the oldest) and the others are withdrawn.
- **Mousse's own data stays closed**: the Mousse home holding the profile (every profile, the instances' sign-ins, Mousse's sign-in and keys), except the bot's files folder and scratch (`mousseDataFolder`, `BotAuthority.check`). A call there is refused with no ask. This was already the floor for folders; it now holds for the whole computer.
- **Paths in full.** A path a runtime would rewrite (`~`, a variable, padding whitespace) is never checked or expanded here: it is refused with no ask, with or without file access, since no Allow would make it usable as written. The refusal names the owner's home folder by its real path and, for `~/…` or `$HOME/…`, the full path meant (`pathFormWall`). The bot's system text names the home folder too, beside its files folder.
- **Per runtime.** Claude Code: the grant gate checks every path; with "run commands" the sandbox writes the whole file system, cannot read Mousse's data but for the bot's folders, and cannot write any entry in it that does not lead to them (`claudeLockedSandbox`, `entriesBeside`). Codex: file changes are checked per path; with "run commands" its writable roots are every entry beside Mousse's data plus the bot's folders, so a command cannot make a new entry directly in a folder on the way to it, such as the home folder. Pi: its gate checks every path; `bash` has no sandbox.
- **A runtime's own storage never asks**, with or without file access, and with Use files switched off on this computer too: Claude Code's project folder for the bot stays readable and writable. Claude Code saves large tool output (web results, long command output) in `<Claude home>/projects/<working folder as a name>/<session>/tool-results/` and reads it back with Read or Grep. The bot's working folder is its files folder, so that project folder holds only this bot's sessions; the grant gate recognises calls there (`claudeOwnStorage`) and allows them (`NormalisedCall.own`), and its sandbox can read it. Codex and Pi have no such storage that a bot's calls reach.

## Use the browser

"Use the browser" is one permission for every browser tool (`browser` in the grant, `BOT_BROWSER_PERMISSION`). The bot asks for it once (a card reading "use the browser"); an ask for any single browser tool, such as `browser_act`, is the same ask, and its card never names a tool. After Allow, `compileBotThread` turns it into the browser tools (all but `browser_request_human`: the bot asks its owner in its reply instead) and the bot's work has them in every run, with no new ask; a chat turn hands browsing to work. Not now, About → Remove and the ask caps work as for every other permission. Other Mousse tools stay refused: an `escalate` for one no bot can hold is refused at once, with no card. A computer can switch the browser off for every bot (see What bots may do here).

The browser is the bot's own (`src/mms/bots/browser/BotBrowsers.ts`), never the owner's tabs or a thread's:

- **One managed Chromium session per bot**, without a window, so a scheduled run works with no app open. It runs on a persistent Chromium profile of its own (`botbrowser_<botId>` under the profile's managed browser data), so sites the owner signs in to for the bot stay signed in for that bot only, and the bot never uses the owner's other sign-ins. A deleted bot's browser closes at once; its profile is erased with the 30-day purge.
- **Owned by the bot's home thread, with no run**, in the browser inventory: both lanes share the session, and no thread's agent or the owner's in-app browser reaches it (another owner is refused).
- **Reached only through the bot's own view and tools.** The session and the bot's profile are kept by `BotBrowsers` (`BOT_BROWSER_KEEPER`, checked in `BrowserSessionManager` by every session method): only the owner's view (`bots.browser.*`, with its hold) and the bot's own browser tools under its grant reach them. Anything else that names the bot's home thread, its session or its profile is refused with "This browser belongs to a bot. Open it from the bot's page." and changes nothing: the general `browser.sessions.takeControl`, `browser.sessions.resume` and `browser.artifacts.read` methods, a thread's browser view (`browser.view.*`, which shows nothing of the home thread and holds nothing), a thread's agent, a group chat, a workflow opening `botbrowser_<botId>`. Another bot is refused by the home-thread ownership above. A session recorded before this rule is kept by its profile.
- **A tab per activation.** Each activation opens and uses only its own tabs; another activation's tab is refused, and a tab list shows its own. When an activation ends, its tabs close; when the last one ends, the browser closes after two idle minutes, unless the owner is watching it or holds it.
- **One call at a time, in turn** (`BrowserTurns`, in `src/mms/browser/viewer/`, which a thread's browser without a window uses too). The session takes one action at a time (a second is refused, "Another action is already in flight") and, having no window, paints only its front tab, which an action brings forward. So when several activations browse at once, each call waits for the one before it to end, in the order they came, across the bot's activations: a call never fails for another one, and never loses its tab mid-action. Opening the session (and a first use's install) needs no turn. The wait is bounded: at most 24 calls wait (`MAX_BROWSER_WAITERS`), each for at most 5 minutes (`BROWSER_TURN_WAIT_MS`), past which the call is refused as busy; a stopped turn leaves the queue at once. The holder is bounded too: the worker ends each of its requests at 60 seconds, and a call that still holds the browser after 5 minutes (`BROWSER_TURN_HOLD_MS`, a little above the longest call: four requests) is stopped with a timeout to its run, and the next one goes. The owner's pictures take no turn: the worker never brings a tab forward for them (see the pictures below). A picture an older app asks for, and each close of an ended activation's tab (which does take a turn), has a stop signal and 15 seconds at most (`BROWSER_SIDE_CALL_MS`). The owner's input takes the next turn, ahead of the calls that wait, and cuts into a run's call under way: that call has 150 ms (`OWNER_CUT_IN_MS`) to end, then it is stopped, its run told its owner is using the browser now, and the input goes. After each input the browser stays the owner's for a second (`OWNER_KEEP_MS`): their next input goes at once and the runs' calls wait, so typing goes at the page's pace and the runs read in the pauses. Only the close of an ended activation's tab is waited for (30 seconds at most, then the input is refused as busy). The input goes only to the tab the owner holds, which the worker brings forward first, since a tab in the back takes no input (see the owner's input below). Take over and Give back take no turn.
- **First use installs it.** On a computer without the managed browser, the first browser call of any bot downloads it through the browser setup (`BrowserSetupService`, once for the installation) and waits for it; the preview reads "Setting up the browser". A computer that can't run it gets a plain refusal.
- **Stop and limits.** Every call carries the activation's signal: a stop, a wall or the deadline ends it. A stopped activation can't use the browser.
- **A slow page is not a failed page.** A page is open once it has committed and its document is ready; one that goes on loading is reported as still loading, and the bot carries on or waits (`browser_wait` with `document-ready`). A page that fails never closes the browser. Failures come in plain classes, each with what to do next, in the bot's tool result and in the owner's view (Chromium's own code only in the details and the tooltip): the site can't be reached, the site refused this browser, the page is nothing but a human check or a consent wall (the owner gets past it), the browser won't open the address (an unsafe port, its own rules, a certificate it does not trust), or the browser can't start (with the cause). A page that opened is never a failure because of what is on it: the bot's result notes a cookie banner (it may dismiss it), a check that is part of the page, a page not found or a server error, and a sign-in form, which is its owner's to fill (the bot has no sign-ins of its own); the owner's view says "needs you: a sign-in" until the page no longer asks. The bot's instructions tell it never to retry a site that refused it or a page that is only a check, and to say so in its report.
- **What sites see.** The browser names itself as the Chrome it is (`Chrome/…`, not `HeadlessChrome`); `navigator.userAgentData` and the `Sec-CH-UA` headers name the same Chromium and system. A page reads `navigator.webdriver` as false only while the owner holds the browser (after Take over, or when they open it to sign in). Everything the bot loads or drives reads true from its first script: every page, frame (at any depth) and page a site opens, with or without an opener. When the browser cannot be sure, the answer is true (`ManagedSession` in the browser worker):
  - While the owner holds the browser, the bot can read its pages but cannot act, open a tab or load a page; a call that was waiting its turn when they took over is refused when the turn comes. Take over stops a page the bot was still loading and closes a tab it was still opening, and the page the owner opens the browser on loads in the next turn, as their input.
  - At Give back every page reads true again. A page that cannot take the mark back within a few seconds (one showing a dialog the owner left open) is closed rather than left reading false.
  - When the owner opens a closed browser on a page, the browser is theirs before that page loads.

  So a human check such as Cloudflare's "Verify you are human", completed by the owner after Take over (and a reload when the check had loaded while the bot drove), passes, and its clearance stays in the bot's profile for later visits.
- **The owner's view** (`bots.browser.*`, apart from the required Bot UI methods, so an older daemon simply shows none): `get` returns the followed tab's URL and title, the activations that used the browser, and who holds it as the asking view sees it; `watch` and `unwatch` start and end the pictures (below); `hold` takes the browser over for a view, keeps it and gives it back; `send` carries that view's numbered input (below); `open` opens the browser for the owner, as their view's hold, to sign in to a site for the bot. `get` with `frame` still answers a fresh JPEG of the tab for an app from before `watch`, and an older app's `control` and `input` still work, as a hold of its window. Taking over, input, `open`, `close` and `get` with `frame` are the desktop app's on this computer alone, like watching (`bots.browser.files`, below, is its main process's alone).
- **Taking the browser over** (`BotBrowsers.hold`, through the general viewer `WatchedBrowser` in `src/mms/browser/viewer/`; the view's side is `botBrowserStore`, over the general `watchedBrowserStore`, with the general `BrowserInputChannel`, `useBrowserInput`, `WatchedBrowserFrame` and `WatchedBrowserPane`, the split view). The host alone decides who holds the bot's browser, the bot or one view of the owner's (an app window, with an id it keeps across reloads), and every view hears it at once.
  - **A hold belongs to the view that took it, on the connection it took it on,** and lasts while that view says it is there, every 5 seconds, whatever is on screen. A call on another connection is not the hold's, even naming the right view and hold. A window that reloads keeps its connection and picks its hold up again from `get` or `watch`, at the host's last input number; a window whose connection dropped presents its hold on its new one (its next heartbeat) and the hold moves there, once: the connection it left never has it again. A window that was hidden asks the moment it is shown again, and says at once if its hold ended meanwhile. A view gone for 2 minutes (the window closed, the app quit) ends its hold: what the person left pressed is let go of, the browser goes back to the bot, and its chat says so once ("I have my browser back: the window you took it over in went away."). Give back lets go of pressed keys and buttons and drops an IME composition (keys held while the page shows a dialog go up as soon as it is answered); the bot hears of the person's visit only as before (its old observation is stale: it observes again), never what they typed.
  - **Another window** sees "Held in another window" and takes the browser over only by pressing Take over there; its `open` is refused the same way. The first window's hold ends, and what it left pressed is let go of. Take over again in the window that holds it gives it a fresh hold, numbered from 1: whatever its old channel still waited on is dropped.
  - **Taking over while the bot acts** ends the bot's action in flight, and its tool call answers that its owner took over and whether the action was applied, not applied, or can't be told (a navigation whose page committed was applied), so the bot does not repeat it blindly.
  - **The hold is the only one.** The bot's browser is the owner's exactly while a view's hold lasts (an older app's `control` is a hold of its window): it is what refuses the runs' actions, what keeps the view on the tab taken (below), and where the owner's input goes. Take over holds exactly the tab the view shows (the followed run's tab; with none followed, the one the last picture showed), as it was when they pressed it, whatever a run does meanwhile.
- **The person's input arrives, or says why not.** Every input goes on the hold's channel (`bots.browser.send`) with the hold's id, its own number and the picture it was made on. The host applies each number once, in order, one at a time (`InputSequencer`): an input that comes before the one ahead of it waits for it up to 250 ms, then what waits behind a gap is refused as `gap` without using its number up, and the view sends it again. A number already taken is answered as a duplicate, so a resend after a lost answer applies nothing twice. Each input is answered as applied, a duplicate, or refused with a plain reason, and goes to the tab the view took, never elsewhere. It is applied in the browser's turn (`BrowserTurns`, above), so it never lands beside a run's call: it goes ahead of the runs' calls that wait, and a run's call under way (only reading is left to a run during a hold) has 150 ms (`OWNER_CUT_IN_MS`) to end before it is stopped and its run told its owner is using the browser now; the browser then stays theirs a second after each input (`OWNER_KEEP_MS`), so a burst of typing never waits on the runs key by key. So "Sending…" and "Not reaching" below are about the page and the connection, never a run's long call. The answer comes once the worker applied the input, never when it was only queued. The view merges an unsent move into the move before it and adds wheel turns up, and never reorders kinds: text typed before Enter reaches the page before Enter.
  - **No refusal leaves a hole.** Every number the view gives out reaches the host as its input or as a skip, which uses the number and applies nothing. An input the service never takes (a prompt answer over 4,096 characters, anything malformed) is refused in the view before it gets a number; one the service refuses anyway (a batch refused as a whole is sent again one by one to find it) is dropped, said once, and its number skipped. A refusal that did not use its number (`gap`, or `busy` when more than 256 wait at the host) is sent again by the view, backing off from 250 ms to 4 s, for 10 seconds after the person made it; after that it is dropped, said once ("Not sent: the page did not take it in time"), and its number skipped. A gap the host reports below everything the view still has is filled with skips.
  - **What the view shows.** A small mark where the person pressed settles when the answer comes. Nothing more while input arrives. Half a second without an answer: "Sending…". Three seconds: "Not reaching <computer>" (this computer, named as the rest of the app names it) with Retry, which resets the back-off and sends everything unanswered again at once (the view also sends again by itself after a failed call). A refusal is said once, in one short line.
  - **Back-pressure.** While 24 inputs wait for an answer, or none has come for three seconds (a page that stops answering: a CDP call can wait up to 30 s), the view takes no new press, key, text or move: each is refused in the view at once, and the line reads "Not reaching <computer>", so typing does not pile up to arrive in a burst later. Letting go (a button or a key going up, Give back) always goes, unless what went down was refused too. When the page answers again, what was taken arrives once, in order, and the line clears by itself.
  - **Pictures that are no longer the page.** Each picture carries a number, and the host keeps, for its last 32 and for every one sent in the last 5 seconds (at most 256: 5 seconds at 30 a second is 150), the tab, page and scroll it showed. The worker reads the scroll as each picture is taken (Chromium without a window reports none with its screencast), and a picture goes to no view before that is read. A point on a picture of the same page, scrolled since, moves by the scroll, so it lands on what the person saw; one now out of view, on another page or on another tab is refused ("Page changed · click again"), and the view shows the page as it is. A press or a key made on a picture the host cannot place (older than that, of another tab, or none) is refused at the host and never reaches the page; the worker also refuses any click, press, move or wheel turn that comes without the place of its picture. Typing made on a picture after its click was refused is refused too, until a later click on that picture lands. A held button is still let go of, and a wheel turn is never refused for scrolling.
  - **What was under a press.** While the owner holds the browser, the worker also reads, with each picture, which element is on top at a grid of 16 by 9 points (80 px apart on a 1280 by 720 page), in an isolated world the page's scripts never see. A press (a button going down, a click) on an older picture is checked at the grid points around it (up to four, those still in view after the scroll): each must still have the same element on top, where it was on the page (within 6 px). If not, the press is refused ("Page changed · click again"). This catches a modal or an overlay that opened over the point, a shift of the layout (a banner that pushed the content down), and an inner area that scrolled under it (checked on Chromium on macOS). It does not catch: a change smaller than the grid, that covers the press but none of the points around it (a small tooltip or popover); a change inside an iframe (the frame element itself is what is on top); a change of what an element shows without moving it (its text, a canvas); a change in the moment between the picture and the reading of its grid; and a press on a picture whose grid could not be read (a page that did not answer within 2 seconds, an older app's pictures), where the scroll check alone stands. An element fixed on screen is compared by its place on the page, so after a scroll a press on it in an older picture is refused rather than moved.
  - **What reaches the page.** Pointer down, moves and up with buttons and click counts (hover, drag, double and right click, text selection); every wheel turn; keys down and up with modifiers and codes (the key code a browser's events carry, never a platform's native code: on a Mac those are other keys, and Chromium would press and repeat those), where a Mac view's Command is the page's Control on a page that is not on a Mac and the editing shortcuts (select all, undo, redo) run their command, since a browser without a window has no menu (on a Mac a key pressed with Command is let go of at once: the window never hears it go up); IME composition and dead keys as composition, committed as text; paste of the person's clipboard text on their paste only (at most 64,000 characters); on a touch screen, a tap clicks, a long press is a right click, and one or two fingers scroll.
  - **The person's clipboard.** Copy (and cut) on the person's own shortcut reads the page's selection as plain text, in an isolated world, and the app writes that text on their clipboard. The browser's own copy never runs: its clipboard never holds what the person copied, for a page or the bot to read back, and the page hears no copy event; cut then deletes the selection in an editable field. Chromium without a window has a clipboard of its own, never this computer's: checked on Chromium on macOS, a page's `navigator.clipboard.writeText`, its `document.execCommand('copy')`, its own copy handler and the browser's copy all leave this computer's clipboard unchanged. While the owner holds the browser, pages are refused the clipboard (`navigator.clipboard` read and write), and the browser's defaults come back when the bot has it again. A page can therefore put nothing on the person's clipboard except through their own copy, as text. What a copy read is answered once: a duplicate of it carries no text.
  - **The page's dialogs and file picker.** An alert, confirm, prompt or leave-page question stops the page until it is answered: the view shows it over the picture with its own buttons, and the page takes nothing else meanwhile ("Answer the page's dialog first"). The input that opened it counts as done once it is open, and a dialog that opens while a press is being checked lets its answer go first. While the owner holds the browser, the tab they took answers its file picker through their view, and only theirs: the card names the site whose frame asks and whether it takes one file or several ("example.com asks for a file"), and nothing goes to the page until the person chooses. Choose… opens this computer's own open-file dialog from the app's main process, which sends the chosen paths to the service on the window's own connection (`bots.browser.files`, not one of the renderer's methods). The service checks them again (the hold, a picker open on the held tab, at most 16 files and 512 MB in all, each a file; over that, "Choose at most 16 files, 512 MB in all.") and answers a one-time token, which the view sends as its `files` input. The renderer never names a path, and the input channel takes none. A token gives its files once, and none outlives the hold.
  - **What it cannot do.** The browser's own menus (its right-click menu, its Edit menu) have no window to show in. A `<select>`'s list opens as a popup the browser has no window to draw (checked on Chromium 153 on macOS): a click shows nothing, and the arrow keys and Enter then go to that unseen list and change nothing; Escape closes it, and typing an option's first letters chooses it. Drag and drop of files from this computer into the page, and pinch zoom, are not sent. The protocol carries no step that needs the view and the service on one computer, except a chosen file, which goes by its path from the app's main process to the service.
  - **Never kept.** What the person types, pastes, copies or chooses goes to the page or their clipboard only: it is not logged, written to the bot's journal or memory, put in the bot's context, or kept for a duplicate's answer.
- **Pictures are pushed, and only while seen.** A view that shows the browser calls `watch` (renewed every 5 seconds; the daemon drops one not renewed for 15) and the daemon pushes `bots.browser.frame` events to that window's own connection: a JPEG when the page paints, the page's size and title only when they change, and the agent cursor as it moves. A still page sends nothing, apart from one picture at full quality about 300 ms after it stops changing. A page that flips between pictures it showed a moment ago (a blinking caret) sends the flip back once, then at most one every 5, 10, 20, 40 and 60 s; a page that changes every second (a clock) sends one picture a second and, after its first two, no full-quality stills. The app watches only while the preview or the split view is on screen and the window is shown, and stops a second after neither is or when the window reloads; with no view watching, the worker runs no screencast at all. Only the desktop app on this computer can watch, a window watches a bot once, at most eight views watch one bot, and a window can end only its own watch.
  - **Sizes:** the preview asks for 480 px wide at most 5 pictures a second; the split view for its own width up to 960 px at most 15 a second, 30 while the owner holds the browser. One capture of the tab serves every view at the widest size asked; each view has its own slot, so a slow one drops pictures and never queues them, and Chromium is asked for no more pictures than some view takes (its acknowledgement waits until a view is free). No picture is over 1 MB: a larger one is taken again smaller.
  - **A tab behind is never brought to the front for the view.** Chromium without a window paints only its front tab, and the bot acts on that one: a view that pulled another tab forward could leave the bot acting on a page that no longer paints. A followed tab behind gets one still picture, and the view reads "On another tab" until the bot uses it again. A tab a site opens never stays in front, and when the tab in front closes, the bot's tab in front before it comes back, so "On another tab" is always true.
  - **Take over brings the tab to the front.** The owner takes the tab the view follows: it comes to the front, as it does for each of their clicks, keys and navigations, so Chromium paints what they do. While the owner holds the browser the view reads "You have it", never "On another tab".
  - **The view tells the truth.** "Live" only while pictures can arrive. When the stream stops (the browser closed, the followed tab closed, the tab the owner took over closed, the service cannot be reached, a watch cannot be renewed) the picture stays and the line reads "Not updating · 12 s"; each renewal answers whether pictures can arrive now (`stalled`), so a renewal never makes the view live by itself. It recovers by itself once pictures can arrive again. A page still loading reads "Loading" (a moving line under the split view's address); one that ran into a problem says it in one line ("Can't reach example.com", "example.com needs you: a sign-in"), with Chromium's code in the tooltip; with several runs browsing, only the followed run's problems show. The owner's own navigation, back, forward and reload return as soon as the page has committed.

**The tab the view follows** (`follow`, `refollow`), which the preview and the split view both show and the owner's input goes to:

- While nobody holds the browser, it follows one activation (`followed`, the view's `activationId`): the first that used the browser, and after it ends the newest that still runs. Its current tab is the one shown; another run's calls never move it, so with several runs browsing the view never jumps between them.
- Take over (or a browser opened for the owner) is a view's hold, and holds the tab the owner sees. Until the hold ends (Give back, or its window gone for 2 minutes), nothing a run does changes the followed tab, and their clicks, scrolling, typing and navigation go to that tab only; an input made on a picture of another tab is refused. The other runs keep their own tabs: they read them in their turn, and acting, opening a tab or loading a page is refused. If the held tab closes (its run ended), their input is refused with "The tab you took over has closed. Give the browser back, then take it over again.", and the view keeps its last picture rather than show another run's tab. When the hold ends the view follows a run's tab again.

In the bot chat, the reply of that activation shows a small live preview: the picture, the page's title and site, the status, and the agent cursor. While that activation still works, the preview sits under the working line. Hovering it shows Expand, which opens the split view: the bot's browser beside its chat, following the same tab, with Take over and Give back, back, forward, reload and an address field. While the split view is open, it alone is watched and the preview shows the same pictures. Activity chips read "using the browser" and "used the browser · example.com".

## Use your MCP tools

A bot can use its owner's MCP servers (Settings → Skills & MCP), one ask per server: "Kai wants to use your GitHub tools." The code is `src/mms/bots/mcp/BotMcp.ts`.

- **Which servers.** Those the owner set up in Mousse for the whole profile and turned on there: the relay catalogue's scope with no project (`RelayCatalog`), which lists Mousse's own profile config. A project's servers (`mousse-project:…`, `external-project:…`), other apps' configs (Cursor, Claude, Codex) and a server named like Mousse's own (`mousse`, `mousse-relay`) are never offered or askable: their ids are not grantable (`mcpGrantable`) or the catalogue leaves them out. The relay switches per runtime (Share with other agents) are for the owner's threads; a bot reaches the profile's servers through Mousse whatever they say (`listProfile`). MCP off in Settings is off for bots too.
- **How the bot knows them.** `mcp_servers`, always on and never grantable (like memory), in both lanes: each server's name and id, a line of Mousse's own ("26 tools, such as create_issue, …", or "still starting: its tools are loading"), whether the bot holds its tools (`yes`, `no`, `some: it has new tools`, `no: it changed since you were allowed it`), whether it is answering, and whether it is still starting. No schema, description or other text of the server's. It is a tool rather than lines in the situation or the system text so those stay stable for the prompt cache, carry no third-party text, and cost nothing until the bot needs them. The system text names the servers it holds ("Your owner's MCP servers: GitHub"); a consult's says it has none ("none in this consult (your main work has GitHub; …)"), since a consult is never given MCP tools.
- **Which server a grant names.** A grant holds a server by its installation and its identity, `<installation>.<identity>` (`mcpServerIdentity`, 10 hex characters): the hash of a remote server's URL origin and path (never its query), or of a local server's command and arguments, with secret-looking values (a value after a flag that names a key or token, a long key-shaped string, a `key=value`) left out, and never its environment or headers. A server edited in place to point elsewhere keeps its installation but gets another identity, so its grant holds nothing: About marks it "Changed", and the next use asks again ("Kai wants to use your GitHub tools again", "GitHub changed since you allowed it: …"), whose Allow replaces the old pairs (`replaces`). A grant made before identities names the bare installation and still holds its server.
- **The ask.** `escalate({ mcp: { server, tool? } })` names a server by name or id. Mousse turns any MCP ask, the bot's or a gate's, into one for the server (`mcpAskFor`): its name, every tool a bot can be offered that the grant lacks (`tools`), `added` when the bot holds some already, `changes`, what the tools' own read-only hints say (all read-only, some can change things, or no hint), and `unusable`, how many of the server's tools a bot can't use (a name a grant can't hold, such as one with `/` or `__`, or a tool the relay leaves out: too many tools, a schema too large). Its fingerprint is the server's (`{mcp:{serverId}}`), so there is one open ask per server however many tools or runs ask. The card reads "Kai wants to use your GitHub tools", its note says what the hints say ("GitHub says some of these tools can change things."; never Mousse's own judgement), and its details line ("13 tools", `BotAskCard.details`) opens to the tool names, with "2 more of GitHub's tools can't be used by a bot." when some can't. **Allow** grants exactly the tools the card listed, each as its own pair in the grant (`withPermission`), so nothing is asked again for them. A tool the server adds later is not granted: its next use is one more ask for the server, "Kai wants to use GitHub's new tools" ("GitHub has new tools. …"), listing only the new ones. The ask caps work as for every permission. A server or tool that is not set up here, a tool a bot can't use, or a server that is not answering with no tools known, is refused at once with no card, in both lanes. No `bots.db` change: the grant format already had `mcp: [{serverId, tool}]`.
- **A server that has not answered yet.** The servers are published as they answer (below), so one that is slow to start shows to the bot as still starting. An ask for it makes a card at once ("GitHub is still starting, so its tools aren't listed yet. Allow turns on once they are.", `loading`), with Allow off and Not now working; Allow is refused by the service too, so it never grants tools the owner has not seen. When the server answers, the card is filled in with its tools and what their hints say, and Allow turns on (`BotEngine.fillMcpAsks`, on each change of the listing); one whose tools the bot holds by then is settled as allowed, and one that fails or is removed keeps Allow off and says so. Before the servers were read at all since Mousse started, an MCP ask makes no card and is not refused as unknown: the bot is told they are still being read and to try again (`BOT_MCP_NOT_READ_TEXT`), and they are read.
- **What the bot is told.** It is told it asked ("Asked the owner. …", `BOT_ASK_REFUSED_TEXT`, `BOT_ASK_DEFERRED_TEXT`) only when a card exists for that permission. For 24 hours after Not now, a run's call or ask of any kind makes no card and is answered "The owner said not now to this. …" (`BOT_ASK_NOT_NOW_TEXT`).
- **Lanes.** MCP tools are work's, like the web and the browser: a chat turn is not offered them (`frontDeskManifest`), and an ask for a server the grant holds is answered with "hand the job to work_start" (`BOT_WORK_HAS_TEXT`). The chat may raise an ask for a server it lacks, as a wall, so the owner answers before work starts.
- **What a turn is offered.** A turn of a bot that holds an MCP permission reads the owner's servers first when the listing is cold, old, or changed since (servers added or removed, settings: `BotMcp.warm`, `ensure` with `fresh`, at most 3 s, never starting a sign-in; a warm listing returns at once); a bot with none starts its turns without reading or starting any server, and reads them only when it calls `mcp_servers`. A change of servers in Mousse reads them again at once (`RelayCatalog.invalidate`). The catalogue publishes the configured servers first, then each server's tools as soon as it answers (`McpManager.getEnabledToolsByServer`'s `onServer`), so a slow server hides only itself. Work is offered the granted tools of servers set up now (`BotMcp.offered`, `BotAuthority.mcpTools`), under the relay's names (`<server>__<tool>`). Their descriptions, and every argument's description and title, are framed as the server's own words, never instructions, cleaned of markup that could read as system text (tags, special tokens, role markers, code fences) and cut short (300 characters for a tool, 120 for an argument); comments and examples in the schema are left out.
- **How a call travels.** Every call goes through Mousse, where the bot's authority checks the `server::tool` pair against the grant before the server sees anything (`callForBot`), then runs on the owner's own connection (`BotMcp.call`, `McpManager.callTool`). The bot never talks to a server itself and never sees its config or credentials.
  - *Claude Code:* the bot turn gets Mousse's relay as its only server beside Mousse's own, both registered over Claude Code's input (#358), with no settings files, plugins or other servers. The relay lists only the turn's offered tools (`RelayHandler.list`, `botOf`), and the grant gate (`ClaudeLockedGate`) checks every `mcp__mousse-relay__…` call by name before Claude Code sends it; any other relay name is refused. The relay checks it again.
  - *Codex:* the relay is attached (`codexMcpConfigOverrides`), the owner's own Codex servers stay off for the thread (`codexBotMcpOverrides`), and the relay is the gate: Codex asks nothing about MCP tools Mousse serves.
  - *Pi:* the user MCP proxy offers the turn its offered tools under their provider names (`ToolRegistry.userMcpForTurn`). Pi's gate checks a call of one of them as an MCP call of the grant (server and tool), as Claude Code's gate does, before it is charged; the registry checks it again before it runs (`callBotMcp`).
- **Results are data.** What a tool returns is framed for the bot as data from that server, never instructions ("[What list_issues on your owner's MCP server "GitHub" returned. …]"), cut at 32,000 characters. Its images reach only a model that takes images in tool results (`toolImages`), at most 4 of at most about 1 MB each; the others, or all of them on a model that can't see images, are named in a note. It is journaled like any tool result (bounded, `external`) and passes the memory guard before it can enter a pack.
- **Limits and failure.** A call obeys the activation's stop signal and deadline and runs at most 2 minutes (`BOT_MCP_CALL_MS`, with Mousse's own timer under the connection's). A server that is down, slow or failing gives the bot one fixed line by kind of failure ("GitHub isn't answering: it took too long.", "… Mousse couldn't reach it.", "GitHub couldn't start on this computer.", "GitHub couldn't run this call."), never the server's own words, a host, a port or a command path; the raw text goes to the owner's log (`BotMcp`), and the run carries on. A call never starts a sign-in (`signIn: false`): an OAuth server without a session refuses at once, and one whose session cannot be renewed fails instead of opening a sign-in page (`FileMcpOAuthProvider.holdSignIn`); the bot is told the owner must sign in again in Settings, and says so in its report rather than asking. A server removed from Mousse or switched off is gone from every turn at once (not offered, and a call is refused by `McpManager.isToolCallAllowed`); its grant entries stay but give nothing.
- **The connection.** A server's connection is the owner's, shared by their threads and the bots, and lives as long as the profile's MCP work, never as long as the call that opened it: a bot's call that is stopped ends only its own wait (`McpManager.connect`). A stdio server whose call timed out is pinged, and restarted only if it no longer answers and no other call runs on it, so a slow call does not lose the server's own state.
- **What the owner sees.** About → Can use lists each server once ("Use your GitHub tools", its tools in the tooltip, and how many of its tools a bot can't use), with Remove, which takes all of them (`withoutPermission`). One that gives nothing now says what is true and is marked so (`BotPermissionItem.mark`): "Gone from Mousse" (not set up any more), "Switched off" (in Settings → Skills & MCP), "MCP is off", or "Changed" (edited since it was allowed); Remove is offered as an option, not as the fix. That is shown only from a listing read since Mousse started (right after a start the servers are read in the background, and nothing is shown gone meanwhile). Chips read "using GitHub" and "used GitHub" (`chipCallOf`: the server's name only, never a tool or its arguments). The bot chat shows no tool rows or arguments.
- **Older builds.** A build without this change refuses to compile a grant that holds MCP tools, so a bot that holds some does not run there until they are removed in About.

## What bots may do here

Each computer caps what every bot on it may do, whatever its grant holds: Settings → Agents → What bots may do here (`settings.bots.here`, `BotComputerLimit` in `src/shared/bots/personal/computerLimit.ts`). Three switches, all on by default: Run commands, Use files on this computer, Use the browser. The owner sets them on the computer they protect. They are one setting for the whole installation, kept in the installation's own `mousse.conf` (the top-level `bots` key, an `installation` key in `settingsClassification.ts`, never in a profile's file), so every profile's bots are held to them, every profile's Settings shows them, and a profile made later starts held to them. No other computer reads or sets them (`settings.*` methods are not routed: `ThreadRouter` refuses them as not available remotely and the owner side registers no such method), and no bot tool, thread agent tool or app tool writes settings. The web, skills, limits and the owner's MCP tools are not covered.

- **What a switch takes away.** Run commands off: no `shell`. Use files off: no file access; the bot's files folder and scratch folder still work, as for a bot that never had it. Use the browser off: no browser tools and no browser for the turn.
- **Where the service holds it.** Where a grant becomes what a turn runs with: what an activation runs with (`effectiveManifest`, after any "Allow this time"), the compiled thread (`compileBotThread`'s `limit`: its tools, the sandbox's folders and the browser), and the authority's check of every call (`createBotAuthority`'s `limit`, read at each call). Every runtime goes through these: Claude Code's grant gate and sandbox, Codex's approvals and sandbox, Pi's gate and the tools it is offered, and the app tools (the browser's). So both lanes, consults, scheduled runs, reminders' work, continuations and work resumed after a restart are held to it.
- **The grant is kept.** A permission above the ceiling stays in the grant and gives nothing while its switch is off; an Allow given meanwhile is kept the same way. Switching it on gives it back from the next turn, with no new ask. About marks such a permission "Off on this computer", with the details in its tooltip (`BOT_OFF_HERE_MARK`, `BotPermissionItem.mark`), and reads again when a switch changes (`computerLimitChanged`).
- **Work already running.** The authority reads the switches at every call, so a switch turned off refuses the next call of a turn already running (a `computer` wall): no card, and the bot is told "Not on this computer: "run commands" is switched off here, so you can't use it or ask for it. …" (`notOnThisComputerText`). That is not enough for commands and file access, which a runtime opens once for the whole turn: Codex runs the read-only commands it trusts without asking anyone (in the `workspace-write` sandbox: with file access, and on Windows), a turn that started with file access runs its commands in a sandbox opened over every folder, and on every runtime a command already running runs on. So when Run commands or Use files is switched off, every bot turn running now that started with it stops at once, on every runtime (`BotEngine.computerLimitChanged`, `cutForLimit`). A consult's powers are recorded like its main turn's (`LiveDispatch.consultPowers`), so a main turn without commands whose consult has them is stopped too, also after a switch went off, on (the consult started) and off again. Its turn and consults are aborted the way a wall ends a dispatch (the run ends `bot_wall`), the bot's chat gets one line that says only what is true then ("Stopped: "run commands" was switched off on this computer."), and the activation goes on in a new turn under the new limit, told why (`limitCutLead`), if it can: whether it does shows in the work itself. The stop clears only the cut-off calls of what its switch took away, in the main turn and its consults (`acknowledgeCut`): a command when Run commands went off, and a file change outside the bot's own folders (its files folder and scratch) when Use files went off. Those are listed to the next turn as interrupted and don't hold the work for an acknowledgement: the owner's own switch stopped them, and the bot no longer has the power. A cut-off change of the bot's own files, a command cut off when only Use files went off, and any other call still hold it, as after any interruption, and so does a file change whose arguments Mousse can't match to the one it allowed (they are matched by the tool ledger's digest, noted when the authority allows the change). A crash, a restart and the owner's Stop are unchanged. A turn that never had it, and the chat turn when commands go off (it never holds them), run on. A turn that finished before the stop reached it is done as usual. The browser is checked at every call on every runtime (its tools are Mousse's own), so switching it off stops nothing: the next browser call is refused. A switch turned on while a turn runs gives that turn nothing new: a call or ask for it is answered as held, and the work continues with it once the turn ends (see Asks).
- **Asks.** An ask for something switched off (`escalate`, or a call the gate refuses) makes no card, in either lane, and counts against no cap. The bot's system text says "off on this computer for every bot, so asking won't help" under What your owner allows now, and leaves out the line that offers to ask for it (`baseInstructionsHere`). A card made before the switch went off stays; Allow on it widens the grant, which gives nothing here until the switch is on.
- **Commands reach files.** With Run commands on and Use files off, what a command can read depends on the runtime and the platform (see Run commands). Held to the system's own folders (`/usr`, `/etc`, …, and `/tmp` with Claude Code) and the bot's folders: Claude Code with its sandbox on Linux, and Codex on Linux and macOS. Not held: Claude Code on macOS reads everything but the home folder; Claude Code on Windows (no sandbox), Claude Code on Linux without bubblewrap or socat, Codex on Windows, and Pi read everything the computer's user can, and the unsandboxed ones can change it too. To keep bots away from files there, switch off Run commands as well. The Run commands switch says so in its tooltip.
- **Commands reach this setting.** It is changed through the background service, which takes only a client holding the owner token kept in Mousse's own data, or by writing the installation's `mousse.conf`. A command without a sandbox (Pi, Claude Code on Windows or without bubblewrap or socat) can do either, so there only Run commands off keeps bots from it. In a sandbox it can do neither: Claude Code's sandbox can't read or write Mousse's data, so it never has the token (its settings also refuse Unix sockets); Codex's sandbox writes only the bot's folders, and on Linux refuses a Unix-socket connect in every mode (checked against the pinned Codex 0.162.1; not checked on macOS or Windows). Codex with file access, or on Windows, can still read Mousse's own data, the token included.
- **The browser.** The bot's browser opens only http(s) pages (`browserNavigationUrl`, at the policy and in the browser worker), so it can't open a `file://` page, and its uploads are refused (its broker has no resolver for local files), whatever the switches say.
- **Space bots** (`src/mms/bots/space`) run nothing today (`NativeBotRuntime.supports` is false for every profile): no model, no commands, no browser. Their planned `reader` profile reads an owner-chosen project; it must be held to Use files before it is turned on.
- **A setting that can't be read fails closed.** Never written (a first start, an update from a build without it): every switch on. Present but not `{ here: { shell, files, browser } }` with three booleans (`null`, `false`, a string, an array, a switch missing or not a boolean): every switch off. When the installation's `mousse.conf` could not be parsed and was kept aside (`mousse.conf.corrupt-…`), the defaults that replace it are written with every switch off and marked (`bots.unreadable`), and Settings says so in one line beside the switches until the owner sets them again (`normalizeBotSettings`, `MousseConfigStore.readOrMigrate`). A profile's own file that can't be read leaves the setting as it is. When the service can't read it at all, no bot gets any of the three.
- **Writing it.** `settings.set` takes `bots` only as `{ here: { … } }` naming one or more of the switches, each a boolean; anything else (`null`, no switch, a switch it does not know, a value that is not a boolean, an extra key) is refused and nothing in that update is saved (`botSettingsWrite`). The service puts the switches named over the ones it holds (`MousseConfigStore.setBotsHere`, every switch off when the stored value can't be read), in the one store the installation has, so a write names only what it changes: each switch in Settings sends only itself, and `mousse config set bots.here.shell false` works. A window, profile or the CLI whose copy is older never turns back a switch changed elsewhere. A switch added later is written the same way. An update that also changes other settings is saved whole or not at all: the switches are written last, and a failure anywhere puts back what was written (`MousseConfigStore.atomically`).
- **Every window follows it.** A change from any profile, window or the CLI reaches every profile's windows as `settings.changed`, with that profile's own settings (`MmsProfileServices`), and an open Settings page shows the switches as the service holds them.

## Schedules

A bot's schedule is an **automation whose Who is the bot**: an ordinary job in the shared scheduled-job store (`ScheduledJob.bot`), claimed by the one `ScheduledJobService`. It is not on the definition, so a schedule changes no revision and needs no approval. Manage, on the Automations page, lists it with the person's other automations, and its Edit details changes When, Do, the name and Tell me; Who stays the bot, and its May is the bot's grant. Its runs are in the Automations inbox like any automation's, and its Needs you items are assigned to the bot (folded under Assigned to bots). The bot's About lists the same records.

- The bot keeps them with `bot_schedule_add`, `bot_schedule_remove` and `bot_schedule_list` (the job scheduler's agent tools own the `schedule_*` names, and never see a bot's jobs). `bots.schedules.add` and `bots.schedules.remove` are the owner's. All of them go through `BotScheduleBook` (`src/mms/scheduled/botJobs.ts`): at most 8 per bot, at most every 5 minutes, on an interval or a cron expression. Each add shows its label as a chip ("every weekday · 09:00").
- A job's id is `<botId>--<scheduleId>`; the schedule id is the one the bot and its chat know.
- Each due occurrence is handed to `BotEngine.runScheduledOccurrence`, which inserts a run activation keyed `sched:<botId>:<scheduleId>:<occurrenceAt>` (so a repeated hand-over inserts nothing). It is skipped, with the reason on the job (`botSkip`), while the bot is paused, while every model is at its usage limit, or while the same schedule's previous run is still queued (`previous_run_still_queued`), runs (`previous_run_still_running`), waits at a wall (`bot_waiting_for_owner`) or waits for the internet (`waiting_for_internet`): a waiting run never expires, so a schedule keeps at most one. Other schedules' runs and the owner's work never skip it: they run beside it. Missed occurrences collapse into one. A new or edited time starts from now and never runs a backlog. Nothing starts before the bot startup pass.
- After each tick, `BotEngine.maintain` ends usage-limit pauses past their reset, starts what waits in a free lane, and runs the daily purge of deleted bots.
- **Tell me** applies to run reports. A run reports its level with `run_report`, as any automation run does; a done run whose level is below the automation's Tell me posts its report without a notification (`bots.message` carries `quiet`). Failures still notify.
- Turning one off in Manage pauses that schedule only; the bot's own Pause stops all its schedules.
- In a profile where bots could not be opened, a bot's schedule is paused once with that reason ("Bots could not be opened in this profile…"; a deleted bot's with "Its bot was deleted."). The next start that opens bots resumes the schedules paused for that reason only.
- Schedules saved by earlier builds in `bots.db` (`bot_schedules`) are moved once into the shared store at profile open (`migrateBotSchedules`); see "Moving schedules".

### Moving schedules

Earlier builds kept schedules in `bots.db` (`bot_schedules`, with their next runs in `bot_schedule_state`) and ticked them with a scheduler of their own. At profile open, before anything ticks, `migrateBotSchedules` (`src/mms/scheduled/botScheduleMigration.ts`) moves them once:

- Each schedule that is not removed becomes the job `<botId>--<scheduleId>` with its prompt, who added it, when it was made, and the next run the old scheduler had (a time edited since its last tick starts from now). A next run already due runs once, as it would have before.
- `bots.db` v5 adds `migrated_at` and `migrated_job_id` to `bot_schedules`; each row is marked with its job after the job is saved. Rows are never deleted, and opening a v4 database first writes the copy `bots.db.pre-v5`.
- It is idempotent: a job that is there already is only marked, so a move stopped part-way is finished at the next open and never makes a job twice. A moved schedule removed later is never moved back.
- `unmigrateBotSchedules` undoes it in code (the jobs go, the marks are cleared); no command runs it. Edits made after the move are not copied back, and schedules added after the move have no row, so they are not brought back.
- A bot's job names a thread that does not exist (`bot-schedule:<botId>`). A build from before the move, which ignores the `bot` field (and cannot open a v5 `bots.db`), finds that thread gone and pauses the job with "Its thread was deleted" instead of running the bot's prompt without the bot. To go back to such a build, restore `bots.db.pre-v5`.
- **Coming back from an older build.** An older build's first save of the jobs drops every field it does not know: `bot`, `draft`, `keys`, `tellMe`, `agent` and `cliName`. This build keeps a copy of those fields in `scheduled/jobs-kept.json`, a file older builds never write, and puts them back at profile open (`ScheduledJobStore.restoreDroppedFields`) on each job that has none of them; a bot's job goes back to its guard thread, and one paused with "Its thread was deleted" runs again; a draft is a draft again, turned off, even if that build turned it on (the scheduler never starts a draft). `migrateBotSchedules` also repairs from `bots.db`: a moved job without its bot gets it back, and a schedule the older build removed (after `bots.db.pre-v5` was restored) is removed from the shared store. What the older build changed meanwhile stays; a job it added has no copy.

## No internet

A bot activation (chat lane or run lane) waits when the internet is gone, instead of failing.

- **The check** (`src/mms/bots/activation/connectivity.ts`, the host's `connectivity`): a DNS lookup and a TCP connection to port 443 of the provider's API host (Claude Code `api.anthropic.com`, Codex `chatgpt.com`, a known Pi provider's host) and of two well-known hosts; any one that answers is online. It never calls a model API. A Pi provider on this computer (Ollama, LM Studio) is never checked. Results are reused for 5 seconds.
- **When.** Before each main dispatch is sent (`sendDispatch`). While a dispatch runs, every 20 seconds once it has made no call for a minute; two failed checks in a row end it. At its deadline, when it made no call for a minute. And when its run fails on a connection error (`[provider_unavailable]`, ENOTFOUND and the like; `isConnectionFailure`); with the internet there, that is the provider's own failure and ends the run as before.
- **While it waits** the activation stays `running` with `end_reason` `waiting_for_internet` (no new column, so older builds still read `bots.db`), and holds its run slot. Its chat gets one notice, "Waiting for internet. I'll carry on when it's back." (`bm_<activationId>_offline`, at most one per activation), and no error row. The summary's `stateText` is "Waiting for internet" (sidebar row, chat header and status line, `waiting: 'internet'`) while every running activation of the bot waits. A dispatch ended for the internet is charged only up to its last call. Waiting is never a failure, never counts toward the failure streak and never raises an ask.
- **When it is back** (checked after 15 s, then 30 s, then every minute): a dispatch that was never sent is sent; one that ended is continued on the same thread with "The internet connection dropped while you were working; it is back now. Continue." (`continueWith`, `network`), as a restart continuation is, without using the automatic restart allowance. Unknown calls still pause it first.
- **Restarts.** A waiting activation is found by the startup pass: a dispatch never sent is sent again through the same check; one that ended waits again and continues once the internet is back.

## Model and depth

A bot's models are **rows** (#673, `src/shared/bots/personal/modelSlots.ts`): **Talk** runs every chat turn, and **Light work**, **Medium work** and **Hard work** run the run lane by the work's level. Each row is a **pick** the owner made: a provider entry, one of its models and its reasoning level (absent is the model's default). Mousse never chooses a model for a bot made with picks. No client payload carries a model or an instance id, except a Sign in button's instance id and the Runs on methods (`bots.model.*`).

- **New bot.** Runs on, New bot's third step, shows the Computer row, then Talk and Work (Light, Medium and Hard work under Advanced). Create bot stays off until every row holds a pick. The first bot's rows start empty ("Pick a model"); a later bot's start from the owner's newest bot whose rows are all picks (`bots.model.choices`' `last`, `BotEngine.lastPicks`), each kept only while it is offered now. `bots.create` takes all four rows (`slots`) and refuses any not offered now (`model_unavailable`, which returns New bot to Runs on); the bot names itself on its Talk pick.
- **Stored.** The definition stays format 2. While any row is a pick on an entry, `main.slots` holds the rows and `main.model` is a mirror older builds run every turn on: `{mode: 'named', model, depth}`, the model of Talk's pick (else Medium work's) followed by one space (`mirrorOf`). Older builds trim a name before matching it, so they run the mirror as that model, and trim every name they write, so they never write the space: once an older build rewrites `main.model` (`use_model`, its single picker), the mirror no longer matches and the rows are dropped for good (`slotsOf`), even if that build later writes the same model again; `main.model` is then read as every row. A change of depth keeps the mirror and the rows. Rows a later build adds are ignored and kept (`modelSlotsProblem` refuses only a known row that is malformed). No `bots.db` change.
- **A pick remembers its sign-in.** Each pick also stores the entry's kind of sign-in (`credential`: subscription, API key, ambient) and the signed-in account's id (`account`, the gateway's salted hash, never a secret) when the entry tells them, written by the daemon from `BotModelChooser.pickable`, never taken from a client. Entry ids come from the display name, so an entry removed and added again under the same name gets the same id, and switching an entry's sign-in to an API key keeps it: a pick whose entry now signs in another way or to another account can't run (`sign_in_changed`, `account_changed`) until the owner picks again, which saves what the entry has now. Where the entry can't tell (Pi has no account id), nothing is compared.
- **Which row a turn takes** (`turnModelOf`). A chat turn takes Talk. A run takes the row of its level: `set_depth` `now` in that run, else the level its work names (`work_start`'s `level`, kept on the trigger), else the bot's **standing level**, `main.model.depth` (`set_depth` `always`; medium, which is `normal`, unless changed). Scheduled runs and reminder work name no level. Light, medium and hard are the depths quick, normal and deep. An activation's own pick (`use_model` `now`, an automation's model by hand) replaces its row. A pick keeps its model and reasoning level at any depth.
- **The level of a job.** The bot gives each piece of work a level (`BOT_CHAT_INSTRUCTIONS`): light for a quick lookup or a small routine job, medium for most work, hard for research, a long or difficult problem, or when the owner asks it to think harder. "Think harder" or "be quicker" from now on is `set_depth` `always`.
- **One job on a model the owner names** (#1067). The owner can say in the chat which model one piece of work should run on ("do this one with Opus", "use the cheap one on OpenRouter for this"). The bot's rows stay as they are; only that work runs on it.
  - *What the bot sees.* `work_models` (chat only) lists the owner's provider entries that a bot's work can run on, each with its models (id, name as the picker shows it, a few other names) and their reasoning levels, from the same choices as Runs on (`BotModelChooser.workChoices`, which reads them as `pickable` does). It also lists the owner's other entries under `cantRunWork`, each with why in plain words: turned off, signed out, not ready, or a runtime that can't hold a bot to its permissions (only Claude Code, Codex and Pi entries can). And it names the bot's usual Work models. The bot matches what the owner said against this list, and asks when it can't tell.
  - *Starting it.* `work_start` takes `model: { instanceId, model, effort? }`. It must be one of those choices now, and `effort` one of that model's levels; otherwise nothing starts and the bot gets a plain reason to pass on ("Work can't run on Cursor: it can't keep to my permissions."). Nothing else is ever chosen in its place. Left out, work runs on its level's row as before.
  - *Where the pin lives.* The pick, with the entry's sign-in now, is the work activation's own pick (`bot_activations.model_override_json`, `BotModelOverride`), written in the same transaction that inserts the activation, as an automation's own pick is. Every dispatch of that activation reads it (`turnModelOf`) and checks it again before it is sent, so a restart, a continuation after an ask or more room, a note that reaches the work, and a compaction (which happens inside the work's own turn) all keep it. If it can't run any more, the work ends with the usual line ("I can't use Cheap Model on OpenRouter: it's turned off.") and never runs on a row instead. `set_depth` `now` inside that work keeps it. Its rows are untouched, so later work and the chat run on them.
  - *When it may be used.* Only when work is started from a chat turn that the owner's own message started (`ownerWords`): never from a bot's first greeting, a reminder, a schedule or inside work (those can't call `work_start`, or have no owner message). Text the bot read somewhere can't move work to another, possibly costlier, model on its own. The bot's instructions say it must not pick a model for work itself.
  - *What the owner sees.* When the model is not the bot's usual one for that level, the work line names it after what it is doing ("working · Opus 5.5 · 4 min"), and the work chip adds it to the title ("started Vacuum comparison · Opus 5.5"); both show "Opus 5.5 on Claude Code, high reasoning, for this work only" on hover. The name is kept on the work's trigger (`model`, display only). These are the only places the chat names a model apart from the line about a pick that can't run.
- **Resolution** (`src/mms/bots/model/`). Candidates are the owner's entries that are enabled, signed in, ready, and whose runtime can hold the bot's policy (`harness.canHoldBot`). A pick runs only on its own entry, with the same kind of sign-in and account, or not at all: never on another model or entry, and never on a paid API key the owner did not pick. A pick is checked before every main dispatch, continuations included (a restart, the internet back, the turn cap, more room, an answered ask), so an entry switched to an API key while a chat waits at an ask is never used; a mismatch is a pick that can't run. A model by name or by usage is chosen at the first dispatch, and again after a reload or a usage limit.
- **A pick at its usage limit** waits; only what runs on that entry does, never the whole bot. The engine keeps the limit for the bot by entry, until its reset (`BotModelState.limits` in `model_json`), or by entry and family when the provider names a window for one family only: Claude's weekly `seven_day_opus` and `seven_day_sonnet` windows hold for Opus or Sonnet on that entry, and every other window (`five_hour`, `seven_day`, Codex's) for the whole entry (`limitFamilyOf`, the run's `usageLimitKind`). Work the owner asked for waits for the reset (`blocked`, `usage_limit`, the waiting state of Long work) and goes on, on the same pick; scheduled runs whose pick is on that entry are skipped with the reason (`usage_limited`); rows on other entries keep running, schedules included. The chat says "Paused until 14:00 (your Claude usage limit)" once per limit, naming the provider family only; later turns on it wait without a call or a line. The status line and sidebar row say "Paused until 14:00" while any row's entry is limited. A turn that meets the limit is not retried elsewhere. Resume clears these limits, and the model choice's mark of the entry (`clearLimited`), and tries again.
- **A pick that can't run** for another reason (its entry removed, turned off, signed out or not ready, the model gone from it, unable to hold the bot, or signed in another way or to another account) resolves as `pick_unavailable`: the activation ends (`bot_pick_unavailable`), never counted as a failed run, and every row holding that pick is **stuck** (`BotModelState.stuck`, `stuckRowsOf`), as is an automation's own pick (`schedule:<id>`). The line names the model and its entry as Runs on does: "I can't use Haiku 5.5 on Team Claude: it's turned off." (`BotPickMiss`, `pickProblemText`), with one action, **Pick a model**, which opens About → Runs on. Both names may be text from elsewhere (an entry's display name, a custom endpoint's model name): each is one plain line, cut to a few dozen characters (`plainLabel`), and the chat shows it as plain text. That line is for the owner only: it is journaled as a hidden kind (`PostInput.hidden`, `model_change`), which no pack, search or read gives the bot.
  - *A work row stuck:* the line is said once per stuck row. Its scheduled runs are skipped with the reason (`model_unavailable`) and make no run thread; work for it (`work_start`, a reminder's work) is not started, and the bot is told why; the chat's situation says which work can't run, so it can tell the owner. Talk keeps working, and its finished turns change nothing about Work.
  - *Talk stuck:* every owner message gets the same line, with no model call, so no message goes unanswered; those messages are not run later. Work rows that can run keep running their schedules.
  - *Clearing:* a row stays stuck until it can run again: each scheduler tick asks the model choice whether each stuck pick can run (`recheckStuck`, also on Resume), and a turn that runs on the pick clears it; or the owner picks again for that row (About → Runs on, `use_model` `always`). Nothing extra is said. Picking another row leaves it stuck. The status line and sidebar row show "Needs you" with Pick a model while any row is stuck.
- **Bots from before picks** keep working exactly as they did. A row with no pick is "Mousse chooses": by usage, the Settings default first, then depth picks a tier and an effort (`quick` is the standard tier at the lowest effort, `normal` the standard tier at its default, `deep` the frontier tier at the highest; within a tier, subscriptions rank before API keys, then newer models, then the entry's own order; tiers come from `models.json` and `src/shared/bots/personal/modelTiers.ts`). A model by name is matched across entries, subscriptions first, and one that is missing or at its limit falls back to by usage. An automation saved with a model by name (before picks kept their entry) runs that way only on such a bot; on a bot whose rows are all picked its name is ignored, it runs on its level's row (Work), and its first run says so once (`OLD_MODEL_NAME_IGNORED`). Runs on shows such a row as "Pick a model", its tooltip saying Mousse chooses (or which model it runs by name) until the owner picks; a row the owner picks becomes a pick, and once every row is one the bot is a picked bot for good: no method sets a row back to Mousse choosing.
- **Sign in.** A bot from before picks with no model and an owner's entry that could hold it once signed in is stuck with Sign in, which opens that entry's card in Settings → Providers.
- **Default bot model** (Settings → Models → Bot model, `settings.botModel`): only for bots from before picks. A row on which Mousse chooses runs on this default, at the effort its depth gives, while it can run the bot. New bots never use it.
- **By hand (#673).** About → Runs on and New bot show the rows with `BotModelRows` (`BotRunsOn.tsx`): a label and one control per row, the app's own model picker (`SettingsModelPicker`, the composer's model menu with the model's reasoning levels beside it), every control the same width in one column. While two or more entries offer models to the bot, a closed row shows its entry after the model, muted as the menu shows it ("Opus 5.5 · High · Team Claude", `severalEntries`, `SettingsModelPicker`'s `entry`), cut with an ellipsis, never wrapped; with one entry, the model alone. The picker is fed the bot's choices (`providers`): the app's listing (`harness.llmProviders`) narrowed to each ready entry's models that can hold a bot (`BotModelChooser.pickable`, `botPickProviderOptions`), without "Off". Simple view: Talk and Work (the three work rows on one pick); with Advanced, Light, Medium and Hard work apart, each starting from Work's pick. Advanced is open while the work rows differ; closing it puts Medium work's pick on all work as it is (`oneWork`), and can't close while Medium work has no pick and the rows differ. A pick that is no longer offered shows its name with "not available". `bots.model.setSlots` saves only the rows the owner changed (`slots`), over the rows as they are at that moment, so a change the bot made meanwhile stays; each must be offered now and is saved with the entry's sign-in now (picking the same model again accepts a changed sign-in). About reads the rows again whenever the bot changes. `bots.model.get` returns the rows as picks or null (`slots`), `named` for rows by name, and the Talk model by name (`model`). `bots.model.set` (an older app's single picker) puts one model on every row, on an entry that offers it, and never sets a picked bot back to by usage. For one automation `bots.schedules.add`'s `model` is saved as a pick on the entry that offers it now (`ScheduledJobBot.pick`, refused when none does; no screen sets it yet), and like any pick it runs there or not at all; a job saved by name only is matched by name as before. Compatibility: `bots.model.setSlots` is optional (`BOTS_WORK_METHODS`); an older service sends no `slots` or `providers`, and the app shows its single Model picker. The computer picker offers only this computer until bots can run on another one (the person's other computers are listed, greyed); New bot shows this computer's name as plain text while it is the only one. This computer is named as the side card and Devices name it (`src/mms/computerName.ts`: macOS's Computer Name, Linux's pretty hostname, Windows' computer name), else by its hostname. The bot's own schedules never name a model.
- **Asking.** `set_depth` and `use_model` take `now` or `always` (saved as a revision with the same grant; chat lane only). `set_depth` `now` sets the level of the activation it is called in (a run moves to that level's row); `always` sets the standing level. Its answer says whether what runs changed: a depth that leaves a turn on the same pick changes nothing (and `now` then sets nothing), and the bot says so instead of "I'll take more time". `use_model` changes only to a model the owner's own message in this activation names (`BotToolHost.ownerWords`, `ownerModelChoice`), among the same choices the picker offers (`BotModelChooser.pickable`); the bot's own argument is never what is accepted, and it must name the same model. Names count only as whole words in a row, ignoring case and punctuation (`modelsNamedBy`); a name inside a longer one the owner said ("GPT-5" in "GPT-5 mini") is the longer one. A bare number, generic words ("pro", "mini", "flash", "default") and a maker's word alone ("gpt", "claude") never name a model. `always` (Talk, Work or both, `for`, all by default) needs a full name of exactly one offered model: its name as the picker shows it ("Opus 5.5"), its own name or its id; a family word ("opus", "haiku") is not enough. Offered on one entry, every row goes there; offered on two, each row stays on the entry it is on when that entry offers it, and otherwise nothing changes. `now` (this chat, never saved) takes a full name the same way, kept on Talk's entry, or a family word when it names exactly one model among the choices on Talk's entry. Any refusal answers the bot with one line: "Nothing changed. Ask the owner to pick the model in About → Runs on." A run never changes its model. Its chip says "switched models" and for what, never the model, and About → Runs on shows the change. Bot instructions forbid naming models or providers, except for a model the owner asks for one piece of work.
- **Images.** There is no Images row: no path a bot can use generates an image within its grant. Pi's image generation (pi-ai's `generateImages`, OpenRouter only) is refused for every Mousse-started Pi (`guardProvider`), since Mousse neither guards nor charges it. Codex's own `image_generation` tool (on by default in Codex 0.167) is not part of the grant and runs on Codex's own model, so a row could not choose it. An Images row needs a bot tool that generates an image on a picked entry through a guarded, charged request, a permission in the grant, and the file saved in the bot's files folder.
- **Usage limits.** A bot turn that hits a usage limit fails at the run level and records the reset time and, when the provider names one, its window. A pick waits on its own entry (above). For a bot from before picks the engine marks that instance limited and resolves again (at most 2 retries per activation), trying the next candidate. With none left, the bot pauses until the reset (`paused_reason='usage_limit'`) and posts "Paused until 14:00 (your Claude usage limit)", naming the provider family only. Its schedules run again at the reset. This never counts as a failed run. Work the owner asked for waits instead of ending (see Long work). Several pieces running on one limited entry each retry and pause on their own, and none counts as a failure; the bot's pause line is posted once (a scheduled run whose sibling already paused the bot adds none), while each piece of the owner's work says it carries on. On a picked bot the line is said once per limit, by the first piece that meets it.

## States and pausing

States are idle, working ("Waiting for internet" while it waits for it), needs you (an open ask), stuck (an error with one action, such as Sign in or Set up a provider), and paused (`src/shared/bots/personal/state.ts`). "Done" is only an animation of the face.

- **Pause** stops schedules only; chat still works. The owner pauses from the menu (`bots.personal.pause`).
- **Three failed runs in a row** pause the schedules, with one notice. A run that ends done resets the count, even with refused asks. Usage limits, waiting for the internet, stops and chat failures never count.
- **Resume** (`bots.personal.resume`) clears every pause, the failure count, the stuck error and the usage limits a picked bot met on its entries. A row whose pick can't run is not a pause: Resume checks it again, and it stays stuck until its pick can run or the owner picks again.

## On a phone and other devices

The owner's phones and other computers see and use the bots of a computer they reach through Bridge. Bots are the owner's, and so are those devices, so both the shared and the private lists stream carry them.

- **Share bots with other devices.** A switch on each computer (Settings, Devices; `mousse-cli bridge bots on|off`), on by default and stored on that computer. While it is off, its lists carry `bots: []` and every `bots.*` call from another device is refused with `forbidden` and the reason `setting_off`; the device says "<Computer> doesn't share its bots with other devices." Turning it on or off pushes the lists again.
- **Lists.** `bridge.lists.open` pushes `bots` beside `chats` (`ListsBot` in `src/mms/bridge/remote/MmsListsSource.ts`): each bot's summary as the Bots list has it, plus `activity`, the live chip of its chat activation (gone when the chip clears). The stream pushes again, debounced, on `bots.changed`, `bots.message` and `bots.activity`. Bots are listed whether or not there are chats; a computer whose bots can't be read lists none. `version` stays 1.
- **Methods** (`src/mms/bridge/remote/RemoteBots.ts`, deny-default, exact keys). Read: `bots.get`, `bots.chat.list`, `bots.chat.attachment`, `bots.memory.list`. Chat: `bots.chat.send`, `bots.chat.stop`, `bots.work.stop`, `bots.chat.markRead`, `bots.asks.answer`. Write: `bots.personal.pause`, `bots.personal.resume`, `bots.create`, `bots.update`, `bots.reminders.cancel`, `bots.schedules.remove`, `bots.permissions.revoke`, `bots.memory.forget`. Each calls the same `BotChatService` method as the desktop, with the same params and results. Delete, the model and computer pickers, new schedules and memory export stay on the computer.
- **Images.** A message's files keep their name and type (`{ name, mime, image? }`). `bots.chat.attachment` reads an image (PNG, JPEG, GIF or WebP, checked by its first bytes; never SVG) of up to 1.5 MiB from the bot's files folder only, in parts of 40 KiB (`offset`), so each part fits one reply.
- **What another device does not get.** No model, no instance id (an error's action keeps its kind and label; Sign in happens on the computer), no paths. It can't attach files, and a memory export ask is refused because it needs a folder picker on the computer.
- **Sizes.** A message from another device is at most 32 KiB. A chat page is cut to the newest messages that fit one reply; the device pages back with `beforeSeq`.
- **Refusals.** An unknown bot; an ask that is gone, answered or not ready yet; a memory export ask; and a reminder, schedule, permission or memory that is no longer there: all are checked before anything changes, so they are plain errors and never an uncertain outcome. A message to a working bot queues as on the desktop; stopping work the bot no longer has returns `{ stopped: false }`. An error's own words stay on the computer (only its code crosses the wire).

## Runtimes that can hold a bot

Bots run on the owner's own provider entries, the same ones their chats use, with the sign-ins they already have: Claude Code, Codex and Pi entries. Mousse adds no entry for bots. A runtime holds a bot when its driver says so (`HarnessDriver.botAuthority`) and `checkPolicy` admits the bot's policy (`src/mms/harness/policy.ts`). There are two ways to hold one:

- **Every call (`toolControl: 'exact'`).** Mousse runs or gates each tool itself.
  - **Pi RPC:** Linux, macOS and Windows, with recorded evidence for this platform (`CONTAINMENT_EVIDENCE`, `src/mms/harness/compatibility.ts`). Bot turns run ephemeral: no saved session, history in the prompt, never kept warm, in the locked environment, in a process group of their own.
  - **A locked Claude Code entry** (`profile: 'locked'`), on Linux on a recorded Claude Code version. Mousse no longer creates one; an entry left from an earlier build ("Claude for bots", `claude:bots`) is removed at startup (`removeRetiredBotRunner`).
- **Every approval (`toolControl: 'approval_only'`, `HarnessDriver.botApprovals`).** The bot's permissions answer every approval the runtime raises, through the same check (`BotCheck`) that `BotEngine` builds for Pi: allowed runs; a missing permission is a wall in the chat lane and a refusal with an ask in a run; anything that can't be asked for is refused. Nobody sees a normal approval prompt. The turn runs in the runtime's asking mode whatever the thread or entry is set to (`checkPolicy` refuses a bot policy bound in any mode but Ask), in the bot's files folder.
  - **Claude Code** (`src/mms/harness/claude/locked.ts`, `ownerEntry`): every call goes through the grant gate in Mousse's `PreToolUse` hook and `canUseTool`. The turn uses the entry's own environment and sign-in, but none of the owner's settings files, plugins or MCP servers (only Mousse's own server, and its relay when the bot's work holds the owner's MCP tools: see Use your MCP tools), offers only the granted built-ins (Bash with "run commands", see above), and is one query that is never kept warm.
  - **Codex** (`src/mms/harness/vendors/codex/botApprovals.ts`): Ask's policy (`untrusted` approvals, no network; the read-only sandbox, or `workspace-write` over the bot's folders with "run commands"). A command it asks about is a `shell` call; a file change is a `write` (a new file) or `edit` call on each path it touches. A change Codex does not describe, or one that would widen where it writes, is declined. Questions to the owner are refused, and the owner's own Codex MCP servers are switched off for the thread (Mousse's server and relay stay); a bot turn does not run when Mousse can't read them.
  - What these runtimes run without asking is not checked: Claude Code asks about every call, but Codex reads files with the commands it trusts and searches the web without asking. Its sandbox keeps those from using the network or changing anything outside the bot's writable folders, but not from reading outside the bot's folders.
- Runtimes that approve tools themselves (`toolControl: 'uncontrolled'`: Cursor, generic ACP agents) can't hold a bot. Neither can other approval-based drivers (Antigravity, ACP presets) until their approvals are wired to the bot's authority.

## The supervisor

Each dispatch's deadline is enforced outside the daemon for the processes a bot turn owns alone. When a runtime reports such a process (Pi's ephemeral bot turns, a locked Claude Code entry), `BotProcessRegistry` (`src/mms/bots/supervisor/`) records the pid and group and starts `bot-supervisor` (`src/cli/fastpath/botSupervisorMain.ts`), a plain Node process, detached. At the deadline it ends the process group (SIGTERM, then SIGKILL after 2 seconds; `taskkill /T /F` on Windows), confirms the exit, and writes a line to `<profile>/bots/supervisor/<dispatchId>.json`, which the daemon folds into `bot_dispatches.exit_at`. A dispatch that settles first stops its supervisor. At startup, `reconcile()` ends the groups of unfinished dispatches. `exit_at` is evidence that the processes are gone (the unknown-call gate reads it), not what is charged: an unfinished dispatch is charged up to the last moment it was known to work (see Long work).

Claude Code and Codex on the owner's entries report no process: Codex's app-server serves the owner's other chats, and Claude Code's process belongs to the SDK's query. Neither is registered or killed for a bot. At the deadline the turn's signal ends the turn through the runtime's own interrupt (`turn/interrupt` for Codex, closing the query for Claude Code).

## Memory

Mousse keeps an append-only **bot journal** in `bots.db` of everything it sees a bot do and be told. Capped, dated **bot memory** entries, the **chat summary** and FTS5 search sit on top of it. Every activation's first dispatch gets a context pack built from it: the chat pack in the chat lane, the run brief in the run lane. The bot has five tools that are always on and never grantable: `memory_search`, `memory_read`, `memory_list`, `memory_save` and `memory_forget`; runs may only save run notes and never forget. Details: [`bot-memory.md`](bot-memory.md).

## Deleting a bot

`bots.delete` archives at once and purges after 30 days:

- **At once:** activations stop, asks are withdrawn, the grant is revoked, the bot leaves every list, and its threads are settled (archived). Scratch folders go when nothing runs in them.
- **After 30 days:** a daily sweep (`BotEngine.sweepDeleted`) deletes the definition, the threads for good, the chat, the schedules, the files folder and the memory rows (`BotMemoryAdmin.purge`). Run history in the Run Engine database and runtimes' session files are not purged; the log says so.
- There is no restore in Phase 1.
