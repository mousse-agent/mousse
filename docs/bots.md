# Bots

How personal bots work as of Bot Mode Phase 1, for developers. The design and its reasons are in the plans: [`plans/bot-architecture.md`](plans/bot-architecture.md) (engine, runtime, daemon API), [`plans/bot-ui.md`](plans/bot-ui.md) (the screens, with mockups in [`plans/mockups/bot-ui/`](plans/mockups/bot-ui/)) and [`plans/bot-context.md`](plans/bot-context.md) (memory). Memory as built is in [`bot-memory.md`](bot-memory.md). Terms are in the [glossary](GLOSSARY.md). Space bots are a separate system (`src/mms/bots/space/`) and are not covered here.

## What a bot is

A bot is an agent a person makes from a **look** and one sentence ("What should it do?"). It lives in the Chats tab, in the Bots section. Its owner talks to it in its **bot chat**, and it also works on its own schedules. Everything else is set by asking it: permissions, schedules, its name, how much time it takes. The UI never shows a tool row or a form, and names a model only on the Runs on pickers, in the one chat line about a picked model it can't use, and on the line and chip of work the owner asked to run on a model that is not its usual one (see "Model and depth" below). New bot is three short steps, shown like Add provider's: Look, What it does (an optional name and the sentence) and Runs on (this computer, and a model for Talk and for Work), where Create bot is. The draft and its step survive moving between steps and closing; a refused create returns to the step that can fix it.

- The definition is format 2 (`src/shared/bots/personal/definition.ts`): name, description, look, role, the main thread spec with its model choice and model rows (see Model and depth), and the grant (`permissions`). `owner` and `placement` are reserved for Teams and bot servers. Format 1 files are upgraded on read.
- `bots.create` names the bot with one short model call (5 seconds at most). When that fails, a name made from the description is used, and the bot picks its own in its first turn. The bot's first message is produced at once, as a chat activation. The create request key and first-turn prompt commit with the bot in `bots.db` (`bot_memory_state`, under `cursor:create:<clientRequestId>`). Retrying the same key returns the same bot, including after a crash before its first turn. Startup queues a missing first turn once; the saved prompt keeps any instruction to choose its own name. Clearing memory keeps this creation record with the capture cursors; deleting the bot keeps it, and only the 30-day purge removes it.
- **About this bot** (`BotAboutPanel`) is a panel on the right of the chat, in Settings' tokens and row anatomy, its width dragged from its left edge and kept per profile. The header puts the face beside the name, what the bot does now, its Talk model, how full its context is and its prompt cache, in words. Sections fold, with a summary line while closed; only Context and cache opens at first, and what the owner opens stays open. Context and cache comes from the bot's latest chat turn that reached its model (`bot_turn_usage`, `botContextSummary`): the tokens its last request carried of the model's window, how that turn's input split between cache reads, cache writes and fresh tokens, and the cache's time left (or since when it expired, or how long it has been idle when the provider gives no lifetime), with the last 7 days' usage below. Automations lists each of the bot's schedules by its automation's name, when it runs and its next time, what each run does in the automation's own words (none for a fixed line), and when its last run ended and how (`BotStore.lastScheduleRuns`). Every Remove, and Cancel on a reminder, asks first (`ConfirmRemoveButton`); Delete bot opens the delete dialog. Pick a model opens Runs on and scrolls the panel to its rows.
- **The prompt.** About shows the description as the bot's prompt, with Edit (`BotPrompt`). Save sends `bots.update` with `description`; the engine (`setOwnerPrompt`) publishes one revision with the new words as both description and role, keeps the words from before the first edit in `promptDefault`, and stamps `promptChangedAt`. Reset to default sends `description: null` and puts `promptDefault` back. Each main dispatch reads the name and words from the published revision as it is prepared (`instructionsOf`, `wordsNow`), so the next turn uses an edit even inside an activation made before it, while a turn already running keeps the text it was given; Claude Code and Pi read the system text per turn; Codex starts a new thread when it changes, and an ACP agent or Cursor (`bot` on their chat input) a new session, each with the history in its first prompt. The words go in the system text as their own `<owner_words>` block, and where they say how to reply they win over "How you talk". While the bot's last 50 messages hold a reply from before the edit, it is told those replies followed older words (`BOT_PROMPT_CHANGED_NOTE`). Once the owner edited it, the bot's `set_profile` can't change the description (`BOT_OWNER_PROMPT_TEXT`); it can still rename itself.
- **The starter grant** (approved by pressing Create bot): read, list, search, edit and write in the bot's files folder only, the web (`web_search`, `web_fetch`), the bot's own tools, and no limits. Work time has no limit: a grant approved when it had one keeps its old `budget.maxActiveMs`, which nothing reads, so its digest and the activations made under it still hold. An ask for more work time that an older build left open is answered when the profile opens (`BotEngine.releaseWorkTimeAsks`): a chat's wall as allowed this time, so its turn carries on, and a run's ask withdrawn, so work that waited on it goes on. The browser is asked for separately (see Use the browser).
- **Allow everything** (#1363) is the bot's Full access: a switch at the top of About → Can use. Turning it on opens a dialog that says what it gives; Allow publishes a revision with `fullTrust: true` and approves its grant (`setFullTrust`, through `bots.permissions.set` with `full_trust`), and turning it off narrows as Remove does. It adds every built-in tool and every Mousse app tool a bot can be granted (`withFullTrust`), inside the effective grant (`effectiveManifest`) and before the owner's switches, so a default or a permission switched off stays off. While it is on, About lists each permission it gives as its own row with a switch (`fromFullTrust`), so the owner can switch one off and keep the rest; the switch-off keeps the grant as it was, and Allow everything is expanded when it is read (`switchedOffPermission`). Switching off a permission the grant does not name (only Allow everything gives it) changes nothing else, as a default's switch does: the grant, the published revision and the draft stay as they are (a revision that names it keeps naming it), a held call of it is withdrawn and the warm chat process is closed. Switching such a row back on only forgets its switch-off, so the bot has exactly what it had before: a permission only Allow everything gave never becomes an entry of the grant, so it goes when Allow everything is turned off, while one the grant named too is restored to the grant and stays. The chat says "I can … again." only when the bot gets it back; switched on after Allow everything was turned off, it says "I still can't …. It needs Allow everything, or your OK when I ask." About → Remove of a permission it gives is refused (`permission_full_trust`) and not offered: it would come straight back, and Remove would forget its switch-off; the owner switches it off instead, or turns Allow everything off first. Approval and the runtime read it the same way: a revision is compared with what the grant gives, Allow everything expanded and the owner's switch-offs left out of both (`holdsWithin`), and runs inside that same expansion (`effectiveManifest`), so a revision that names a tool only Allow everything gives needs no approval and runs with it. An open card counts as Allowed only when the bot gets its permission as the runtime reads it: the revision of the turn that asked (the published one once it ended) inside the grant, Allow everything expanded, less the switch-offs (`settleHeldAsks`, `revisionGives`). A revision that leaves Allow everything out does not get what it does not name, so its cards stay open. `bots.permissions.set`, with `full_trust` or any other permission, is refused to a bridged call and to a client whose authenticated hello did not say it is the app (`clientType: 'gui'`); any authenticated local client that says so can call it. Switching a permission on has the same gate. Settings and Labs switches, what each kind of turn may do, a subagent's hold and asks first still apply; limits stay as they are. `canonicalManifest` writes it only when on, so every grant without it keeps its digest.

## Lanes

Each bot has two lanes. The chat lane runs one activation at a time; the run lane runs everything side by side, with no count per bot or per profile. Each activation keeps its own spend ledger, counts, deadline and supervisor. The chat is the bot's front desk and the run lane does its work, so the owner can always talk to it (see "The chat and its work").

- **Slots.** An activation that runs (waiting for the internet included) or waits at a wall holds a slot of its lane (`holding`, `slotFree`). The chat lane has one; the run lane has no count, so its work, a reminder's work and scheduled runs all start at once. `pump` starts what waits across all the profile's bots in one order (`nextRun`): work that waited and may go on first (more room was allowed, or its usage limit reset), then the queue in its order (`runOrder`): work the owner asked for in the chat (or by hand), then a reminder's work, then scheduled runs, oldest first in each, whichever bot it is of. Each start is taken in its own `bots.db` transaction, so two pumps never start one twice. Run work queues only while its bot's journal cannot be written. Real locks stay: one turn at a time per thread, and the chat's one slot.
- **The queue's ceiling** (`MAX_QUEUED_ACTIVATIONS`, 10,000) counts a bot's queued and parked work, except work waiting on an action card. It is there only to stop a runaway; normal use never reaches it. What already waits is never dropped: beyond the ceiling, the newest queued activation is refused (`refuseOverQueue`, `end_reason` `queue_full`) and its owner told. Refused work says so in the chat ("I had too much waiting, so I couldn't take on …"); a refused scheduled run says why on its automation (`dropped_queue_full`, as a skipped occurrence does), and the chat says at most once per local calendar day (this computer's time zone) that scheduled runs are being refused (`bm_<botId>_sched_dropped_<day>`).

| | Chat lane | Run lane |
|---|---|---|
| Started by | the owner's message (`bots.chat.send`), the bot's creation, a wake, or another bot's message (`bot_send`) | work the chat hands off (`work_start`), a reminder's work, a schedule, or by hand (`bots.activate`, internal) |
| Thread | the home thread, execution key `bot:<id>` | a new child thread, `bot:<id>:act:<activationId>` |
| Context | cleared at each activation's first dispatch (`clearConversationContext`), then the chat pack | the run brief, keyed by the schedule id |
| Missing permission | a wall: the turn ends with an ask card, and the answer continues it | refused; the run carries on (see Asks) |
| Tools | the grant without what takes long (the web, the browser, `shell`, the owner's MCP tools, the profiler's watch), plus the work and reminder tools | the whole grant, the subagent tools and `model_list` (see Subagents of work), no other work tools |
| Ends with | a reply (`text` row) | a run report (`run_report` row), also the notification |

- Clearing the home context keeps the transcript but sends no thread history, so no bot turn depends on a runtime session surviving. Claude Code and Codex resume their native session only while the history Mousse sends is the one saved after the last turn, so a cleared context starts a new one. Continuations inside one activation (a wall answer, a reload) keep the activation's own turns and may resume.
- An owner's message joins the running owner chat turn, or the newest waiting one, only when both the sending device and its permission limit match. Other messages queue as their own turns. A message sent while the chat waits at a wall counts as Not now for its asks, and the turn continues with that message.
- **Joined messages.** A running chat turn reads another message at its next step. If it ends before reading it and its own authority checks saw only reads or no calls, its reply stays as an unsent draft (`draft:<activationId>` in `bot_memory_state`). The same turn continues with that draft and the new message, and answers everything in one reply; its typing bubble stays up. A turn that changed anything posts its reply first and continues as before. A continuation never holds a second draft. If it fails or is stopped without a later reply, the original draft is posted with its original reply quote. A reply with an applet, card or picture is sent before continuing. Startup recovery posts a missing draft only for a turn that ended (done, failed or cancelled); a paused turn or one at a wall keeps its draft for the combined reply. A dispatch with no reliable authority record is never held. If the continuation pauses, its first answer stays unsent until the owner presses Continue or Stop. A new message starts its own turn and does not release that answer. Posting a reply removes the draft; forgetting an owner message of that turn removes its draft too.
- Ordinary sends, steers and queue writes to a bot's threads are still refused (`bot_thread_read_only`). The owner's chat goes through `bots.chat.*`, so every turn keeps the bot's grant and lock.
- **The bot chat is `bot_messages`** in `bots.db`: owner messages, replies, run reports, notices with ask cards, error lines, and the chips of each message. The renderer reads only this table, never transcripts, so tool rows and model names can't leak. A reply or report holds the turn's final message only, the row its thread ends on: notes the model wrote between tool calls stay in the thread (`OrchestratorResponse.message` of a bot turn; a thread's run keeps the turn's whole text).
- **A chat turn that ends without its reply is told to the next.** A failed turn, an interrupted one (a run cut off, or a restart) and one the owner stopped each leave one line in the bot's journal, Mousse's notice keyed by the turn and how it ended (`turn:<activationId>:failed|interrupted|stopped`, `chatTurnEndRow`), so a turn that reports the same end twice leaves one line. A failure carries its error on one line, at most 200 characters. The next chat turn reads it in its recent chat ("Mousse: Your turn failed before it finished: …") and can tell the owner what went wrong. The owner's chat is unchanged: its own plain error line, never the provider's words, and nothing for a Stop.
- Each activation has a scratch folder, deleted when it ends. A bot's chat turns share one folder (`scratch/chat-<hashed bot id>`, `BotEngine.scratchFor`), started empty each turn, so their launch stays the same (Warm chat process); a chat turn that starts while an earlier one still holds it (paused or blocked), and each run, gets one of its own. Documents the bot keeps go to its **files folder**, `<profile>/bots/files/<botId>/`, which every bot may write and which About never lists. Both lanes read and change it under the starter grant, so lists and plans the owner keeps with the bot live there as files, one each, with their names and dates listed in each chat pack and run brief. The bot reads a file when it needs it; no memory note per list is needed, and existing notes are left alone.
- **The bot chat's composer** is the thread composer (`ChatComposer`) without a thread's run settings: no model picker, reasoning level, permission mode, context ring, `/` commands or skills, since a bot picks its own model. It keeps the same box, attach (the button, dropping files and pasting images), dictation (also while the bot works, beside Stop: `dictateWhileStoppable`), Up for the last message, and Send or Stop, and adds an emoji button (`BotEmoji.tsx`, a small grid of everyday emoji, no dependency).
- **Attached files** are copied into the bot's files folder, under `attachments/<date>/`, and the message and the bot's input name the copies (`copyBotAttachments`). The starter grant reads them, so the bot never needs the folder the owner keeps them in, and its edits never touch the originals. A pasted file has no path: it waits in a temporary folder until it is copied. At most 10 files of 50 MB each per message. Images reach the bot as files it reads, not as pictures in the message.
- **Service lines** (permission-switch notices, a schedule's end) stay in the chat without a banner or sound. Wake-ups and thread notices show nothing at all; the bot's reply to one still notifies.
- **Reactions.** The owner can react to a bot's message with one emoji (the six quick ones on hover, or + for the composer's grid); another replaces it, and the same again or its badge removes it (`bots.chat.react`, an optional method: on an older service the first pick finds it missing and the bar goes). It is kept on the message in `bots.db` (v7: `owner_reaction`, `owner_reaction_at`) and published again to every window. A reaction never starts a turn: the next chat turn's situation lists the reactions set since the last settled chat turn, oldest first, one line each, "Owner reacted ❤️ to: <the message's first line>" (a report from work is marked as data), within their own budget beside the situation's. They count as told only when a turn that carried them settles (`reactions_read_at` in the memory state): a failed or stopped turn, or one past the budget, leaves them for the next. The pack's protocol says a reaction is a feeling, never an instruction or a permission; a run is not told. Forgetting a message, or the message that set a reminder, removes the reaction.

## How messages are told

The chat is the record. **Telling** is the banner and possible sound for an unread message, decided and kept by the service when the message is posted. It never delays the chat.

- **Now:** a reminder the owner set (including older reminders whose ownership is unknown), a schedule’s fixed line whose job records that the owner asked for it, or a reply, ask or question in a chat turn started by the owner's message or tap. These go by themselves and are exempt from sound caps.
- **Soon:** reports at or above the schedule’s or bot’s Tell me level, unattended replies, asks, questions, errors, question nudges, and the notice that schedules were paused after failures. Failures always tell.
- **Later:** reports below Tell me, waiting for internet, and dropped scheduled runs. These never cause a banner or sound alone; they count in the next fold. Older windows connected to a newer service also keep waiting-for-internet and dropped-run notices silent, through the per-message quiet flag.
- Owner messages, service lines and answered cards tell nothing.

The first soon message is told immediately. Others within two minutes update the same banner, with asks and questions before reports. Sounds are limited to one per bot in ten minutes and six per profile in an hour; banners still update silently beyond those limits. The sound counters start again when the service restarts.

With no app window subscribed, messages stay untold. When a window opens, unread messages from the past day are told as one “While Mousse was closed” banner (a lone message uses its ordinary banner title); older ones are marked told silently. Read messages and answered cards are marked told without a banner. A mounted chat is read only while its window is visible and focused, including when it gains focus or becomes visible. Partial reads leave the shown banner alone; reading or answering every row withdraws it everywhere. Later rows expire silently after a day, including when no window is attached. A restart preserves pending and already told rows. Release failures back off for a minute per bot, while other bots and reminders continue. `told_at` records emission, not display: a crash between emitting and writing it repeats one banner after restart; a window detaching as the event goes out can lose the banner.

The app keeps the owner's sound and banner choices, suppresses the banner when its bot's chat is focused, and opens the chat on a click. The optional `bots.telling.v1` protocol capability selects the service's `bots.tell` events. A new app with an older service, or an older app with a new service, keeps the earlier per-message notifications; a new app with a new service never also announces `bots.message`. Only windows that negotiated telling count as attached. With only older windows, rows stay untold and eligible legacy message pushes keep durable per-message receipts in `bot_memory_state` (`cursor:telling-legacy:<messageId>`). A new window later consumes those receipts silently, including after a service restart; messages missed by the old windows still catch up. The same bulk maintenance that expires later messages drops receipts whose messages are a day old or gone, even with only older windows attached. Clear chat, Reset and Forget remove receipts along with the messages they delete or redact, while preserving unrelated capture and creation cursors. A receipt records a sent frame, not an OS banner, so a failed receipt write or a crash between the send and receipt can repeat that legacy announcement. Old and new apps attached together each announce through their own path; this duplication across app versions is accepted.

## What a bot's chat shows

A bot's chat shows a reply as a thread's transcript does, through the same components; what is kept from bots is kept for a reason of their own, named here.

| A thread's reply | A bot's chat |
|---|---|
| Markdown (`agent-elements/markdown.tsx`): tables in their own scroller, code with Copy and Wrap, math, Mermaid diagrams, alerts, task lists, links | Same component (`Markdown` with `images`) |
| Pictures inline, in the conversation's preview with Previous and Next | Same preview. Kept stricter: a web picture is a link, never loaded, and SVG never shows (a reply can be shaped by what the bot read on the web, and a picture's address could carry what it knows) |
| Applets: the card under the reply, its own view, the sandbox | Same card (`AppletCard`) and panel (`AppletPanelView`), opened beside the chat; same sandbox |
| Pictures a tool returned | Shown with the bot's next message, from its files folder, as its picture message (one large, several in a carousel) |
| Copy, Read aloud | Same buttons |
| Reply to a message | The bot's chat has it; a thread doesn't yet (#1049) |
| Tool rows, diffs and changed files, thinking, plans, questions, model names and token counts | Kept from bots: a reply's steps fold behind its "Worked for" line in plain words, its presence and work are in the header, asks are quick replies, and a model is named only on work that runs on one of its own (above). A runtime's own question tools stay refused; a bot asks with `question_ask`, whose answers are quick replies too (see Questions) |
| Edit, Retry and Fork of a prompt | Kept from bots: the chat is one conversation kept with the bot's memory, with no branches |
| Opening a linked file | A Files pane beside the chat, from a path's chip, with Show in folder |
| A thread pasted or dropped into the composer (Copy reference) | Same pill; sent as the thread's link, drawn as its chip, and read by the bot with `thread_read` (see `chat-links-and-references.md`). Never a private thread; a subagent is read as far as the bot reaches the thread that started it |
| Find in the conversation; revising an applet in a later turn; a picture from the bot's browser shared on purpose; voice clips in the composer | Not yet |

- **Markdown.** The chat's messages are the thread's `Markdown` with the chat's image rule (`MarkdownImages`, `BotMarkdownImage`): every picture, written in Markdown or as HTML, reaches the rule with its `src` as written, and a `<picture>`'s sources are dropped. Blocks parsed under the rule are cached apart from a thread's (`MarkdownSetupContext`), so the same text never reuses a thread's parse. Raw HTML is sanitized as in a thread (Streamdown's sanitizer and URL hardening); links go through the thread's `classifyLink` and `routeLink` (in Chats a web link opens in the person's own browser).
- **Applets.** A bot's main turns, chat and work, have `publish_applet` (`BOT_APPLET_TOOL`), always on and never grantable, like memory: making an applet needs no power the grant controls. A consult and a subagent never have it. The bot's instructions carry the same applet guidance as a thread's agent. Its turn publishes as a thread's does: the thread's reply keeps the applet as a presentation part, and the bot's chat row keeps a reference to it (`replyApplets`, matched by source, `BotChatApplet`), never the source; the journal names it ("[Applet: Budget]"). The reference rides in the row's attachments after its files (with `applet` and an empty path), so a file's index never moves and `bots.db` keeps its version; an older build shows it as its title. The app runs it from the bot's thread exactly as a thread's: `applets.get` serves only an applet a shown reply of that thread carries, and the guest is the same sandboxed view (no network, storage, app bridge or other applets). Its Add to conversation and Ask to fix go to the bot's composer, never sent by themselves.
- **Pictures from tools.** An image an MCP tool hands a bot's turn, and a screenshot its browser takes (`browser_screenshot`, as `browser-screenshot-<time>.png`), is saved in its files folder, under `images/<date>/` like the pictures it makes (`saveBotPicture`: never through a link out of the folder; a file whose write fails part way is removed), and the activation's next message carries it as a file (`keepToolImages`, at most 6 a message; PNG, JPEG, GIF or WebP by their first bytes, at most 8 MB). That message is the turn's reply or the work's report; when the work asks its owner first, its question's bubble or its held action's card, so the owner sees the picture before answering, and the report after does not repeat it. The bot is told its owner sees it and where it was saved; a picture not kept (over 8 MB, past the 6, or not saved) is named as not shown instead. A picture the bot makes, or any picture in its files folder it names in its reply, shows the same way.

## The chat and its work

A person who works for you keeps talking to you while they work. A bot does the same (`docs/plans/bot-always-free.md`):

- **The chat answers in moments.** A chat turn is compiled with `frontDesk` (`compileBotThread`, `frontDeskManifest`): it is not offered the browser, `shell` or the computer, even when the grant holds them, and it gets the work and reminder tools (`BOT_WORK_TOOLS`), which are always on and never grantable, like memory. Its web, service reads and MCP calls are quick calls within fixed budgets (see Quick calls in the chat). So a chat turn is a model call and a few short tool calls, and the queue behind it is seconds long. The grant and its digest do not change.
- **Work runs beside it.** `work_start({ title, brief, level?, model? })` inserts a run-lane activation with the trigger `{ kind: 'work', input, title, replyTo, from, level?, model? }` and returns at once (`level`, light, medium or hard, picks its Work row; `model` is a model the owner named for this work alone; see Model and depth); the chat then says it is on it. The brief stands on its own: a run sees the bot's memory, not the chat. Up to three pieces run at once (see Lanes), so a quick lookup starts beside an hour-long job; the chat's instructions tell it to start one rather than tell the owner to wait. Work that does not fit waits, and `work_start` says what it waits behind (`waitsBehind`). Its report is posted as a `run_report` that answers the owner's message that asked (`replyTo`).
- **While it runs.** The chat pack's situation lists the work in progress with its live activity ("Your work now: …"), so "how's it going?" needs no tool. `work_list` gives the same with ids and the last three that ended; `work_stop` stops one, and the others carry on; `work_note` keeps a note in `bot_work_notes`. Waiting work gets its notes with its request. Notes go only to work that waits or runs, never to paused or blocked work. Each note keeps the owner's message it came from, so forgetting that message removes the note and its copies in the dispatch prompts. What Forget cannot reach: a note (or a brief) that running work already read is also in that work's own thread, in its transcript and in the context Mousse keeps for it, which a continuation of the same work sends again, and in the runtime's session, until the work ends. A run's thread is never given to a model after its work ends; like every thread transcript and runtime session file, it is outside Forget ([`bot-memory.md`](bot-memory.md)).
- **A note reaches running work while it works.** Each main dispatch carries a steer (`PreparedBotTurn.steer`, `steerFor`), which the orchestrator offers the runtime as the turn's own steer source (`botSteerSource`): an agent's steer, so it waits for a running tool and goes in at the runtime's next step. The note goes in framed as the owner's addition to the job (`noteSteerText`), and the work's report leads with what changed. It is marked read in `bots.db` only when the runtime reports the model read it (`accepted`). Delivery is at least once, usually once: a note the runtime hands back waits for the dispatch's end and goes on as before (`advance` posts what it had and continues the thread with it); a note it took but never reported read (a Stop, a crash, or a result that came first) goes the same way, marked "(may be a repeat)" with a line telling the work not to redo what it already did (`offeredNotes`, `NOTE_REPEAT_LINE`); after a restart every unread note is marked so, since what the earlier process knew is gone. Nothing goes in once the activation no longer runs (Stop wins), with under 30 seconds of the dispatch left, or into the thread's queue: the steer adds text and never widens the grant (a permission allowed meanwhile still comes with the next dispatch). While the runtime compacts the turn's context a note waits for it, at most 3 minutes (`BOT_COMPACTION_HOLD_MS`, `SteerHold.compactionLimitMs`): one whose end is never reported holds it no longer. Per runtime: Claude Code (a bot's turn is one query) interrupts the query between tool calls and resumes the same session under the same lock with the note as its prompt; a call its grant gate already let start holds the cut until it ends, and a call made once the cut is decided is refused before it runs (`ClaudeLockedGate.cut`), so no call is cut mid-run. An interrupt that comes too late (the query already answered and closed, so Claude Code never confirms it) leaves the turn running: the note restarts it once the query ends, and the chat shows no error. Codex adds it to the turn with `turn/steer`; Pi takes it at its next step. A runtime that takes no steers (`steer: 'queue_only'`) keeps the earlier way. `work_note` tells the chat which (`noteReach`, `workNoteAnswer`), as the bot's own doing: from its next step, in a few minutes (while a compaction runs), once the step it is on ends, or when it starts.
- **Asks.** An ask for the browser, the computer or commands that the bot's grant holds is answered "your work already has this" with no card, in `permission_ask` and at the gate (`grantHolds`, read from the active grant at call time); anything else allowed since the chat turn started comes to it once its reply ends (see Asks below). When work needs a permission the bot lacks, the chat asks for it first, as before, and hands the work off once the owner answered; a run that meets one carries on and asks, as any run.
- **Stored updates reach the work.** Notes and answers carried in a dispatch are confirmed for retry purposes only after the model produces output or that dispatch completes. Carried/read markers still govern late answers, Forget and re-giving notes after compaction exactly as before. A failed or interrupted attempt with neither leaves them pending for the next continuation. Waits and held-call outcomes use the same confirmation, so a restart or network failure can repeat an update but cannot silently discard it. Live steers keep their explicit runtime read acknowledgement. A note carried by a started but unconfirmed dispatch uses the existing “(may be a repeat)” warning when carried again. This retry rule applies to all work even with asks first off: failed attempts before output carry updates again, waits are confirmed on output or completion, and carrying dispatches store `workTold: 'pending'`. In master as of #1339, notes and answers were marked read at dispatch start for work that had waited, and at preparation for other work; those carried/read timings remain unchanged.
- **Repeated work starts.** Within one chat activation, identical `work_start` requests return work that is still queued, running or waiting, or has finished successfully, across dispatches and a restart. If the last attempt failed, was stopped, cancelled or dropped, the same request starts a new attempt. Each attempt has a stable numbered key, so replaying the retry itself returns that attempt. The key uses the activation and a digest of the title, brief, level, model (including its reasoning level) and slot; runtime tool call ids do not affect it. Changing any of those fields starts separate work, and the same request in a later chat turn can start work again. A repeated request's answer and chip say the work is already in progress, queued or ended; they never claim a fresh start.
- **One voice.** To its owner a bot is one person, so the chat turn and its work speak alike, in the first person, and never of the work as someone else or of how Mousse runs it (`BOT_BASE_INSTRUCTIONS`, How you talk). The tools' answers are worded so the bot can repeat them as its own: `work_note` answers with what the bot now does in that job and when, quoting the owner's words ("From your next step on "SSD search", you also do this: …"), and a note that came after the job ended says it had already finished and offers to do it again. The chips say what the bot did: `noted` (the job's title on hover), `started` and `stopped` with the job's title, and `looked into` for a consult. A report reaches the chat as the bot's own message, and the chat pack shows it to later turns as "Me, reporting from my work" (`WORK_REPORT_SPEAKER`).
- **What the owner sees.** The bot chat reads as a one-to-one messenger (`BotChatView.tsx`, `botChatShape.ts`): bubbles with a time each, no face or name on the bot's. The typing bubble and the composer's Stop follow the chat's own turn only (`BotSummary.chat`). While that turn writes its reply, the bubble shows it a finished sentence or paragraph at a time, paced as a thread's live reply (`usePacedText`), read from the home thread's streamed message (`botLiveReplies.ts`, display only); a short reply shows whole when posted, a step clears it back to the typing dots, and the posted message replaces it. A turn stopped from that window, or one that fails, before its message keeps what it had in that window only, muted and marked "Stopped", never stored; any other turn that ends with no message (a quiet turn's `[SILENT]`, which never shows) leaves nothing. Under the bot's name in the header is its presence: "typing…", the work running longest and how many more ("System check +1"), "paused", or "free"; a sticker on its face shows what it does now (a pen while it types, else the lead work's live chip: the browser, the web, a command, files). While work runs or waits (`BotSummary.work`) the presence opens its list: each piece's title, what it is doing (the live chip of that activation), how long it has run, and Stop (`bots.work.stop`). A reply that only hands work off or passes a note on ("On it.") shows no bubble: a 👍 on the owner's message and a quiet line, "alpha started System check", or "Passed on" under the owner's message; what it inferred from is the reply's chips and its length, read in the renderer. The other chips of a reply fold behind its "Worked for 32s" line, as plain steps. An ask is quick replies under the bubble (Allow, Not now, Details), and an answered one a quiet line ("You let alpha use the browser"). Paths in a message are file chips (the name; the full path on hover) that open in a Files pane beside the chat, with Show in folder, which selects the file (`localFiles` in the preload, `src/main/localFiles.ts`: only an existing file by its absolute path). A reply's pictures (its Markdown images, a picture it made included, the paths it names that are pictures, and the pictures it sent as files; `botReplyImages.ts`) show above its words as a messenger's image message, one at a good size or several in a carousel that scrolls with snap; a click opens the app's preview on the reply's pictures, with Save (a copy where the owner picks) and Show in folder, and a right-click offers Open, Save as…, Show in folder and Copy image. The Bots row lists each bot once, its state in words on hover; Recent has the direct chats.
- **Failures.** Failed work never counts toward pausing the schedules (`countFailure`), and done work doesn't reset the count. Work dropped from a full queue says so in the chat, and scheduled runs dropped so say it once a day (see Lanes).

## Quick calls in the chat

The chat makes quick calls itself (#1361) and still hands long jobs to work. `web_search`, `web_fetch`, `secret_fetch` and the owner's MCP tools run in a chat turn under fixed budgets (`ChatQuickCalls`, `BotAuthority.quickCalls`), so the chat's one slot is never held long:

- **Budgets.** Each call has 15 seconds (`BOT_CHAT_CALL_MS`), and a turn's calls 45 seconds together (`BOT_CHAT_TOOL_MS`), counted on the clock while any of them runs: calls that overlap share it, and each call that starts gets at most what is left, so however they overlap they keep the turn busy at most 45 seconds. A call once the 45 are spent is not sent. A result is cut at 32,000 characters, and what a call returns after its deadline is dropped. The deadline reaches the call as its `signal`.
- **Only Mousse's own web.** The chat's web is Mousse's `web_search` and `web_fetch`, whose handlers keep to the deadline. Claude Code's WebSearch and WebFetch are not offered to it (`BOT_CHAT_NATIVE_OFF`), and Codex's hosted web search is off for it (`codexBotWebOff`). Work keeps the runtime's own web beside Mousse's.
- **MCP through the catalogue.** The chat holds the same MCP tools as work, but its runtime is not listed them on Codex and Pi: the catalogue's `mcp` group names them and `use_tool` calls them, so the chat's tool list stays small and the same from turn to turn. On Claude Code they are listed deferred and loaded by its tool search. A direct call, `use_tool` and a tool search's load all go through `callForBot`, which checks the grant on every call.
- **When time runs out.** A call known to only read (`web_search`, `web_fetch`, `secret_fetch`, and an MCP tool whose server says `readOnlyHint: true` in its listing as it is now, not as the turn was offered it, and whose stored level is not asks first) is stopped and answered `work_required` with `fix: 'work_start'`. An MCP call counts as one only if it was read-only when it started and still is: one whose hint is gone meanwhile is treated as a call that may write. Any other MCP call may have changed something: when its deadline cuts it after it was sent, it is answered `uncertain` with `fix: 'work_start'`, never retried and never moved to work by itself. A tool's name never makes it read-only.
- **The owner writes meanwhile.** Every message of theirs, an answer to a work's question written on its bubble included, stops the running chat turn's calls known to only read at once (`ownerWroteInTx`, `ChatQuickCalls.steered`), whatever the message then does: one that joins the turn is read at its next step; one that waits for a turn of its own (from another device, a tap, or while a turn the owner did not start runs, such as a held call's result) tells the call so, and the turn ends sooner. A call that may write is never stopped by it: it ends within its 15 seconds, and only Stop or the deadline stops it sooner.
- **What stays work's.** Commands keep the runtime's own sandbox and time in work, and the browser and the computer never collide with work that uses them, so `shell`, the browser and the computer stay work-only (`BOT_WORK_ONLY_TOOLS`). A background command the chat starts (`watch_start`) stays detached: it returns a handle at once, and its end wakes the chat. An MCP call that asks first is held for the owner without holding the chat (see Asks first).

## Commands in the chat

The owner's `/` commands are run by Mousse and never reach the bot, so they cost no tokens. A `/` at the start of the composer opens the list (each row the command and what it does), narrowed as the owner types; arrows move, Enter and Tab pick (Enter on a command typed in full runs it), Escape closes, and the mouse works too. A message whose first word is `/` and a letter is a command; an unknown one gets a short error line and is not sent; a path such as `/Users/me/notes.txt` is an ordinary message. Each result is a quiet line in the chat for the owner alone, kept in that window only (`BotLocalNote`): never stored, never in a pack. Parsing and the list are `botCommands.ts`, running them `runBotCommand.ts`, and the list is the composer's own (`ChatComposer`'s `commandSuggestions`).

| Command | What it does | Through |
|---|---|---|
| `/clear` | Wipes the chat's messages; memory stays | `bots.chat.clear` |
| `/stop` | Stops the chat's turn, every piece of work and every background command | `bots.chat.stop`, `bots.work.stop` |
| `/status` | Work, background commands, threads, schedules and reminders, a line each | the bot's summary and `bots.get` |
| `/pause`, `/resume` | Pause and Resume (see States and pausing) | `bots.personal.pause`, `bots.personal.resume` |
| `/memory` | Opens the Memory dialog | |
| `/forget` | After a confirm, forgets every memory entry | `bots.memory.wipe` |
| `/forget history` | After a confirm, wipes the chat, its history and run notes; the owner's entries and the bot's notes stay | `bots.memory.wipe` with `keep: 'saved'` |
| `/reset` | After a confirm, a fresh start: chat, memory, schedules and reminders go; name, look, permissions and models stay | `bots.reset` |
| `/model` | Lists every slot and its model | `bots.model.get` |
| `/model <slot> <model> [description]` | Sets a slot: `talk`, `work` (all three levels), `light`, `medium`, `hard` or `images`; any other name is a custom slot (see Model and depth), whose description is the rest of the line | `bots.model.setSlots`, `bots.model.setImage`, `bots.model.setCustom` |
| `/model <slot> off` | Removes a custom slot; a base slot can't be removed | `bots.model.setCustom` |

After `/model ` the list offers the slots, with what each runs on, and after a slot the models as `entry:model` (`openai-codex:gpt-6.1-sol`), from the bot's choices. A model may also be named by its id alone when one entry offers it. The confirms are the bot dialogs' (`BotDialogs.tsx`). `/model` is the one place the chat names models apart from those above: the lines are the owner's, and the bot never sees them.

## Subagents of work

A piece of work can split its job among subagents: helpers that each do one part on a thread of their own and return a result to the work, never to the owner (`subagent_*` in `src/mms/run/mcp/appTools/bots.ts`, the engine's "Subagents of work" in `BotEngine`). Like memory, the tools are always on and never grantable, and they are no permission: a subagent can do only what its work can, so there is no card and no switch for them.

- **Who has them.** A run's turns (work, a reminder's work, a scheduled run): its main turn and each of its subagents, at any depth. `compileBotThread`'s `subagents` adds `subagent_start`, `subagent_send`, `subagent_wait`, `subagent_result`, `subagent_stop` and `model_list`, and the authority carries the turn's handle (`BotAuthority.subagents`). The chat and a consult have neither. A subagent's own subagent hangs from that subagent's run and shows under its thread; it holds no more than that subagent (`compileSubagent`'s parent manifest, within the grant now), runs on that subagent's model unless it names another, is held against that subagent's entry rather than the work's (`holdOf`'s `parentEntry`, so no level runs commands less contained than the one above it), starts with the owner's corrections since the work's run its tree hangs from, carries the work's chain and counts, and ends with that subagent's turn. Each parent names, waits for and hears the ends of its own subagents only. The run engine starts one only through the bot port (`authorizeSubagent`: a running subagent of the same work, under its live main turn); a bot subagent's ordinary delegation tool is refused. There is no cap on depth or count: the work's totals and Stop hold the whole tree. The work's instructions say, in one line, that it may split a job this way, that it keeps subagents on its own model unless a part needs another (another entry is another provider, sent its instructions and the brief), that subagents can do only what it can and their time counts against its own, that before it reports it waits for the ones it needs and stops the rest, and that it stays responsible for the result.
- **What a subagent holds.** Its turn is compiled by the same `compileBotThread`, with `subagent`, from what the work's turn holds at that moment (`LiveDispatch.held`: the grant held to the revision, the work's "Allow this time", less what is switched off in About), within what the activation holds now: an Allow given while the work's turn runs reaches neither until the work's next turn, and a Remove or a switch turned off since narrows both. It keeps the built-ins, the files folder, the owner's MCP tools and skills as the work's turn has them, and of the Mousse app tools what a thread's subagent may use: the web, the browser, the owner's threads as the work holds them, the profiler, and a task list of its own (`BOT_SUBAGENT_APP_TOOLS`, an allowlist, `subagentManifest`, `subagentBotTools`), less what its entry would hold less tightly than the work's (next section). None of the bot's own tools, and nothing a thread's subagent is refused: no `permission_ask`, memory, schedules, reminders, pictures (`make_image`), its name, depth or model, `run_report`, the automation tools, "change how Mousse looks", scheduled jobs, secrets, quick actions or work tools; its own subagents it may start (above). What it does with the owner's threads it does as its work would (`OrchestratorService.botSenderOf` takes a subagent of a turn that may act). Its authority (`role: 'subagent'`) checks every call like the work's, at every check point of every runtime, and the registry holds every app tool to it again; a call of what it lacks is refused with no card and no count against the asks (`BOT_SUBAGENT_LACKS_TEXT`), and it says so in its result. Its system text is its own (`BOT_SUBAGENT_INSTRUCTIONS`): one part of a job, a result for the work, what it may use, with nothing to ask for, and one line for what it runs without on its entry (`subagentWithheldLine`).
- **Its model.** The work's own model now, unless the work names one of `model_list`' choices (an entry, a model and maybe a reasoning level, matched as `work_start`'s is). Before each of its turns, `subagent_start` and `subagent_send` alike, a named pick is resolved again on its own entry for this bot (its sign-in, its usage limit, whether it can hold a bot) and never replaced by another, and one on the work's model takes the model the work runs on now and its entry's usage limit for this bot. The turn is compiled for that entry's runtime (its tool names, `checkPolicy`), so an entry that can't hold the bot, or a Codex not checked for bots (`runsOnNote`, and Codex itself refuses the turn), is refused in plain words and nothing starts. In work, `model_list` marks each entry with what a subagent there would run without (`subagentLacks`) or why it can't run there (`subagentCantRun`), says to keep subagents on the work's own model unless a part needs another, and that a stronger model costs the owner more.
- **What another entry is sent.** A subagent on another entry is another provider's model, and that provider is sent: the bot's name and the owner's description of it, the files folder's path and the owner's home folder's path, the bot's role (when it says more than the description) and the owner's main instructions for it (they carry rules the subagent must follow), what it may use ("What your owner allows now", with the names of the owner's MCP servers it holds), the subagent's own system text, the brief the work wrote, and then its tool calls and their results; it can read the bot's files into that provider's context, as the work can into its own. It is sent no memory, no chat, no report and nothing of the work's own thread.
- **Limits.** There is no count of subagents at once, per piece of work or per day: the work starts as many as the job needs, and nothing limits their time. A title is unique in the work, and a repeat of one tool call starts nothing new. A follow-up (`subagent_send`) to one that has finished is more work on its own thread, with what it already did, and counts as no new subagent; it is refused until the work has read (or been told of) what the last turn returned, since `subagent_result` reads the last turn only. To one still working, it is a note its turn takes in at its next step, once (refused until its runtime is called, and only its own work reaches it). A brief or a message over 32,768 characters is refused whole, never cut (the tools' schemas say so too). A subagent runs under its work's main dispatch: its counts and spend are the work's, it ends with the work's turn, and its running time is counted in the work's once, when it ends (`chargeSubagentRun`, `bot_subagent_runs.used_ms`), a count that limits nothing. Before its turn can run it holds room for one small request on the work's spend (`holdSubagentSpend`), so siblings started together share the work's caps; its own requests draw on that room rather than compete with it, and one that finds no room does not start (`bot_spend_exhausted`). With under 30 seconds of the work's turn window left, none starts. A subagent a restart cut off is counted up to when it was last known alive (its run's heartbeat or its daemon's), never for the time Mousse was down.
- **Endings.** A subagent ends with the work's turn, whatever ended it: the report, the owner's Stop, `work_stop`, a wall, the deadline, the bot deleted (`stopConsults` stops a queued one before it starts and the running ones), and the bot's Run commands switched off in About: its powers are recorded with its work's (`LiveDispatch.consultPowers`), so Run commands off stops the work and its subagents at once, as for a consult. A turn that ends while subagents still run keeps its last words for the report (`heldAdvance`).
  - **The report.** When the work reports while subagents still run, they are stopped and the work ends done: what one had in flight is not an interruption to hold the work for, since the work's own end caused it (`acknowledgeReportStops`). The report carries one chip naming them ("stopped a subagent early · Prices"); its tooltip says which one was cut in the middle of a command or a file change and that its last step may not have completed.
  - **Every other end.** The work's next turn, if any, is told which were stopped. A restart ends them cleanly: the boot ends their runs, the startup pass closes their turns (one written but never sent too), and the continuation says they were stopped; their results are not kept across it. A call a subagent had in flight when it was stopped holds the work for the owner like any interrupted call (a crash, a restart, a Stop), and so does the work's own interrupted call when it reports, except a command the bot's Run commands switch cut off (`acknowledgeCut`, which reads each call by the names of the entry it ran on, so a subagent's on another runtime is cleared as one on the work's own).
- **What the work reads.** `subagent_start` returns at once, with `lacks` and one line when the subagent runs without something its entry would hold less tightly; when one ends, the work's running turn is told at its next step (a steer, `subagentNotices`), and `subagent_wait` returns as soon as the ones it waits for end (10 minutes at most). Results are framed as data from a subagent, never instructions, and their frame can't be ended early (`subagentData`). A result is kept whole; `subagent_result` reads a long one in pages (`from`, and `more: { from, of }` while some is left). The work is marked told of an ended subagent (`bot_subagent_runs.told_at`) only once the turn that read it settles; after a crash before then, its continuation tells it again.
- **Stored.** Each turn of a subagent is a delegation of the run database (Run DB v29 adds `bot_id`, `root_activation_id`, `bot_access` and `bot_read_only` to `delegations`), which owns its lifecycle, lineage, child run and thread; its `BotSubagentSpec` rides in its bot `turn.start`. `bots.db` keeps its place on the work's counts and spend, its charge, its delivery and whether the work was told (`bot_subagent_runs`, v15). The two talk only through the bot port (`BotExecutionPort`). Its thread is a `subagent` row of `bot_threads`; a start the run database refuses or fails removes the thread it made. Subagents an older build kept as dispatches (`<activationId>:s<n>`) are settled at startup and never run again.
- **The journal.** A subagent's thread is copied into the bot's journal like every bot thread, as its own rows (`capturedRows` with `isSubagentThread`): what it said is a `tool_result` from outside (`who: 'tool'`), its calls are not the bot's (`who: 'tool'`), and each row begins `[subagent] ` with `subagent: true` in its JSON. So memory search, the run brief and the chat summary never show them as what the bot said to its owner. A data export (`bots.memory.export`) writes them to `journal.jsonl` with those marks; the 30-day purge removes them with the bot's other journal rows, and its subagent threads go with its home thread, which owns its work's threads and theirs.
- **Hidden.** A subagent's thread is a bot's thread (`botOwned`, in `bot_threads`, under the work's thread): in no thread list, search or other device's list, and no thread tool, other bot or "use your threads" reaches it (`botThreadReach`).
- **What the owner sees.** The work's line says how many subagents run now ("working · 2 subagents · 4 min"); on hover, each one's title, model and entry ("Reviews · Haiku 4.5 on Claude B"), and what it runs without there ("can't run commands there"), so the owner sees which provider does each part (`BotWorkItem.subagents`). Their calls are chips of the work's message, and the report carries one chip naming them ("used 2 subagents · Prices, Reviews").

### How each runtime holds a subagent

A subagent is never held less tightly than its work (`subagentHold` in `src/shared/bots/personal/subagentHold.ts`, `BotEngine.holdOf`). For the work's entry and the subagent's entry on this computer, each power the work's turn holds is compared by what each driver says about how it holds a bot here now (`HarnessDriver.botHold`: Claude Code's sandbox read with the entry's own PATH, as each turn reads it; Codex; Pi), using the facts of Run commands above:

- **Held at least as tightly there:** the subagent has it as the work does.
- **Held less tightly, and the runtime runs without it:** the subagent is compiled without it (no tool for it, and every call of it refused), its system text says so in one line, and the work is told in `subagent_start`'s result, so it can keep that part of the job or pick another entry.
- **Held less tightly, and the runtime can't run without it:** `subagent_start` is refused for that entry, with why and the entries that would do, and nothing starts.

The same entry is always the same, and so is another entry on the same runtime (two Claude Code entries differ only when one's PATH lacks bubblewrap or socat). A runtime whose driver says nothing is taken to hold nothing. Files (only the bot's own folders; each runtime's gate checks every path), the browser, the owner's MCP tools and skills (Mousse's own tools on every runtime) are held the same everywhere. The web differs only for a work without it: Codex's hosted web search is switched off for every bot turn without the web (`web_search = "disabled"`, `codexBotWebOff`, read on every checked version), so no runtime reaches the web then; a runtime that searched whatever the bot holds would refuse such a subagent. Commands differ, and every runtime runs without them, so they are withheld, never refused. How far a bot's commands reach (`commandHold`), from tightest: reads the system's and the bot's folders only, everything but the home folder, everything; writes the bot's folders only, everything; with or without the network:

| Runtime, platform | Commands |
|---|---|
| Claude Code in its sandbox, Linux | system's and bot's folders, plus `/tmp`; writes bot's; no network |
| Claude Code in its sandbox, macOS | everything but the home folder; writes bot's; no network |
| Claude Code without its sandbox (Windows; Linux without bubblewrap or socat) | everything; writes everything; network |
| Codex, Linux and macOS | system's and bot's folders; writes bot's; no network |
| Codex, Windows | everything; writes bot's; no network |
| Pi | everything; writes everything; network |

So a subagent runs without commands, though its work has them, in these pairings (work → subagent); every other pairing keeps them:

| Platform | Pairings |
|---|---|
| Linux | Claude Code (sandboxed) or Codex → Pi, or → Claude Code without its sandbox; Codex → sandboxed Claude Code (its `/tmp` is readable) |
| macOS | Claude Code → Pi; Codex → Claude Code or Pi |
| Windows | Codex → Claude Code or Pi |

`tests/bots/botSubagentHold.test.ts` holds this table, and `tests/harness/botSubagentHoldReal.test.ts` checks the hold itself on the real binaries on Linux: a subagent on Codex under work on Claude Code, keeps commands that read nothing of the home folder outside the bot's folders; one on Claude Code under work on Codex runs without commands because Claude Code opens `/tmp`.

## What a compaction cannot remove

When a model's context fills inside one long dispatch, the runtime compacts it by itself. What must never be lost is the bot's system text (`sessionInstructions` for a bot turn: `botInstructions`, its role, its lane's rules and "What your owner allows now"), which the runtime keeps through a compaction; its memory pack and its request stay in the turn's message (`turnPreamble`), and are given again after one.

- **The system text.** Claude Code's system prompt is replaced by it (`ClaudeLockedTurn.systemPrompt`, a custom prompt rendered fresh each request, `snapshot: false`, so a turn after an Allow resumes the session with the wider permissions in it); Codex takes it as developer instructions, which a Codex thread keeps from when it was opened, so a bot's dispatch whose system text differs from its thread's (after an Allow or a Remove) starts a new Codex thread under the new text, with the history in its prompt (`SavedThread.instructionsHash`): what survives Codex's own compaction is never the old permissions; Pi adds it to its own system prompt. None of the owner's own settings files, plugins or MCP servers are loaded for it. It holds nothing per turn (no time, no counts), so it is the same on every turn of an activation and the prompt cache holds across them; it changes only when the permissions or the bot's name change.
- **The tool catalogue.** The system text names the bot's core tools and gives every other tool group one line (`BOT_CATALOGUE`, `botCatalogueIndex`); the bot reads a group's guidance and tools with `tool_catalogue` the first time it needs them. Claude Code lists every tool and loads them on demand with its tool search (`ENABLE_TOOL_SEARCH` on for bot turns); Codex and Pi list only the core set (`BOT_CORE_TOOLS`) and call the rest through `use_tool`, which the registry runs as the tool it names, through every check a direct call passes. The list never changes within a conversation. See bot-context.md §15.
- **After a compaction.** Claude Code reports one inside the turn (its `compacting` status, then its `compact_boundary`, `TurnFrames`), and Pi reports its own (`compaction_start`, `compaction_end`). The orchestrator passes the end on (`BotTurnSteer.compacted`), and at the next safe point the turn gets one framed message with its memory pack and its request again, and the notes the owner added since (`regiveText`), read from `bots.db` then, so a message the owner forgot since is not given back. Once per compaction: several in a row before it went in are given once; it is no note, posts nothing in the chat and starts no dispatch. One the turn never read is dropped at its end, as the next dispatch carries the pack anyway.
- **Codex** reports no compaction inside a turn that Mousse reads, so after its own compaction a bot on Codex keeps its system text (developer instructions) but has its pack and request only as Codex's summary, until its next dispatch.

## Long work

Work that takes long has no time limit. It is held only to the limits its grant sets (turns, tool calls, tokens or spend), when it sets any, never to a runtime's limits on one turn. Each turn of it runs in a window of five hours (`BOT_TURN_WINDOW_MS`), which keeps its timer, its supervisor and its runtime's wall time finite (a turn itself has no time limit, only the run engine's no-progress check, `TURN_STALL_MS`): a turn that reaches it ends, and the work goes on in a fresh turn of the same thread with "Your turn ran as long as one turn may; what you did so far is kept." (`endWindow`, then `continueAfterTurnCap`, as at a runtime's step cap but not counted with those continuations). Nobody is asked. A run that made no call at all in its whole window, with the internet there, ends failed (`no_progress`).

Work that waits uses one path: `BotEngine.park` writes the existing blocked status and end reason inside the wake source's transaction; `releaseParked` releases its browser and pack after commit. `WORK_WAIT_RULES` in `activation/workWaiting.ts` defines which activations may park, readiness, stranded endings, Continue refusals, owner-wait and shown-attention facts, note acceptance, store-backed continuation options and the projected work line. Both the chat and `work_list` use its status. `workWaits`, `resumeWork`, `settleStrandedWork` and the chat projection read these rules. Owner-started work can park for any of these reasons; scheduled runs can park on an action card, but still end at a limit. No stored values or message ids change.

| Reason (stored wake marker) | What wakes it | Stranded when | Work line and card |
|---|---|---|---|
| `approval` (`approval_answered`) | Send, Not now or settlement | No action row: `action_gone` and a notice | Waiting on you; action card, then carries on with its outcome |
| `waiting` (`wait_ready`) | Its time or event | No timer row: `wait_gone` and a notice | Checks again at a time or waits for an event |
| `question` (`question_answered`) | Tap, reply or default | Its question is gone: `question_gone` and a notice | Waiting on you; question bubble with answers |
| `budget_exhausted` (`room_allowed`) | Allow on its limit | No open ask for that limit: `nothing_to_wait_for` and a notice | Held; partial result with the limit card; queued after Allow |
| `usage_limit` | Reset time or Resume | The bot has a usage pause with no reset time: `nothing_to_wait_for` and a notice | Held; legacy bots show their bot-wide pause line; picked models show their entry's limit line once per limit, without pausing the bot. Both give the retry time and Resume |

Parked work has no general week expiry. Stop still ends it; the queue cap excludes action-card waits. Each time or event wait keeps its own deadline; a held-call card waits until answered or withdrawn. A provider that omits a reset time gets a 30-minute retry time, so it is not stranded just because the provider omitted one. The details below describe the wake sources and their messages; they all use the shared parking rules.

- **The cap on model turns in one dispatch.** Claude Code ends one query after 300 model turns (`CLAUDE_LOCKED_MAX_TURNS`, only a bot's turn sets it; it was 100). That result is `provider_turn_cap`, not a failure: the activation carries on in the same thread, as after a restart, with "You reached the most steps one turn may take; what you did so far is kept. Continue." (`continueWith`, `turnCap`). The continuation is held to the activation's turn budget, when its grant has one: with it used up, it ends at that limit as any run or chat does (see Asks). What the capped turn did is not lost: the orchestrator hands back what it said last (`OrchestratorResponse.partial`, the open reply, else the one it finished last), and its words and chips go into the activation's next message (`carried`), so a continuation that runs out at once still posts them with its ask. Where the activity sink gives the calls behind its chips (`drainCalls`), the capped turn carries its calls instead, and that message rolls them up with its own: one chip per kind for the whole work ("saved 30 files", not "saved 2 files" once for each turn), as the continuations have no count. Kept calls have long text cut to 4,096 characters, which no chip reads. Codex has no such cap, and Pi has none of its own (it counts against the grant's turn budget). The continuations are not counted: work goes on for as many turns as it needs, as a coding agent session does, and only the grant's own limits, a Stop or a hung turn's no-progress check end it. (Older builds ended an activation after ten, `end_reason` `turn_cap_repeated`; its record keeps its line.)
- **Work that runs out of room.** Work the owner asked for (trigger `work`: `work_start` and a reminder's work) that uses up its turns, tool calls or spend waits instead of failing (`budgetEnd`). It is `blocked` with `end_reason` `budget_exhausted` (`workWaits`, `BOT_WORK_WAIT_REASONS`), so it no longer keeps a provider turn running; no new column, so older builds still read `bots.db`. Its chat gets one notice, a reply to the owner's message that asked: "I ran out of room before finishing. Allow more and I'll carry on. Here is what I have so far:", the turn's last words (the reply it finished last when it was cut right after a call: its turn is cut with `BotRoomAbort`, and only that cut hands back a finished reply, `stoppedReplyText`; a chat's wall, a reload or a Stop hands back only the reply still open) and its chips, with the card of the limit ask (posted by the dispatch's reply when its turn ends, `postReply`, else at once, `postRoom`; once per dispatch). The bot's one open ask for that limit is the one it waits on: a scheduled run's ask is taken over (`moveAsk`), else one is written When a chat waits at a wall for the same limit, the work waits on that wall's card, and its notice carries it (`roomAskOf`). Which limit the work waits on is kept in memory until its notice is posted, then read from its own ask or the card on its notice (`waitingOn`); spend limits are known only that way. The work shows as held in the work line and `work_list`, with Stop, and takes notes.
  - **Every answer settles the work that waits on that limit**, in the answer's own transaction (`settleRoomInTx`): Allow and Not now on any card for it, a message the owner sends instead of answering a chat's wall for it (it counts as Not now), and `respond`. Which limit each piece waits on is read before the answer widens the grant.
  - **Allow** widens the grant as for any ask. It carries on only work that waits on that same limit (an Allow of more steps never wakes work that waits on a spend limit), and that has room now under the wider grant (no limit used up, spend limits included), however long it waited. Work it carries on moves to `room_allowed`; before anything queued, it goes on in the same thread with "You have more room now; what you had so far was already sent to the owner. Carry on where you left off." (`pump`, `resumeWork`); its report answers the owner's message as before. Work that still has no room (an "allow this time" for a chat gives it none) ends with one line that says so. The card reads "Allowed: … It carries on with this now." ("… 3 pieces of work carry on now." when it carried on more than one, `BotAskCard.carried`) only when this answer carried work on: work that waited on it (owning it, or showing its card) waits its turn now or has gone on since (`BotAskCard.carriesOn`, `limitOutcome`). Work that ended without going on, or failed with its ask under an older build, carries nothing on, so its card reads as a run's ("It uses it from the next run.").
  - **Not now** ends it (`failed`, `budget_denied`) with what it posted; nothing new is posted, as the card says Not now. Stop ends it at any time, and stopped work never goes on.
  - **Waiting work counts toward the run lane's queue ceiling** (`refuseOverQueue`; running work is not counted) but is never dropped: beyond the ceiling, the newest queued activation is refused instead, work with "I had too much waiting, so I couldn't take on "…". Ask me again when I'm less busy."
  - **Waiting work waits until it is woken, answered or stopped**, however long that takes. Each tick (`maintain`) and the startup pass end only waiting work that nothing would wake: work that waits for room with no open ask for its limit, or for a usage limit with no reset time to wait for. It fails (`nothing_to_wait_for`) with one line, a reply to the owner's message: "I stopped "…": nothing could let it carry on any more. Ask me again if you still want it." (`settleStrandedWork`).
  - **Continue** (the owner's, `continueActivation`) refuses waiting work, with a plain message (`bot_work_waiting`: "This work ran out of room. Answer its ask to let it carry on, or stop it.", or for a usage limit "… press Resume to try now."), so it never keeps a provider turn running at a wall of its own. Its summary's `canContinue` is false.
  - **Grant changes.** About → Remove and Allow everything off move waiting work to the narrower grant with queued work (`narrowGrant`, a dispatch it has not sent included), so it goes on under what is approved now, never the wider grant; a running turn goes on with each call checked against the narrower grant, and a chat turn that waits at a card ends as at any narrowing (`endUnderGrant`). A chat turn that goes on after the grant narrows and then stops at a card, at the end of its reply or at once (a tool-call limit, a call it no longer has), ends there, unless by then the grant gives all its own grant did (Allow everything turned back on, say): it then moves onto that grant alone, with its unsent dispatches, and waits there; other work on the old grant, a paused run say, stays where it is (`waitsUnderActiveGrant`, `regrant` with `only`). This is decided in the same transaction that moves it to its cards; a restart before it ended ends it then (`reconcileActivation`), as it does a turn left at a card under any grant no longer in place. Approving a grant that holds everything the old one did, with limits as high or higher (`manifestSubset`; Allow everything and an MCP tool's asks-first hold count), moves unfinished work onto it in the same transaction (`regrant`; what each grant gives is compared, so one with Allow everything that leaves out a tool it gives still holds it) with its limits raised for its next dispatch (`raiseLimits`), and it goes on, across a restart too. Revoking the grant, or approving one that gives less (a capability removed, a tool asking first again, Allow everything off, a lower limit), ends waiting work with queued and running work, and a chat turn that waits at a card (`cancelled`, `endUnderGrant`), and a running turn's next call is refused; withdraws their asks so no card brings them back and the chat is free, and posts one line: "I stopped "…": my permissions changed." (in the chat, "I stopped there: my permissions changed.")
  - A start of Mousse posts a notice the earlier process never wrote (`repostRoom`), and work allowed before it stopped goes on once (`waitingBots`). While it waits it lets go of the bot's browser; its next turn opens tabs of its own.
  - A scheduled run and a run started by hand end as before: failed, with an ask that offers the higher limit for later runs. Work that runs out within a day of a Not now to that limit ends at once too ("I ran out of room on this run, so I stopped.", no ask), and its turn's last words are still posted after that line.
- **Work a usage limit stopped.** When every model is at its usage limit, work the owner asked for waits (`blocked`, `end_reason` `usage_limit`, `usagePause`) instead of ending; a scheduled run ends as before. The chat's one line says so: "Paused until 14:00 (your Claude usage limit). I'll carry on with this then." A provider that gives no reset time pauses the bot for 30 minutes at a time (`USAGE_RECHECK_MS`), and the line says that instead: "Paused (your Claude usage limit, with no reset time given). I'll try this again every 30 minutes until it goes through." (a scheduled run's: "I'll try again at 14:30."). When the pause ends (`maintain` at the first tick past the reset, or the owner's Resume), the work goes on in the same thread before anything queued, on a model chosen again: "A usage limit stopped you while you were working; it has reset now. Continue where you left off." A first dispatch that never went out (no model was free) is sent as it was. Under the owner's own pause (or one after failed runs) there is no usage pause to end, so the work waits for the reset time itself (kept in memory; after a restart it tries once at the start). It shows as held, never counts as a failed run, and Stop ends it.
- **A restart counts only the work done.** A dispatch's active time is a count that limits nothing: the whole window is counted when it starts and refunded when it ends. The last moment it is known to have been working is kept in `bot_dispatches.checkpoint_at`, at most once a second (`BOT_CHECKPOINT_EVERY_MS`): when a call is checked (any tool call, its consults' included, or a counted model request), when a call finishes (`tool.status` in the run log, `toolCallEnded`), and at each look at the live dispatch every 20 seconds (`BOT_OFFLINE_WATCH_MS`, the same look that checks the internet), unless it made no call for a minute and the internet is gone. After a crash the startup pass charges it up to that moment and no further, on every runtime (P3, whatever the supervisor's `exit_at` says, since that includes the time Mousse was down), so a long command in flight is charged, and a crash under-charges by one look at most. As the profile closes (`close`, or the in-process end of a turn the shutdown cut), it is charged up to the shutdown itself, unless it was waiting for the internet then (up to its last working moment). Such a turn never fails its activation: the startup pass carries it on once with "Mousse restarted while you were working." (rows 11 and 12, as before), in a fresh window. The boot's own end of such a run (`settleRun`) is left to the startup pass.

## Replies

Every bot message can name the message it answers (`bot_messages.reply_to`, bots.db v6): a chat reply the owner's message its turn holds (`ownerMessageOf`), a work report and a reminder the message that asked for them. The chat shows a short quote of it (who wrote it and its first line, `BotChatQuote`) when it is not the message right above; clicking it scrolls there. The owner can reply to any message (Reply on hover): `bots.chat.send` carries `replyTo`, a message of the same bot only, and the bot's input starts with `(Replying to your message: "…")` (`messageInput`, which also rebuilds the input from the row after a restart).

## Questions

A chat turn, and work the owner asked for, can ask the owner a question with answers to tap (`question_ask`, #1123): 2 to 5 short choices, each with an optional line of detail, or yes/no, and "Other…" for an answer in the owner's own words. It is the bot's way to ask an ordinary question. A permission is still an ask (`permission_ask`), and a "Yes" to a question grants nothing; the bot's instructions and the tool's description say so.

- **Apart from asks.** Questions live in `bot_questions` (`bots.db` v8), not in `bot_escalations`, so none of the permission paths (walls, one open ask per permission, Allow) reads them. Like memory, `question_ask` is always on and never grantable. A chat turn, work (trigger `work`: `work_start` and a reminder's work) and a scheduled run are offered it (`compileBotThread`'s `questions`, `asksOwner`; What each kind of turn may do); a scheduled run that asks parks for the answer as work does. Runs started by hand, consults and subagents never have it, and are told "You can't ask your owner from here: carry on, and ask in your report."
- **No counts; repeats refused** (#1363). One call asks one question, or up to 4 together (`questions`, each its own bubble, answered on its own). There is no count per turn, per piece of work, per bot or per day. Within one chat turn or piece of work, the same question again (`questionIdentity`: its words without case, spacing or a final question mark, and its answers in any order) returns the one still open; one that was shown and that the owner has not written about since is refused as `duplicate_ask` (`questionRepeats`, by `ownerLastWroteSeq`). The tool returns `questionId` (`questionIds` for several).
- **Withdrawing** (#1446). `question_withdraw({ questionId })` takes back a question the bot no longer needs, wherever `question_ask` is offered. Only the chat turn or the piece of work that asked it may, and only while it is open: one compare-and-set on the question, the bot and the activation (`withdrawOwnQuestion`). Its bubble reads "No longer needed" in every window, and work does not wait on it or end over it. When the owner's answer came first, nothing changes and the bot gets `{ withdrawn: false, status: 'answered', answer }`.
- **Shown under the reply.** The question is kept when the bot asks and posted when its turn ends, as a bubble of its own under the reply (`bm_<activation>_q<n>`, with `bot_messages.question_id`), in the reply's transaction (`postReply`); the startup pass posts it with a reply Mousse stopped before writing. Nothing waits on it: the turn ends as before. A turn that is stopped or fails withdraws a question it never showed (`BotStore.moveActivation`), and the startup pass withdraws any other that no reply will carry.
- **A tap** (`bots.questions.answer`, an optional method: the app sends it only to a service that showed a question) is the owner's reply to the bubble, written with the label as its text, in one transaction with the question answered. It starts or continues a chat turn as a message does, and the bot's input starts with `(Answering your question: "…")` (`messageInput`). Its turn is keyed `answer:`, not `chat:`: the label is the bot's words, so that turn can't start, message or stop the owner's threads (`ownerChatTurn`), and `use_model` and work on a model of its own leave a tapped answer out of the owner's words (`ownerWords`). A question already answered (on another device, or by a second tap) is refused before anything is written (`question_answered`). A tap never answers a permission ask the chat waits at (a message sent there counts as Not now): its turn waits behind that ask.
- **A typed answer** is Reply on the bubble, or "Other…", which puts the question above the composer: an ordinary `bots.chat.send` with `replyTo`, which answers the question with the owner's words. Those count as the owner's own, as any message's do.
- **Moving on.** Any other message from the owner moves the bot's open questions on (`moved_on`), in the transaction that writes the message; answering one question leaves the ones its turn asked with it open, with their follow-ups, and the bot's input starts with `(You had asked: "…" (A · B · Something else). If this message answers it, go on from there; if you still need to know, ask again.)`. The buttons stay, quieter, and a later tap still answers the question.
- **A question and a permission ask in one turn.** `question_ask` after `permission_ask` in the same turn is refused ("Ask it once the owner has answered your permission ask."). `permission_ask` after `question_ask` wins: the turn waits at its wall, its question is withdrawn without being shown (a tap there would count as Not now), and the wall's continuation tells the bot to ask again (`askAgainLine`).
- **What the chat shows.** The question's bubble with its answers under it as quick replies, in the ask's look (`BotQuestionReplies`); a tapped answer as a quiet line, "You answered “Flat B”", where the owner's bubble would be (the question on hover); a typed answer as the owner's bubble quoting the question. A message's `text` also carries the answers as plain text after the question ("Flat A · Flat B · Something else", from `plainFrom` on), for an app that doesn't draw them, for notifications and for the journal, so the chat pack shows the bot its own choices. An app whose service lacks the method shows that text and no buttons, and the owner answers with Reply.
- **Other devices** answer with the same method (`REMOTE_BOT_METHODS`), under the same rules as `bots.chat.send`: the device must reach the bot, and the turn is held to the device's limit.
- **Forget, delete and export.** Forgetting the bubble redacts the question and its answers, and withdraws it if it was waiting; forgetting the owner's answer redacts the answer. Deleting a bot withdraws its questions, and the purge removes them. An export of the bot's memory adds `questions.jsonl`.

### Questions from work

Work that needs the owner's choice asks and waits for the answer, between provider turns, and goes on in its own thread with it.

- **Asking.** In one transaction the question is kept and its bubble posted at once (`askFromWork`): a notice in the bot's own words that answers the owner's message that asked for the work, with the answers to tap. `question_ask` answers "Asked: your owner sees it in the chat, with its buttons. Stop here and end your turn now; you carry on in this thread with their answer." For the rest of that dispatch every call is refused, never walled, with "You asked your owner a question. End your turn now; you continue with their answer." (`askedIn`, in memory), so the turn ends cleanly instead of being cut.
- **Asking without waiting.** With `wait: false` (#1372) the turn goes on: nothing is refused, and the tool answers with the question's id and tells the bot to keep working on what doesn't need the answer. An answer (a tap, a reply, the chat's `request_answer`, or the bot's default) that comes while the work still runs goes into the running turn as a note naming the question (`deliverToRunningWorkInTx`): at its next step on a runtime that takes notes as it works, else with the continuation when the turn ends. The question then counts as read, so the work does not stop on it. A question still open when the turn ends makes the work wait as below. While such a question is open the bot needs its owner, and the chat's situation lists it, as for waiting work. A restart while the work runs restarts it as cut-off work, and the question stays open. In a chat turn `wait` changes nothing. Work that asked several and waits goes on once every one is answered, and hears every answer once (`workQuestionOpen`, `unreadWorkQuestions`).
- **Waiting.** When the turn ends, `advance` parks the work through `park` as `blocked` with end reason `question` (in `BOT_WORK_WAIT_REASONS`, so older builds read it as plain waiting work), which releases its browser and context pack. Its last words are not posted, as its bubble is what the owner sees; its chips go with its next message (`carried`). Work never goes on while its question is open: any continuation (a restart, a reload, the turn cap, more room, the internet back) waits for the answer instead (`continueWith`, `parkForQuestion`). The work line shows it as "waiting on you" (`BotWorkItem.waitsFor`), with Stop; `work_list` and the chat's situation list it with its question and id; and the bot shows Needs you, "Asked: Which flat…?" (a permission ask's words come first). It takes no notes while it waits (`work_note` says so); the answer is the way on. The owner's Continue is refused with "This work waits for your answer to its question. Answer it to let it carry on, or stop it."
- **Answering.** A tap or a reply on the bubble is the owner's answer to that work, not a chat message: their row belongs to the work (its activation, lane run), no chat turn starts, and no chat question is moved on (`BotChatService.answerWork`). In the same transaction the question is answered and the work moves to `question_answered`, which `nextRun` resumes first, as it does `room_allowed`. Answering one question wakes only its own work. The continuation says "Your owner answered your question "…": Flat B. Carry on where you left off." once (`read_at`); a permission allowed meanwhile comes with it (`allowedSinceRefused`). A tap stays the bot's label, never the owner's own words, and grants nothing: work never acts on the owner's threads or switches models, and the resumed turn runs under the same grant.
- **From the chat.** When the owner answers in the chat in their own words, the chat passes it on with `request_answer({ requestId, answer })` (formerly `request_answer`) (`relayAnswer`): only in a chat turn the owner's own message or tapped answer started (never one another start began), and only for a question work waits on. The answer keeps that owner message (`answer_message`), so Forget reaches it, and the bubble reads "Answered in chat: …". Once the owner forgot a message of theirs in that turn, nothing is passed on, even while the turn still runs.
- **Nothing is left waiting.** Work that ends, however it ends (Stop, the grant revoked or replaced, a full queue, deleting the bot), withdraws its open question in the same transaction (`moveActivation`), and its bubble reads "No longer needed". Forgetting the question's bubble withdraws it, and the work ends with "I stopped "…": the question I was waiting on is gone. Ask me again if you still want it." at once when the app forgets it (`afterForget`), else at the next tick (`settleStrandedWork`); work still ending the turn that asked ends so when that turn ends, and a restart or any continuation ends it the same way (`forgottenWorkQuestion`). Forgetting the owner's answer before the work read it opens the question again, and the work waits for an answer again; after, it stays in that work's thread until the work ends, as a note does. Either way its copies go, found by the question rather than by their words: the line that carried the answer, kept with it when it went out (`answer_json.sent`), from that work's dispatch prompts and the journal rows captured from its thread, the chat's `request_answer` call that passed it on, and, with the bubble, the work's `question_ask` call (`redactQuestionCopies`).
- **Restarts.** Everything is in `bots.db`: work that waits stays waiting, work answered but not yet carried on goes on once at the first pump after the startup pass, and work Mousse stopped right after `question_ask` waits for the answer instead of carrying on as cut work (`reconcileActivation`).

### Follow-ups when the owner doesn't answer

The bot chooses one when it asks (`question_ask`'s `ifNoAnswer`, `after` and `default`; `questionFollowOf`), and it is kept with the question (`follow_json`). A permission ask has none: asks still wait for the owner, as before.

- **What it chooses.** `ifNoAnswer: 'nudge'`, the default: Mousse reminds the owner, and work that waits on the question keeps waiting. `ifNoAnswer: 'default'` with `default` (one of its choices) and `after` (minutes): if the owner hasn't answered by then, the bot goes with that choice. `after` is 15 to 1440 minutes; left out, a nudge comes after an hour and a default after half an hour. The tool's description and the bot's instructions say a default is only for a minor choice that is easy to undo, never for one that spends money, can't be undone or speaks for the owner. A `default` given alone means `ifNoAnswer: 'default'`; anything else wrong (no default, a default that isn't a choice, too short a time) is refused with what to fix.
- **When.** The time counts from when the owner sees the question: its bubble's post sets `next_at` (`firstFollowUpAt`). A due follow-up also checks again before acting after sleep or a restart. A default's bubble says when it goes ahead ("Goes with Flat A at 15:30 if you don't answer").
- **One timer.** Follow-ups run on the reminders' timer: one engine timer for the soonest reminder or `next_at` of any bot (`armDue`, re-armed at most every 6 hours), each pass of `deliverDueReminders` follows up every due question (`followUpQuestion`), a failure is tried again a minute later, and each scheduler tick is a backstop (`maintain`). Only an open question is ever followed up, so one the owner answered or moved on from, or that was withdrawn or forgotten, never is; each of those clears `next_at`.
- **A nudge** is a fixed line from Mousse with no model call: a bot row `bm_<question>_n<k>`, "Still need your answer on this one.", that replies to the question's bubble and carries the same question, so its buttons are at the bottom of the chat and it tells as soon, including when the original question was now, naming the question so it reads on its own on a phone ("Still need your answer: Which flat…? — Flat A / Flat B", `nudgeNotificationText`, built from the bubble each time and never stored). Answering either (a tap, a reply on it, "Other…") answers the question and updates both. At most two per question: the first at its time, the next about 24 hours later; then `next_at` is cleared and the question just stays open. A bot's nudges, all its questions together, are at most one an hour and three in any 24 hours (`nudgeSlot`); one beyond that moves to the next free time, and a nudge dated after now (the clock was set back) still counts. A nudge is journaled as its own line, without the answers, so forgetting the bubble leaves no copy of them.
- **A default, from work.** In one transaction the question becomes `defaulted` (`answer_json` `{ choice, by: 'default' }`, no owner row) and the work moves to `question_answered`, so it carries on: "Your owner didn't answer your question "…" within 30 minutes, so go with "Flat A", as you said you would, and say so in your report." The work runs under the same grant, and the bubble reads "No answer · went with Flat A". A default that falls due while a chat turn the owner's own message started is queued or running waits for that turn to end (a minute at a time), because it may pass on their answer (`request_answer`), which then wins.
- **A default, from the chat.** The question becomes `defaulted`, and a chat turn of its own is queued (`question:<id>:default`, a manual trigger with no owner): "You asked your owner "…" and said you'd go with "Flat A" if they didn't answer within 30 minutes. They haven't. Go with "Flat A" now and tell them in one short line…". It is not the owner's turn: nothing in it counts as their words. It may still act on their threads, as a wake or a thread's notice may (#1359). It queues behind a busy chat, and never answers a permission ask the chat waits at. A chat question can't default after the owner wrote anything: their message moved it on.
- **A late answer.** A defaulted question keeps its buttons, quieter, under "No answer · went with Flat A". While the work hasn't carried on with the default yet (its continuation has not started), the owner's answer replaces it. Once it has, and the work still runs or waits, their row belongs to the work and reaches it as a note (`lateWorkAnswerInTx`): "Your owner answered your earlier question late, after you went with your default: Flat B. Change course if you still can, and say so in your report." After the work ended, or for a chat question, it is an ordinary reply to the chat, whose input starts `(Answering your question late: "…". You had already gone with "Flat A".)`. Either way it is kept with the default (`answer_json.late`), the bubble reads "Went with Flat A · you said Flat B", and a second late answer is refused. A tapped late answer is still the bot's label, never the owner's own words.
- **Restarts.** Everything is in `bots.db`. At start, a default that fell due while Mousse was off is applied once, and its line says so ("This was due at 15:30; Mousse was off then. Check "Flat A" still makes sense."). Nudges that fell due are posted once, never as a backlog: the next counts from then.
- **Forget.** Forgetting the bubble also takes the default's label from the question, and the default's line from the work's prompts and captured journal rows, or from the chat turn it queued (its request, prompts and journal rows; `answer_json.sent`), found by the question. The line a late answer's chat turn was told, which quotes the question and the default, is kept with the question too (`answer_json.copies`) and goes the same way. A default the work hadn't read yet is withdrawn with the bubble, and the work ends with its line. Forgetting a late answer removes it and its note, from the note, the prompts and the rows captured from that work, found by the message and the work rather than by its words (a note like "Flat B" is too short for the journal's own copy search); the default stays. Forgetting an answer the work hadn't read opens the question again with no follow-up.
- **Away for days.** Two nudges at most, then silence; defaults go ahead at their time, as the bot asked. Work that waits on a question keeps waiting until the owner answers or stops it.

## Cards

A bot's main turns, chat and work (scheduled runs too), can attach a small card to their next message with `show_card({ card })` (`BOT_CARD_TOOL`, #1123). Like memory it is always on and never grantable; a consult and a subagent never have it, and are told "You can't show cards from here: say it in words." `question_ask` takes one `card` too, shown on the question's bubble above its answers.

- **Four fixed kinds** (`src/shared/bots/personal/cards.ts`): `facts` (1 to 12 rows of a label of at most 40 characters and a value of at most 300, one line, where only links, bold and code are drawn), `checklist` (1 to 20 items, each `done`, `doing`, `todo` or `skipped`; read-only), `progress` (`done` of `total` and a label, a snapshot; live progress stays the work line) and `gallery` (1 to 8 pictures). Each kind takes only its own fields: an unknown type or field, or a value out of its limits, is refused with what to fix (`cardOf`), and a damaged card read back from `bots.db` is dropped. A title is at most 80 characters.
- **Gallery pictures** are files in the bot's own files folder: the pictures it makes (`make_image`), the ones a tool handed its turn (`keepToolImages`) and any other PNG, JPEG, GIF or WebP there, by their first bytes, never SVG, at most 8 MB. A path may be full, `file://`, or relative to the folder; links are followed and the file they reach must be inside the folder (`galleryPicture`). Never a web address. Each picture is also one of the message's files (`card` on the file), so another device reads it with `bots.chat.attachment`, which checks the folder again, and an older app shows it as a file.
- **Where it goes.** An accepted card waits in memory for the activation's next message, as tool pictures do (`replyCards`): the chat turn's reply or work's report, or an update work posts before it. A turn that made a card and wrote nothing posts the card alone. A message holds as many cards as fit in 8 KB; over that the tool says to put the rest in words. Mousse stopping before the message is written loses the card, not the message.
- **Kept** in `bot_messages.cards_json` (v8). The app draws each kind from its own components (`BotCards.tsx`), never HTML or script from the bot: facts with the same component as a reply's list of bold keys (`KeyValueRows`), so both look the same; a gallery with the reply's picture strip, carousel and preview (`BotReplyMedia`).
- **As plain text** (`plainCard`): facts as "Label: value" lines, a checklist as "[x] …" lines, progress as "3 of 5 · label", a gallery as its files' names, each under its title. A message's `text` carries its cards so after its words, from `plainFrom` on (before a question's answers), for an app that doesn't draw them, a notification (the words, or the first card when there are none) and another device; the Recent line and the quote of a message with no words use it too. Its journal row holds the same copy, so search and the chat pack show the bot its own cards.
- **Forget.** Forgetting the message blanks its cards and the gallery's files on it, found by the message (the pictures stay in the files folder), and its journal row goes as any message's. A `show_card` call is journaled by its kind alone (`show_card facts`), so no copy outlives the message; a question's card goes with its bubble, as the rest of the question does.

## Reminders

`remind({ text, inMinutes | at, work? })` keeps a one-off reminder in `bot_reminders` (v6); `reminder_list` and `reminder_cancel` manage them, as many waiting as the bot needs, at most a year ahead. `at` is a local date and time on this computer. One engine timer waits for the soonest reminder or question follow-up (`armDue`, re-armed at most every 6 hours), and each scheduler tick checks again (`maintain`). A watchdog checks every 10 seconds for a clock jump more than 30 seconds beyond its expected tick, then checks due reminders, wakes and question follow-ups at once. Due timers are delivered before upkeep reads pull requests. While upkeep runs, later ticks check due timers and keep one further upkeep pass at the latest tick's time, so newly queued work is picked up. Those ticks return after their reminder check so the Automations inbox can sync; the queued upkeep runs separately. The watchdog stops when the engine closes. When one is due (`deliverDueReminders`):

- a text reminder is posted as a `run_report` answering the message that asked, in the same transaction that marks it delivered, with no model run;
- a reminder with `work` starts that work (`reminder:<id>`), whose report answers the same message; when the bot can't run then (its permissions wait for approval, its thread is in the trash), the reminder is said with why;
- one that fails to be said (a full disk) is tried again a minute later, never in a loop;
- one that fell due while Mousse was off is said at the next start, prefixed with its time ("(For 14:30) …").

A delivered text reminder offers **In 10 min · In 1 hour · Tomorrow 9:00**, using the question's quick replies. A tap (`bots.reminders.snooze`, optional on older services) creates one new reminder with the same text and the same request it answers, with no model run or owner message. Tomorrow is always 09:00 on the next calendar day on this computer. The buttons become a quiet “Snoozed until 6:10 PM” line in the same clock format as message times; another day includes the chat’s date label too. The tomorrow reply uses the same clock format. A second tap is refused while its copy is waiting or delivered; cancelling the copy brings the buttons back. Replies expire 24 hours after the reminder is said, and an old tap is refused. The new reminder offers the same replies when said. Work reminders and wakes have no snooze replies. Snoozed copies have no count either, appear in About and `reminder_list`, and use `reminder_cancel`. Forgetting the request cancels its snoozed copies too. Devices must be allowed to reach the bot to snooze it.

New reminders store `owner_set` from the calling activation: true for `chat:`, `chat:after:` and `answer:`, false for the bot's own turns. Wakes always store false, and snooze taps store true. Older rows keep NULL. Schedules added in an owner's message or tapped-answer turn keep `bot.ownerAsked: true` in the shared scheduler, including across an older build's save and restore. These values record who started the turn. A reminder the bot set tells as soon; one the owner set tells as now. Prompt schedules use their Tell me; fixed-line consistency is described under Schedules.

A deleted bot's reminders are cancelled at once and purged with it. Forgetting the owner's message that asked for a reminder or work (`memory_forget`, Forget in About) cancels the reminder and removes its words, and the work's brief and notes. Repeating reminders are schedules.

The engine's `nextDueAt(botId)` reads one list of due sources: waiting reminders and wakes, shown open question follow-ups, and active schedules' next times. Omitting the bot reads the profile. Settled, cancelled and deleted rows and paused schedules do not count. Schedules also do not count while their bot is paused by the owner, after failures, or for a usage limit. This exclusion only affects nextDueAt: fixed lines still fire during a usage-limit pause through the shared scheduler. The delivery timer uses that list with its existing retry backoff, excluding schedules: the shared scheduler still claims and starts those. The wake-from-sleep watchdog and single upkeep pass are unchanged.

`isIdle(botId, { within })` is an internal check with no callers outside tests yet. It requires no queued, running or walled activation, no blocked work that still waits to go on (`workWaits`), except a time or event wait whose due time is outside the window, no running background command or active thread the bot started (`launchedActive`; a thread on hold, which only its owner moves on, is not active), no unread joined chat messages, and nothing due within the window (milliseconds, 30 minutes by default, including the boundary). Paused activations and blocked rows stopped short with nothing to resume do not keep the bot busy. A failing lookup of threads the bot started answers not idle.

Idle does not mean nothing waits on the owner. A bot whose only open thing is a chat question or an ask a run carried on past is idle, since nothing of the bot waits to resume (unless a follow-up is due inside the window). A caller that must not act behind the owner's back must separately check whether the bot waits on its owner: the summary's `needsOwner`.

## Work that waits

A piece of work can call `work_wait({ inMinutes | at | thread | pr, on?, hours?, why })` and end its turn. It keeps its thread, history and tools, ends its provider turn, and carries on there once with a `[Mousse]` line explaining what happened and its own `why`. A scheduled run may wait the same way: while it waits, the schedule's later occurrences are skipped ("the bot is waiting"), as for a held call. Chat uses `wake`; a run started by hand ends with its report; subagents cannot park work.

A timed wait lasts from five minutes to seven days. Thread and pull request waits use the same checks and data framing as wakes, with the same default 24-hour expiry and seven-day maximum. An expired event wait still resumes once and says why, including a closed pull request. A wait due while Mousse was off becomes ready before the stranded-work sweep at the next start, labelled with its original time even after a week offline. A ready time/event wait no longer expires while it waits for a slot.

Only one wait may be open per piece of work. Waits share wakes' chain and loop detection: the chain is counted, never capped, and the same wait (same brief, same thing waited on) set more than 3 times in that piece of work since the owner last wrote is refused (`refuseWakeLoop`, by `work_id`: separate pieces of work and the chat's own wakes never count against each other). An owner note to the work or an answer to its question resets its wait chain; a default answer does not. There is no count of waits, wakes or waiting reminders. Work's turn budget, when its grant has one, persists across waits; waiting is not counted as active time. There is no general week expiry or total lifetime cap for parked work; the wait itself keeps the deadline above.

The work line says when it checks again, in the viewing device's message clock format, or what event it waits for. Pause preserves waiting work and its row; when due, it follows the same admission rules as other ready owner work during a pause. Stop ends the work and cancels its wait. Finishing, failing, forgetting the request and deleting the bot cancel the wait too; a wait cancelled or removed elsewhere ends the work with a line. The wait is a wake row with `work_id`, on the existing timer and event readers, and is not a separate follow-up in About → Reminders or `reminder_list`. Delivery marks the wait delivered and work ready in one transaction; it starts no chat turn and posts no wake line. Delivery does not mark the wait told: `continueWith` reads delivered, unread waits from storage regardless of the current park reason. The saved dispatch names the wait ids, and only its start marks them told. Limit cards, usage holds, a full queue and restart therefore keep the event and `why` for the turn that finally starts. For work that has waited, pending wall answers, notes and question answers accompany it in the order of their stored event times; their read markers also commit with that dispatch’s start. Ready waits follow existing ready parked work (owner answers/more room and usage resets, still in their existing order) and precede the ordinary queue.

Time and event waits both use their row as a due source. An overdue wait whose work has not parked yet is excluded from due sources; parking delivers it in the same transaction. An overdue wait on a pull request that has not fired is first read once more, as an event wake is at its deadline: parking, the upkeep pass and startup leave it waiting for that read, and the work resumes with what it shows. Like an event wake today, an event wait hours away is idle until it falls within the due window, unless something else keeps the bot busy. A ready wait is busy until it resumes.

## Wakes

A wake is the bot's own follow-up: `wake({ brief, inMinutes | at | thread | pr, on?, hours? })` from a chat turn. It is the third kind of reminder, in the same `bot_reminders` table (v9 adds `wake`, `event_json`, `fired_json`, `chain`), on the same timer, listed and cancelled with `reminder_list` and `reminder_cancel` and in About → Reminders ("Follows up when acme/app#12 merges", with when it gives up on hover). It is never an automation and never on the Automations page.

- **When it comes,** the bot carries on in its own chat: a chat turn keyed `wake:<id>`, which no person started (`ownerChatTurn` is false for memory rights, but `threadsActOf` permits thread actions under its grant), queued in the transaction that marks the wake delivered, so it wakes once. Like a run, it saves only run notes, can replace only run notes, and cannot forget memory; facts about the owner and standing notes need a turn their message or tapped answer started. Its input is a `[Mousse]` line with what happened (the thread's id and status, or the pull request and its merge, completed checks or new review) and the brief the bot wrote (`wakeInput`). Nothing shows in the chat but what the bot says, and no typing or working line while it runs. A paused bot, or one that can't run then, has the wake said as a line instead.
- **Events.** `thread`: one of the owner's threads the bot may see (it needs "use your threads"; `botThreadReach`), working when the wake is set; it fires when the run that worked then ends (a run that ended while its turn still saves it, not a message queued behind it), with that run's outcome, even if a later run of the thread has started (`wakeThread`, checked when any run ends or a thread is archived, and each scheduler tick). The end of another run of the thread, such as a queued message taken back, doesn't fire it. `pr`: `owner/repo#N` or its link, read through the owner's project of that repository (`pullRequestState`, every 2 minutes), open when set; `on` is `merged` (the default, including stored events without it), `checks`, or `review`. Checks fire once at least one check exists on the current head and none are queued or running, carrying passed, failed and waiting-for-approval counts with failed and waiting names; a changed head waits for its own checks. A check waiting for a maintainer or environment approval is settled, so the bot can tell its owner what needs them. Skipped/neutral checks are complete but count as neither passed nor failed. Reviews fire on the first approved, changes-requested or commented review beyond the newest submitted review seen in the initial PR read. The stored GitHub timestamp and review ids distinguish new reviews, including ones in the same second, without comparing GitHub's clock with this computer's. A wake stored before this cursor was added retains its original local-time cutoff. Pending and dismissed reviews do not count. Reviews by anyone count, including the owner's account and review bots; a bot's own command can therefore trigger its wake. A PR closed or merged while checks or a review are awaited ends the wake once, saying which, unless the checks finished or the review was submitted before the merge or close by GitHub's own times; then those fire. Reads use the same two-minute interval, retry failures until expiry, and survive restart.
- **Checks read limit.** The rollup describes only checks GitHub has reported for the head it currently shows. A required check that has not reported, a later-queued workflow, or GitHub briefly showing the previous head after a push can make a wake report success early. The observed head's short SHA is included as framed data so the bot can check which commit it read. This does not prove every required check ran.
- Failed and waiting check names are each capped at 20 names of 120 characters, both when stored and shown; full counts remain and the input says how many names were omitted.
- Check names, reviewer logins and PR titles enter the wake input in escaped data frames and the journal marks them as outside data. A paused bot's line uses fixed fields, such as “Following up · acme/app#12 · checks passed”, “… · 2 checks failed”, “… · 1 check waits for approval” and “… · review: changes requested”. About lists “when acme/app#12's checks finish” or “when acme/app#12 is reviewed”.
- **Expiry.** A wake on an event gives up after `hours` (default 24, at most a week; `due_at` holds that time). A wake on a pull request reads it once more at that time, so a merge, checks or review that came by then by GitHub's own times still fire; when that read fails, the wake gives up saying the pull request couldn't be read (`expired_unread`), and keeps saying so if storing that fails once. That read asks GitHub again: it never reuses a cached read, or joins one in flight, from before the deadline. Pull request reads go one at a time, so wakes past their deadlines at startup are read in turn. A closed pull request, an archived or deleted thread, a thread out of the bot's sight, or the time passing first wakes it once anyway, saying why (`fired_json`: `{ kind: 'ended', reason }`).
- **Brief.** Wakes and background commands refuse a brief over 2,000 characters after trimming, with a request to shorten it. A brief of exactly 2,000 characters is kept whole.
- **Loops, not counts.** There is no count of wakes in a row or in a day. `chain` still records how many in a row with no owner's message between them (a wake set in a wake's own turn is the next) and the wake's input names it, but nothing caps it. The one limit is loop detection (`refuseWakeLoop`): since the owner last wrote (`BotStore.ownerLastWroteAt`), a bot's chat sets the same wake at most 3 times (a work wait counts only that work's waits) (`MAX_SAME_WAKES`; the same brief, ignoring case, spacing and punctuation, waiting on the same thing: `wakeLoopKey`; cancelled ones count). The chat's next is held for the owner as a message past the limit is (`bot_chain_holds`, with Continue and Stop in the chat; the wake tool answers `status: "held"`, and `thread_send`'s `notify` says it was not set), and the same wake again while one is held is refused; Continue sets it and counts from there (`chainBudgetFrom`). A work wait's loop is still refused. Either way the bot is told to tell its owner where things stand. A brief that says what changed, or a wait on something new, is no loop. A wake starts when it is due, at any hour.
- The bot is told to use wakes when it waits on something (a pull request, a build, a thread it started) instead of checking on a schedule or promising to look later.

### Background commands

`watch_start({ command, brief, title?, match?, minutes? })` runs a command in the background and wakes the bot in its chat when it is done: when it exits (with its exit code), when a line of its output matches `match` (a regular expression; it is stopped then), or when it reaches its time limit (default 60 minutes, at most 360; it is stopped then). `watch_list` and `watch_stop` manage them. It is for what the bot waits on that a command can watch: a build, tests, `gh run watch`. For pull request checks or reviews, use `wake({ pr, on: 'checks' | 'review', brief })` instead; it needs no background command or command permission and survives a restart.

- **A wake.** Each one is a wake on a `watcher` event (`bot_reminders`, the same table and timer): loop detection holds for it (the same command and brief again and again is refused), and it is listed with the bot's reminders. The wake's input says how it ended, the line that matched, and the last 1,500 characters of its output, framed as data from the command (`wakeInput`).
- **Who may.** Any chat turn, whatever started it (the owner's message, the first message, a wake, a question's default, a tapped answer or another bot's message), and the main turn of any run (work, a scheduled run, a run started by hand), while the bot holds "run commands" (its revision inside the grant, less what is switched off in About: `holdsCommands`), and not while it is paused. From a run it is detached: the tool returns its id at once, the run goes on and ends as usual, and the wake comes in the chat, never to the run. A turn whose start no build names is refused before a command spawns or a wake row is written. `watch_list` and `watch_stop` are available to every chat turn too. There is no count of how many run at once. A change that takes "run commands" away stops them.
- **How it runs.** In a shell (`sh`; `cmd` on Windows), from the bot's files folder, in the locked environment (`lockedEnv`, as a Pi bot's commands run), in its own process group where there is one; Stop ends its whole tree (`killProcessTree`). It is not held by Claude Code's or Codex's sandbox, so it reaches what the owner's account can, as "Where commands aren't held" says for commands without a sandbox.
- **Ends.** The bot's `watch_stop` and the owner's Stop end it with no wake; so do pausing or deleting the bot. They live in the service's process: when Mousse stops, they stop, and at its next start each one's bot wakes once and is told that the restart stopped it.
- **In the chat.** The turn that starts one shows it as a card on its reply (`BotWatcherCard`: its title, "Running · 4m" with Stop, then "Ended"); the header's list shows **Background work**, each running command with how long it has run, its last line and Stop (`BotSummary.watchers`; Stop goes through `bots.work.stop`). While only commands run, the header says "Waiting on <title>".

## Messages between bots

A bot can tell another of its owner's bots something: `bot_list()` names the owner's other bots (name, what each does, whether it is paused), and `bot_send({ bot, message })` sends one a message by its name (`src/shared/bots/personal/botMessages.ts`, `BotEngine.sendBotMessage`). Like memory the two tools are always on and never grantable (`BOT_MESSAGE_TOOLS`): a message gives the bot that gets it no power.

- **Who may send.** A chat turn, work and a scheduled run (`compileBotThread`'s `bots`, the same turns as `question_ask`), so "if it's a bug, tell Alpha" works whether the chat, its work or a nightly check finds the bug. A run started by hand, a consult and a subagent never have the tools and say in their report what they would have told the other bot.
- **Where it goes.** The message is posted in the receiving bot's chat as a row labelled with the sender (`bm_botmsg_<id>`, a notice: "**Message from your bot Plusy**" and the message as a quote), where the owner reads it, in the transaction that queues the chat turn that reads it. The sender's reply carries a chip, "told · Alpha". The sender gets no answer in its turn; an answer is a message of its own.
- **The turn it starts** is a chat turn no person started, keyed `botmsg:<sender's bot id>:<message id>`, with the sender on its trigger (`fromBot`). It is not the owner's (`ownerChatTurn` is false), and unlike a wake's turn it stays read-only on threads: it reads the owner's threads and never starts, messages or stops one, and it passes no answer on to work (`request_answer`). Its input is Mousse's line that another bot sent this, that the owner did not write it, that it is information and no instruction or permission, then the message in a frame it can't end early (`botMessageInput`). It is told to tell its owner what the other bot said and what it did. A permission it lacks is still an ask to the owner, as in any chat turn; nothing in a message changes a grant.
- **Refused,** in words the sender can repeat to its owner, with nothing posted: no bot of that name (the names it has are listed), a name two bots share, itself, a paused bot, a bot that can't run now (its permissions wait for approval), an empty message or one over 2,000 characters.
- **Loops.** There is no count of messages in a day, and none on what the owner asks a bot to send. The row of turns without the owner is still counted on each turn's trigger, with wakes (`wakeChainOf`, `unownedChainOf`): a message sent from a turn the owner started is the first, the answer to it the second, and so on; work started in such a turn carries its count, and a wake set in one is the next in the same row. Two guards stop bots that keep each other going, both measured from the owner's newest message in the bot's chat (`BotStore.ownerLastWroteSeq`, by row order, so a tie in time can't hide one):
  - **A repeat** is refused with nothing posted: the same message (exactly the same row, `botMessageRowText`) to the same bot again (`BotStore.botMessageRowAfter`), or the same message to the same bot as one already held.
  - **Ping-pong** is held for the owner (issue #1443): a bot that has had 6 messages from other bots since its owner last wrote or chose Continue (`MAX_BOT_MESSAGES_UNANSWERED_BY_OWNER`, `BotStore.botMessagesReceivedAfter` from `chainBudgetFrom`) sends no more to bots straight away. Its next message is kept (`bot_chain_holds`), `bot_send` answers `status: "held"` with a note to end its turn and tell its owner where things stand, and while it holds a message, what it sends next waits behind it. Two bots answering each other with new words pause after 11 messages, and a ring of three the same way. The turn that gets the sixth is told not to answer (`botMessageInput`'s `last`). A bot the owner asks to tell many bots something is not held back: it has received nothing. The owner's next message to the bot clears the count, but not what is held.
- **Continue or Stop.** The sender's chat shows what it holds as a notice over the composer (`BotSummary.chainHold`: how many, to which bots, how many wake-ups), with Continue and Stop (`bots.chainHold.answer`, named by the batch's `holdId`, its oldest held step). Continue gives the bot's chain a new budget (`BotStore.renewChainBudget`, as the owner's own message would) and sends what it holds, oldest first; Stop drops it. A step that does not go (Stop, or a bot paused or deleted by Continue) leaves a notice in the sender's chat, which it reads with its next turn. Each step leaves `held` in the transaction that sends it, so after a crash midway Continue sends the rest and nothing twice. An answer for a batch already settled, or for another bot, is refused (`hold_settled`); the card then names what still waits. Only a person at a window on this computer answers: the CLI, agents and other devices are refused (`forbidden`), and the method is not in `REMOTE_BOT_METHODS`.
- **Stored.** The row is an ordinary chat message, the turn an ordinary chat activation; an older build reads both and ignores `fromBot`. What is held is a `bot_chain_holds` row (`bots.db` v16), and the latest Continue is `bot_memory_state`'s `chain-renewed`. Threads never read either.
- **The risk that remains.** A bot's message can carry what its sender read on the web or in a file. The receiving bot is told it is information, and its turn can't act on the owner's threads, but what it does with its own permissions (its files, commands if it has them) rests on the model's judgement.

## Asks

An ask is a request for one permission, shown as a card with Allow and Not now (`bot_escalations`, `mode` `wall` or `ask`).

- **In a chat turn** the bot's authority check returns a wall: the dispatch ends, the reply carries the card, and the answer continues the turn ("The owner allowed …" or "The owner said not now …"). Several `permission_ask` calls in one turn put all their cards on that one message. Walls are not counted (#1363).
- **In a run** the check returns a third outcome, `refused`: the call fails with "The owner has not allowed this yet. You asked them; carry on without it and say in your report what you skipped." and the dispatch goes on. One open ask is kept per permission (by fingerprint), across every piece of work that runs at once; later runs, and other pieces running beside it, get the same refusal and write no new ask. Each piece refused it remembers so (`refusedAsks`), so an Allow reaches every one of them when its turn ends (see the next bullets). Asks are not counted (#1363). An ask that waits never blocks a run or skips a schedule.
- **Repeats.** An ask is its permission, whatever its words (`askFingerprint`; any thread tool is "use your threads"). Asking again while one is open gets that one. Asking again for one the owner said Not now to, with no message from them since (`ownerWroteSinceDenial`, by `ownerLastWroteSeq`; every Not now answered since they last wrote is read, `deniedSinceAllowed`), is refused as `duplicate_ask` with no card, in both lanes (`repeatedAsk`), while any such Not now was said under a grant that gives the same as the one in place: Allow everything expanded, less what is switched off, and without what a grant keeps but nothing reads: an older grant's work time and folders, a retired app tool (`givenKey`, kept with the Not now: `denialOf`). A grant changed and changed back, or one that lists again a tool Allow everything gives, is the same; the refusal lasts until they write or what the grant gives changes. A limit is never a repeat.
- **Budgets** are different: work the owner asked for that runs out of turns, tool calls or spend waits for the answer to an ask for more room, with what it had posted, and Allow carries it on (see Long work); any other run ends as failed, with an ask for more room. Only work is charged: time spent waiting for the internet is not (see No internet), and a run that made no call at all in its whole turn window, with the internet there, ends failed with no ask (`no_progress`, "I couldn't get anything done on this run, so I stopped.").
- **Allow** publishes and approves the widened grant. A run that is no longer running when the owner allows its ask gets it from the next run, with no follow-up activation; one still running continues with it (next bullet), and work that waits on a limit goes on (see Long work). A run's answered card says which: "It carries on with this now." while the run that asked still runs or waits, or once it went on after the answer (`BotAskCard.carriesOn`); "It uses it from the next run." when it had ended and other runs were going; "Nothing is running now; it has this from now on." when nothing of the bot ran or waited at the answer (`idle`). **Not now** closes the ask; a run may ask again for it after 24 hours, and an Allow of the same permission from any other card still counts. Asks never expire.
- **No card for what the grant holds.** A turn keeps the permissions it started with (its tools, sandbox and browser are set up for them), so a turn that was already running when the owner pressed Allow still lacks the new permission. Its `permission_ask`, its gate refusal and its call of a browser tool (answered by the app-tool registry, `BotAuthority.held`) are answered at once, with no card and no count against the caps (`grantHolds`, read from the active grant at call time):
  - A chat turn is told to hand commands, the web and the browser to work (`BOT_WORK_HAS_TEXT`); the chat is never offered them.
  - For anything else, a chat turn is told it gets it once its reply ends (`BOT_ASK_HELD_CHAT_TEXT`), and a run-lane turn (work or a scheduled run) once its turn ends (`BOT_ASK_HELD_NEXT_TEXT`). The refusal is kept (in memory) and, when the turn completes, the reply or what the run has so far is posted (a run's as a `notice`) and the activation continues in the same thread with a new dispatch under the wider grant (`continueWith`, as for notes); a run's report then leads with what changed.
  - A consult is told it can't use it and to say what needs it (`BOT_ASK_HELD_CONSULT_TEXT`).
  - When the turn started with it but still can't use it (a narrower thread), or the runtime would not offer it to the next turn (Claude Code locked for bots withholds commands without a proven sandbox, `botWithheldTools`), the turn is told it can't be used on this turn and to say in its report what it skipped (`BOT_ASK_HELD_UNAVAILABLE_TEXT`), and nothing continues for it.
  - A refusal is forgotten once a dispatch of the activation starts with the permission (a reload, a usage-limit retry or a restart after the Allow), so that dispatch's report is the report and no further turn follows. After a restart the kept refusals are gone, and the continuation runs under the current grant anyway.
  - The running dispatch's permissions are never widened in place: a new dispatch compiles the tools, sandbox and browser from the approved grant together. A permission removed in About is not in the active grant, so it is asked for again as before.
- About lists what the bot can use, each with Remove (`bots.permissions.revoke`), and what every bot has by default with a switch only. Narrowing needs no approval.
- Card wording comes from `askText` (`src/shared/bots/personal/askText.ts`).
- The bot asks straight away: when the owner wants something it has no permission for, its instructions (`src/mms/bots/instructions.ts`) tell it to call `permission_ask` at once, with one plain sentence on why, and then say it has asked. It never asks the owner whether it should ask.
- Nothing the owner has switched off for the bot is asked for: no card, and the bot is told it is switched off (see Switching a bot's permissions off).

## Run commands

"Run commands" (the neutral tool `shell`) is one permission for any command. The bot asks for it once (a card reading "run commands"); after Allow it is in the grant like any other tool, and no command is asked about again, even by work that was already running (see Asks). Commands run in the bot's work: a chat turn hands them off. Not now, the repeat rule and About → Remove work as for every other permission. The authority allows every `shell` call once the grant holds it, whatever command or folder the call names (`botAuthority.ts`); without it, a command is a wall in the chat and a refusal with an ask in a run. Commands start in the bot's files folder. How far a command reaches depends on the runtime:

- **Claude Code** (owner's entry): Bash is offered only when the grant holds `shell`. Where Claude Code's own sandbox can run (bubblewrap and socat on Linux, Seatbelt on macOS), Bash runs in it: writable are the bot's files folder and its scratch folder. On Linux every top folder but the system's own (`LINUX_SYSTEM_FOLDERS`: `/usr`, `/bin`, `/lib`, `/etc`, `/proc`, `/dev`, `/sys`, `/tmp`, …) and the home folder are unreadable, so `/home`, `/mnt` (on WSL, the Windows drives), `/media`, `/opt`, `/srv`, `/var`, `/root` and `/run` are closed. `/run` holds removable drives (`/run/media/<user>`) and the user's runtime folder (`/run/user/<uid>`: network mounts, sign-in sockets); the sandbox needs nothing there (checked on Ubuntu 24.04: commands, Python and the bot's own folders work with all of `/run` closed). On NixOS the system's programs and the setuid wrappers live under `/run` (`/run/current-system/sw/bin` on the PATH, `/run/wrappers`), so those two stay readable when they exist, and nothing else under `/run` (`LINUX_RUN_KEPT_OPEN`); they lead into `/nix`, which is open. Not checked on a real NixOS. The top folders are the ones there when the turn starts: a drive mounted later at a new top folder stays readable until the next turn. When `/` can't be listed, every command of the turn is refused with a plain reason (`claudeCommandsRefusal`) rather than run with only the home folder closed. On macOS only the home folder is unreadable. The bot's own folders and Claude Code's own storage stay readable. The network is closed; `dangerouslyDisableSandbox` is refused (`claudeLockedSandbox`). Where the sandbox can't run (Windows, or Linux without bubblewrap or socat), Bash still runs, outside any sandbox, because the owner allowed commands as a whole.
  - **Command environment.** The turn starts without unrelated owner variables such as `GITHUB_TOKEN`, `OPENAI_API_KEY`, `MY_SECRET` and `NODE_OPTIONS`. It keeps Claude Code's own configuration as families: `ANTHROPIC_*`, `CLAUDE_CODE_USE_*`, the other sign-in inputs, `CLAUDE_*CONFIG_DIR`, `VERTEX_REGION_CLAUDE_*`, `ENABLE_PROMPT_CACHING_*`, proxies and certificate paths. `AWS_*` variables come through only for Bedrock, Mantle or Claude Platform on AWS. Google variables are limited to named application-default-credential, project, location, quota and configuration-path inputs, and only for Vertex or Claude Models on Google Cloud. Azure variables are limited to named identity and sign-in configuration inputs, and only for Foundry. Other Google and Azure product keys, such as `GOOGLE_API_KEY` and `AZURE_OPENAI_API_KEY`, stay out even when those routes are on. That covers both Mousse's environment and Claude settings' `env`, including future names in these families.
    - The Claude Code process itself needs its API key, auth token, custom headers and active cloud's credentials. What keeps these from a bot's Bash is the sandbox's credential deny list (the three variables `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN`) and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1`. The scrub removes only credentials it recognizes. In particular, `ANTHROPIC_CUSTOM_HEADERS` can carry an `Authorization` header, and the scrub removes it only if it recognizes it as a credential. This protection needs Claude Code **2.1.251 or later**: before that version the scrub removed only `ANTHROPIC_API_KEY` and `AWS_SECRET_ACCESS_KEY`, so other cloud credentials could reach Bash. Mousse does not enforce this version requirement on the owner's entry. Commands without a filesystem sandbox can still read credential files accessible to the owner's account.
    - The scrub also removes `CLAUDE_CONFIG_DIR` from subprocesses, so Bash cannot use that variable to find the turn's Claude home. On Linux it puts Bash in a separate PID namespace: `ps`, `pgrep` and `kill` cannot see or signal host processes, including a process started in an earlier Bash call. The launch filter remains necessary because the scrub leaves GitHub tokens, proxy settings and secrets it does not recognize in place. Temporary files use the activation's created scratch folder when no private Claude temporary folder is available.
  - **`/tmp` on Linux.** It stays readable (writing is denied with the other temporary folders): Claude Code's sandbox keeps its own sockets there, and other programs keep theirs. The start-up pipe of the owner's MCP servers is made in Mousse's own data, for every thread (`CLAUDE_MCP_START_FOLDER`); a start folder a killed service left there is removed when the service next starts, unless a start of this process holds it or it changed in the last five minutes, the longest a start keeps its pipe (`sweepClaudeMcpStartFolders`).
    - **What Mousse still keeps in `/tmp`.** Each folder is private to the user (mode 700), but a bot's command runs as that user: the ChatGPT token broker's socket folder (the socket itself can't be used: the sandbox refuses every connect to a Unix socket), and for the seconds a task runs, `mousse-pr-*` (the title and text of a pull request the owner opens), `mousse-pathspec-*` (the paths of files the owner stages or discards), `mousse-trace-*` (Git's trace of the hooks of the owner's commit or push) and `mousse-acp-*` (the working folder of an ACP agent's check). The sandbox denies reading every `mousse-…` entry of the temporary folders by name (`mousseTempEntries`, as Codex's profile does), and a command can't change or add anything there. The names are read when the turn starts, so one made later (a pull request the owner opens while the bot works) stays readable until the next turn. Moving them into Mousse's data would close those too, but needs the same clean-up after a crash as the start folders, and the Git code would then write into the real data folder from its tests.
    - **Claude Code's own temporary folder.** Claude Code keeps every session's command output in `/tmp/claude-<uid>`, the owner's own sessions included, and its sandbox opens that folder, read and write, to the session's commands. So a bot's turn keeps its own in a private folder of the user's runtime folder (`$XDG_RUNTIME_DIR/mb<hash>`, `CLAUDE_CODE_TMPDIR`; at most 30 bytes, since Claude Code gives a longer one only to itself and not to the commands it runs), and `/tmp/claude-<uid>` is closed to its commands, read and write (`claudeBotTemp`). The folder is the bot's (named after its files folder): it is emptied when the last of the bot's turns running ends (`holdClaudeBotTemp`) and removed when the bot is deleted (`removeClaudeBotTemp`). Without a private runtime folder under `/run` (`$XDG_RUNTIME_DIR` unset, elsewhere, not the user's, open to others, or a path too long, as with a user id of eight digits or more), the turn keeps Claude Code's shared folder, and its commands can read and change other sessions' command output there; the service log says so once, with why.
- **Codex**: with `shell`, on Linux and macOS the thread runs under Mousse's own permission profile (`mousse-bot`, `CODEX_BOT_PROFILE`, defined in the thread's config), with no network (`codexTurnPolicy`, `codexBotSandbox`). Every command asks under it, read-only ones such as `cat` and `ls` included (checked on the real binary), so the grant answers each one. It wins over a sandbox the owner's own Codex config names. Commands read Codex's `:minimal` (the system's own programs, libraries and settings: `/usr`, `/etc`, `/dev`, `/proc`; on Linux no `/tmp` and nothing of `/run` but what WSL mounts there), the Codex package that runs them and the bot's folders, and write only the bot's folders. On Windows the thread runs in the `workspace-write` sandbox, as it always has: writes go only to the bot's folders, with no network, but its commands read every file and Codex runs the read-only ones it trusts without asking (see Where commands aren't held). Approvals stay `untrusted`, and the grant answers every command approval with accept. A retry outside the sandbox ("retry without sandbox?") is always declined. Without `shell` the thread starts with Codex's command tools off (`features.shell_tool`, `features.unified_exec`: `CODEX_COMMAND_FEATURES`), so it has no command tool at all, read-only ones included, on every platform.
  - **Codex's other tools.** Every bot turn starts with the features that add a tool no bot may have switched off in its thread config, whatever the owner's Codex config says (`CODEX_BOT_FEATURES_OFF`): `view_image` (opens any image by its path, unasked and outside the sandbox), image generation, subagents (`multi_agent`, `multi_agent_v2`), apps, plugins and their MCP servers, hooks, Codex's own browser and computer use, memories, code mode, the sandbox-permission ask, messages and questions to a person, goals, sleep and suggestions; and, found with every feature on: `token_budget` (`new_context`, which starts the model's context over, and `get_context_remaining`), `deferred_executor` (`wait_for_environment`), `agent_message_board` (a board between agents), `code_mode_tool_search` (loads tools the turn wasn't offered), from 0.164.0 `executor_capability_discovery_v2` (a `skills` namespace that reads the owner's installed skills), `use_legacy_landlock` (replaces the bubblewrap sandbox the bot's profile relies on), and `rollout_budget` (it won't load without settings whose form isn't documented, so it was never seen with its tools). One feature can't be switched off for a thread, because Codex reads it once for its whole process: `multi_env_copy_file` (from 0.164.0, copies a file by its path between two environments). While the owner's own Codex config has it on, a bot's turn doesn't run, and its chat says "Codex's own setting "multi_env_copy_file" is on, and my work can't run with it. Switch it off in Codex's config.toml to let me work here." (`CODEX_BOT_FEATURES_REFUSED`); the owner's own threads keep it. What every checked Codex still offers, read on the real binary with every feature it lists on in the owner's config (`tests/harness/codexBotTools.test.ts`, `CODEX_BOT_ACCOUNTED_TOOLS`): the time (`current_time_reminder`), `request_user_input` (answered with an error for a bot: nobody is asked), OpenAI's hosted `web_search` (no file of this computer; switched off for every bot turn whose grant holds no web, so a bot without "the web" and the chat, which never uses it, search nothing: `web_search = "disabled"` in the thread config, `codexBotWebOff`, checked on every version in `CODEX_BOT_CHECKED` with web search live in the owner's config), `apply_patch` (each change asks and the authority decides by path), the command tools with `shell`, and, on models whose catalog entry says so, code mode's `exec` and `wait` (JavaScript with no file system or network, calling only those tools, the MCP resources of Mousse's own server, which has none, and the time) and the subagent tools of `collaboration` (`spawn_agent` and the rest), which no config removes; from 0.170.0, models with v2 subagents also get `send_message_to_user_async` (a message to the person in the model's own words, which reaches no file, command or network), which its feature switched off no longer removes. A subagent inherits the thread's features and sandbox (it has no command tool when the bot has none), and Mousse answers none of its approvals: they are cancelled, so a child runs no command or file change that asks, and under the bot's profile every command asks. So without `shell`, a bot on Codex opens no file by its path outside its own folders.
  - **Only a checked Codex runs a bot.** Codex ignores a feature name it doesn't know, so on another version a tool added or renamed there could reach a bot. Mousse can't see the tools Codex offers a turn (Codex sends them straight to the model provider), so it reads the version Codex reports when its process starts (the user agent of `initialize`, `codexVersionOf`), and a bot's turn runs only on a version in `CODEX_BOT_CHECKED` (`childPolicy.ts`, beside `CODEX_BOT_ACCOUNTED_TOOLS`, each with the day it was checked): 0.162.1 (the pinned one) and every release from 0.163.0 to 0.169.0, checked 2026-11-13, and 0.170.0, checked 2026-11-19. On any other version, older or newer, the turn doesn't start and the bot's chat says "This version of Codex hasn't been checked for bots yet, so my work can't run on it." (when Codex didn't say its version: "Mousse couldn't tell which version of Codex this is, so my work can't run on it."). Before any work is sent, About → Runs on and New bot say it once under the rows when a row is picked on such an entry, "Bots' work won't run on this version of Codex: it hasn't been checked for bots yet.", with the installed and the checked versions in its tooltip (`HarnessDriver.botRunsOnNote`, read with the version the entry's check found). The owner's own threads on that entry run as before. A Codex entry Mousse manages runs the pinned version. Meanwhile the owner can move a bot to another entry.
  - **Checking a new Codex release** (on Linux, with bubblewrap on the PATH; no sign-in, the model is a fake in the test):
    1. `npm pack @openai/codex@<version>-linux-x64` and unpack it into a folder of its own.
    2. `MOUSSE_CODEX_BINARIES=<folder>/package/vendor/x86_64-unknown-linux-musl/bin/codex npx vitest run tests/harness/codexBotTools.test.ts tests/harness/codexBotMousseData.test.ts` (several binaries: separate them with `:`). A tool nobody has accounted for fails it; `MOUSSE_CODEX_FEATURES_LEFT_OUT=<feature,…>` finds which feature adds it. Switch that feature off for bots in `CODEX_BOT_FEATURES_OFF`, or, if a thread can't switch it off, refuse it in `CODEX_BOT_FEATURES_REFUSED`, or account for the tool in `CODEX_BOT_ACCOUNTED_TOOLS` with what it can reach.
    3. Also run `npx vitest run tests/harness/claudeMcpCommandLine.test.ts` for a sandbox change shared with Claude Code. Use a development home and fake credentials, as these tests do. The Claude sandbox cases require `TMPDIR` under the test user's home and `XDG_RUNTIME_DIR` at a private directory owned by that user under `/run`, besides bubblewrap and socat on PATH. A skipped sandbox case is not evidence of containment.

- **Pi**: with `shell` the turn offers Pi's `bash` tool; it runs with only the locked platform and network allowlist, from the bot's files folder, with no sandbox. The model's API key arrives through Mousse's private bridge rather than the process environment; ambient cloud credentials needed by the model process are removed from commands' environments. Threads keep their existing environment.

So a command is held to the system's folders (`/usr`, `/etc`, …, and `/tmp` with Claude Code) and the bot's folders only by Claude Code's sandbox on Linux and by Codex on Linux and macOS. On macOS with Claude Code it can read everything but the home folder.

### Where commands aren't held

Only a sandbox that can close a folder holds a bot's commands: Claude Code's on Linux (with bubblewrap and socat) and on macOS, and Codex's on Linux and macOS. Where commands run without one (on Windows, with every runtime; with Claude Code on Linux without bubblewrap or socat; with Pi, everywhere), a bot that holds "run commands" can read and change anything its owner's account can on that computer, Mousse's own data and the CLIs' sign-ins included. The same holds for its background commands (`watch_start`) everywhere, and for its secret commands (`secret_run`) everywhere but Linux with bubblewrap, where Mousse runs them in its own sandbox; both always start in the locked environment, never with the service's. Not allowing a bot "run commands", or switching it off in About, closes that for that bot. Codex on Windows runs a bot's commands as it always has (its `workspace-write` sandbox reads every file): refusing Codex alone there would take work from the owner and close nothing that Claude Code and Pi leave open. A bot without "run commands" has no command tool at all on Codex, on Windows too (`CODEX_COMMAND_FEATURES` off).

## Files

A bot's file tools reach only its own folders: its files folder (`bots/files/<botId>`) and the activation's scratch folder. There is no permission that opens more. "Use files on this computer" (every folder, read and write) was removed, because a bot allowed to run commands reached past it anyway. Work on files in one of the owner's projects goes to a thread in that project instead (see Work in threads). For a file from anywhere else, the owner attaches it or copies it into the bot's files folder, and the bot's instructions say so.

- **Shared lists and plans.** Every runtime is told to read a list or plan just before changing it, in one edit. Pi keeps file versions per activation, keyed by the native real path; a new file uses its real parent plus its name. Files up to 2 MiB use SHA-256 hashes. Larger files use size, modification time, change time (`ctimeMs`), device and inode. The guard never reads more than 2 MiB, even if the file grows during the check. Metadata is weaker than a content hash but keeps large files editable.
- **Pi reads and overwrites.** A read counts as whole when it covers the file from its first line to EOF without truncation, even with `offset: 1` or a limit that reaches EOF. Consecutive pages also count as whole once they cover an unchanged version from start to end. A gap, uncertain coverage or a changed version never counts as a whole read. Partial reads permit version-checked edits; editing refreshes the version but discards incomplete page coverage. A successful whole-file write counts as read whole. A refused overwrite of a short file says to "read it again without offset or limit"; for a file too long for one Pi read, it says to "change it with edit, which is checked against what you read, or read every page first".
- **Pi's version check.** An existing file never read in this activation, or whose version changed since its last successful read or write, refuses edit and write: "This file changed since you read it. Read it again, then make your change." This is a tool error with no ask, wall, ledger row or call charge. New files need no read. Failed calls do not refresh the version. Dispatches of one activation share versions and page coverage; another activation or bot does not. After a service restart, existing files need a fresh read. Scratch files are unchanged. This check is not an atomic filesystem transaction: an outside writer can still race an admitted call. Shell and background commands are not covered.
- **Other runtimes' stale edits.** Mousse adds no read-version check to Claude Code or Codex. Claude Code checks every file call through its hooks and grant gate; Codex checks file changes when it asks for approval, while trusted read commands can run without asking (see How each runtime holds a bot). [Claude Code's current Edit documentation](https://code.claude.com/docs/en/tools-reference#edit-tool-behavior) allows a changed file when the old text still matches exactly and uniquely and reading it needs no prompt; otherwise it requires a fresh read. Its read-before-edit/write requirement also varies by model. That is not a whole-file stale-version refusal. Anthropic's [Tools reference, "Write tool behavior"](https://code.claude.com/docs/en/tools-reference#write-tool-behavior), read 2026-11-16, says newer models may overwrite an existing file never read in the session when Read is available and reading needs no permission prompt, as in a bot's files folder. Older models and partially read files still require a read. Neither Claude Code nor Codex refuses a stale overwrite based on this activation's last read. Codex's [patch implementation](https://github.com/openai/codex/blob/main/codex-rs/apply-patch/src/file_update.rs) checks patch context against current contents, not a remembered version from a previous read. Changes elsewhere in the file need not prevent the patch. Neither runtime's binaries were run to check this.
- **Refused, never asked.** A file call outside the bot's folders is refused with no card. `permission_ask` for a folder is refused with no card (`permissionProblem`, `BOT_NO_FOLDER_ASK_TEXT`), and the `permission_ask` tool offers no folder form.
- **Grants an older build wrote.** A grant or published revision with a `workspace` (such as `{roots: ['C:\'], access: 'write'}`) is kept exactly as stored, so its digest stays the approved one and nothing asks for approval again; nothing reads it for what the bot may do (`compileBotThread`, `manifestSubset`, `intersectManifest` and About ignore it). Nothing is migrated in `bots.db`.
- **Asks an older build wrote.** When bots open (`BotEngine.withdrawFileAsks`), every open file ask is withdrawn and its card re-published: it stays in the chat as history, a chat waiting at it stops waiting, and Allow on it is refused and grants nothing (`BOT_FILE_ASK_GONE_TEXT`). Answered ones stay as they were.
- **Paths in full.** A path a runtime would rewrite (`~`, a variable, padding whitespace) is never checked or expanded here: it is refused with no ask. The refusal names the owner's home folder by its real path and, for `~/…` or `$HOME/…`, the full path meant (`pathFormWall`). The bot's system text names the home folder too, beside its files folder.
- **What enforces it.** File tools check paths on every platform, including Windows: case and real paths, junctions and symbolic links, and local network path forms (`localPathOf`). Windows alternate streams and ambiguous path forms are refused. Codex checks both paths of a file move or patch. Commands have a separate boundary (see Run commands).
- **A runtime's own storage never asks**: Claude Code's project folder for the bot stays available to its file tools; a symbolic link inside it is checked where it leads, and Linux commands cannot change that storage. Claude Code saves large tool output (web results, long command output) in `<Claude home>/projects/<working folder as a name>/<session>/tool-results/` and reads it back with Read or Grep. The bot's working folder is its files folder, so that project folder holds only this bot's sessions; the grant gate recognises calls there (`claudeOwnStorage`) and allows them (`NormalisedCall.own`), and its sandbox can read it. Codex and Pi have no such storage that a bot's calls reach.

## Use the browser

"Use the browser" is one permission for every browser tool (`browser` in the grant, `BOT_BROWSER_PERMISSION`). The bot asks for it once (a card reading "use the browser"); an ask for any single browser tool, such as `browser_act`, is the same ask, and its card never names a tool. After Allow, `compileBotThread` turns it into the browser tools (all but `browser_request_human`: the bot asks its owner in its reply instead) and the bot's work has them in every run, with no new ask; a chat turn hands browsing to work. Not now, About → Remove and the repeat rule work as for every other permission. Other Mousse tools stay refused: an `permission_ask` for one no bot can hold is refused at once, with no card.

The browser is the bot's own (`src/mms/bots/browser/BotBrowsers.ts`), never the owner's tabs or a thread's:

- **One managed Chromium session per bot**, without a window, so a scheduled run works with no app open. It runs on a persistent Chromium profile of its own (`botbrowser_<botId>` under the profile's managed browser data), so sites the owner signs in to for the bot stay signed in for that bot only, and the bot never uses the owner's other sign-ins. A deleted bot's browser closes at once; its profile is erased with the 30-day purge.
- **Owned by the bot's home thread, with no run**, in the browser inventory: both lanes share the session, and no thread's agent or the owner's in-app browser reaches it (another owner is refused).
- **Reached only through the bot's own view and tools.** The session and the bot's profile are kept by `BotBrowsers` (`BOT_BROWSER_KEEPER`, checked in `BrowserSessionManager` by every session method): only the owner's view (`bots.browser.*`, with its hold) and the bot's own browser tools under its grant reach them. Anything else that names the bot's home thread, its session or its profile is refused with "This browser belongs to a bot. Open it from the bot's page." and changes nothing: the general `browser.sessions.resume` and `browser.artifacts.read` methods, a thread's browser view (`browser.view.*`, which shows nothing of the home thread and holds nothing), a thread's agent, a group chat, a workflow opening `botbrowser_<botId>`. Another bot is refused by the home-thread ownership above. A session recorded before this rule is kept by its profile.
- **A tab per activation.** Each activation opens and uses only its own tabs; another activation's tab is refused, a tab list shows its own, and a call without a tab from an activation with no page of its own is refused (it would read or screenshot another run's front tab). When an activation ends, its tabs close; when the last one ends, the browser closes after ten idle minutes (`BOT_BROWSER_IDLE_MS`), unless the owner is watching it or holds it. Work that lets go of the browser to wait for its owner's answer (a question, an action to approve) keeps its tabs open and its own, and the view on its page, whatever other activations do, for the owner to check the page or take it over: the browser stays open for thirty minutes from then at least (`BOT_BROWSER_HANDOFF_IDLE_MS`, kept per waiting activation, never cut short by another's end). When that work goes on, it uses its tabs that are still open, and its thirty minutes no longer count; stopped while it waits, its tabs close as an ordinary end's do.
- **One call at a time, in turn** (`BrowserTurns`, in `src/mms/browser/viewer/`, which a thread's browser without a window uses too). The session takes one action at a time (a second is refused, "Another action is already in flight") and, having no window, paints only its front tab, which an action brings forward. So when several activations browse at once, each call waits for the one before it to end, in the order they came, across the bot's activations: a call never fails for another one, and never loses its tab mid-action. Opening the session (and a first use's install) needs no turn. The wait is bounded: at most 24 calls wait (`MAX_BROWSER_WAITERS`), each for at most 5 minutes (`BROWSER_TURN_WAIT_MS`), past which the call is refused as busy; a stopped turn leaves the queue at once. The holder is bounded too: the worker ends each of its requests at 60 seconds, and a call that still holds the browser after 5 minutes (`BROWSER_TURN_HOLD_MS`, a little above the longest call: four requests) is stopped with a timeout to its run, and the next one goes. The owner's pictures take no turn: the worker never brings a tab forward for them (see the pictures below). A picture an older app asks for, and each close of an ended activation's tab (which does take a turn), has a stop signal and 15 seconds at most (`BROWSER_SIDE_CALL_MS`). The owner's input takes the next turn, ahead of the calls that wait, and cuts into a run's call under way: that call has 150 ms (`OWNER_CUT_IN_MS`) to end, then it is stopped, its run told its owner is using the browser now, and the input goes. After each input the browser stays the owner's for a second (`OWNER_KEEP_MS`): their next input goes at once and the runs' calls wait, so typing goes at the page's pace and the runs read in the pauses. Only the close of an ended activation's tab is waited for (30 seconds at most, then the input is refused as busy). The input goes only to the tab the owner holds, which the worker brings forward first, since a tab in the back takes no input (see the owner's input below). Take over and Give back take no turn.
- **First use installs it.** On a computer without the managed browser, the first browser call of any bot downloads it through the browser setup (`BrowserSetupService`, once for the installation) and waits for it; the preview reads "Setting up the browser". A computer that can't run it gets a plain refusal.
- **Stop and limits.** Every call carries the activation's signal: a stop, a wall or the deadline ends it. A stopped activation can't use the browser.
- **A slow page is not a failed page.** A page is open once it has committed and its document is ready; one that goes on loading is reported as still loading, and the bot carries on or waits (`browser_wait` with `document-ready`). A page that fails never closes the browser. Failures come in plain classes, each with what to do next, in the bot's tool result and in the owner's view (Chromium's own code only in the details and the tooltip): the site can't be reached, the site refused this browser, the page is nothing but a human check or a consent wall (the owner gets past it), the browser won't open the address (an unsafe port, its own rules, a certificate it does not trust), or the browser can't start (with the cause). A page that opened is never a failure because of what is on it: the bot's result notes a cookie banner (it may dismiss it), a check that is part of the page, a page not found or a server error, and a sign-in form, which is its owner's to fill (the bot has no sign-ins of its own); the owner's view says "needs you: a sign-in" until the page no longer asks. The bot's instructions tell it never to retry a site that refused it or a page that is only a check, and to say so in its report.
- **What sites see.** The browser names itself as the Chrome it is (`Chrome/…`, not `HeadlessChrome`); `navigator.userAgentData` and the `Sec-CH-UA` headers name the same Chromium and system. A page reads `navigator.webdriver` as false only while the owner holds the browser (after Take over, or when they open it to sign in). Everything the bot loads or drives reads true from its first script: every page, frame (at any depth) and page a site opens, with or without an opener. When the browser cannot be sure, the answer is true (`ManagedSession` in the browser worker):
  - While the owner holds the browser, the bot can read its pages but cannot act, open a tab or load a page; a call that was waiting its turn when they took over is refused when the turn comes. Take over stops a page the bot was still loading and closes a tab it was still opening, and the page the owner opens the browser on loads in the next turn, as their input.
  - At Give back every page reads true again. A page that cannot take the mark back within a few seconds (one showing a dialog the owner left open) is closed rather than left reading false.
  - When the owner opens a closed browser on a page, the browser is theirs before that page loads.

  So a human check such as Cloudflare's "Verify you are human", completed by the owner after Take over (and a reload when the check had loaded while the bot drove), passes, and its clearance stays in the bot's profile for later visits.
- **The owner's view** (`bots.browser.*`, apart from the required Bot UI methods, so an older daemon simply shows none): `get` returns the followed tab's URL and title, the activations that used the browser, and who holds it as the asking view sees it; `watch` and `unwatch` start and end the pictures (below); `hold` takes the browser over for a view, keeps it and gives it back; `send` carries that view's numbered input (below); `open` opens the browser for the owner, as their view's hold, to sign in to a site for the bot. `get` with `frame` still answers a fresh JPEG of the tab for an app from before `watch`, and an older app's `control` and `input` still work, as a hold of its window. Taking over, input, `open`, `close` and `get` with `frame` are the desktop app's on this computer alone, like watching (`bots.browser.files`, below, is its main process's alone).
- **Taking the browser over** (`BotBrowsers.hold`, through the general viewer `WatchedBrowser` in `src/mms/browser/viewer/`; the view's side is `botBrowserStore`, over the general `watchedBrowserStore`, with the general `BrowserInputChannel`, `useBrowserInput`, `WatchedBrowserFrame` and `WatchedBrowserPane`, the split view). The host alone decides who holds the bot's browser, the bot or one view of the owner's (an app window, with an id it keeps across reloads), and every view hears it at once.
  - **A hold belongs to the view that took it, on the connection it took it on,** and lasts while that view says it is there, every 5 seconds, whatever is on screen. A call on another connection is not the hold's, even naming the right view and hold. A window that reloads keeps its connection and picks its hold up again from `get` or `watch`, at the host's last input number; a window whose connection dropped presents its hold on its new one (its next heartbeat) and the hold moves there, once: the connection it left never has it again. A window that was hidden asks the moment it is shown again, and says at once if its hold ended meanwhile. A view gone for 2 minutes (the window closed, the app quit) ends its hold: what the person left pressed is let go of, the browser goes back to the bot, and its chat says so once ("I have my browser back: the window you took it over in went away."). Give back lets go of pressed keys and buttons and drops an IME composition (keys held while the page shows a dialog go up as soon as it is answered); the bot hears of the person's visit only as before (its old observation is stale: it observes again), never what they typed.
  - **Another window** sees "Held in another window" and takes the browser over only by pressing Take over there; its `open` is refused the same way. The first window's hold ends, and what it left pressed is let go of. Take over again in the window that holds it gives it a fresh hold, numbered from 1: whatever its old channel still waited on is dropped.
  - **Taking over while the bot acts** ends the bot's action in flight, and its tool call answers that its owner took over and whether the action was applied, not applied, or can't be told (a navigation whose page committed was applied), so the bot does not repeat it blindly.
  - **The hold is the only one.** The bot's browser is the owner's exactly while a view's hold lasts (an older app's `control` is a hold of its window): it is what refuses the runs' actions, what keeps the view on the tab taken (below), and where the owner's input goes. Take over holds exactly the tab the view shows (the followed run's tab; with none followed, the one the last picture showed), as it was when they pressed it, whatever a run does meanwhile.
- **The person's input arrives, or says why not.** Every input goes on the hold's channel (`bots.browser.send`) with the hold's id, its own number and the picture it was made on. The host applies each number once, in order, one at a time (`InputSequencer`): an input that comes before the one ahead of it waits for it up to 250 ms, then what waits behind a gap is refused as `gap` without using its number up, and the view sends it again. A number already taken is answered as a duplicate, so a resend after a lost answer applies nothing twice. Each input is answered as applied, a duplicate, or refused with a plain reason, and goes to the tab the view took, never elsewhere. It is applied in the browser's turn (`BrowserTurns`, above), so it never lands beside a run's call: it goes ahead of the runs' calls that wait, and a run's call under way (only reading is left to a run during a hold) has 150 ms (`OWNER_CUT_IN_MS`) to end before it is stopped and its run told its owner is using the browser now; the browser then stays theirs a second after each input (`OWNER_KEEP_MS`), so a burst of typing never waits on the runs key by key. So "Sending…" and "Not reaching" below are about the page and the connection, never a run's long call. The answer comes once the worker applied the input, never when it was only queued. The view merges an unsent move into the move before it and adds wheel turns up, and never reorders kinds: text typed before Enter reaches the page before Enter.
  - **No refusal leaves a hole.** Every number the view gives out reaches the host as its input or as a skip, which uses the number and applies nothing. An input the service never takes (a prompt answer over 4,096 characters, anything malformed) is refused in the view before it gets a number; one the service refuses anyway (a batch refused as a whole is sent again one by one to find it) is dropped, said once, and its number skipped. A refusal that did not use its number (`gap`, or `busy` when more than 256 wait at the host) is sent again by the view, backing off from 250 ms to 4 s, for 10 seconds after the person made it; after that it is dropped, said once ("Not sent: the page did not take it in time"), and its number skipped. A gap the host reports below everything the view still has is filled with skips.
  - **What the view shows.** A small mark where the person pressed settles when the answer comes. Nothing more while input arrives. Half a second without an answer: "Sending…". Three seconds: "Not reaching <computer>" (this computer, named as the rest of the app names it) with Retry, which resets the back-off and sends everything unanswered again at once (the view also sends again by itself after a failed call). A refusal is said once, in one short line.
  - **Back-pressure.** While 24 inputs wait for an answer, or none has come for three seconds (a page that stops answering: a CDP call can wait up to 30 s), the view takes no new press, key, text or move: each is refused in the view at once, and the line reads "Not reaching <computer>", so typing does not pile up to arrive in a burst later. Letting go (a button or a key going up, Give back) always goes, unless what went down was refused too. When the page answers again, what was taken arrives once, in order, and the line clears by itself.
  - **Pictures that are no longer the page.** Each picture carries a number, and the host keeps, for its last 32 and for every one sent in the last 5 seconds (at most 256: 5 seconds at 30 a second is 150), the tab, page and scroll it showed. The worker reads the scroll as each picture is taken (Chromium without a window reports none with its screencast), and a picture goes to no view before that is read. A point on a picture of the same page, scrolled since, moves by the scroll, so it lands on what the person saw; one now out of view, on another page or on another tab is refused ("Page changed · click again"), and the view shows the page as it is. A press or a key made on a picture the host cannot place (older than that, of another tab, or none) is refused at the host and never reaches the page; the worker also refuses any click, press, move or wheel turn that comes without the place of its picture. Typing made on a picture after its click was refused is refused too, until a later click on that picture lands. A held button is still let go of, and a wheel turn is never refused for scrolling.
  - **What was under a press.** While the owner holds the browser, the worker also reads, with each picture, which element is on top at a grid of 16 by 9 points (80 px apart on a 1280 by 720 page), in an isolated world the page's scripts never see. A press (a button going down, a click) on an older picture is checked at the grid points around it (up to four, those still in view after the scroll): each must still have the same element on top, where it was on the page (within 6 px). If not, the press is refused ("Page changed · click again"). This catches a modal or an overlay that opened over the point, a shift of the layout (a banner that pushed the content down), and an inner area that scrolled under it (checked on Chromium on macOS). It does not catch: a change smaller than the grid, that covers the press but none of the points around it (a small tooltip or popover); a change inside an iframe (the frame element itself is what is on top); a change of what an element shows without moving it (its text, a canvas); a change in the moment between the picture and the reading of its grid; and a press on a picture whose grid could not be read (a page that did not answer within 2 seconds, an older app's pictures), where the scroll check alone stands. An element fixed on screen is compared by its place on the page, so after a scroll a press on it in an older picture is refused rather than moved.
  - **What reaches the page.** Pointer down, moves and up with buttons and click counts (hover, drag, double and right click, text selection); every wheel turn; keys down and up with modifiers and codes (the key code a browser's events carry, never a platform's native code: on a Mac those are other keys, and Chromium would press and repeat those), where a Mac view's Command is the page's Control on a page that is not on a Mac and the editing shortcuts (select all, undo, redo) run their command, since a browser without a window has no menu (on a Mac a key pressed with Command is let go of at once: the window never hears it go up); IME composition and dead keys as composition, committed as text; paste of the person's clipboard text on their paste only (at most 64,000 characters); on a touch screen, a tap clicks, a long press is a right click, and one or two fingers scroll.
  - **The person's clipboard.** Copy (and cut) on the person's own shortcut reads the page's selection as plain text, in an isolated world, and the app writes that text on their clipboard. The browser's own copy never runs: its clipboard never holds what the person copied, for a page or the bot to read back, and the page hears no copy event; cut then deletes the selection in an editable field. Chromium without a window has a clipboard of its own, never this computer's: checked on Chromium on macOS, a page's `navigator.clipboard.writeText`, its `document.execCommand('copy')`, its own copy handler and the browser's copy all leave this computer's clipboard unchanged. While the owner holds the browser, pages are refused the clipboard (`navigator.clipboard` read and write), and the browser's defaults come back when the bot has it again. A page can therefore put nothing on the person's clipboard except through their own copy, as text. What a copy read is answered once: a duplicate of it carries no text.
  - **The page's dialogs and file picker.** An alert, confirm, prompt or leave-page question stops the page until it is answered: the view shows it over the picture with its own buttons, and the page takes nothing else meanwhile ("Answer the page's dialog first"). The input that opened it counts as done once it is open, and a dialog that opens while a press is being checked lets its answer go first. While the owner holds the browser, the tab they took answers its file picker through their view, and only theirs: the card names the site whose frame asks and whether it takes one file or several ("example.com asks for a file"), and nothing goes to the page until the person chooses. Choose… opens this computer's own open-file dialog from the app's main process, which sends the chosen paths to the service on the window's own connection (`bots.browser.files`, not one of the renderer's methods). The service checks them again (the hold, a picker open on the held tab, at most 16 files and 512 MB in all, each a file; over that, "Choose at most 16 files, 512 MB in all.") and answers a one-time token, which the view sends as its `files` input. The renderer never names a path, and the input channel takes none. A token gives its files once, and none outlives the hold.
  - **What it cannot do.** The browser's own menus (its right-click menu, its Edit menu) have no window to show in. A `<select>`'s list opens as a popup the browser has no window to draw (checked on Chromium 153 on macOS): a click shows nothing, and the arrow keys and Enter then go to that unseen list and change nothing; Escape closes it, and typing an option's first letters chooses it. Drag and drop of files from this computer into the page, and pinch zoom, are not sent. The protocol carries no step that needs the view and the service on one computer, except a chosen file, which goes by its path from the app's main process to the service.
  - **Never kept.** What the person types, pastes, copies or chooses goes to the page or their clipboard only: it is not logged, written to the bot's journal or memory, put in the bot's context, or kept for a duplicate's answer.
- **Pictures are pushed, and only while seen.** A view that shows the browser calls `watch` (renewed every 5 seconds; the daemon drops one not renewed for 15) and the daemon pushes `bots.browser.frame` events to that window's own connection: a JPEG when the page paints, the page's size and title only when they change, and the agent cursor as it moves. A still page sends nothing, apart from one picture at full quality about 300 ms after it stops changing. A page that flips between pictures it showed a moment ago (a blinking caret) sends the flip back once, then at most one every 5, 10, 20, 40 and 60 s; a page that changes every second (a clock) sends one picture a second and, after its first two, no full-quality stills. The app watches only while the preview or the split view is on screen and the window is shown, and stops a second after neither is or when the window reloads; with no view watching, the worker runs no screencast at all. Only the desktop app on this computer can watch, a window watches a bot once, at most eight views watch one bot, and a window can end only its own watch.
  - **Sizes:** the preview asks for 480 px wide at most 5 pictures a second; the split view for the page's width at the screen's pixel ratio, up to 1920 px, at most 15 a second, 30 while the owner holds the browser.
  - **The page has the split view's size.** While the split view shows the browser, every tab's page is laid out at the split view's own size, as a window resized (`page.resize`, `WATCHED_BROWSER_PAGE`): its content area in CSS pixels, from 320 by 240 to 1920 by 2160, at the screen's pixel ratio up to 2 (lower when the picture would be over 1920 by 2160 pixels), so the picture fills it. The view says its size once it has stayed put for 250 ms (a drag of the divider, the app window resized), on its watch (`page`). The resize takes the owner's turn (`BrowserTurns.personCall`): ahead of the runs' calls that wait, after the call under way, which it never stops, and with no Take over. The bot's next observation sees the new size; its screenshots stay at the page's CSS size, and a coordinate from an observation before the resize is refused as stale. With two windows' split views open, the window that holds the browser sets the size, else the one opened last; the other shows the whole picture, scaled. When no split view is seen (closed, hidden, its window gone), the page goes back to 1280 by 720. A thread agent's browser in its Browser panel (`ThreadBrowsers`) does the same.
  - **A picture from before a resize places nothing.** The session counts its resizes, and each picture carries the count it was taken at (`sizeSeq` in its place), or -1 when Chromium says it shows a size the page has left. A press, click or move made on such a picture is refused ("Page changed · click again"), never placed by the old layout; a wheel turn still goes. One capture of the tab serves every view at the widest size asked; each view has its own slot, so a slow one drops pictures and never queues them, and Chromium is asked for no more pictures than some view takes (its acknowledgement waits until a view is free). No picture is over 1 MB: a larger one is taken again smaller.
  - **A tab behind is never brought to the front for the view.** Chromium without a window paints only its front tab, and the bot acts on that one: a view that pulled another tab forward could leave the bot acting on a page that no longer paints. A followed tab behind gets one still picture, and the view reads "On another tab" until the bot uses it again. A tab a site opens never stays in front, and when the tab in front closes, the bot's tab in front before it comes back, so "On another tab" is always true.
  - **Take over brings the tab to the front.** The owner takes the tab the view follows: it comes to the front, as it does for each of their clicks, keys and navigations, so Chromium paints what they do. While the owner holds the browser the view reads "You have it", never "On another tab".
  - **The view tells the truth.** "Live" only while pictures can arrive. When the stream stops (the browser closed, the followed tab closed, the tab the owner took over closed, the service cannot be reached, a watch cannot be renewed) the picture stays and the line reads "Not updating · 12 s"; each renewal answers whether pictures can arrive now (`stalled`), so a renewal never makes the view live by itself. It recovers by itself once pictures can arrive again. A page still loading reads "Loading" (a moving line under the split view's address); one that ran into a problem says it in one line ("Can't reach example.com", "example.com needs you: a sign-in"), with Chromium's code in the tooltip; with several runs browsing, only the followed run's problems show. The owner's own navigation, back, forward and reload return as soon as the page has committed.


**Open in a window.** On the computer the bot's browser runs on, the split view also offers Open in a window: the bot's browser as a real browser window on that computer's screen, with its own rendering and the person's own mouse, keyboard, clipboard, dropdown lists and file dialogs, instead of pictures. Its tooltip says that pages reload when the window opens and when it closes.

- **Why pages reload.** Chromium decides at start whether it has windows, and a browser started without one can never show one (Chromium's own documentation; on the real browser, `Browser.setWindowBounds` and `Target.createTarget` with `newWindow` answer but show nothing). So the browser starts again with a window on the bot's own profile, and again without one when the window closes (`ManagedSession.restart`). The session stays the same one: the same id, lock and tab ids, so each run keeps its tabs.
- **What survives.** Each tab comes back at its address and loads again. Sign-ins kept on disk are the profile's own. Session-only sign-ins (cookies with no expiry) are read before each restart and set again after it. A tab the person closes in the window stays closed; tabs they open themselves in the window are not kept.
- **What is lost.** Whatever was part-way through on a page: text typed and not sent, scroll position, back and forward history, `sessionStorage`, a step in progress. When the person closes the window with its own close button, Chromium drops session-only cookies as the window closes, before anything can read them, so the browser keeps a copy while the window is open, read every second and soon after each page loads: a session-only sign-in a page's script set in the last second before the window closed can be lost. Close window in the panel reads them at that moment and loses nothing.
- **When it does not open.** A page waiting on the person in a way a reload would lose without anyone seeing is refused in one line: a dialog ("A page is asking something. Answer it first, then open the window."), a file request, or a download still running. The bot's own step under way never needs waiting for: taking the browser over already ended it, and the bot was told whether it took effect.
- **The window is the hold.** Opening takes the browser over (the same one hold as Take over, with its heartbeat) and the window lasts exactly as long as that hold. The bot's runs are refused and told their owner is using the browser; nothing is pictured or streamed; the split view says in one line that the browser is open in a window, with Close window in place of Give back. Close window, the window's own close button, Give back, another window taking the browser over, or the hold running out (the app gone for 2 minutes) all close the window; the browser starts again without one and goes back to the bot (or to the window that took it). A window whose browser stops by itself (a crash, or its process ended from outside) brings the browser back the same way, and the bot's chat says so in one line, since a sign-in from its last second may not have been kept. The service stopping closes the window with the browser; the next start opens the bot's browser without a window, as always.
- **Who may open it.** Only the desktop app on the computer the browser runs on, on the person's click, never a bot, an agent, a group chat, a workflow, the command line or another computer: `bots.browser.window` is called by the app's main process alone (the renderer's request bridge does not offer it), on the window's own connection, for the view that holds the browser, and goes through the session manager's ownership check like every call on the bot's browser. Only that app is told it may offer the control (`windowable`).
- **Where it opens.** On the screen of the app that asked. On Linux the app's main process names its own display (`DISPLAY` and `XAUTHORITY`, or `WAYLAND_DISPLAY` and `XDG_RUNTIME_DIR`), never the renderer. On Windows and macOS the window opens on the desktop the service runs in, which is the person's own: Mousse starts its service at sign-in. The control is not offered where the service has no desktop someone sees (Windows session 0, a macOS service started over SSH), and a window that does not come up says so in one line and leaves the browser as it was, without a window.
- **What stays the same.** The window shows the bot's own profile only, never the person's own browser, tabs or sign-ins. It is driven over the same private pipe, with no debugging port and no port file. It names itself as the same Chrome, and `navigator.webdriver` reads false in it, since the person holds the browser the whole time it is open.

**The tab the view follows** (`follow`, `refollow`), which the preview and the split view both show and the owner's input goes to:

- While nobody holds the browser, it follows one activation (`followed`, the view's `activationId`): the first that used the browser, and after it ends the newest that still runs. Its current tab is the one shown; another run's calls never move it, so with several runs browsing the view never jumps between them.
- Take over (or a browser opened for the owner) is a view's hold, and holds the tab the owner sees. Until the hold ends (Give back, or its window gone for 2 minutes), nothing a run does changes the followed tab, and their clicks, scrolling, typing and navigation go to that tab only; an input made on a picture of another tab is refused. The other runs keep their own tabs: they read them in their turn, and acting, opening a tab or loading a page is refused. If the held tab closes (its run ended), their input is refused with "The tab you took over has closed. Give the browser back, then take it over again.", and the view keeps its last picture rather than show another run's tab. When the hold ends the view follows a run's tab again.

In the bot chat, the reply of that activation shows a small live preview: the picture, the page's title and site, the status, and the agent cursor. While that activation still works, the preview sits under the working line. Hovering it shows Expand, which opens the split view: the bot's browser beside its chat, following the same tab, with Take over and Give back, back, forward, reload and an address field. While the split view is open, it alone is watched, and the preview is one line ("Browser open beside the chat") with no picture; it comes back when the split view closes. Its steps read "Used the browser · example.com", and its face's sticker is the browser while it uses it.

## Use your MCP tools

A bot can use every MCP server its owner set up in Mousse (Settings → Skills & MCP) without asking: MCP is on by default for every bot, new and old, and About → Can use switches it off for one bot, all of it or one server at a time (see Switching a bot's permissions off). Tools which can change things still ask before each use. The code is `src/mms/bots/mcp/BotMcp.ts`.

- **Which servers.** Those the owner set up in Mousse for the whole profile and turned on there: the relay catalogue's scope with no project (`RelayCatalog`), which lists Mousse's own profile config. A project's servers (`mousse-project:…`, `external-project:…`), other apps' configs (Cursor, Claude, Codex) and a server named like Mousse's own (`mousse`, `mousse-relay`) are never offered or askable: their ids are not grantable (`mcpGrantable`) or the catalogue leaves them out. The relay switches per runtime (Share with other agents) are for the owner's threads; a bot reaches the profile's servers through Mousse whatever they say (`listProfile`). MCP off in Settings is off for bots too.
- **How the bot knows them.** `mcp_servers`, always on and never grantable (like memory), in both lanes: each server's name and id, a line of Mousse's own ("26 tools, such as create_issue, …", or "still starting: its tools are loading"), whether the bot can use its tools (`yes`, `no` for a server with none it can use, or `no: switched off by your owner`), whether it is answering, and whether it is still starting. No schema, description or other text of the server's. It is a tool rather than lines in the situation or the system text so those stay stable for the prompt cache, carry no third-party text, and cost nothing until the bot needs them. The system text names the servers it has ("Your owner's MCP servers: GitHub", or "switched off by your owner for now, so asking won't help"); a consult's says it has none ("none in this consult (your main work has GitHub; …)"), since a consult is never given MCP tools.
- **What a turn holds.** What an activation runs with (`BotEngine.effectiveManifest`, through `withDefaults`) adds every tool of every server set up now, by the server's id as it is now, to what the grant names, less the servers switched off: the grant and its digest never change, so no bot is asked to approve again. A grant an older build approved may still name servers per tool (`<installation>.<identity>`, `mcpServerIdentity`); those pairs still count, and a switch takes them away too. A server edited in place gets another identity and is simply used under its new one.
- **No ask.** `permission_ask` no longer offers MCP servers. An ask that still names one (a gate refusal, or an older bot's `permission_ask({ mcp })`) makes no card: a server switched off is refused as switched off (`permissionOff`), one the bot has is answered "already allowed", and one still starting, or listed after the turn started, is answered that its tools come without asking (`BotEngine.mcpAsk`). Cards an older build raised are still shown and answered as before (`mcpAskFor`, `fillMcpAsks`, `withPermission`); their Allow adds pairs every bot has anyway.
- **A server that has not answered yet.** The servers are published as they answer (below), so one that is slow to start shows to the bot as still starting, and its tools reach the next turn after it has listed them. Before the servers were read at all since Mousse started, the bot is told they are still being read (`BOT_MCP_NOT_READ_TEXT`), and they are read.
- **What the bot is told.** It is told it asked ("Asked the owner. …", `BOT_ASK_REFUSED_TEXT`, `BOT_ASK_DEFERRED_TEXT`) only when a card exists for that permission. For 24 hours after Not now, a run's call or ask of any kind makes no card and is answered "The owner said not now to this. …" (`BOT_ASK_NOT_NOW_TEXT`).
- **Lanes.** Work and the chat hold the same MCP tools. The chat calls them as quick calls, through its catalogue (see Quick calls in the chat).
- **What a turn is offered.** Work of a bot whose MCP is on reads the owner's servers first when the listing is cold, old, or changed since (servers added or removed, settings: `BotMcp.warm`, `ensure` with `fresh`, at most 3 s, never starting a sign-in; a warm listing returns at once); a chat turn never waits for it: it is offered the tools of the listing it finds, and a cold listing is read beside it, and a bot with MCP switched off reads nothing at its turns. A change of servers in Mousse reads them again at once (`RelayCatalog.invalidate`). The catalogue publishes the configured servers first, then each server's tools as soon as it answers (`McpManager.getEnabledToolsByServer`'s `onServer`), so a slow server hides only itself. Work is offered the tools of servers set up now that it holds (`BotMcp.offered`, `BotAuthority.mcpTools`), under the relay's names (`<server>__<tool>`). Their descriptions, and every argument's description and title, are framed as the server's own words, never instructions, cleaned of markup that could read as system text (tags, special tokens, role markers, code fences) and cut short (300 characters for a tool, 120 for an argument); comments and examples in the schema are left out.
- **How a call travels.** Every call goes through Mousse, where the bot's authority checks the `server::tool` pair against the grant before the server sees anything (`callForBot`), then runs on the owner's own connection (`BotMcp.call`, `McpManager.callTool`). It is pinned to the tool as listed when it starts, and checked again once the connection is ready, right before it is sent: the server still set up and on, its config and schema the same, MCP still on in Settings, the tool still listed as one a bot can be offered (a valid schema, relayed), the bot's grant and switches (`BotAuthority.allows`, no ask and no chip), and the tool's level as it stands then (`BotAuthority.mcpHeldNow`, on every turn, whether or not Asks First was on when it started). A tool with no such listing, or no installed revision to pin to, is never sent, even when the manager could still call it. One changed while it connected sends nothing, and the bot is told so; one that started to ask the owner first (its stored level, or its server's hint) is told to call again, and that call is held with a card; in a turn that started with Asks First off, which cannot hold it, it is refused for the rest of the turn. A call is counted on the activation's tool calls once, when it passes that last check (`BotAuthority.callRuns`): one refused at any check counts nothing, and a held call counts when its owner's Send sends it (on Pi, whose budget counted it when the model made it, not again, after its chat turn ended too). The bot never talks to a server itself and never sees its config or credentials.
  - *Claude Code:* the bot turn gets Mousse's relay as its only server beside Mousse's own, both registered over Claude Code's input (#358), with no settings files, plugins or other servers. The relay lists only the turn's offered tools (`RelayHandler.list`, `botOf`), and the grant gate (`ClaudeLockedGate`) checks every `mcp__mousse-relay__…` call by name before Claude Code sends it; any other relay name is refused. The relay checks it again.
  - *Codex:* the relay is attached (`codexMcpConfigOverrides`), the owner's own Codex servers stay off for the thread (`codexBotMcpOverrides`), and the relay is the gate: Codex asks nothing about MCP tools Mousse serves.
  - *Pi:* the user MCP proxy offers the turn its offered tools under their provider names (`ToolRegistry.userMcpForTurn`). Pi's gate checks a call of one of them as an MCP call of the grant (server and tool), as Claude Code's gate does, before it is charged; the registry checks it again before it runs (`callBotMcp`).
- **Results are data.** What a tool returns is framed for the bot as data from that server, never instructions ("[What list_issues on your owner's MCP server "GitHub" returned. …]"), cut at 32,000 characters. Its images reach only a model that takes images in tool results (`toolImages`), at most 4 of at most about 1 MB each; the others, or all of them on a model that can't see images, are named in a note. It is journaled like any tool result (bounded, `external`) and passes the memory guard before it can enter a pack.
- **Limits and failure.** A call obeys the activation's stop signal and deadline and runs at most 2 minutes (`BOT_MCP_CALL_MS`, with Mousse's own timer under the connection's). A server that is down, slow or failing gives the bot one fixed line by kind of failure ("GitHub isn't answering: it took too long.", "… Mousse couldn't reach it.", "GitHub couldn't start on this computer.", "GitHub couldn't run this call."), never the server's own words, a host, a port or a command path; the raw text goes to the owner's log (`BotMcp`), and the run carries on. A call never starts a sign-in (`signIn: false`): an OAuth server without a session refuses at once, and one whose session cannot be renewed fails instead of opening a sign-in page (`FileMcpOAuthProvider.holdSignIn`); the bot is told the owner must sign in again in Settings, and says so in its report rather than asking. A server removed from Mousse or switched off in Settings is gone from every turn at once (not offered, and a call is refused by `McpManager.isToolCallAllowed`).
- **The connection.** A server's connection is the owner's, shared by their threads and the bots, and lives as long as the profile's MCP work, never as long as the call that opened it: a bot's call that is stopped ends only its own wait (`McpManager.connect`). A stdio server whose call timed out is pinged, and restarted only if it no longer answers and no other call runs on it, so a slow call does not lose the server's own state.
- **What the owner sees.** About → Can use has a "Use your MCP servers" row with a switch, and while it is on, one row inset below it per server set up now ("Use your GitHub tools", how many tools and a few names, or "Asks you first…" when some of its tools may send or change things), each with its own switch and no Remove (`BotEngine.defaultItems`, `BotPermissionItem.builtIn`). Chips read "using GitHub" and "used GitHub" (`chipCallOf`: the server's name only, never a tool or its arguments). The bot chat shows no tool rows or arguments.
- **Older builds.** A build from before MCP was on by default gives a bot only the servers its grant names, and ignores the switches.

## Use your threads

"Use your threads" is one permission, off by default, that lets a bot work with its owner's threads (`threads` in the grant, `BOT_THREADS_PERMISSION`): read them, start a thread on a model the owner has, message or stop one, and archive or unarchive one. The bot asks for it once, when the owner wants something done with their threads ("start a thread to fix the login page"); the card reads "Alpha wants to use your threads" and "Threads it starts run with full access on this computer.", with the rest in its tooltip. About lists it with the same tooltip and Remove. Not now, Remove, its switch and the repeat rule work as for every other permission.

- **Which tools, and when.** `compileBotThread` turns the permission into the thread tools a turn may use, reusing the thread agents' own tools and limits (`src/mms/run/mcp/appTools/thread.ts`). Reading (`BOT_THREAD_READ_TOOLS`) in every turn but a consult's: `thread_list`, `thread_search`, `thread_read`, `thread_wait`, `queue_list`, `git_status`, `git_diff` and `computer_list`. Acting (`BOT_THREAD_ACT_TOOLS`) is offered in every main turn but a consult's and works only in a turn that may act (`threadsActOf`: a run, a chat turn the owner's message or tapped answer started, the bot's first message, or a chat turn a wake, an unanswered question's default or a thread's outcome notice started, so the bot can carry on a job it was told about); in any other chat turn a call is refused (`BotAuthority.threadsReadOnly`), so a chat's tool list is the same from turn to turn: `thread_create`, `thread_send`, `thread_interrupt`, `thread_archive`, `thread_hide`, `thread_update` (its `hidden` only), `thread_steer`, `thread_fork`, `thread_merge_back`, the queue tools (`queue_enqueue`, and `queue_update` with op `edit`, `remove`, `move` or `send_now`) and `request_answer`. A turn another bot's message started reads only, and is told why in those words (`BOT_THREADS_NOT_OWNER_TEXT`). A chat turn the owner started is different: see The risk that remains, below. The delegation tools are not offered: a bot's work has its own subagents (Subagents of work), held to its grant. The tool list a bot's thread is shown holds the thread tools its turn is offered (`ToolListing.botTurnTools`): none without the permission, with the switch off, or in a consult.
- **Steer, queues, forks and approvals.** Each goes through the same handler and service checks a thread's agent's call does, with the bot's reach (`botThreadReach`) in place of the lineage rules, and names one of the owner's threads (never the bot's own chat: its queue, fork or Git status is not a thread's). A steer (`thread_steer`) and a queued or edited message are labelled as the bot's (`botMessageText`) and run in the thread's own mode, or no wider than the device the owner wrote from, as its messages do (`OrchestratorService.steerRunAsAgent`, `queueCommandAsAgent`); a promotion still waits while the owner has a question or approval open there. A fork (`thread_fork`) starts from a thread the bot may reach and shows in the sidebar; `thread_merge_back` hands a fork's work back to the thread it was forked from when both are in its reach, and the owner's Allow is its answer (`botGrantAnswers`), so nothing asks. `request_answer` answers the questions and approvals of a thread the bot started, whoever started the turn there, with no switch, no wider than the bot's limit narrowed by the thread's own mode (`OrchestratorService.supervisorOf`); its text answers reach the thread labelled as the bot's, and those requests don't ping the owner or show in Needs me. In any other thread it answers approvals only, only while the owner's switch "Agents may answer approvals on other threads" is on, with the rule every agent is held to (never on a turn the owner started, never a plain question), the bot standing for Full access or the device's limit. Never the provider's own checks, never "always". Each is a chip with the thread to open.
- **Git.** A bot has no project of its own, so its `git_status` and `git_diff` name one of the owner's threads (its worktree, else its project folder) or projects (`MousseTool.botInputSchema`, `AppToolHost.gitFolderOf`), and read there with the scoped Git read, not trusting Git metadata in that folder (`writable`).
- **Other computers.** The owner's computers that let agents work there (Settings → Devices) are reached as a thread's agent reaches them: `computer_list`, `thread_list`, `thread_search` and `thread_read` with `computer` or a qualified id, `thread_wait`, `thread_send`, `thread_steer`, `thread_interrupt`, and `thread_create` with `computer`, where the bot names the project here whose repository the thread is for (`fromProjectId`, since its chat has none). That computer decides what this one's agents may do there, as for any agent; a thread there runs in Full access (or the device's limit), narrowed to that computer's limit for this one. What the bot reads there is framed as data, as here. `notify` is for threads here: a bot waits on one there with `thread_wait`.
- **Who it reaches.** The owner's ordinary threads in every project, and the threads it started. The permission is what lets the bot in. One rule decides it for every tool (`botThreadReach`, the registry's scope check `ToolAccessPolicy.botReach`, and each handler), and list and search use the same rule, so a thread they hide is never reachable by its id: never a bot's thread (its own chat or another bot's), the Automation manager's thread or a private thread, and a thread that does not exist is refused in the same words. A subagent below a thread the bot reaches is read and waited on as an agent reads one (`thread_list` with `includeSubagents`, `thread_read`, `thread_wait`), and never messaged, stopped or archived: its parent manages it.
- **What it reads** uses a thread agent's caps and views: `thread_list` (500 at most) and `thread_search` (200) give a handle and one line per thread, and `thread_read` gives one line on the thread and its last reply (`summary`, the default), its messages (`messages`: the newest 10 by default, 200 at most, each cut at 4,096 characters and read on with `textOffset`, 64 KB a page) or its run events (`events`, 500 at most). `thread_wait` gives a run's final text cut at 4,000. Each result is framed as data from the owner's threads, never instructions, like an MCP result, and its text can't end the frame early. When the permission is removed or the switch goes off, a running turn loses the thread tools at once: they are Mousse's own, checked at every call like the browser's, so no turn is stopped for it; the next call is refused, a wait in flight ends within a second with the refusal and nothing of the thread (`BotAuthority.stillHolds`, `BOT_WAIT_CHECK_MS`), and messages still queued are withdrawn (below; `BotEngine.setPermission` for the switch).
- **A thread it starts** (`thread_create`, with a title and a first message) is an ordinary thread under its project, that the owner opens and uses like any other. It starts hidden from the sidebar (below) unless the bot asks to show it. It runs in **Full access**: its agent runs commands and changes files without asking. A turn another device's message started is held to that device's limit instead (see below). It runs on the model the bot names (`instanceId` and `model`, from the models `thread_list` gives a turn that may start one: every entry and model the composer lists on this computer), else the profile's default, never the bot's own. Its launcher is the bot's chat thread (`Thread.createdByThreadId`), and it keeps the bot's name from then (`Thread.startedByBot`), so the app shows "Started by Alpha" above it (`ThreadStartedByBar`), and "Started by Alpha (deleted)" once the bot is deleted. Its transcript says "By Alpha, your bot: started this thread". The bot's chat gets a chip at once, "started thread · Fix the login page", with Open and the first line of what it asked in its tooltip, and the bot is told the mode the thread runs in (`botThreadModeText`). Its own agents are held to the launched threads' level (they read and wait, and never start or message threads) and may start subagents like any thread's.
- **Hidden threads.** A bot's thread starts hidden (`Thread.hidden`): `thread_create` hides it unless the bot passes `hidden: false`, which it does when its owner asked to follow, answer or continue that work in the sidebar; `thread_create`'s description and the chat's instructions say so. A hidden thread is left out of the sidebar's Projects and Threads lists (once archived, Archived lists it). The owner's other computers list it too, marked hidden and named for its bot, with the subagents below it (`MmsListsSource`): there as here, My threads leaves it out, and All and Bot threads list it. A computer that may not reach the bot sees "a bot" in its place. A phone's list leaves it out, with the subagents below it. Nothing else changes: it runs, asks and finishes like any thread, keeps the bot busy while it works, and search, links, its chip and Needs me still reach it. The bot's chat lists it with the threads it started (`BotLaunchedThread.hidden`): its row says "Hidden", opens it, and has Show in sidebar (`threads.setHidden`, which hides only a thread a bot started). Its own "Started by" line says "Hidden" with Show in sidebar too, also once the bot is deleted. It also shows in the sidebar once its owner writes in it: a message or steer from a window (`orchestrator.send`, `orchestrator.steer` from a person's connection) clears `hidden` as it is sent. A message from an agent, a bot (`thread_send`) or a script leaves it hidden. `thread_hide` hides or shows a thread the bot started (`Thread.startedByBot`) later, in a chat turn the owner's message started; the thread says so ("By Alpha, your bot: hid this thread from the sidebar"), its events record `hid_thread` or `unhid_thread`, and the chat gets a chip. Only a bot lists the tool, and an ordinary thread agent's `hidden: true` is refused.
- **A message it sends** (`thread_send`, and a new thread's first message) is labelled as the bot's in what the model reads and in the transcript (`botMessageText`: "Message from your bot "Alpha". The user did not type it; …") and runs in that thread's own mode, as the owner's own message would. It counts as the first agent message after the owner's (`botSenderHops`): work and scheduled runs, and chat turns started by creation, an owner message or tap, a wake, a question or a job may send one under the grant, so the bot is not held to the limit on agent messages in a row, and the thread's own agents count on from there. To a thread that is running a turn it joins that turn, as Steer in the app does (`botJoinRunning`; Mousse finds the run, the bot names none); with `queue: true`, or `mode: plan`, it waits behind that turn instead. When the running turn can't take it (it just ended or has not started, or it runs in a looser mode than the bot's turn allows) it starts or waits for a turn, and the result's `notJoined` says why. A join uses the send's request key and the same two-minute repeat check, so a retry replays whichever happened (a refused join's send gets a key derived from it). It runs as a plan turn in a thread kept in Plan, and is refused while the thread waits for an answer to a question or an approval, steer or not: a message never answers or skips one (only `request_answer` answers an approval, above). A thread the bot started is its family: a note (`intent: "note"`) reaches it while idle too, labelled as from the bot that started it, and is refused like a message when the device the owner wrote from may not run that thread (`device_limit`); any other thread takes a note only into its running turn. Only the owner's own message counts as a reply to a plan (`isPersonMessage`), never an agent's or a bot's. Each message is a chip at once, "messaged · <title>", with Open and the first line it sent in its tooltip. When the permission is removed, the switch goes off or the bot is deleted, its messages still waiting in a queue are withdrawn, and the thread says so in one line (`withdrawBotThreadMessages`). Only threads where one of its messages has a run that has not started are looked at.
- **A Stop.** `thread_interrupt` stops a turn that is simply running, and the thread says the bot stopped it ("By Alpha, your bot: stopped the turn that was running"). It is refused, in the same words as a message, while the thread or one of its subagents waits on an approval or a question: a Stop would close those for the owner.
- **Another device.** A phone or another computer the owner uses can message the bot (`bots.chat.send`), and that chat turn is held to the device's own limit here (Settings, Devices; `BotOwnerTurn.limit`): a thread it starts runs in that mode, not Full access, and a message into a thread that runs wider is refused. The card for this permission can be allowed only on this computer or from a device whose limit is Full access; from any other device Allow is refused with "Allow this on the computer." A device with no limit on record here is held to Accept edits, the default of a device's limit (`DEFAULT_MAX_PERMISSION_MODE`), which is also the most it may run directly (`botDeviceLimitFrom`). A message from a device that continues a turn waiting at a wall writes the limit onto that turn with the message itself, so a restart before the turn continues keeps it. A message from this computer's own window is unchanged.
- **Archive.** `thread_archive` archives a thread whose work is merged or dropped, when the owner asks; `archived: false` unarchives it. It goes through the app's own Archive (`OrchestratorService.archiveThread`, which `threads.archive` uses too), so the thread moves to Archived with its pull request watch ended, exactly as when the owner archives it, and nothing is deleted. It reaches what a Stop reaches (`botThreadReach`: never the bot's own chat or another bot's thread, a private thread, a subagent or the Automation manager's). A thread that has a run working or paused, or a subagent below it that does, is refused with "stop it first with thread_interrupt" (`thread_running`): a bot's archive never ends work by itself. The thread says who did it ("By Alpha, your bot: archived this thread"), its events record an `agent.action` (`archived_thread` or `unarchived_thread`), and the bot's chat gets a chip at once, "archived · <title>" or "unarchived · <title>", with Open. A thread's agent has the same tool under one rule: a turn a person started (never a subagent's) archives its own thread when the turn ends, archives another thread it can reach at once or unarchives it with `archived: false`, and is refused for a thread that is still working; see `docs/run-engine/SPEC.md` §15.1.
- **Limits.** A bot starts and messages as many threads as the work needs: there is no count per chat turn, per run or per day, no cap on how many of its threads work at once, and its messages are never refused as one agent message too many in a row (`botSenderHops`). Its `thread_create` and `thread_send` read a description of their own that says so (`MousseTool.botDescription`, listed for a bot's thread by `ToolRegistry.listForThread`). Queue limits still hold: a thread takes at most 3 waiting messages from it and 10 from all agents, and the same text again within two minutes is refused. A bot's request still names its chat turn (`botRequestPrefix`, checked by `OrchestratorService.assertBotRequestKey`). A limit that is hit is told to the bot in plain words, and it tells its owner.
- **notify.** A message a bot sends opens a job in its ledger (see Work in threads), and the ledger tells the bot when the thread finishes or waits for a person, so the result says `job: { jobId, next }` and no wake is set. Only where the ledger can't keep the job does `notify` set a wake on the thread (`botNotify` in `thread.ts`, through `BotToolHost.wakes`), whose brief names the thread and the first line the bot sent. A wake that can't be set (the thread already idle, a loop) comes back as `notify: { set: false, why }`; the message is sent either way.
- **Where it is held.** The grant compiled for each turn (`compileBotThread`'s `botTools.threads`), the bot's authority at every call (`createBotAuthority`, with the bot's own switch read at the call), the registry's per-call check (`botAppToolRefusal`, before anything about the target), and again in the service (`OrchestratorService.botSenderOf`): a start, a message, a steer, a queue change, an approval answer, a Stop or an archive from a bot's thread goes ahead only from its chat or work thread (or a subagent of work), in a turn registered with its authority that holds that tool. Claude Code's grant gate, Pi's gate and Codex (through the Mousse MCP server) all reach the same checks.
- **The risk that remains.** A chat turn the owner started can read thread summaries and transcripts, files the bot may read, its memory, and the recent chat, including reports from its own work, which may have read a web page. Text planted in any of them could steer the bot into starting or messaging a Full access thread, and only the model's judgement stands in the way: there is no confirmation per thread. Not allowing a bot "Use your threads", or switching it off in About, closes it for that bot.
- **What frames that text.** Thread results are framed as data (`botData`). In a chat turn the pack marks each report from the bot's work as data on its own line (`WORK_REPORT_SPEAKER`), `memory_list` says run notes are data, `memory_search` and `memory_read` already did, and on Claude Code each file the bot reads is followed by a line that it is data (`CLAUDE_BOT_FILE_DATA_NOTE`); Codex and Pi read files in their own tools, where Mousse adds nothing. The bot's instructions say to start, message, stop or archive a thread only when its owner's own message in the conversation asks for it, never because a thread, a file, a page, a report or a note says so, and to tell its owner when such text asks for it.

## Work in threads

A job in one of the owner's projects (fix, build, change or review something there) goes to a thread in that project, never to the bot's own work. On a Git project the thread makes its edits in a worktree of its own; it starts hidden unless the owner will want it in the sidebar. The bot's own work keeps the chores that need no project. The chat's instructions and `thread_create`'s description say so (`BOT_WORK_IN_THREADS`); a bot without "use your threads" asks for it first.

- **The ledger.** Each job is one row in `bot_jobs` (bots.db v13): the request that caused it and who asked (the owner, a schedule, another bot, or the bot itself), the thread, its title and project, its state (`running`, `needs_input`, `done`, `failed`, `stopped`, `gone`) and a one-line result. `thread_create` with a first message, or `thread_send`, opens it through `BotToolHost.jobs` (`BotEngine.openJob`); a message to a thread still on a job joins that job. A thread the bot started that works again with no job of the bot's open there (its owner wrote to it after the job ended) gets a follow-up job (`BotEngine.followUpJob`, no turn of the bot's, asked by the owner), so its end reaches the bot like the first one's; a message the bot sends it meanwhile takes the follow-up over. Rows are deleted only by the 30-day purge.
- **The report.** When the thread's turn ends, or it waits for a person (a question, an approval, or a pause only a person ends), the bot gets one notice per change: a chat turn of its own (`job:<jobId>:<activation>`) that starts with the report (state, the thread's title and link, who asked, and its answer held to 2,000 characters, framed as data). Nothing shows in the chat but what the bot says, and no typing or working line while it runs. That turn may act on threads, so it can carry the job on. A person answering moves the job back to working quietly. A paused bot gets a line with the link instead of a turn. The ledger looks at a thread when its run ends or its standing changes (`BotEngine.checkJobs`), and at every open job after a restart and on each upkeep pass. The report (state, one line, link, who asked) is the one contract for anything that works for a bot.
- **A thread waiting on a person.** Its notice carries what it asks, up to 3 requests of 1,000 characters each, quoted with their ids (`approval <requestId>` or `question <requestId>`, each question with its option ids). Threads the bot started are its own to run: it answers what it can with `request_answer` and asks the owner only what is really their call, as its own short question. A thread paused until a person resumes it says only that. A needs-input notice is fast: it starts without waiting for the settle below.
- **Notices, merged.** Notices are the chat turns no person started: a wake-up (`wake:`), a thread's notice (`job:`) or message (`threadmsg:`), and another bot's message (`botmsg:`). Each is still queued as its own row, but the chat lane picks them in order (`nextChat`): the owner's turn first, then any other turn that isn't a notice, then a batch of notices once it settles, 4 seconds after the newest of its class arrived and never later than 30 seconds after the oldest (`NOTICE_SETTLE_MS`, `NOTICE_SETTLE_MAX_MS`; one timer per bot). Acting notices (wake, job, thread message) merge only with each other, other bots' messages only with each other, since those turns may not act on threads. The first of a batch leads: its turn's input is all of them in order, up to 24,000 characters (`NOTICE_BATCH_MAX_CHARS`; what is left starts the next batch at once), and its first dispatch records the rows it took in (`merged`). Those rows end `cancelled`, with `end_reason` `merged`, only when the leader ends done (`BotStore.moveActivation`); a leader that fails leaves them queued, and they run after it as they were. A restart before the first dispatch takes the batch again. Merged rows never show as stopped: About's runs list and the last outcome skip them.
- **Related jobs.** After the last job notice of a request in a batch comes one line: the titles of that request's other jobs still running or waiting ("Still going for the same request: …"), or that none is. A request is the turn its jobs came from, followed back through notice turns, merged rows and work to the turn that started it (`jobRoot`), so a job opened from a notice turn counts with the request it carries on.
- **The owner writes first.** An owner's message waiting with notices starts first. Their turn takes the acting notices that wait as data, after the message under one heading and without the notices' `reply="if-needed"` (`noticeAsData`); other bots' messages wait for their own turn, and an owner's turn from another device with a narrower limit (`owner.limit`) takes nothing. An owner's message while a notice turn runs steers it once with a fixed line, "Your owner just wrote to you. Wrap this up now; their message is next." (`OWNER_WAITS_STEER`, in memory: a restart drops it), never with the owner's words.
- **In the chat's memory.** The chat turn's pack lists the newest 6 jobs ("Threads you handed work to", with their links) in an epoch's base, and a later turn's update lists only the jobs that changed since (4 at most). Days later the bot still knows which thread did which job without searching.
- **The cap.** A report from the bot's own work is held to the same 2,000 characters in the chat's pack, with the journal row that holds it all (`memory_read`).
- **The sidebar** lists a thread unless it is hidden. While bot threads are listed, a project's menu has Hide bot threads and the Threads tab's menu has Hide all bot threads: each hides the bot threads listed there (`threads.setHidden`, threads of this computer), and a failure shows a toast with Retry.

## Use the profiler

Every bot can read Mousse's own profiler (Settings → Labs → Profiler) without asking: it is no longer a permission (`BOT_DROPPED_PERMISSIONS`). It is not an MCP server, so `mcp_servers` never lists it. A grant an older build approved may still list `profiler`: it loads with the same digest and gives nothing more (`BOT_RETIRED_APP_TOOLS`), and an `permission_ask` for it is answered that it needs no asking, with no card.

- **Which tools, and when.** `compileBotThread` gives the profiler tools to a main turn and a subagent (`botTools.profiler`): work gets every read and sample tool (`BOT_PROFILER_TOOLS`: overview, service breakdown, window breakdown, GPU hints, child processes, sample now and watch); a chat turn gets all but `profiler_watch` (`BOT_PROFILER_CHAT_TOOLS`), which samples for minutes, so the chat stays free and hands a watch to work. A consult gets none. A bot's thread lists only the profiler tools its turn holds (`ToolListing.botTurnTools`, as for the thread tools).
- **Never the heap summary.** `profiler_heap_summary` pauses the service: no bot is offered it, an `permission_ask` for it is refused with no card, and a grant can't hold it (`BOT_APP_TOOLS`).
- **Labs still decides.** Each call is held to Labs → Profiler as for any agent: with the profiler off, agent access off or the tool's own switch off, the tool is not listed and a call gets the profiler's plain refusal, which the bot passes on to its owner.
- **Threads in its reports.** `profiler_service_breakdown` names a thread by id for a bot only when `thread_list` would list it to that bot (`botMayNameThread`): none without "use your threads", and never a private thread, a bot's thread (its own included), a subagent or the Automation manager's. Every other thread counts only in the total, as other profiles always do.
- **What the owner sees.** Its calls roll up into one step under the reply, "checked Mousse's memory and CPU".

## Change how Mousse looks

Every bot has the theme tools `theme_read` and `theme_set` without asking, exactly as a thread's agent has them in Full access: Mousse's look is no longer a permission (`BOT_DROPPED_PERMISSIONS`). A grant an older build approved may still list `themes`: it loads with the same digest and gives nothing more, and an `permission_ask` for it is answered that it needs no asking, with no card.

- **No approval.** A thread's agent is asked before theme CSS or a new wallpaper unless the thread is in Full access, and before any other change unless it may edit. A bot's turn binds in Ask and nobody answers it (`approvals: 'never'`), so the registry asks nobody for a tool a bot holds (`MousseTool.botGrantAnswers`, set on `theme_set` only): a bot has Full access for these two tools. Nothing waits on a person, so nothing hangs.
- **The same checks.** CSS that could load anything from outside Mousse is dropped when the window applies it, and `theme_set` says which rules; colors must be plain colors; a wallpaper is checked and copied by the profile's wallpaper store as any agent's: an absolute path on this computer (the bot's files folder or anywhere else), never a network share or a device path, a PNG, JPEG or WebP within the size limits.
- **Which turns.** `compileBotThread` gives both tools to a main turn, chat and work alike (`botTools.themes`). A consult and a subagent get none (`BOT_SUBAGENT_APP_TOOLS` is an allowlist), and `theme_set` refuses any bot turn but its own (`role` other than `activation`), as it refuses a thread's subagent. A bot's thread lists them only when its turn holds them (`ToolListing.botTurnTools`, as for the thread and profiler tools).
- **What the owner sees.** `theme_read` rolls up into "looked at your themes", `theme_set` into "changed how Mousse looks". Settings → Appearance switches the theme back, and `theme_set { restore: true }` puts back the theme from before agents changed it (the profile keeps it in `appearance/theme-restore.json` until it is restored or the owner picks another theme).

## Schedule work in your threads

Every bot has the scheduled-job tools a thread's agent has without asking (`schedule_list`, `schedule_create`, `schedule_update`, `schedule_pause`, `schedule_run`, `schedule_delete`): a job that runs a turn in one of the owner's threads (`threadId`) or starts a new thread per run in one of their projects (`projectId`, since a bot has no project of its own). It is no longer a permission; a grant that still lists `schedules` loads unchanged and gives nothing more. Something only the bot does at a time stays `bot_schedule_add`.

- **No Allow.** A thread's first job asks the owner Allow / Not now in Automations; a bot's jobs are made without that ask. The profile's limits on agent jobs (how many, how often, how long they live) hold as for any agent.
- **Whose jobs.** A bot sees and changes only the jobs it made, whichever of its turns made them: they are filed under its chat thread (`AppToolHost.botHomeOf`). A job is bound only to a thread the bot may reach (`botThreadReach`).
- **Which turns.** `schedule_list` in every main turn; making, changing, pausing, running and removing a job only in a turn that may act on threads (`threadsActOf`); a chat turn that may not is offered them all the same and refused at the call, with why (`BOT_SCHEDULES_NOT_OWNER_TEXT`). Never a consult or a subagent. Its jobs run in Full access, or no wider than the device the owner wrote from (`scheduledCreatorLimits`).

## Use secrets you give it

Every bot has `secret_request` without asking, `secret_fetch` in its chat and its work, and `secret_run` where it also holds "run commands", as a thread's agent has them. It is no longer a permission; a grant that still lists `secrets` loads unchanged and gives nothing more, and every bot may keep a pasted key (below).

- **Pasting a key.** The desktop bot composer offers “Keep as secret” for recognized credential shapes, not for every possible secret. It recognizes provider-prefixed keys, labelled AWS secret access keys and AWS pairs across CSV, JSON, environment lines and prose, private-key blocks, credential URLs with long, varied token values (including OAuth fragments and signed S3/GCS links) and an Authorization Bearer line. Bare JWTs, arbitrary passwords, attached files (including dropped `.env` files), and text pastes of 32 KB or more that become attachments are not checked. Choose the private card's keep time (24 hours by default); the value goes to the local vault for the bot's home thread under a free, service-specific name. The composer replaces the matched span with “the secret NAME” for review; an AWS pair keeps the secret half and leaves the access key ID visible. Private drafts survive chat switches in window memory only, including text added by applets and memory quotes. A successful save says “Kept as NAME” even if it finished after an edit or while another chat was open. The notice clears on the next edit or Send; remembered copies expire with the keep time or clear on Send. A save that finishes after the window reloads cannot be announced there; the saved secret is still listed in Settings → Secrets. An AWS access key ID alone is public: paste its secret access key too. With temporary credentials (`ASIA…`), the session token stays in the message; it is useless without the secret access key. Send as text keeps unsaved text unchanged; ignoring the offer takes one extra Send. A refused save leaves the key private and explains the error. Phones are unchanged: secrets and this offer are desktop-only.

- **The card.** `secret_request` opens the same private card a thread shows (`SecretRequests`), filed under the bot's chat thread whichever of its turns asked (`botHomeOf`), and the bot's chat shows it above the composer (`BotSecretRequests`). The owner types the secret there, or picks a saved one, never in the chat; the bot gets only its name. A bot's turn answers no approvals, but this ask reaches its owner (`MousseTool.botAsksOwner`), so the call waits for the answer, up to the card's hour, as a thread's does.
- **Bound to one service.** A bot may ask with `for: { service: "openai" }` (also anthropic, github, stripe, notion or huggingface), or `for: { origin: "https://api.example.com" }`. The private card names the service or host and says “read only”.
  - **Where the key goes.** Mousse keeps the value for requests to that origin, in one fixed header, with known services limited to listed API paths. Notion and Anthropic also have fixed version headers (`Notion-Version` and `anthropic-version`).
  - **Custom hosts.** Private IP literals and local host names, including `.home.arpa`, `.lan` and private-address forms of nip.io or sslip.io, are refused. An unknown host has no path limits; its card warns that Mousse can't tell what its reads do.
  - **Saved keys.** A saved secret is offered only for the same binding. Settings → Secrets lists the service, or “bound, service unavailable” when the binding cannot be read, and removes it as usual. A bound secret gets no readable file, and `secret_run` and an MCP server's `${secret:NAME}` settings refuse it.
  - **Service reads.** Changelog entry 30 replaces entry 29's temporary advice to work without a bound key. `secret_fetch` reads the bound service in the chat (a quick call), main work and scheduled turns, with GET and HEAD only. Hand-started runs, subagents and consults cannot call it. Admitted reads appear in the work's steps with the service name.
  - **Refusals.** An unbound key, paths outside the binding, ambiguous or encoded path separators, semicolon path parameters, Unicode dot and slash lookalikes, and invisible format characters are refused. Headers cannot contain secret-shaped values or override authentication or fixed version headers. Authorization, binding, method, path, query and header checks happen before counting: a refused validation uses no allowance and reveals no other bot's service. A full URL naming another host explains the bound host and that another host needs its own saved secret and binding.
  - **Responses.** Requests connect to a checked public address and follow no redirects. Responses are masked and framed as data, including a redirect's Location. Service reads default to accepting JSON and plain text.
  - **Response files.** Text up to 64 KiB stays inline; larger or binary responses are saved with masked values under the run folder's `fetches/`. Only the newest 20 response files recorded by this daemon are kept; pre-existing or unrelated files are never pruned. These files last only for that work; the tool tells the bot to save any needed result before it ends.
  - **File safety.** Mousse checks the fetch folder before sending; an unsafe folder then uses no allowance. Every request handed to the network counts, including a later save refusal or transport failure. A reset or unknown transport failure says the request may have reached the service and counts toward the limit. Hourly and daily cap refusals say to try again later. Files are created exclusively without following links, and Mousse verifies the open file before writing any bytes; pruning uses the checked directory and only recorded names. A save failure after sending says the request was sent and the response could not be saved on this computer.
  - **Limits.** The timeout is 30 seconds and the response limit is 5 MiB. The hourly allowance is shared across all bots using the same secret. Over 20 reads per secret in a rolling hour or 100 reads per bot in a rolling day is refused, without a card.
  - **History and restart.** Each call records an action, keeping header names without their values. After a restart, interrupted reads are marked failed and are not replayed. “May change things” is deferred to the [tool plan's request service](plans/tool-api.md): asks first covers only the bot's own MCP calls.
- **Keeping the binding.** `secrets/bindings.json` stores known services by id and custom origins with their fixed header. Known services use the current table's paths and version headers. A separate per-name guard keeps a bound key unusable if its binding is missing or unreadable; malformed entries do not prevent Settings from listing other secrets. Unreadable binding files are left unchanged when another binding is saved; the private card says “Bound, service unavailable” and keeps the request open. Deleting a secret on this build removes its value and guard, and its binding entry when the file is readable. An unreadable binding file stays unchanged; expiry and Settings removal still finish, while new saves wait until bindings can be read. A leftover binding reserves its name on the private card. Saving an ordinary key under that name clears the old binding and guard only when the previous value is absent; an existing bound value cannot be replaced this way. Older builds ignore bindings while they run and can pass a bound key to commands or make a readable copy. They do not rewrite the binding file, so the binding holds again on the new build, which removes stale readable copies.
- **What the binding cannot stop.** Commands that no sandbox holds (background commands, `secret_run` outside Linux with bubblewrap, and a runtime's commands as listed in “Where commands aren't held”) run as the owner's account and can read the secret store itself. A binding stops the bot from handing the value to a command. It does not stop a command that reads the store's file.
- **The command.** `secret_run` runs from the bot's files folder with the secret as an environment variable or a private file, its output masked, and needs "run commands" too: the chat, which hands commands to work, is never offered it. Nobody is asked (`botGrantAnswers`).
- **How it runs.** A bot's secret command runs as its background commands do (`watch_start`, Background commands), never with the service's environment (`runWithSecrets`'s `contain`, `botSecretCommand.ts`). Mousse can't run it inside the runtime's own sandbox. It gets the locked environment (`lockedEnv`, as a Pi bot's commands run) plus only the secrets the call names. Where Mousse has a sandbox for it, Linux with bubblewrap, it runs there: the system's own folders read-only, the bot's files and scratch folders writable, a private `/tmp`, the private folder of its secret files read-only, no network and its own process namespace. Elsewhere (Windows, macOS, Linux without bubblewrap) it runs in a shell (`sh`; `cmd` on Windows) from the bot's files folder, in its own process group where there is one, and reaches what the owner's account can, as "Where commands aren't held" says. It needs "run commands", so it never reaches more than the owner already allowed that bot's commands.
- **Masking limits.** Responses, saved files and history mask the whole value, its standard and URL-safe base64 forms (padded or unpadded), hexadecimal, and percent-encoded forms (including optional escapes of unreserved characters, fully encoded UTF-8 bytes and mixed-case percent escapes). JSON slash and Unicode escapes are covered too, including escaped slashes at outer layers, mixed literal/escaped characters and two enclosing JSON strings. A service can still transform a value beyond these forms: base64 of a larger string such as `user:key`, UTF-16 bytes, HTML entities, compressed data, mixed-case hexadecimal encodings, combinations or repeats of encodings, more JSON nesting, splitting, truncation or changed letter case are known limits. Masking is not a general decoder.
- **Masking on every thread of the bot.** A secret given to the bot is masked on all of its threads, not only its chat: the service masks a thread's text with the secrets of the bot's chat thread too (`OrchestratorService.threadSecretMasker`, `BotThreads.homeOf`). So its work, subagents and consults keep it masked in their messages, run results, native history and replies.
- **Which turns.** Main turns, chat and work; never a consult or a subagent (a thread's subagent has neither).

## Add quick actions

Every bot has `create_quick_action` without asking: a button in the owner's Actions list that sends a message or runs a command when they press it. A thread's agent asks for each one; a bot adds it without asking (`preApproved`), with the same checks. Main turns only. It is no longer a permission; a grant that still lists `quick_actions` loads unchanged and gives nothing more.

## Its task list

`task_create`, `task_list` and `task_update` keep a checklist on the turn's own thread, as a thread's agent does. They act on nothing else, so like memory they are always on and never grantable, in main turns and subagents (`BOT_TASK_TOOLS`), never a consult.

## What a bot does differently from a thread

Everything a thread's agent can do, a bot can too, through the permissions above. A few things go another way, on purpose:

- **The chat hands long work on.** A chat turn hands commands, the web, the browser and MCP tools to work (`BOT_WORK_ONLY_TOOLS`, `frontDeskManifest`), so the chat stays free to talk; its work holds them all. The owner asks in the chat, and the work does it.
- **No heap snapshot.** `profiler_heap_summary` pauses the service, so no bot holds it; the other profiler tools give its numbers.
- **No goal.** A thread's `/goal` is the owner's, and `goal_update` reports on it; a bot's thread never has one (`ThreadGoals.requireThread`). A bot keeps going on a job through its work, which runs until it is done and waits and wakes on its own (Work that waits, Wakes).
- **Subagents of its own.** A bot's work splits a job with `subagent_*` rather than `delegate_task`; its subagents hold what a thread's subagent may use, within its grant (Subagents of work).

## What each kind of turn may do

What started a turn (its provenance, `bot_activations.provenance`) decides a few of its tools. One table holds every difference (`BOT_TURN_KINDS` in `src/mms/bots/activation/turnKinds.ts`), and every rule reads it: `asksOwner`, `ownerChatTurn`, `memoryLaneOf`, `threadsActOf`, the work-wait rules and the tools' own checks. A chat turn is offered the same tools whatever started it, so its prompt and warm process stay the same; a cell that says no is refused when the tool is called (`BotAuthority.turnRefusals`). A run is compiled with only what its row allows.

|---|---|---|---|---|---|---|---|---|---|---|---|
| The owner's message (chat) | chat | yes | act | yes | yes | yes | yes | no | yes | yes | no |
| A tapped answer (chat) | chat | yes | act | yes | yes | yes | yes | no | yes | yes | no |
| The first message, a wake, a question's default, a thread's notice or message (chat) | run | no | act | yes | yes | no | yes | no | yes | yes | no |
| Another bot's message, Resume of one (chat) | run | no | read | yes | yes | no | yes | no | yes | yes | no |
| A held call's result (chat) | run | no | as the turn that held it | yes | yes | no | yes | no | yes | yes | no |
| Work (run) | run | no | act | yes, detached | yes | no | yes | yes | yes | no | yes |
| A schedule (run) | run | no | act | yes, detached | yes | no | yes | yes | yes | no | yes |

Why each "no" stays:

- **Memory and `say`.** Only the owner's message or tap says what the bot keeps about them, or a fixed line a schedule will say in their name.
- **`request_answer`.** An answer passed on to work must be the owner's: their message, or the answer they tapped.
- **Threads, read only.** Another bot's message is text the owner never saw; it must not steer their threads.
- **`work_wait` in the chat.** The chat has one slot, and nothing it starts may hold it while it waits: it sets a `wake`.
- **`work_start` in a run.** Work does its job itself, splitting it among subagents; it hands nothing on. A run's reminder therefore says its text and carries no work.
- **Subagents in the chat.** The chat hands long jobs to work.
- **A run started by hand.** Nobody asked it to ask, wait or message other bots, and nobody waits on its report.
- **A start no build names.** A row a newer build wrote, or a provenance on the wrong lane: it may only read and answer, until a build names it in the table.

Consults and subagents compile their own narrowed tools and never read the table. A held call's result (`action_result`) acts on the owner's threads only as far as the chat turn that held the call could, and to its device's limit: its trigger carries that turn's `threadsReadOnly` and `owner.limit` (`threadsActOf`, `ownerTurn`).

- **A cell is not a permission.** `watch_start` also needs "run commands" twice: held by the bot (it outlives the turn, and every one stops when the bot loses it) and by the turn itself, its revision inside the grant narrowed by its thread (`turnHoldsCommands`). A run whose thread is narrowed without commands starts no background command.
- **A removed schedule.** A scheduled run whose schedule the owner removed while it ran may not ask or wait (`scheduleGone`): a parked run of a removed schedule is cancelled, so nothing could carry it on. It ends with its report.
- **How a refusal reads.** A chat turn's cell that says no is refused by the tool registry with `not_granted`, `request_answer`'s owner-only rule too.

## What holds a bot

A bot may do only what its own grant holds, less what the owner has switched off for it in About (see Switching a bot's permissions off). Nothing else widens or caps it: there is no setting per computer. "What bots may do here", three switches in Settings → Agents that once capped every bot on a computer, was removed. An installation's `mousse.conf` that still holds its top-level `bots` key keeps it as stored, like other leftover keys (an older build still reads it), and nothing reads it; a `settings.set` that still names `bots` saves the rest of the update and ignores it.

- **A thread is not held by the bot's other permissions.** A thread a bot starts runs in Full access, and a message it sends runs in the thread's own mode, so with "use your threads" a bot can run commands and reach files through a thread even without "run commands". Leave "use your threads" off, or switch it off in About, for a bot that must not run commands.
- **Pictures need no permission switch.** Making a picture (`make_image`, see Model and depth → Images) runs no command, reads no file and opens no page: Mousse calls the picked model and writes the result into the bot's files folder only. It is held by the Images row.
- **The browser.** The bot's browser opens only http(s) pages (`browserNavigationUrl`, at the policy and in the browser worker), so it can't open a `file://` page, and its uploads are refused (its broker has no resolver for local files).
- **Space bots** (`src/mms/bots/space`) run nothing today (`NativeBotRuntime.supports` is false for every profile): no model, no commands, no browser. Their planned `reader` profile reads an owner-chosen project; it must be held to the bot's own folders before it is turned on.

## Schedules

A bot's schedule is an **automation whose Who is the bot**: an ordinary job in the shared scheduled-job store (`ScheduledJob.bot`), claimed by the one `ScheduledJobService`. It is not on the definition, so a schedule changes no revision and needs no approval. Manage, on the Automations page, lists it with the person's other automations, and its Edit details changes When, Do, the name and Tell me; Who stays the bot, and its May is the bot's grant. Its runs are in the Automations inbox like any automation's, and its Needs you items are assigned to the bot (folded under Assigned to bots). The bot's About lists the same records.

A prompt schedule can take `onlyIfChanged: { url, contains? }` in `bot_schedule_add`. Mousse checks that public web page before each occurrence without a model call. The first check records a baseline; unchanged text leaves no activation, inbox run, last-run time or skipped reason. A change starts one run with the whole compared text in `page-change.txt` in that run's folder, framed as untrusted data. `contains` compares a 4,000-character window around its first case-insensitive match; missing text compares as empty, so appearing and disappearing both count. Fixed lines (`say`) cannot use it.

About names the page; Automations keeps its usual time wording, for example “Every 15 min · when example.com changes”. Six unreadable checks in a row, or a day of failures, post one report and one failed run: “I can't read example.com any more: it returned HTTP 403.” A redirect reports “I can't read example.com any more: it moved to example.org.” Update the schedule's address in that case. A successful check quietly clears the streak. Requests follow no redirects, accept only public resolved addresses and stop after 15 seconds or 2 MiB. IPv4-mapped, NAT64 and transition IPv6 addresses are refused. Editing starts a new baseline; a fetch interrupted by restart is retried.

The setting, check state and fetched text stay in `bot_memory_state` in the profile's Mousse-owned data, outside the bot's writable folders. Only a change writes a run file, without following symlinks; the file is removed when the run ends. Removing or ending the schedule removes its watch state; a running run keeps its change file until it ends. Forgetting history keeps page watches, just like other automation settings. Orphan cleanup runs at startup only and leaves watches alone if the job list cannot be read. The saved prompt includes the parsed watch URL and optional matching text, visible as Do in Automations; an older build runs that prompt every time, spending more model runs without losing the watch.

- The bot keeps them with `bot_schedule_add`, `bot_schedule_remove` and `bot_schedule_list` (the job scheduler's agent tools own the `schedule_*` names, and never see a bot's jobs). `bots.schedules.add` and `bots.schedules.remove` are the owner's. All of them go through `BotScheduleBook` (`src/mms/scheduled/botJobs.ts`): at most once a minute (and at most 1,000 per bot, `MAX_BOT_SCHEDULES`, a ceiling only a runaway reaches), on an interval or a cron expression. Each add shows its label as a chip ("every weekday · 09:00").
- Cron follows this computer's time zone, as for a person's automations. Times a clock change skips are not run; Edit details' "(why?)" lists them. Every cron schedule skips the second pass of a repeated hour.
- **An end.** `bot_schedule_add` takes optional `until`, a future local date (`2026-11-21`, through that day) or date and time (`2026-11-21T18:00`) on this computer. Unreadable dates and past times are refused with what to fix. The shared job's `expiresAt` ends it: no later occurrence starts, About no longer lists it, and one quiet Mousse line says “‘Inbox check’ ended, as planned.” The automation stays in Automations with “Ended, as planned.” Its card and About append “ · until Fri 21 Nov”.
- **Who asked for a fixed line.** Every newly added `say` records `ownerAsked: true`: only an owner-started turn can add it, and an owner can edit its words on Automations. An older writer may drop the ownership flag alone. An intact `say` with a missing flag is read as owner-set and the repaired flag is kept on the next save, so it continues without losing a reminder or running a model. An explicit false is preserved instead: the words stay saved, the line is not said, and the schedule pauses with an explanation to set its words again in Automations and Resume, or use a prompt. Restoring both `say` and `ownerAsked` uses the same kept-field rule: unchanged Do restores both; a newer Do keeps its prompt and discards the stale fixed words while preserving who originally added that schedule.
- **Expiry and self-completion.** At `until`, queued or waiting scheduled runs are withdrawn quietly, with existing asks withdrawn. An executing run may finish its report, under the schedule's Tell me setting; a later wall ends with that report and no new card. Expiry says “ended, as planned”, never “Stopped”. If `schedule_done` wins first, its run keeps going to its report (including through a wall), and only its “Stopped” line appears, even if shared-store removal must retry past the date. Fixed lines have no run and cannot call `schedule_done`: they keep saying the line until their date or until removed, and always notify like reminders. A completed run's Tell me fallback does not apply to them.
- **A fixed line.** Give `say` instead of `prompt` for words that only need saying, up to 500 characters with no hidden or direction-changing characters. Each occurrence posts those words as the bot, without a thread, activation or model call, even when every model is at its usage limit. Owner and failure pauses still stop it, as does deleting the bot. It counts, lists, pauses and removes like any schedule. The card and About read “Says “Take your pills” · every day 08:00”, with the end appended when given. A line over two minutes late starts with “(For 08:00) ”, as a reminder does; the same half-gap downtime rule below skips stale lines. The last occurrence key for each schedule and its chat row commit together, so a repeated hand-over says nothing again. `bot.say` keeps the words and `prompt` keeps “Say exactly: …” for older builds. Editing a `Say exactly: …` Do keeps it as a fixed line; changing Do to other instructions makes it a prompt that runs. Said lines always notify, like reminders the owner set; their Tell me row says “Always, like a reminder”. Only turns the owner’s message or tap started can add `say`; other turns use `prompt`.
- **Ending a schedule.** A scheduled run can call `schedule_done({ why })` when what its schedule was waiting for has happened or can no longer happen. It ends only the schedule on that run's activation; no argument can name another one. The run continues through turn limits, restarts, retries and walls to its report, and Mousse then adds one quiet line, “Stopped ‘Vacuum price check’.”, even when the report is quiet. If the run fails or is stopped, its end still posts the line once. The reason is 1 to 200 characters, kept on the run for its journal; it is never shown as an instruction or used for the line. Repeating the call is harmless. Chat, manual runs, owner work, consults and subagents cannot use it. It is always available to scheduled runs and is never a permission. A schedule with an end condition states that condition in its prompt.
- **Removal stops waiting work.** Removing a schedule from About, Automations or the bot's chat, or ending it from its own run with `schedule_done`, cancels its queued, paused, parked and wall-waiting runs, except the run whose own `schedule_done` ended it, with `schedule_removed`, closes their asks and withdraws waiting questions. They start no new dispatch, post no error, count as cancelled rather than failed, and do not pause the bot. A run already executing can continue to its report. If it then reaches a permission or budget wall, it ends with what it had so far as its report and offers no card. The run whose own `schedule_done` ended the schedule is preserved even while waiting at a wall. Cancelled waiting runs release their browser tabs and scratch folders and settle in the Automations inbox without a failure item; deleted bots’ scheduled runs settle quietly too. Deleting a bot keeps its existing rule: all its work, including queued and running scheduled work, is cancelled. The shared job is removed first; cancellation is atomic inside `bots.db`, and startup repairs an interruption between the stores. For `schedule_done`, the completion intent is saved on the run before shared-store removal, so a retry, upkeep or startup can finish cleanup. A saved completion intent refuses further occurrences even if the shared store cannot remove the job, and cleanup failure never holds back startup or the report. Startup also carries on with activation repair, unfinished creations and due reminders if the scheduler cannot be read, and retries the removal check during upkeep. Pending removal retries are kept in memory after the startup read; a failing schedule warns once per session.
- A job's id is `<botId>--<scheduleId>`; the schedule id is the one the bot and its chat know.
- Each due occurrence is handed to `BotEngine.runScheduledOccurrence`, which inserts a run activation keyed `sched:<botId>:<scheduleId>:<occurrenceKey>` on the claim’s original occurrence (so a repeated hand-over inserts nothing, even when a later scheduled time has arrived). It is skipped, with the reason on the job (`botSkip`), while the bot is paused, while every model is at its usage limit, or while the same schedule's previous run is still queued (`previous_run_still_queued`), runs (`previous_run_still_running`), waits at a wall or for its question's answer (`bot_waiting_for_owner`), waits for its time or event (`previous_run_waiting`) or waits for the internet (`waiting_for_internet`): a waiting run never expires, so a schedule keeps at most one. Other schedules' runs and the owner's work never skip it: they run beside it. Missed occurrences collapse into one. A new or edited time starts from now and never runs a backlog. Nothing starts before the bot startup pass.
- **After the computer was off or asleep.** Missed occurrences collapse into at most one run, for the latest scheduled time at or before now. It runs only while now is closer to that time than to the next scheduled time; at the midpoint or later it is skipped. A daily 09:00 briefing opened at 15:00 runs; opened at 22:00 it waits for tomorrow. After Friday evening through Monday morning off, Monday’s 09:00 briefing runs at 09:30 and says two runs were skipped. The latest occurrence is found from a short window near now, so a year off never walks a year of minute ticks. The detected downtime is kept beside the scheduler heartbeat, so a service restart before bots are ready keeps the same rule. The automation keeps the reason, for example "Missed Tue 09:00 (computer off)", without counting a failure or pausing the schedule. A busy scheduler's delay alone never skips a run.
- A caught-up run keeps its due time and the missed count on its schedule trigger and is told "This run was due at 08:00; this computer was off or asleep, and 3 runs were skipped." The count of skipped runs excludes the occurrence being run; zero is left out and one says "1 run was skipped". When the missed count reaches its limit of 1,000, it says "over 999 runs were skipped". A due time on another local day names the day too, such as "Mon 09:00". A report posted more than 15 minutes after its due time starts with "(Due 09:00, this computer was off or asleep) ". Quiet runs still post nothing.
- After each tick, `BotEngine.maintain` ends usage-limit pauses past their reset, starts what waits in a free lane, and runs the daily purge of deleted bots.
- **No telling setting.** A bot has no Tells you level, no can-wake exception and no tool to set them: it messages its owner when it judges it should, and a turn no person started may end with `[SILENT]`. A wish about how or when to be told is an owner memory entry like any other. There are no quiet hours either: a `notifications.quietHours` value an earlier build stored is ignored. Earlier builds kept the bot's level and can-wake choice in `bot_registry.tell_json` and one automation's exception in its job's `bot.canWakeMe`; both are ignored now, and the jobs file drops `canWakeMe` on its next save.
- **Tell me** on an automation applies to its run reports: Needs you, Worth a look (the default), FYI too or Every run sets the lowest level that notifies. A run without a reported level counts as Worth a look. A run reports its level with `run_report`, as any automation run does; a done run whose level is below the automation's Tell me posts its report as later (the legacy `bots.message` also carries `quiet`). Failures still notify.
- **Nothing new.** A scheduled run that reports `quiet` with `run_report`, or whose last message is `[SILENT]` (`isSilentOutput`), posts no report: the chat shows nothing and nothing notifies (`postReply`); the run and its line stay in Automations. The engine reads the level through `runLevel` (`AutomationRuns.levelOfActivation`). An open ask or a card it made still shows, without the marker. Work the owner asked for and chat replies are posted as written.
- **Quiet wake-ups.** A chat turn no person started or waits on (a wake-up, a thread's notice, another bot's message), and work such a turn started, posts nothing when its reply is `[SILENT]` (`unattendedChatTurn`, `postReply`): no message and no notification. The marker counts only as a line of its own; a reply that says more posts the rest without it (`withoutSilentMarker`), so a real report is never swallowed. Silence is the default: the chat's instructions (`reply="if-needed"`) tell it to reply once in its own words, with links, when a result needs the owner or changes the plan, or exactly `[SILENT]`; work it started from such a turn ends with one short line or `[SILENT]`. A turn the owner started, and a question's default answer, always post.
- **Out of sight.** A wake-up, a thread's notice or message, or another bot's message never shows in the chat, and while the bot works on one the chat shows no typing, working line or streaming words (`unattendedChatTurn`); the Bots list doesn't show it working either. Only what the bot then says posts, as any reply. Lines older versions posted for these events (`bm_wake_…`) are left out of the chat, the Bots list preview and the unread count (`BotStore`'s `SHOWN_MESSAGE`).
- **"No response requested."** Claude Code writes this line when it resumes a session a steer cut. It never reaches the chat: the provider drops a result that only repeats a line Claude Code made up (`TurnFrames.resultText`), and the engine strips it, as a whole paragraph anywhere in a reply of either lane (`withoutRuntimePlaceholder`). The provider also says when a one-shot turn restarted with a steer ended with no words of the model's after it (`TurnResult.steerUnanswered`, carried to `BotTurnDispatcher.settle` as `unanswered`). An owner's chat turn cut that way, or whose reply holds the placeholder, never posts what it had: it holds it back and goes on once to answer their messages (`unanswered` continuation). A chat turn that read the owner's messages as it answered waits for its final words before anything is posted, so a cut seen late is still caught. Cut off again, it posts what it held back and what it had, with a line asking the owner to send their message again (`UNANSWERED_REPLY`).
- **Where I left off.** A scheduled run can pass `leftOff` to `run_report`: at most 600 characters saying what it checked up to and what is pending. The note is held until the run ends done, then replaces that schedule's note in bot memory, including a quiet report that posts nothing. A failure or stop keeps the previous note. The tool result says whether the note is pending or why it cannot be kept. Only that schedule's next runs get the note, after their reports, with whitespace collapsed and fixed data markers, marked as the bot's own data rather than instructions. A `[SILENT]` end keeps the previous note. In chat, `bot_schedule_list` returns screened notes marked as unattended data; runs get schedule details without notes. Forget clears a note holding a long enough match of forgotten words or citing a redacted journal row; removing the schedule removes its note.
- **No step for the owner.** A schedule the bot adds is on at once. The chat turn that added it shows it as an automation card on its reply (`BotAutomationCard`, made by Mousse, never by `show_card`, and not counted among the bot's three cards): its name and schedule, a click opens it in Automations, and Pause (Resume once paused) acts on its job. The card reads whether it is paused, or removed, from the bot's runs (`BotRunItem.jobId`, `paused`). Its plain copy is "Automation: <name> · <schedule>"; no chip repeats it.
- Turning one off in Manage pauses that schedule only; the bot's own Pause stops all its schedules.
- In a profile where bots could not be opened, a bot's schedule is paused once with that reason ("Bots could not be opened in this profile…"; a deleted bot's with "Its bot was deleted."). The next start that opens bots resumes the schedules paused for that reason only.
- Schedules saved by earlier builds in `bots.db` (`bot_schedules`) are moved once into the shared store at profile open (`migrateBotSchedules`); see "Moving schedules".

### Moving schedules

Earlier builds kept schedules in `bots.db` (`bot_schedules`, with their next runs in `bot_schedule_state`) and ticked them with a scheduler of their own. At profile open, before anything ticks, `migrateBotSchedules` (`src/mms/scheduled/botScheduleMigration.ts`) moves them once:

- Each schedule that is not removed becomes the job `<botId>--<scheduleId>` with its prompt, who added it, when it was made, and the next run the old scheduler had (a time edited since its last tick starts from now). A next run already due runs once, as it would have before.
- `bots.db` v5 adds `migrated_at` and `migrated_job_id` to `bot_schedules`; each row is marked with its job after the job is saved. Rows are never deleted, and opening a v4 database first writes the copy `bots.db.pre-v5`.
- It is idempotent: a job that is there already is only marked, so a move stopped part-way is finished at the next open and never makes a job twice. A moved schedule removed later is never moved back.
- `unmigrateBotSchedules` undoes it in code (the jobs go, the marks are cleared); no command runs it. Edits made after the move are not copied back, and schedules added after the move have no row, so they are not brought back.
- A bot's job names a thread that does not exist (`bot-schedule:<botId>`). A build from before the move, which ignores the `bot` field (and cannot open a v5 `bots.db`), finds that thread gone and pauses the job with "Its thread was deleted" instead of running the bot's prompt without the bot. To go back to such a build, restore `bots.db.pre-v5`.
- **Coming back from an older build.** An older build's first save of the jobs drops every field it does not know: `bot`, `draft`, `keys`, `tellMe`, `agent` and `cliName`. This build keeps a copy of those fields in `scheduled/jobs-kept.json`, a file older builds never write, and puts them back at profile open (`ScheduledJobStore.restoreDroppedFields`) on each job that has none of them; missing keys inside a surviving `bot` field are merged back too (`say` and `ownerAsked`); `say` is restored only if Do still matches the kept “Say exactly: …” prompt, so an older build’s edit wins; a bot's job goes back to its guard thread, and one paused with "Its thread was deleted" runs again; a draft is a draft again, turned off, even if that build turned it on (the scheduler never starts a draft). `migrateBotSchedules` also repairs from `bots.db`: a moved job without its bot gets it back, and a schedule the older build removed (after `bots.db.pre-v5` was restored) is removed from the shared store. What the older build changed meanwhile stays; a job it added has no copy.

## No internet

A bot activation (chat lane or run lane) waits when the internet is gone, instead of failing.

- **The check** (`src/mms/bots/activation/connectivity.ts`, the host's `connectivity`): a DNS lookup and a TCP connection to port 443 of the provider's API host (Claude Code `api.anthropic.com`, Codex `chatgpt.com`, a known Pi provider's host) and of two well-known hosts; any one that answers is online. It never calls a model API. A Pi provider on this computer (Ollama, LM Studio) is never checked. Results are reused for 5 seconds.
- **When.** Before each main dispatch is sent (`sendDispatch`); a failed check there is confirmed by one fresh round (no reused result) before the activation waits, and when both fail the log names the activation and how each host's probe ended (`ok`, `timeout`, an error code). While a dispatch runs, every 20 seconds once it has made no call for a minute; two failed checks in a row end it. At its deadline, when it made no call for a minute. And when its run fails on a connection error (`[provider_unavailable]`, ENOTFOUND and the like; `isConnectionFailure`); with the internet there, that is the provider's own failure and ends the run as before.
- **While it waits** the activation stays `running` with `end_reason` `waiting_for_internet` (no new column, so older builds still read `bots.db`), and remains active. Its chat gets one notice, "Waiting for internet. I'll carry on when it's back." (`bm_<activationId>_offline`, at most one per activation), and no error row. The summary's `stateText` is "Waiting for internet" (sidebar row, chat header and status line, `waiting: 'internet'`) while every running activation of the bot waits. A dispatch ended for the internet is charged only up to its last call. Waiting is never a failure, never counts toward the failure streak and never raises an ask.
- **When it is back** (checked after 15 s, then 30 s, then every minute): a dispatch that was never sent is sent; one that ended is continued on the same thread with "The internet connection dropped while you were working; it is back now. Continue." (`continueWith`, `network`), as a restart continuation is, without using the automatic restart allowance. Unknown calls still pause it first.
- **Restarts.** A waiting activation is found by the startup pass: a dispatch never sent is sent again through the same check; one that ended waits again and continues once the internet is back.

## Model and depth

A bot's models are **rows** (#673, `src/shared/bots/personal/modelSlots.ts`): **Talk** runs every chat turn, and **Light work**, **Medium work** and **Hard work** run the run lane by the work's level. Each row is a **pick** the owner made: a provider entry, one of its models and its reasoning level (absent is the model's default). Mousse never chooses a model for a bot made with picks. No client payload carries a model or an instance id, except a Sign in button's instance id and the Runs on methods (`bots.model.*`).

- **New bot.** Runs on, New bot's third step, shows the Computer row, then Talk and Work (Light, Medium and Hard work under Advanced). Create bot stays off until every row holds a pick. The first bot's rows start empty ("Pick a model"); a later bot's start from the owner's newest bot whose rows are all picks (`bots.model.choices`' `last`, `BotEngine.lastPicks`), each kept only while it is offered now. `bots.create` takes all four rows (`slots`) and refuses any not offered now (`model_unavailable`, which returns New bot to Runs on); the bot names itself on its Talk pick.
- **Stored.** The definition stays format 2. While any row is a pick on an entry, `main.slots` holds the rows and `main.model` is a mirror older builds run every turn on: `{mode: 'named', model, depth}`, the model of Talk's pick (else Medium work's) followed by one space (`mirrorOf`). Older builds trim a name before matching it, so they run the mirror as that model, and trim every name they write, so they never write the space: once an older build rewrites `main.model` (`use_model`, its single picker), the mirror no longer matches and the rows are dropped for good (`slotsOf`), even if that build later writes the same model again; `main.model` is then read as every row. A change of depth keeps the mirror and the rows. Rows a later build adds are ignored and kept (`modelSlotsProblem` refuses only a known row that is malformed). No `bots.db` change.
- **A pick remembers its sign-in.** Each pick also stores the entry's kind of sign-in (`credential`: subscription, API key, ambient) and the signed-in account's id (`account`, the gateway's salted hash, never a secret) when the entry tells them, written by the daemon from `BotModelChooser.pickable`, never taken from a client. Entry ids come from the display name, so an entry removed and added again under the same name gets the same id, and switching an entry's sign-in to an API key keeps it: a pick whose entry now signs in another way or to another account can't run (`sign_in_changed`, `account_changed`) until the owner picks again, which saves what the entry has now. Where the entry can't tell (Pi has no account id), nothing is compared.
- **Which row a turn takes** (`turnModelOf`). A chat turn takes Talk. A run takes the row of its level: `set_depth` `now` in that run, else the level its work names (`work_start`'s `level`, kept on the trigger), else the bot's **standing level**, `main.model.depth` (`set_depth` `always`; medium, which is `normal`, unless changed). Scheduled runs and reminder work name no level. Light, medium and hard are the depths quick, normal and deep. An activation's own pick (`use_model` `now`, an automation's model by hand) replaces its row. A pick keeps its model and reasoning level at any depth.
- **The level of a job.** The bot gives each piece of work a level (`BOT_CHAT_INSTRUCTIONS`): light for a quick lookup or a small routine job, medium for most work, hard for research, a long or difficult problem, or when the owner asks it to think harder. "Think harder" or "be quicker" from now on is `set_depth` `always`.
- **One job on a model the owner names** (#1067). The owner can say in the chat which model one piece of work should run on ("do this one with Opus", "use the cheap one on OpenRouter for this"). The bot's rows stay as they are; only that work runs on it.
  - *What the bot sees.* `model_list` (chat only) lists the owner's provider entries that a bot's work can run on, each with its models (id, name as the picker shows it, a few other names) and their reasoning levels, from the same choices as Runs on (`BotModelChooser.workChoices`, which reads them as `pickable` does). It also lists the owner's other entries under `cantRunWork`, each with why in plain words: turned off, signed out, not ready, or a runtime that can't hold a bot to its permissions (only Claude Code, Codex and Pi entries can). And it names the bot's usual Work models. The bot matches what the owner said against this list, and asks when it can't tell.
  - *Starting it.* `work_start` takes `model: { instanceId, model, effort? }`. It must be one of those choices now, and `effort` one of that model's levels; otherwise nothing starts and the bot gets a plain reason to pass on ("Work can't run on Cursor: it can't keep to my permissions."). Nothing else is ever chosen in its place. Left out, work runs on its level's row as before.
  - *Where the pin lives.* The pick, with the entry's sign-in now, is the work activation's own pick (`bot_activations.model_override_json`, `BotModelOverride`), written in the same transaction that inserts the activation, as an automation's own pick is. Every dispatch of that activation reads it (`turnModelOf`) and checks it again before it is sent, so a restart, a continuation after an ask or more room, a note that reaches the work, and a compaction (which happens inside the work's own turn) all keep it. If it can't run any more, the work ends with the usual line ("I can't use Cheap Model on OpenRouter: it's turned off.") and never runs on a row instead. `set_depth` `now` inside that work keeps it. Its rows are untouched, so later work and the chat run on them.
  - *When it may be used.* Only when work is started from a chat turn that the owner's own message started (`ownerWords`): never from a bot's first greeting, a reminder, a schedule or inside work (those can't call `work_start`, or have no owner message). Text the bot read somewhere can't move work to another, possibly costlier, model on its own. The bot's instructions say it must not pick a model for work itself.
  - *What the owner sees.* When the model is not the bot's usual one for that level, the work's line in the header's list names it after what it is doing ("working · Opus 5.5 · 4 min"), with "Opus 5.5 on Claude Code, high reasoning, for this work only" on hover; the chip keeps it in its title ("started Vacuum comparison · Opus 5.5"), and a reply that shows its steps shows it there, with the same hover. The name is kept on the work's trigger (`model`, display only). These are the only places the chat names a model apart from the line about a pick that can't run.
- **Resolution** (`src/mms/bots/model/`). Candidates are the owner's entries that are enabled, signed in, ready, and whose runtime can hold the bot's policy (`harness.canHoldBot`). A pick runs only on its own entry, with the same kind of sign-in and account, or not at all: never on another model or entry, and never on a paid API key the owner did not pick. A pick is checked before every main dispatch, continuations included (a restart, the internet back, the turn cap, more room, an answered ask), so an entry switched to an API key while a chat waits at an ask is never used; a mismatch is a pick that can't run. A model by name or by usage is chosen at the first dispatch, and again after a reload or a usage limit.
- **A pick at its usage limit** waits; only what runs on that entry does, never the whole bot. The engine keeps the limit for the bot by entry, until its reset (`BotModelState.limits` in `model_json`), or by entry and family when the provider names a window for one family only: Claude's weekly `seven_day_opus` and `seven_day_sonnet` windows hold for Opus or Sonnet on that entry, and every other window (`five_hour`, `seven_day`, Codex's) for the whole entry (`limitFamilyOf`, the run's `usageLimitKind`). Work the owner asked for waits for the reset (`blocked`, `usage_limit`, the waiting state of Long work) and goes on, on the same pick; scheduled runs whose pick is on that entry are skipped with the reason (`usage_limited`); rows on other entries keep running, schedules included. The chat says "Paused until 14:00 (your Claude usage limit)" once per limit, naming the provider family only; later turns on it wait without a call or a line. The status line and sidebar row say "Paused until 14:00" while any row's entry is limited. A turn that meets the limit is not retried elsewhere. Resume clears these limits, and the model choice's mark of the entry (`clearLimited`), and tries again.
- **A pick that can't run** for another reason (its entry removed, turned off, signed out or not ready, the model gone from it, unable to hold the bot, or signed in another way or to another account) resolves as `pick_unavailable`: the activation ends (`bot_pick_unavailable`), never counted as a failed run, and every row holding that pick is **stuck** (`BotModelState.stuck`, `stuckRowsOf`), as is an automation's own pick (`schedule:<id>`). The line names the model and its entry as Runs on does: "I can't use Haiku 5.5 on Team Claude: it's turned off." (`BotPickMiss`, `pickProblemText`), with one action, **Pick a model**, which opens About → Runs on. Both names may be text from elsewhere (an entry's display name, a custom endpoint's model name): each is one plain line, cut to a few dozen characters (`plainLabel`), and the chat shows it as plain text. That line is for the owner only: it is journaled as a hidden kind (`PostInput.hidden`, `model_change`), which no pack, search or read gives the bot.
  - *A work row stuck:* the line is said once per stuck row. Its scheduled runs are skipped with the reason (`model_unavailable`) and make no run thread; work for it (`work_start`, a reminder's work) is not started, and the bot is told why; the chat's situation says which work can't run, so it can tell the owner. Talk keeps working, and its finished turns change nothing about Work.
  - *Talk stuck:* every owner message gets the same line, with no model call, so no message goes unanswered; those messages are not run later. Work rows that can run keep running their schedules.
  - *Clearing:* a row stays stuck until it can run again: each scheduler tick asks the model choice whether each stuck pick can run (`recheckStuck`, also on Resume), and a turn that runs on the pick clears it; or the owner picks again for that row (About → Runs on, `use_model` `always`). Nothing extra is said. Picking another row leaves it stuck. The status line and sidebar row show "Needs you" with Pick a model while any row is stuck.
- **Bots from before picks** keep working as they did, with one guard. A row with no pick runs on a row the owner did pick (`pickSourceOf`: Medium work's pick, else Talk's, else Light or Hard work's), so work with no Work model runs on Talk's model and never on a pricier model by usage; when that pick can't run, the work stops with its line, as any pick does. Only while no row is picked is a row "Mousse chooses": by usage, the Settings default first, then depth picks a tier and an effort (`quick` is the standard tier at the lowest effort, `normal` the standard tier at its default, `deep` the frontier tier at the highest, but a frontier model paid by use (an API key, a gateway) only after the standard tier, so work by usage never runs on a pricier model than the chat would; within a tier, subscriptions rank before API keys, then newer models, then the entry's own order; tiers come from `models.json` and `src/shared/bots/personal/modelTiers.ts`). A model by name is matched across entries, subscriptions first, and one that is missing or at its limit falls back to by usage. An automation saved with a model by name (before picks kept their entry) runs that way only on such a bot; on a bot whose rows are all picked its name is ignored, it runs on its level's row (Work), and its first run says so once (`OLD_MODEL_NAME_IGNORED`). In About, Runs on shows a row that runs on another row's pick as "Same as Talk" (or "Same as Medium work"), its tooltip naming the model; with no row picked, "Pick a model", its tooltip saying which model it runs by name, if any, until the owner picks; a row the owner picks becomes a pick, and once every row is one the bot is a picked bot for good: no method sets a row back to Mousse choosing.
- **Sign in.** A bot from before picks with no model and an owner's entry that could hold it once signed in is stuck with Sign in, which opens that entry's card in Settings → Providers.
- **Default bot model** (Settings → Models → Bot model, `settings.botModel`): only for bots from before picks. A row on which Mousse chooses runs on this default, at the effort its depth gives, while it can run the bot. New bots never use it.
- **By hand (#673).** About → Runs on and New bot show the rows with `BotModelRows` (`BotRunsOn.tsx`): a label and one control per row, the app's own model picker (`SettingsModelPicker`, the composer's model menu with the model's reasoning levels beside it), every control the same width in one column. While two or more entries offer models to the bot, a closed row shows its entry after the model, muted as the menu shows it ("Opus 5.5 · High · Team Claude", `severalEntries`, `SettingsModelPicker`'s `entry`), cut with an ellipsis, never wrapped; with one entry, the model alone. The picker is fed the bot's choices (`providers`): the app's listing (`harness.llmProviders`) narrowed to each ready entry's models that can hold a bot (`BotModelChooser.pickable`, `botPickProviderOptions`), without "Off". Simple view: Talk and Work (the three work rows on one pick); with Advanced, Light, Medium and Hard work apart, each starting from Work's pick. Advanced is open while the work rows differ; closing it puts Medium work's pick on all work as it is (`oneWork`), and can't close while Medium work has no pick and the rows differ. A pick that is no longer offered shows its name with "not available". `bots.model.setSlots` saves only the rows the owner changed (`slots`), over the rows as they are at that moment, so a change the bot made meanwhile stays; each must be offered now and is saved with the entry's sign-in now (picking the same model again accepts a changed sign-in). About reads the rows again whenever the bot changes. `bots.model.get` returns the rows as picks or null (`slots`), `named` for rows by name, and the Talk model by name (`model`). `bots.model.set` (an older app's single picker) puts one model on every row, on an entry that offers it, and never sets a picked bot back to by usage. For one automation `bots.schedules.add`'s `model` is saved as a pick on the entry that offers it now (`ScheduledJobBot.pick`, refused when none does; no screen sets it yet), and like any pick it runs there or not at all; a job saved by name only is matched by name as before. Compatibility: `bots.model.setSlots` is optional (`BOTS_WORK_METHODS`); an older service sends no `slots` or `providers`, and the app shows its single Model picker. The computer picker offers only this computer until bots can run on another one (the person's other computers are listed, greyed); New bot shows this computer's name as plain text while it is the only one. This computer is named as the side card and Devices name it (`src/mms/computerName.ts`: macOS's Computer Name, Linux's pretty hostname, Windows' computer name), else by its hostname. The bot's own schedules never name a model.
- **Asking.** `set_depth` and `use_model` take `now` or `always` (saved as a revision with the same grant; chat lane only). `set_depth` `now` sets the level of the activation it is called in (a run moves to that level's row); `always` sets the standing level. Its answer says whether what runs changed: a depth that leaves a turn on the same pick changes nothing (and `now` then sets nothing), and the bot says so instead of "I'll take more time". `use_model` changes only to a model the owner's own message in this activation names (`BotToolHost.ownerWords`, `ownerModelChoice`), among the same choices the picker offers (`BotModelChooser.pickable`); the bot's own argument is never what is accepted, and it must name the same model. Names count only as whole words in a row, ignoring case and punctuation (`modelsNamedBy`); a name inside a longer one the owner said ("GPT-5" in "GPT-5 mini") is the longer one. A bare number, generic words ("pro", "mini", "flash", "default") and a maker's word alone ("gpt", "claude") never name a model. `always` (Talk, Work or both, `for`, all by default) needs a full name of exactly one offered model: its name as the picker shows it ("Opus 5.5"), its own name or its id; a family word ("opus", "haiku") is not enough. Offered on one entry, every row goes there; offered on two, each row stays on the entry it is on when that entry offers it, and otherwise nothing changes. `now` (this chat, never saved) takes a full name the same way, kept on Talk's entry, or a family word when it names exactly one model among the choices on Talk's entry. Any refusal answers the bot with one line: "Nothing changed. Ask the owner to pick the model in About → Runs on." A run never changes its model. Its chip says "switched models" and for what, never the model, and About → Runs on shows the change. Bot instructions forbid naming models or providers, except for a model the owner asks for one piece of work.
- **Images** (#1088). Under Advanced, below the work rows, Runs on (About and New bot) has an **Images** row: the model the bot makes pictures with. It is the same label and model picker as the other rows, fed the image models Mousse can call itself (`bots.model.choices`' `imageProviders`), with **None** in the menu's footer; it starts at None, and Advanced opens when it holds a pick. While no entry of the owner's offers one, the control says "None available" and its tooltip says to add an OpenRouter entry with an API key (`imagesMissing`). Its tooltip names the model and entry and today's pictures ("3 of 20 today").
  - *The pick is the consent.* No permission and no ask: only a bot whose Images row holds a pick has `make_image` (`compileBotThread`'s `botTools.images`, read from the published definition at every dispatch, and `BOT_IMAGE_TOOL` is offerable but never grantable), in the chat and in work, never in a consult. It is listed to Claude Code and Codex only while the turn holds it (`ToolListing.botTurnTools`) and offered to Pi only then; every call is checked again by the authority and by the service, which reads the row at the call, so None takes the tool away from the next turn and refuses a call already under way. Without a pick the bot's instructions have no picture line, and its base instructions say to tell the owner they can pick an image model in Runs on.
  - *Which entries can.* An image model is one in pi-ai's catalogue for the entry's provider (`Models.getModelsOfType('image', …)`) that returns a picture, on a ready Pi entry (`HarnessGateway.imageModels`, `piImageModels`). In pi-ai 1.4.0 that is OpenRouter only (Gemini, GPT Image, FLUX, Seedream and others through OpenRouter), with an API key or OpenRouter's own sign-in, which gives a key. `openrouter/auto` and other routers are left out: they choose another model. Not offered: Claude Code (no image model), Codex (its own `image_generation` runs on Codex's own model, outside the grant, and stays off for bots, `CODEX_BOT_FEATURES_OFF`), Cursor (its own tool), OpenAI and Gemini API keys on Pi (pi-ai has no image request for them yet; adding one is new provider code), and custom endpoints.
  - *How it runs.* `make_image` (`description`, and `shape`: square, landscape or portrait, sent as OpenRouter's aspect ratio, which some models ignore) asks `BotImageMaker` (`src/mms/bots/images/`). It re-reads the pick; a pick no longer offered (entry removed, off, signed out, not ready, model gone, or signed in another way or to another account than when it was picked) is refused in plain words without naming the model ("Your owner's image model can't be used now: it's turned off. Nothing was made. …"), and nothing is made on another model. Then it checks the caps, charges one model request on the activation's counters (`maxTurns`) and, when the bot has a token or USD limit, reserves and settles spend at the catalogue's price (a model the catalogue gives no price for counts as free). The request is one pi-ai `generateImages` call in Mousse's process (`HarnessGateway.generateImage`, after the checks every dispatch passes: turned on, not stopped, not retired, signed in in Mousse), with no retry and a 3-minute bound. Pi's own `generateImages` stays refused for every Pi Mousse starts (`guardProvider`): pictures never come from inside a runtime.
  - *Caps.* At most 20 pictures a bot per local day and 4 per activation (one chat turn with its continuations, or one piece of work; `BOT_IMAGES_PER_DAY`, `BOT_IMAGES_PER_TURN`). Every request sent counts, also one that made no picture. The counts are kept in `<profile>/bots/images.json`, outside every bot's files folder, written before the request is sent, so a continued or restarted turn does not start over. The bot is told which cap it reached.
  - *Failures.* A request that made no picture gives the bot one fixed line by kind (refused, the entry's key refused, no credit, busy or at a limit, no answer, no picture, failed; `ImageRequestError`, `failureKind`), always ending "Nothing was made."; the provider's own words go to the log only.
  - *Where the picture goes.* Only a PNG, JPEG, WebP or GIF (checked by its first bytes) of at most 8 MB is saved, in the bot's files folder under `images/<date>/<first words of the description>-<time>.<type>`, as a new file (never over one, never through a link out of the files folder, whose real path is checked). The result gives the bot the file's name and path and a markdown line (`![…](file:///…)`) to put in its reply, so the chat shows it as it shows other pictures from the files folder; the bot can send the file, or use it in later work. Another device shows pictures up to 1.5 MiB (`bots.chat.attachment`).
  - *Older builds.* The row is stored as `main.slots.image` beside the four rows. An older build ignores a row key it does not know (`modelSlotsProblem`), keeps it while the rows are live (`withSlots`), and never offers `make_image` (it has no such tool): the bot runs as before and makes no pictures there. Once an older build rewrites `main.model`, every row is dropped, Images too, as for the others. `bots.model.setImage` and `bots.create`'s `image` are sent only to a service whose choices carry `imageProviders`.
- **Custom slots.** The owner can name more models for kinds of work in the bot's chat (`/model iosdev <model> iOS apps, Swift, Xcode`, `bots.model.setCustom`): a name (lower case, a letter then letters, digits, `-` or `_`, at most 24 characters, never a base slot's: talk, work, light, medium, hard, images), a pick, and a one-line description of at most 200 characters. At most 1,000 per bot (`MAX_BOT_CUSTOM_SLOTS`, a ceiling only a runaway reaches). The pick is checked and saved with the entry's sign-in as a row's is (`model_unavailable` when it is not offered); a new pick without words keeps the slot's description; null removes the slot. They are stored as `main.slots.custom` beside the rows (`customSlotsOf`, `withCustomSlot`), read only while the rows are live, a revision with the same grant; older builds ignore and keep them. `bots.model.get` returns them as `custom`, without the sign-in.
  - *Routing.* While the bot has custom slots, the chat's situation lists each one's name and description, with one line: work whose job matches a slot starts with `work_start`'s `slot`; other work by level, as before. Without slots the pack is unchanged. `slot` needs no words of the owner's (the owner set the slot up for this), but must name a slot the bot has, or nothing starts and the bot is told the slots there are. It is kept on the work's trigger (`slot`), and `turnModelOf` runs that work on the slot's pick (`slot` is `custom:<name>`), at its level's depth. A model the owner named for the work (`model`) still wins. The slot is read from the revision the work was queued under, as rows are: a slot removed before then falls back to the level's row. A slot's pick that can't run ends that work with the usual line; no row is marked stuck for it. The work line does not name a slot's model.
- **Usage limits.** A bot turn that hits a usage limit fails at the run level and records the reset time and, when the provider names one, its window. A pick waits on its own entry (above). For a bot from before picks the engine marks that instance limited and resolves again (at most 2 retries per activation), trying the next candidate. With none left, the bot pauses until the reset (`paused_reason='usage_limit'`) and posts "Paused until 14:00 (your Claude usage limit)", naming the provider family only. Its schedules run again at the reset. This never counts as a failed run. Work the owner asked for waits instead of ending (see Long work). Several pieces running on one limited entry each retry and pause on their own, and none counts as a failure; the bot's pause line is posted once (a scheduled run whose sibling already paused the bot adds none), while each piece of the owner's work says it carries on. On a picked bot the line is said once per limit, by the first piece that meets it.

## States and pausing

States are idle, working ("Waiting for internet" while it waits for it), needs you (a shown open permission ask, work waiting on an answer, or a shown open chat question while nothing is running, queued or managed), stuck (an error with one action, such as Sign in or Set up a provider), and paused (`src/shared/bots/personal/state.ts`). "Done" is only an animation of the face.

The Chats tab's bot faces, Recent lines and the bot's header use this same summary, including open chat questions ("Asked: …") when otherwise idle. While work is running, queued or managed, a chat question does not replace the working face or work line; it still counts toward the badge. A question the owner moved on from stays tappable but quiet; answered, defaulted and withdrawn questions no longer show needs you.

The dock or taskbar badge and the title bar's count include threads and bots waiting on the owner, one per bot however many asks or questions it has open. A paused or deleted bot does not count. An error alone does not count, but a bot with an error and an open ask or question does (`BotSummary.needsOwner`, independent of the state whose error takes priority). Answering in any window or device updates the count through the pushed bot list. Each window refreshes the bot list once when its profile is activated, before Chats is opened, then follows pushed changes. Only the Chats views poll. The sidebar toggle names threads and bots separately, keeping the thread wording when no bots need an answer.

- **Pause** stops schedules only; chat still works. The owner pauses from the menu (`bots.personal.pause`).
- **Three failed runs in a row** pause the schedules, with one notice. A run that ends done resets the count, even with refused asks. Usage limits, waiting for the internet, stops and chat failures never count.
- **Resume** (`bots.personal.resume`) clears every pause, the failure count, the stuck error and the usage limits a picked bot met on its entries. A row whose pick can't run is not a pause: Resume checks it again, and it stays stuck until its pick can run or the owner picks again.

## Switching a bot's permissions off

About → Can use has a switch and Remove on each permission row. What every bot has by default has a switch and no Remove (`BotPermissionItem.builtIn`): MCP as a whole, each MCP server set up now (inset below it while MCP is on), skills, and the automation tools. Off keeps the permission listed but gives the bot none of it. On restores it on the next turn, without another ask or card. Remove forgets it; giving it back needs an ask again. The bot's own always-on tools and its starter permissions have no rows or switches. This includes the starter web tools; an older grant's extra native web permission still has its row.

This switch is the only one: a permission works whenever it is in the grant and its switch is on. The existing runtime limits still apply: commands may reach other files where the runtime has no file sandbox. Switch commands off to stop them.

Where a grant becomes what a turn runs with, the switch is read: what an activation runs with (`effectiveManifest`, after any "Allow this time", so no overlay adds it back), the thread compiled from it (`compileBotThread`: its tools, the sandbox's folders and the browser), and the authority's check of every call (`createBotAuthority`'s `disabled`, read at each call, before anything else). Every runtime goes through these: Claude Code's grant gate and sandbox, Codex's approvals and sandbox, Pi's gate and the tools it is offered, and the app tools. A call refused this way makes no card and counts against no cap; the bot's system text says "switched off by your owner for now, so asking won't help" for commands, the browser and threads, and leaves out the line that offers to ask for it (`baseInstructionsWithout`).

The default switches (`default:mcp`, `default:mcp:<installation>`, `default:skills`, `default:automations`, `BotEngine.setDefault`) narrow neither the grant nor the published definition: they are read where defaults are added (`withDefaults`), in `permissionOff` at every call, and in the system text, which says the switched-off thing is off and leaves out its catalogue group. A running turn is refused its next call, a call waiting on its card is withdrawn (as when a grant narrows), and an automation's let-alone exception for one of its tools is kept, and holds again once it is back on; the warm chat process is closed so the next chat turn is offered the right tools. A server whose tools can't be listed for now (failing, starting, a cold start) is still the bot's: a card for one of its tools stays open. A context thread narrowed to some skills has just those. A server an older build switched off stays off, under its own switch, and switching it on clears that row too. An older build's switch on one skill, one automation tool or a group permission every bot now has (the profiler, themes, scheduled jobs, secrets, quick actions) no longer holds anything back: those rows are ignored.

Switching commands off stops this bot's running turns, consults and subagents that opened it (`cutForSwitch`), and the work carries on in a new turn without it, told why. The commands that stop cut off are listed to that turn as interrupted and don't hold the work for an acknowledgement (`acknowledgeCut`); any other call still holds it, as after any interruption. Other permissions are refused at the next call. The chat quietly says what changed. Off also holds back reminders, scheduled work, restarts and Allow this time. An older ask card cannot turn it on, and the bot makes no new card for it while it is off.

The off state is kept in existing `bots.db` grant rows with `revoked_at = off:<permission id>`; the row remembers the permission, while the active grant and published definition are narrowed. No database migration is needed. **An older build gives nothing from these inactive rows** and sees the narrower active grant. It cannot show or restore the disabled permission; it can ask for a fresh explicit Allow. On a newer build the switch remains off even after that older build's Allow. A downgrade does not silently give access back.

The app window can flip the switch. A device within the bot's Devices choice may switch it off; switching it on follows the same rule as Allow on its card (Use your threads requires a Full access device). A device outside that choice gets the missing-bot answer. Bot, agent and MCP tools cannot flip it.

## Two layers: which devices reach a bot, and what a bot may do

A bot is held on two sides, both set on the computer that holds it (its home computer) and kept there:

| | Which devices reach a bot | What a bot may do |
|---|---|---|
| Asks | Which of the owner's devices may see and use this bot? | What may this bot do? |
| Where | About → Devices (each bot), and Bots on this computer (each device, Settings → Devices) | About → Can use (each permission, its switch and Remove) |
| Holds back | Another device: its lists, the bot's chat, memory, cards, notifications | The bot itself: commands, the browser, threads, skills, MCP tools |
| Default | Every device | Its starter grant; more only after an Allow |

### Which devices reach a bot

- **Per bot.** About → Devices: All my devices (every bot made before this, and a new bot), Only this computer, or Chosen devices, each ticked from the owner's device list. Kept in `<profile>/bots/device-access.json` (`BotDeviceAccessStore`), not in `bots.db`, so no database version moves. New bot's Runs on has Devices too, after the models: Everywhere (the default) or This computer only, and About changes it later (shown when the service says `reachOnCreate` in `bots.model.choices`; an older service gets no `access`). The Bots list puts a lock before a bot that is not on every device, and the bot's menu has Make private (Only this computer, in one click).
- **Saved before the bot exists.** `bots.create`'s choice is written before the bot is published, so no list or call ever shows a new private bot to a device it leaves out. A create that fails before publishing takes its choice off again; a crash between the two leaves a choice for a bot that was never made, which the next start removes (`BotDeviceAccessStore.dropBots`) before any create can run. A retry of the same request returns the bot it made and changes nothing. Everywhere writes nothing, unless what is stored can't be read.
- **Per device.** Settings → Devices → Bots on this computer, beside each device's other switches (`net_node_policy.bots`, `bridge.policy`'s `bots`, `mousse-cli bridge limits <node> --bots on|off`). On by default. Off, the device reaches no bot here, whatever each bot says.
- **To a device that is left out, the bot does not exist.** Every bot method of another device goes through one wrapper (`remoteBotMethods`'s `method`), which checks the device's switch and the bot's choice before the call is admitted and again as it runs, so a method added later is held too. A bot the device may not reach answers word for word as a bot that is not there (`stream_unknown`); a device whose switch is off is refused every method as when Share bots is off (`forbidden`, `setting_off`). Guessing an id, a home or work thread, an ask, a reminder or an attachment of a hidden bot gets the same answer as guessing one that does not exist: the bot is checked first.
- **Lists.** `bridge.lists.open` opens a lists stream of the caller's own (`mousse:lists:<node>`), which only that device may read (`ThreadStreamAdapter.boundReader`, checked in `NodeStreamAuthority.canRead`) and which lists only the bots it reaches. Another computer's private lists list the bots that computer reaches. The shared lists stream that phones opened before (a device may still hold its id) lists only the bots every device of the account reaches.
- **Threads a bot started** are the owner's ordinary threads and stay visible to every device that sees threads. Their "Started by" names the bot only to a device that reaches it; any other gets `startedByBot: { botId: "", name: "a bot" }` and no launcher (`withHiddenBots`, in the phone's results, routed results, thread snapshots and metadata), and the app shows "Started by a bot". A stream every device may read names the bot only when every device reaches it. What the bot wrote into such a thread, and the thread's own "By <bot>, your bot: …" lines, are thread text and are not changed, so a device that reads that thread, or finds it by searching for the bot's name, still sees the name there.
- **Disk usage** (`storage.usage` from a phone) counts a bot's own threads without naming them, for every device: they are named after the bot and its work.
- **Already under way.** A device taken off a bot, or switched off, gets nothing at its next call and its lists drop the bot at once. A message it sent that is still queued is not delivered: its chat turn is cancelled and the chat says "Not delivered: the device it came from can no longer reach me." (`BotChatService.withdrawQueued`). A card is no longer answerable from it. Work the bot is doing, and a turn already running, carry on: they are the owner's. What the device already received (its cached lists, chat and notifications) stays on it; the computer cannot take it back.
- **Who changes it.** Only this computer's own window and its command line: `bots.devices.get` and `bots.devices.set` are local methods that refuse a call through Bridge or from any other kind of client, are not in another device's table (`REMOTE_BOT_METHODS`) and never route (`bots.` and `bridge.` stay local). `bots.update` from a device takes only a name and a look. A device's `bots.create` may ask for `reach`: `home_and_maker` (Chosen devices, that device alone) or `all`; it can't ask for any other device or for this computer alone. Without `reach`, the new bot is kept within that device's reach, but a choice already saved for it (the owner made it private while the create finished) is never widened (`keepMakerInReach`). A home that takes `reach` says so in `net.info` (`bots: { 'bots.create': 2 }`); a device must not send it to a home that does not, which refuses unknown keys. It changes no other bot. No bot tool, agent tool or MCP tool changes either.
- **Fails closed.** A bot without a stored choice reaches every device. A choice or file that can't be read means only this computer; the next change puts a file that can't be read aside (`device-access.json.corrupt-<time>`). A device removed from the account leaves every bot's list. A device's switch reads as off for any stored value but 1.
- **Versions.** An update keeps every bot on every device and every device's switch on. An older build ignores the file and the column, so while one runs (a downgrade) every device reaches every bot again; the choices apply again on the next update. A newer device talking to an older home computer sees what it always did: the choice lives and is enforced only on the home computer. An older phone talking to a newer one is held like any other device.
- **What it does not do.** It does not hide a bot from someone using the bot's own computer. It does not stop a device that can work on this computer's threads, open terminals or connect an editor here from doing its own work, with its own agents and commands, and those can read the bot's data on this computer's disk. It does not change which threads other devices see. It cannot take back what a device already received: its cached lists, chats and notifications, and earlier records of a stream it read.

## On a phone and other devices

The owner's phones and other computers see and use the bots of a computer they reach through Bridge, each within Which devices reach a bot (above).

- **Share bots with other devices.** A switch on each computer (Settings, Devices; `mousse-cli bridge bots on|off`), on by default and stored on that computer. While it is off, its lists carry `bots: []` and every `bots.*` call from another device is refused with `forbidden` and the reason `setting_off`; the device says "<Computer> doesn't share its bots with other devices." Turning it on or off pushes the lists again.
- **Lists.** `bridge.lists.open` pushes `bots` (those the device reaches) beside `chats` (`ListsBot` in `src/mms/bridge/remote/MmsListsSource.ts`): each bot's summary as the Bots list has it, plus `activity`, the live chip of its chat activation (gone when the chip clears). The stream pushes again, debounced, on `bots.changed`, `bots.message` and `bots.activity`. Bots are listed whether or not there are chats; a computer whose bots can't be read lists none. `version` stays 1.
- **Methods** (`src/mms/bridge/remote/RemoteBots.ts`, deny-default, exact keys). Read: `bots.get`, `bots.chat.list`, `bots.chat.attachment`, `bots.memory.list`. Chat: `bots.chat.send`, `bots.chat.stop`, `bots.work.stop`, `bots.chat.markRead`, `bots.asks.answer`. Write: `bots.personal.pause`, `bots.personal.resume`, `bots.create`, `bots.update`, `bots.reminders.cancel`, `bots.schedules.remove`, `bots.permissions.revoke`, `bots.memory.forget`, `bots.memory.edit`. Each calls the same `BotChatService` method as the desktop, with the same params and results. Delete, the model and computer pickers, new schedules and memory export stay on the computer.
- **Images.** A message's files keep their name and type (`{ name, mime, image? }`). `bots.chat.attachment` reads an image (PNG, JPEG, GIF or WebP, checked by its first bytes; never SVG) of up to 1.5 MiB from the bot's files folder only, in parts of 40 KiB (`offset`), so each part fits one reply.
- **Applets** run only on the computer: another device gets a line naming each one ("Applet: Budget. It opens on the computer."), never its reference.
- **Cards** come as the desktop gets them, except a gallery's pictures, which carry their name, caption and place among the message's files (`index`, for `bots.chat.attachment`) instead of a path. An app that doesn't draw cards shows them as text (`plainFrom`).
- **What another device does not get.** No model, no instance id (an error's action keeps its kind and label; Sign in happens on the computer), no paths. It can't attach files, and a memory export ask is refused because it needs a folder picker on the computer.
- **Sizes.** A message from another device is at most 32 KiB. A chat page is cut to the newest messages that fit one reply; the device pages back with `beforeSeq`.
- **Refusals.** An unknown bot; an ask that is gone, answered or not ready yet; a memory export ask; and a reminder, schedule, permission or memory that is no longer there: all are checked before anything changes, so they are plain errors and never an uncertain outcome. A message to a working bot queues as on the desktop; stopping work the bot no longer has returns `{ stopped: false }`. An error's own words stay on the computer (only its code crosses the wire).

## Runtimes that can hold a bot

Bots run on the owner's own provider entries, the same ones their chats use, with their existing sign-ins. Supported entries include Claude Code, Codex, Pi and Google Antigravity using the `agy` CLI. Mousse adds no entry for bots. A runtime holds a bot when its driver says so (`HarnessDriver.botAuthority`) and `checkPolicy` admits the bot's policy (`src/mms/harness/policy.ts`). There are two ways to hold one:

- **Every call (`toolControl: 'exact'`).** Mousse runs or gates each tool itself.
  - **Pi RPC:** Linux, macOS and Windows, with recorded evidence for this platform (`CONTAINMENT_EVIDENCE`, `src/mms/harness/compatibility.ts`). Bot turns run ephemeral: no saved session, history in the prompt, never kept warm, in the locked environment, in a process group of their own.
  - **A locked Claude Code entry** (`profile: 'locked'`), on Linux on a recorded Claude Code version. Mousse no longer creates one; an entry left from an earlier build ("Claude for bots", `claude:bots`) is removed at startup (`removeRetiredBotRunner`).
- **Every approval (`toolControl: 'approval_only'`, `HarnessDriver.botApprovals`).** The bot's permissions answer every approval the runtime raises, through the same check (`BotCheck`) that `BotEngine` builds for Pi: allowed runs; a missing permission is a wall in the chat lane and a refusal with an ask in a run; anything that can't be asked for is refused. Nobody sees a normal approval prompt. The turn runs in the runtime's asking mode whatever the thread or entry is set to (`checkPolicy` refuses a bot policy bound in any mode but Ask), in the bot's files folder.
  - **Claude Code** (`src/mms/harness/claude/locked.ts`, `ownerEntry`): every call goes through the grant gate in Mousse's `PreToolUse` hook and `canUseTool`. The turn starts from the locked environment plus only the entry's sign-in variables and sign-in storage locations, with `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` to strip credentials from the subprocesses Claude Code starts. It loads none of the owner's settings files, plugins or MCP servers (only Mousse's own server, and its relay when the bot's work holds the owner's MCP tools: see Use your MCP tools), offers only the granted built-ins (Bash with "run commands", see above). A chat turn runs on the chat's warm process (Warm chat process below); every other turn is one query.
  - **Codex** (`src/mms/harness/vendors/codex/botApprovals.ts`): Ask's policy (`untrusted` approvals, no network; the read-only sandbox, or with "run commands" Mousse's profile on Linux and macOS, and `workspace-write` otherwise; see Run commands). A command it asks about is a `shell` call; a file change is a `write` (a new file) or `edit` call on each path it touches. A change Codex does not describe, or one that would widen where it writes, is declined. Questions to the owner are refused, and the owner's own Codex MCP servers are switched off for the bot turn, including `mousse` and `mousse-relay` when Mousse supplies no attachment under that name. If the owner's config defines a name the turn attaches (even a server set to disabled), the bot turn is refused with the bot's own words, naming every conflicting server and the config file to edit. For example: 'Your Codex config has an MCP server named "mousse-relay", a name Mousse needs for my work. Rename it in Codex's config.toml to let me work on Codex.' A server defined in an active project layer names that project's `.codex/config.toml`, with its path relative to the turn's project folder. If both names conflict, one refusal names both; if several files define them, it names those files too. Codex merges server tables recursively, so Mousse cannot erase the owner's leftover command, headers, credentials or tool filters with its attachment overrides. This check includes active config layers and leaves the owner's own threads unchanged. A bot turn does not run when Mousse can't read the owner's Codex config at its start (`config/read` fails): neither those servers nor the features a thread can't switch off could be checked, and the bot's chat says "Mousse couldn't read Codex's own settings, so my work can't run on it now." (`CODEX_BOT_SETUP_UNREADABLE_TEXT`); the owner's own threads are not affected.
  - **Google Antigravity** (`agy`): pick the Google Antigravity entry in Runs on. Bot turns use an isolated Antigravity settings directory and the MCP servers Mousse attaches for the turn. Mousse checks file, command and web permission requests against the bot's grant and answers once. It refuses unrecognised tool requests and native question forms. If Antigravity stops after a refusal, Mousse can tell it why and give it another prompt to finish the turn. The agent process closes at the end of each bot turn.
  - An approval check applies when the runtime asks for permission. Antigravity can read and search on its own, and it runs granted commands without a bot-specific sandbox. See Run commands for Codex's sandbox on each platform.
- Generic ACP agents and Cursor approve tools themselves (`toolControl: 'uncontrolled'`). They are available in regular threads. Runs on shows ready custom ACP agents as unavailable with a reason. The other ACP presets still need to route their requests through the bot's grant before they can run bots.


### Warm chat process

On the owner's Claude Code entry, a bot's chat keeps one Claude Code process running between its turns, as a thread's live session does (`acquireLive`). The first chat turn starts it; later chat turns give it their prompt at once, without starting Claude Code, waiting for its init or registering Mousse's server again.

- **Which turns.** Only the chat lane's own turns (`BotAuthority.warm`, set by `BotEngine.authorityFor` for chat activations, `botKeepsWarm`). Work and run turns, and turns on a `locked` entry, stay one process per turn.
- **A turn that runs a command closes it.** A chat turn is offered no commands today (they go to its work, `frontDeskManifest`), but whether it may keep its process does not depend on that. A command can outlive the call that started it. So the grant gate notes a shell call before it lets it through, in the `PreToolUse` hook or in `canUseTool`, whichever comes first (`ClaudeLockedGate`'s `onCommand`), and the process closes when that turn ends, with everything it started (`closeBotLive`). The next turn starts a fresh one. A refused call notes nothing: it ran nothing.
- **Reused only while the launch is the same.** The process is reused only when the turn's launch key matches the one it was started with (`claudeBotLaunchKey`): the lane, the turn kind and the compiled grant digest, plus a digest of every launch option (the locked environment, the settings file's contents, the tools offered, the system prompt, the working folder, the model and effort). Anything different closes it and starts a fresh one. The chat's scratch folder is the same from turn to turn for this reason: on macOS and Linux the locked environment's `TMPDIR` is in it, so a folder per turn would start a new process every turn. Mousse's credential is renewed in place, as on a thread (`renewMousseServer`).
- **Between turns.** The process holds no prompt. The turn that ended leaves an aborted signal on it, so the `PreToolUse` hook and `canUseTool` refuse every call; that turn's grant gate also refuses once its dispatch has ended or the grant changed (`BotAuthority.live`), and Mousse's server refuses a call stamped with an earlier turn's token. A turn Claude Code starts by itself (a background task's wake) closes the process instead of running.
- **Each turn.** Every tool call is checked against the current turn's grant gate. A turn that fails, is stopped, or reaches its deadline closes the process; the next turn starts a fresh one. A process, new or already running, gets its prompt without waiting for this turn's sign-in reading while the last one, under five minutes old, said signed in (`signInFresh`; a bot's one-shot query too); the reading still runs, and a signed-out one ends the turn and the process.
- **Closed** after 5 minutes idle (`BOT_LIVE_IDLE_CLOSE_MS`), when the bot is paused, unpublished or deleted, when its permissions are approved, revoked or granted again (`BotStore.launchChanged` → `releaseBotProcess`), when the model, effort or anything else in its launch changes, when the chat's context is cleared (the saved history no longer matches), and when Mousse shuts down. Its settings file lives as long as it does.
- **Where a reply's time goes.** Each chat turn logs one `[turn-timing]` line in the service log (`src/mms/diagnostics/turnTiming.ts`): milliseconds from the owner's message to `dispatch`, the orchestrator's `lease`, `checkpoint`, `appTurn` and `harness`, then the runtime's `provider`, `processWarm` or `processNew`, `signIn`, `prompt`, `firstFrame`, `messageStart` and `firstText`, from monotonic clocks. A turn with no first word logs nothing.

## The supervisor

Each dispatch's deadline is enforced outside the daemon for the processes a bot turn owns alone. When a runtime reports such a process (Pi's ephemeral bot turns, a locked Claude Code entry), `BotProcessRegistry` (`src/mms/bots/supervisor/`) records the pid and group and starts `bot-supervisor` (`src/cli/fastpath/botSupervisorMain.ts`), a plain Node process, detached. At the deadline it ends the process group (SIGTERM, then SIGKILL after 2 seconds; `taskkill /T /F` on Windows), confirms the exit, and writes a line to `<profile>/bots/supervisor/<dispatchId>.json`, which the daemon folds into `bot_dispatches.exit_at`. A dispatch that settles first stops its supervisor. At startup, `reconcile()` ends the groups of unfinished dispatches. `exit_at` is evidence that the processes are gone (the unknown-call gate reads it), not what is charged: an unfinished dispatch is charged up to the last moment it was known to work (see Long work).

Claude Code and Codex on the owner's entries report no process: Codex's app-server serves the owner's other chats, and Claude Code's process belongs to the SDK's query. Neither is registered or killed for a bot. At the deadline the turn's signal ends the turn through the runtime's own interrupt (`turn/interrupt` for Codex, closing the query for Claude Code).

## Memory

Mousse keeps an append-only **bot journal** in `bots.db` of everything it sees a bot do and be told. Capped, dated **bot memory** entries, the **chat summary** and FTS5 search sit on top of it. Every activation's first dispatch gets a context pack built from it: the chat pack in the chat lane, the run brief in the run lane. The bot has five tools that are always on and never grantable: `memory_search`, `memory_read`, `memory_list`, `memory_save` and `memory_forget`; runs may only save run notes and never forget. Beside them the bot keeps its **open items** (`item_save`, `item_list`): what its owner asked for and what it promised, listed in every chat turn until delivered or dropped, each with the chat row it came from. Details: [`bot-memory.md`](bot-memory.md).

Corrections and edits keep a memory entry in its original pack position. When the standing-wish fallback cannot save because the owner entries are full, the next chat situation tells the bot how many wishes did not fit and asks it to explain and ask which notes to drop. The notice clears only after a chat turn carrying it settles.

### What's new for bots

A bot made before a change still has memory and chat history that say the old thing. `src/mms/bots/changelog.ts` lists each change a bot would otherwise get wrong, one short entry with an id and a date. A bot's next pack after an update carries the entries it has not seen, after the `<bot_memory>` wrapper, as winning over its memory and history; a chat pack also tells it to replace the memory entries they contradict with `memory_save`, without mentioning it to the owner. A settled chat turn that carried them marks them seen (`changelog_seen` in the memory state); a run follows them but marks nothing. A bot with no history yet is marked as having seen every entry and told nothing. While support turns asks first off (`botAsksFirstOff`), its entries are withheld; the seen cursor stops before the next unseen one, so later entries can repeat until asks first is back on, while bots that already saw every withheld entry advance normally. The owner's chat shows nothing of this. An entry for a removed behaviour lists its old words in `gone`, and `tests/bots/botChangelog.test.ts` fails while a bot's instructions or tool descriptions still say them.

### Fresh starts from the chat

The owner's slash commands in the bot's chat, on the computer only (not in `REMOTE_BOT_METHODS`):

- **`/clear`** (`bots.chat.clear`): the chat's turns end, a queued one too, and so does work that waits for the owner's answer (at a wall, or on its question), since its card goes with the chat. Open asks and questions are withdrawn, so is every call held from the chat not yet sent (one still connecting after Send included), and every chat message is deleted. The journal and memory stay, so the bot still remembers what was said. Other work goes on, and its report is posted into the cleared chat.
- **`/forget`** (`bots.memory.wipe`): every current entry is forgotten, each as the owner's Forget does one (`BotMemoryAdmin.forgetAll`). The chat stays.
- **`/forget history`** (`bots.memory.wipe` with `keep: 'saved'`): the chat is cleared as `/clear` clears it, then the journal, the chat summary, the search rows and the run notes go (`BotMemoryStore.wipe`). The owner's entries and the bot's notes stay as they are, readable and in every pack; forgotten entries stay forgotten. The next chat pack has no old conversation. The capture cursors of the bot's threads stay, so their old rows are never copied back in.
- **`/reset`** (`bots.reset`, `BotEngine.resetBot`): everything that runs or waits ends (the chat, work, scheduled runs and their subagents, background commands, messages waiting in the owner's threads), and asks, questions, reminders and wakes go, in one transaction as a delete does. Then its schedules leave the shared store, its chat is deleted, its memory goes (but the capture cursors), and the pause, failure count, stuck error and usage limits are cleared as Resume clears them. The name, look, permissions, model rows and custom slots stay. Ended activations stay in `bots.db`, so `work_list`'s recent work still lists the last few.

## Deleting a bot

`bots.delete` archives at once and purges after 30 days:

- **At once:** activations stop, asks and questions are withdrawn, the grant is revoked, the bot leaves every list, and its threads are archived. Scratch folders go when nothing runs in them.
- **After 30 days:** a daily sweep (`BotEngine.sweepDeleted`) deletes the definition, the threads for good, the chat, the schedules, the files folder and the memory rows (`BotMemoryAdmin.purge`). Run history in the Run Engine database and runtimes' session files are not purged; the log says so.
- There is no restore in Phase 1.

### Asks first

Thread questions and tool approvals have no default timeout (#1481). A bot’s own question can still take the default it named. Held-call cards also wait without a deadline. The ten-minute window after Send bounds only the wait for its service.

Turning the switch off withdraws every open card and accepted call that has not started running, together in one transaction, at startup, on a settings change or on upkeep. Its chat row says Not sent. The work is told: “Your owner changed a setting, so this request was withdrawn and nothing was sent. Do not make this call again in this work; say in your report what you would have sent.” Running calls finish. With no rows, the switch-off path changes nothing. An internal manual activation (not Automations’ Run now) cannot hold a call: it is told, “A run started by hand can't wait for your owner. Say in your report what you would have sent.”

Asks first is on by default. Tools that can change things ask before each use, in the chat, work and scheduled runs. There is no Settings control; support can set `"botAsksFirstOff": true` under `experimental` in the settings file to roll back. The old `botAsksFirst` key is ignored, including the false value older builds saved by default. With it off, new granted-tool calls run as before, open and accepted unstarted calls withdraw, and running calls finish.

Each call asks when either the read-only hint offered to its turn or the current hint asks; a tool missing from the current listing asks. The explicit Restart action re-lists only a server still enabled in the current config; failures are logged. Config edits, disable, delete and sign-in changes close connections without reconnecting them. tools/list_changed notifications refresh listings. Send forces a fresh listing of that server, waiting at most three seconds. If it is still listing, Send can use a successful answer from the last 30 seconds, measured with a monotonic clock, only while the tool is still present with the same hint. Otherwise it refuses without sending. A cold, starting or failing listing keeps its waiting card; Send checks the binding once the server is warm. An explicit read-only hint runs without asking; an explicit not-read-only hint asks, whatever the name. Without a hint, the whole first word must be one of: get, list, search, read, find, fetch, show, describe, query and count. No later word may be a changing word (send, delete, remove, archive, update, create, add, set, put, post, write, edit, modify, move, copy, mark, reply, forward, publish, upload, cancel, close, merge, approve, assign, invite, share, submit, run, execute, trigger, start, stop, pay, transfer, book, order, buy, rename, clear, reset, import, sync, save or unsubscribe), and the name must contain none of the joining words `and`, `then` or `or`. Other names ask. Names split at underscores, hyphens, dots and camelCase; one leading word matching the server or installation name is skipped. Thus `github_list_issues` reads, while `update_list`, `listing_update` and `getaway` ask. `fetch_and_archive`, `get_and_send` and `listDelete` ask because they contain a changing or joining word. The rule cannot discover what a tool really does. A stored development `asks_first` level always asks, even with a read-only hint. No grant, digest or revision is rewritten, and existing bots need no new permission approval.

Before a bot’s first held card, one quiet notice says: “<bot> asks you before using tools that may send or change things. Tools that say they only read don't ask.” The `asks-first:introduced` memory-state flag commits with the card; it survives restarts and history wipes. Bots that never call an asking tool get no introduction. The next card itself explains a tool that starts asking; there is no separate hint-change notice. About marks a service when any granted tool asks, using current hints or names alone before listing. A changed effective level invalidates a waiting card with “This changed since you saw it”. Scheduled runs park on their card and later occurrences are skipped until it is answered or withdrawn. Not now refuses an exact repeat only within that occurrence; the next occurrence tries again and can raise a fresh card. Scheduled-run instructions say that Not now covers only that run. A leftOff note about an unsent call is framed as something to ask for again. Only the first occurrence after a decline gets the reminder, FYI raise and unsent-call sentence. Sending the same tool and argument digest clears that reminder; sending a different call does not. Later no-call runs stay quiet. The leftOff prefix never stacks. It is replaced when a later run saves a new leftOff note; until then, the previously saved note remains. Work and wakes keep their existing repeat rule. Run now starts an ordinary scheduled occurrence: it parks on a card too. Chat guidance about Send goes only to bots that hold MCP tools or can ask for them. Work and its MCP-holding subagents repeat any needed results from the earlier held turn, whose words the owner did not see.

A call held from the chat (#1361) never holds the chat. Its card is written with `lane = 'chat'` (the action, the card and its journal rows), and the chat turn is told “This call is held for your owner. End your turn now.”, is never parked and ends done, freeing the chat at once. Its origin is the owner's when their own message or tap started the turn, otherwise unattended. The card outlives that turn: ending done does not withdraw it (`withdrawWork`), and Send and the grant checks accept it while it is open, accepted or running (`actionPair`), still under the live grant, the server's live config and schema, and an unpaused bot. It is retired when its chat turn failed or was cancelled, on narrowing or revocation, with asks first off, when the bot is paused or deleted, when the owner's message it answered is forgotten, or when the owner clears the chat (`/clear`, `withdrawChat`), so no stale Send runs it and it holds back no same request. A chat turn with a held card is never parked for it (approval parking is work's): when the owner's later message makes it go on, it reads the message and then ends done, and one a restart cut off after its card was written ends done at recovery, its card kept. That holds even when the crash came before the call's ledger row settled: when the only unsettled call is the held call's own ledger row (its invocation id, kept with the card as the hold wrote it), the hold sent nothing, so it is a known outcome and the turn is not paused as uncertain (`onlyHeldCallUnsettled`). Any other unsettled call still pauses it, one with the same tool and arguments too, and so does a card that kept no ledger row. Send runs it once, also after newer messages and a restart, under a 60-second timer (`BOT_CHAT_ACTION_MS`); work's windows are unchanged. A bot paused after Send but before the call reaches its server sends nothing, even when it is resumed before the connection is ready, and so does a chat cleared meanwhile (`/clear`): the pause or the clear marks the sending call retired, and the last check before dispatch (`assertRunning`) settles it failed. A call already past that check finishes. Whether a call may have reached its server is decided only by whether it passed that check (`BotMcp.call`): one stopped before it, by a refusal, a retirement or its 60-second timer while it still connects, settles failed, never uncertain. When it reaches done, failed or uncertain, the same `bots.db` transaction queues one chat turn keyed `action:<actionId>` (`insertActivationOnce`, provenance `action_result`) that tells the owner its result; a paused bot's turn waits for Resume (`nextChat` skips it while any pause holds), while the owner's own messages still get their turns. When no turn can be queued (the grant was revoked or narrowed while it ran, or the bot's thread is in the trash), the outcome is posted in the chat instead as one notice (`bm_<actionId>_result`, "Mail · Send was sent. Alpha can't follow up on it now."), which says what happened by how the call settled: "was sent", "was sent; the tool reported an error", ": Mousse couldn't tell if it went through" (uncertain), or "was not sent" (refused before it reached the server), which the bot reads in its next turn. History forgotten while the call ran removes its words, never that the tool reported an error, so the notice still says it was sent; neither is ever added later, so the result reaches the owner exactly once. Not now records the answer and starts no turn.

Existing rows remain review cards even with the switch off. The card shows only what Mousse stored from the call, using the masked copy. Every argument stays readable, including all recipients, the sending account, attachments and subject. Arguments sit in a framed data region, with each value drawn separately. Values longer than 280 characters or four lines open in place; short bodies show directly; a scrolling region signals when more remains below. Text and non-text values have distinct styles, and empty text is labelled. Quoted text escapes its own quotes and backslashes, so text containing quotes or the words “(empty text)” stays distinct. Field names show line-break marks and “(no name)” for an empty name. Non-ASCII letters or digits in addresses, domains, links and phone numbers get a neutral note; ordinary prose in other scripts does not. Arguments and the tool’s answer are plain text with no live links. Mousse’s notices sit outside the data region with its own mark. Hidden values have their own marker, and a warning beside Send names each hidden field by its path, with one unquoted box per name segment. Send and Not now are the only answers; neither is selected by default.

A repeated call by the same bot warns when the same service, tool and exact arguments were already sent, answered with a tool error, or had an uncertain outcome, across its work and scheduled runs. The warning includes the day when the earlier call was not today. It cannot catch any change to the arguments, however small: a trailing space, a recipient changed from text to a list, or a different hidden value makes a different call. A settled card shows its title and service, then a short, single-line identifying value from its first visible recipient or subject field (`to`, `recipient`, `email`, `channel`, `subject` or `title`), when present, under the title; then the outcome and settlement time before the tool answer and the review fold. That outcome carries the card’s only time. The fold says “What it sent”, “What it tried to send”, “What it will send”, “What it is sending” or “What it would have sent”, according to the outcome; a tool error keeps the framed tool answer visible. A scrolling review says “More below” without a warning icon. A cold Send is refused cleanly before effects and starts a bounded background refresh; the card stays open with live buttons, and another tap can send once warmed. Startup also warms open cards. Its local refusal ends “Try again when it is available.” An unreachable service leaves the card open; only a successfully loaded, differing binding means it changed. A refused Send reloads the card from the row and shows the service’s explanation. Only an open row offers answers.

An open card can receive at most two nudges through the question follow-up path and the same engine timer. The first is one hour after the owner was told about the original card; the second is 24 hours after the first nudge was told. Questions and action cards share the bot’s spacing budget: at most one nudge an hour and three in 24 hours. Nudges say “Wants to …”, never arrive after the card is answered or withdrawn, or while the switch is off. Telling receipts and nudge rows preserve timing and the count across restart; missed time never produces a backlog. Accepted, settled, forgotten and expired calls do not nudge. An hourly schedule’s card gets the same two nudges, then waits silently. No extra question row or timer is made. Only the newest row for a call shows the full review and its answer buttons. Earlier copies become quiet lines naming the action: the original says Asked and nudge copies say Reminded. The live card keeps the original asked time.

An accepted Send waiting for its service reads `Waiting for <service>…` with no answer buttons; it changes to “Sending…” only when dispatch starts. If the ten-minute window ends before dispatch, the review shows the stored service-unreachable sentence and settlement time, with “What it would have sent” behind the fold. A forgotten review keeps only the readable tool title, “Forgotten”, its outcome and time. It has no sending account, argument box, tool answer or internal counters. A forgotten digest cannot trigger an exact-repeat warning.

When you return to the chat, the bot can see the masked review, its nudges and its latest settled outcome as quoted Mousse updates. Forgetting the card also removes its nudge copies and status facts from the journal and rebuilt older context; a forgotten row adds no further status facts. Those updates do not start a chat turn by themselves.

Find in chat searches a card’s title and visible status line. It does not search argument values or tool answers.

Other devices receive the same card and repeat warning within the bot’s Reach. Like an ordinary permission card, it can be read from a device with View and chat access, but both Send and Not now require Work permission. MCP Send does not additionally require Full access. If the complete card cannot fit, Send is disabled with a request to review and send on the computer; Not now remains available. An older phone app shows the stored plain message and cannot answer the card: `Waiting for <service>…`, the service-unreachable sentence after a timeout, or “[forgotten]” for erased content. About keeps one row per service and its existing switch and Remove. A service with an asking tool says that asks first holds actions that send or change something, and that what it does through threads, commands or secrets it was given does not wait for a card; there is no control to let all future sends through.

A held call belongs to one piece of work and one runtime call in its dispatch. A waiting card keeps its exact arguments, hidden values included, for as long as it waits. Stop, Not now, withdrawal, Forget and clear chat clear those executable arguments. Send keeps them while the accepted call waits for its service or is running, then clears them when it settles, including a timeout or an uncertain outcome after restart. The masked review may remain. Mousse keeps its exact arguments in the action row until it settles; the chat, journal and export get a masked copy. Only unmistakable credential shapes are refused before a card is written: provider-prefixed keys, PEM private-key blocks, a password in a URL's userinfo, or a secret-named URL query value. Document IDs, base64 attachments, JWT-shaped page tokens and prose mentioning passwords remain reviewable. Values are not decoded or normalized to find more possible secrets: split or hex keys, upper-case `SK-` and a zero-width character inside `sk-` remain visible for the owner to judge.

A value is hidden by its key name only where the installed input schema declares that property, following `properties`, array `items`, local `$ref`, every `allOf`, `anyOf` and `oneOf` branch, `if`/`then`/`else`, `dependentSchemas` and indexed `prefixItems`. `$dynamicRef` is treated as unresolved. References have a cycle guard and a 32-step expansion limit. Under a broken, remote or depth-limited schema part, secret-named keys are hidden conservatively throughout that subtree; free-form keys elsewhere remain visible. Invented names in free-form objects stay visible, at every depth. The masked copy represents a hidden value as `{ "$mousse": "hidden", "text": "hidden · will be sent" }`; the exact value is sent unchanged on Send. Literal argument objects with a `$mousse` key are escaped as `{ "$mousse": "literal", "value": <the literal object with its children reviewed> }`, recursively. Text saying "hidden · will be sent" is ordinary argument text. `card_json.hasHiddenValues` records whether a hidden value actually exists, for the card to say so beside its buttons.

Argument text is never cut from the review: at most 256,000 characters of serialized argument JSON are accepted in total, and larger calls are refused with a request to send less. Send names the action and the argument digest shown with it. It is bound to the installed server's configuration, the server id and tool name, the tool's schema, the held server/tool pair and its permission level, and the starting device's permission limit. Unrelated permissions and a grant revision bump leave that binding intact; removing or changing the pair withdraws its card, and granting it again does not revive the old card. A changed binding needs a fresh review. Cards held by the #1340 build use the older whole-grant binding and are withdrawn on upgrade. These are development profiles only; the upgrade fails safe. A device's Send is refused when the complete message and its reply envelope exceed its 56 KiB limit: "Open it on the computer to send." Not now still works.

Mousse makes the stored call once, without asking the model to recreate it. It commits approval and then the start of execution separately. After a restart, an approved call is checked again before running; a call whose execution had started becomes uncertain and is never repeated. A call that never left Mousse, or Not now, reads "Not sent". When the server answered with an error the row is `failed` but reads "The tool reported an error": the work gets its framed error and is told that the tool may have done part of it, so it must check before trying again. A request sent without an answer becomes `uncertain`, "Couldn't tell if it went through".

Settled actions join the same ordered, timed updates as waits, notes and answers. An action that caused the resume leads with its outcome. Its id is kept on the dispatch. Work's stored updates (waits, action outcomes, notes and answers, including work without wait history) count as told only when a dispatch carrying them produces model output or completes. Nonempty model text or thinking, or a model tool-call start, confirms delivery; merely preparing or starting a request does not. A failed, interrupted or replaced dispatch without that evidence leaves its updates pending, including after a time-limit card. A repeated update is acceptable; losing one is not. Carried/read (`read_at` and `applied_at`, plus the dispatch's `workDelivery`) keeps its existing meaning for late taps, Forget and compaction. Confirmation is a separate fact used only to decide what the next prompt carries: `unreadWorkAnswers`, `unreadWorkQuestion` and `unreadWorkNotes` include carried-but-unconfirmed updates without clearing those read markers. New carrying dispatches start with `prompt.workTold = pending`; `BotStore.confirmWorkDelivery` changes only that marker to `output` or `completed`. Reads happen before any confirmation write transaction, so a dispatch with no updates never opens one. A failed confirmation is caught and logged once per dispatch; it never fails the runtime's turn, and the next continuation can carry the update again. Completion of a new dispatch is confirmed explicitly; older rows with no marker also accept a completed stored outcome. Startup recovers a completion written before settlement. A usage retry carries the previous prompt's update ids, so it confirms only what that prompt contained. A database written by master as of #1339 has `workDelivery` for work that waited but no confirmation marker. If its carrying dispatch ended at a wall, a deadline or a turn cap, its notes and answers can be told once more after upgrading (twice is acceptable; losing them is not). Their carried/read behavior is preserved. Earlier databases with no such delivery ids gain no retrospective replay. Approval parks before a time or event wait. Work that has ended for good has no unread action outcome. An admitted continuation moves the work to running before reading its updates, in the same transaction that inserts its dispatch; a failed previous turn cannot hide an outcome from recovery. Admission uses the engine’s existing continuation guards, including for network, usage, restart, reload, more room and Continue.

A held call is withdrawn, with executable arguments cleared in the same transaction, when its work ends (Stop, failure or a limit included), its card or the owner's request is forgotten, or its grant changes. Removing its tool or MCP server withdraws it on positive configuration evidence or when a successful listing no longer contains that tool. Starting, failing and not-yet-listed servers leave cards intact; Send still checks the binding. An accepted call waits for its service for at most ten minutes after the tap. The row reads "Not sent". A tool or permission withdrawal lets the work carry on with the outcome through the same unread updates; forgetting only its card withdraws and forgets the call, then continues the work told: "Your owner removed this request. Do not ask for it again unless they write." No tombstone text is read back to the work. Forgetting its request ends the work through the normal engine ending, with its journal entry and release of scratch, browser, progress and live status. A work row stranded on a settled call without its continuation marker ends too. Forget of a card or its request also tombstones the content of every matching action, including settled calls, in both its record and export. A running call is never withdrawn: it settles, or becomes uncertain after a restart. Deleting the bot keeps withdrawn and settled rows until the 30-day purge.

`/clear` ends work waiting on its cards and removes the cards with the chat; running and settled action records stay, preserving the protection against running a call twice. `/reset` ends all work first and keeps those records too. `/forget history` also replaces every action's display arguments, argument digest, card metadata and stored result with fixed forgotten markers. The owner-message and work-note counters in its card metadata stay, as do its call key, target, status and timestamps. A forgotten row no longer matches an argument digest; the call key still prevents a second execution. A late result cannot restore forgotten content. Exact arguments of an already running call stay until it settles; the work's runtime transcript and the provider's own session are not rewritten.

An owner pause keeps a held card: a pause is not a refusal. Send says `Resume <bot> to send this.` while paused. Pausing also withdraws an approved call still waiting for its service; recovery while owner-paused settles it as not sent, and its outcome joins unread updates for Resume. A work or schedule card has no expiry: it waits for Send, Not now, Stop or an existing withdrawal cause (tool or permission change, schedule edit, removal or end, switch off, bot removal or Forget). Already-open development cards stop expiring too. Already-expired rows keep their text and refusal. The unused `expires_at` column is filled with `9999-12-31T23:59:59.999Z` for new rows to satisfy the existing schema; neither the due timer nor Send reads it for open cards, so no database-version change is needed. An accepted Send must reach the service within ten minutes of the owner's tap (`APPROVED_SEND_WINDOW_MS`, from `answered_at`), independent of how long the card waited. The due timer includes that deadline, so restart, sleep or a missing listing cannot leave it waiting indefinitely. Before dispatch the row stays `approved`, with message text `Waiting for <service>…`; execution changes it to `running`, "Sending…". Past the ten minutes it settles `failed`, clears executable arguments, and says `<Service> couldn't be reached, so nothing was sent.` The work gets that outcome once through the ordered update list and may decide to ask again. A late Send on that timed-out card says “This can't be sent any more.” Only a cold, still-open card invites a retry. This timeout is neither a declined nor an expired card: it does not trigger the identical-call refusal. Once dispatched, a running call settles normally or becomes uncertain after restart.

For owner-started work, forgetting a still-open or accepted waiting card blocks further calls of that tool in that piece of work until the owner writes or notes the work, including calls with changed arguments. Another tool is unaffected. Forgetting an already settled card only removes its content: it keeps its sent, not-sent, tool-error or uncertain outcome and does not block later calls. This uses a content-free owner-removal marker and owner-input numbers in the tombstoned card metadata; no digest or call content is kept for it.

For work started by an owner message or tap, after Not now or an older row’s expiry the same work cannot post another card for the same tool and argument digest until its owner writes to the chat or adds a note to the work. That refusal writes neither a card nor an action row; a Mousse update in the same ordered list preserves it for the next continuation. It is not an owner note: it neither steers the work as owner words nor starts another turn or report. Its delivery is confirmed on model output or completion, as for settled calls. A changed call after Not now gets a new card, however many cards were declined or expired before it. Mousse compares exact arguments: it cannot tell that a reworded message is “the same email”. Asks are not counted, in line with the tool plan. Any owner row, including a tapped answer to a question, lifts the exact-repeat refusal, as it does for wake loops. Only one call can wait at a time, and all later app tools are refused until it is answered. Send and Not now reset the work's wait chain and its repeated-wait history, as the owner's question answer does; an expiry does not.

The engine keeps its action-note and action-owner counters in `bot_memory_state` under `cursor:action-note:<work>` and `cursor:action-owner:<work>`. These survive restarts without a database-version change and are deleted in the transaction that ends the work. Pending Mousse refusal updates use `cursor:action-refusal:<work>:…`; their ids travel in `workRefusalIds` and they are removed when output or completion confirms delivery. Unconfirmed updates survive an interrupted continuation while work remains resumable (for example running, waiting or paused). They are deleted in the same transaction that makes the work terminal (`done`, `failed` or `cancelled`); startup also removes entries for already ended or missing work. All of this state stays out of the memory export and is removed by the bot's purge. The numeric owner/message facts in a tombstoned card remain for refusal decisions.

Hidden argument values of four to eight characters require an adjacent character outside `[A-Za-z0-9_]` only at an edge whose own character is an ASCII letter, digit or underscore. Other edges require no boundary; longer values are replaced wherever they occur. Values shorter than four characters are left alone. Replacement runs in the server's own text before Mousse frames it, including JSON-escaped string echoes and numeric echoes. Credential masking still applies to the result. Transformed echoes (for example encoded, upper-case or truncated values) are not caught by this exact-value replacement. The stored result is capped at 64 KiB in total; images are omitted with a note, never cut into invalid data. Journal key-name masking applies only to work with a held action; other work keeps master's tool input capture.

Send and Not now require Work access from the answering device, within the bot’s Reach and subject to the complete-card size check above. Executable arguments are cleared from the action row with every settled state. The model's own tool call, including its exact arguments, remains in the work's runtime transcript and the provider's session file. Mousse does not rewrite those transcripts; clearing the stored action arguments does not remove those copies. Asks first is on by default and holds the bot’s own MCP calls classified as asking at call time. What it does through threads, commands or secrets it was given does not wait for a card. It does not cover commands (including background and secret commands), browser actions, the owner’s threads or thread jobs, approval answers, messages to other bots, or MCP tools that only read.


A scheduled run holds its exact call and parks until Send, Not now, Stop or withdrawal. It keeps its thread and receives the outcome in the same ordered unread updates as work; output or completion confirms delivery. Later calls by the run and its subagents, including thread tools, are refused while its call waits. Calls after the first hold in that turn are told: “Not sent: one call already waits for your owner in this turn, and this one was not held. End your turn now. After your owner answers, ask again only if it is still needed and is not the same request.” Later occurrences of that schedule are skipped as “the bot is waiting for your answer”, including while the resumed run finishes; other schedules can run beside it. With asks first off, scheduled calls run exactly as before and create no held row.

A schedule keeps at most one run waiting on a card, however long it waits; missed occurrences collapse into one. Its binding includes only the saved instructions, timing, end date, model or pick, on/off state and fixed line, independent of scheduler ticks. A name or Tell me change keeps the card valid. A paused schedule refuses Send. Saving an edit to those fields withdraws the waiting card and tells its run. Send rechecks the revision too, and a stale Send returns “This changed since you saw it. Nothing was sent.” immediately. If the schedule save succeeds but approval cleanup fails, the edit still succeeds and chat and About refresh; the stale call remains fenced by the revision check and cleanup is retried during reconciliation. Removing or ending a schedule withdraws its open calls in the run-ending transaction; a parked run delivers its last report without another approval card. Older expired cards from the same schedule still show as one line, such as “3 expired · not sent”. When they all name the same action, the line names it too. The line opens in place to show each compact review, its asked and expired times, and its “What it would have sent” fold. Quiet copies of those calls stay folded with them; their stored rows remain.

The identical-call refusal after Not now or an older row’s expiry and a forgotten-card refusal share one history per bot and tool across all schedules and work started by a turn the owner did not start. This includes work handed off by creation, wakes, default answers or another bot’s message, and automatically started reminder work. Different calls are not counted. Unattended work and schedules share a limit of three open cards per bot and tool. Only open cards count; answering one frees a place. Declined, sent, withdrawn and older expired cards never count. Owner-started work has no such cap beyond its one waiting call. Work started by the owner’s own message or tap keeps its per-piece history. Removing, recreating or editing a schedule does not lift them: a bot can edit its schedules too. A refused run is told to carry on without the call, say what it skipped in its report and wait for the owner's words. A new occurrence cannot reset that refusal. Approval notices are told at least Soon.

Unread counts the stored message rows even when older adjacent expired cards show as one line. An older phone shows each stored row separately. The expired-card fold applies within the displayed chat and stops at an unrelated row, including a summary of older chat; a waiting card stays visible. Nudge copies stay quiet, do not count as expired calls and do not split their call’s group.

For every origin, a call identical to one already waiting on an open card for the same bot, service and tool is refused with an explanation that it is already waiting for the owner. The refusal explains that the earlier card can still send the call once, and tells the work to say that in its report rather than claim it was not sent. That card’s eventual outcome still belongs only to the work that held it. No new action or card is written, and it does not create another waiting card. A retry with the original call key still finds its existing row. Different owner-started pieces of work may each hold different calls.

The fact that lifts a refusal is unchanged: any message or tap from the owner counts, including an answer to a question the work asked with `wait: false` while it kept working. It lifts the identical-declined and forgotten-card rules; it does not make a duplicate of a still-open card. Work origin comes from its stored starting activation (`trigger.from`): owner messages use `chat:`, tapped answers use `answer:`, and unattended starts have other keys. An unresolvable origin is refused rather than guessed.

A tap on a question asked by an unattended turn is an owner start: work handed off by that tapped-answer turn gets the owner’s per-piece exact-repeat history. Unread still counts the stored message rows while the chat displays one folded expiry line.

The Automations inbox keeps a scheduled run waiting on a held-call card running until its continuation ends; Send, Not now and an older row’s expiry do not finish its inbox row by themselves.

#### Letting one automation act alone

In your own chat message, ask to let one automation do one thing without asking. Send one of its calls first. The computer then offers Allow and Not now for that automation, that tool, and the exact destination arguments of its newest successful sent call. A tool whose input schema declares no place always asks. Names from structured results are shown when they identify the destination; otherwise its exact value is shown. This is answered on the computer; a phone cannot Allow it. Display names come from the tool’s earlier result; Details always lists the raw place values.

Allow keeps a computer-local exception, separate from the bot's grant. Only that automation, tool and place can use it, and only for calls that already ask first. Run now is an occurrence of the same automation and can use its exception. Work, subagents and independent runs gain no authority. The argument names must match the sent call exactly. Only string body, subject, text and content fields and safe file names may vary. Objects, arrays, numbers, null and all other arguments stay exact, including nested destinations. Text may reuse an address-like token only from the sent call’s same field. Email addresses, URLs (including `//host/path`), handles (`@name`), hosts, IP addresses, host:port pairs, schemes and dotted words count. A new token gets a card; a repeated signature address is fine with surrounding punctuation. Sentence breaks, labels such as “Total: value”, plain times, amounts and dates may change. After 20 calls for that tool in an hour or 100 calls for the bot in a day, an automatic call becomes an ordinary Send / Not now card. Calls the owner sent count too. Send still works above those limits. The card says “Kai has used this action 20 times this hour. Send this one too?” or “Kai has used tools 100 times today. Send this one too?”

A `name` may vary only when its sent value has a non-empty extension and the tool declares a folder-like place: folder, folder ID, parent, parent ID, path, dir, directory, drive or drive ID. Otherwise it stays exact, including extensionless names and names of branches, tables or DNS records. A varying file name keeps its extension (case-insensitive), has at most 255 raw characters, starts with a letter or digit, and uses only letters, digits, spaces and `._()+,-`. It must already be in NFKC form with no invisible format characters. Trailing spaces or dots, `..`, percent escapes and Windows reserved stems such as CON, NUL or COM1 are refused. Common domain endings (`com net org io dev app co ai info biz gov edu me us uk de`) keep a name exact even in a folder-like place. The raw name is what gets sent.

Dotted words such as “report.pdf” and “Node.js” count as address-like tokens in text. A new one asks first; one already present in that same field may repeat while the surrounding words change. This deliberately errs on the safe side. A space only after a dot, as in `evil. com`, is treated as a sentence break; `evil . com` still asks. Bracketed dots such as `evil[.]com` ask. Human word forms such as “(dot)” and “(at)”, and phone numbers, are outside this check. Bare legacy IPv4 shorthands such as `127.1` and `2130706433` are free text without a scheme, as are short numeric forms such as `10:80` and `127:1`. The left side of a free-text ratio has at most three digits; larger numeric host:port forms ask.

The address check normalises text, strips combining marks and invisible characters, and decodes numeric and named HTML entities and percent escapes once; ordinary typographic entities are decoded too; unknown named entities ask; it never changes the text sent. Consent is refused when the sent call has more than 256 distinct address-like tokens. Text longer than 64,000 characters after NFKC asks without scanning. Currency amounts (including refunds such as `-$5.00`, `-€12,50` and `−$5`), percentages, the units `k M B ms s h d x`, ISO timestamps, ratios, time ranges and numeric labels such as `Tickets:4` may vary. A capitalised numeric label keeps its label word from the sent call’s same field; lowercase host:port values stay exact. If the sent call’s masked review cannot establish its exact arguments, it always asks. A stored review cut to 32,000 characters cannot establish long inline content exactly (for example, a base64 scan above about 24 KB), so that call asks each time; a current Send card may retain the full review. Earlier argument contracts are discarded when these rules change.

About lists each exception with Remove and no switch. A phone can remove one. The first detected change to the tool schema, server identity or configuration removes the exception; changing it back does not restore it. Send a new call and ask again. Removing the schedule, changing its prompt, revoking the tool pair or grant, deleting the bot, or forgetting its memory or history removes the exception. Forgetting any sent call removes all of that bot’s exceptions, which fails safe. A call interrupted by a restart is reported as uncertain when the run continues; every later call to that tool in the same run asks first, even with reworded content. Its final report says that the first attempt may already have gone through, even when a retry was declined or failed. Only a declined retry of an uncertain call to the same target gets the retry header; it is prepended and keeps every original report line. A plain decline keeps the bot’s report unchanged, including quiet reports. A tool-reported error does not latch the run, because the server answered. Changing only the time keeps it. Temporarily switching MCP or a tool off, or a server being unavailable, keeps the exception but prevents its use until the same binding is available again. The asks-first rollback setting ignores all exceptions and refuses new requests.
