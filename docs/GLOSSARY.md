# Glossary

Use these terms in issues, PRs, comments, and docs. If you need a term that is not here, explain it the first time it appears or use plain words instead. Add a term only when people will keep using it.

- **Daemon (MMS):** the background process (`mousse-cli service run`) that runs the Mousse Main Service. It owns agents, queues, the scheduler, and channels, and keeps running when clients quit.
- **Client:** the Electron GUI or the CLI. Clients talk to the daemon over a local socket and never run agents themselves.
- **Profile:** one person's threads, projects, schedules, channels, and settings inside an installation. Provider credentials and the model catalog are shared by all profiles.
- **Project:** a workspace directory registered in a profile.
- **Thread:** a conversation and its work history. A thread that changes a Git repository gets its own branch and worktree.
- **Turn:** one user message and the agent work it starts.
- **Run:** the saved record of a turn in the Run Engine, with its own ID. Stop, Steer, and Undo act on a run.
- **Steer:** a message sent to a turn that is still running, to change its direction.
- **Stop:** ends what a thread is doing and everything its subagents are doing, at every depth. The Stop button, the CLI, a channel's `/stop`, Lineage's Stop and Stop all, `task_cancel`, deleting a thread and settling it are all the same Stop. A subagent's result that is already waiting to be read is kept.
- **Provider:** the agent backend a thread uses, such as Claude or Codex. Each provider has an adapter that translates its protocol.
- **Provider instance (instance):** one configured provider a profile can pick, with a stable id such as `claude`, `codex`, `pi:openai` or `claude:work`. Every caller chooses an agent by instance id and model. Settings → Providers shows each instance as an entry.
- **Private home:** the folder of its own (`<profile>/harness/<id>/home`) an instance of Claude Code, Codex or Grok runs in, so it signs in to its own account and never reads the user's `~/.claude`, `~/.codex` or `~/.grok`. An instance without one runs on the user's own setup.
- **Signed out in Mousse:** an instance on the user's own setup that was signed out on its card. Mousse stops using it and keeps it signed out across restarts, while the agent's own sign-in (in a terminal) is unchanged.
- **Known problem:** an agent version listed as not working with Mousse in the compatibility table (`docs/providers/compatibility.md`). Nothing runs on it until it is updated or the user runs that version anyway.
- **Setup matrix:** the table of which agent setups (operating system, where the agent comes from, how it signs in) were tested, and why the others are not: `docs/providers/setup-matrix.md`, generated from `setup-matrix.json`.
- **Agent telemetry:** an agent's own usage and error reports to the company that makes it. Each provider's Telemetry setting (Off or Agent's own setting) decides whether Mousse starts it with the agent's documented switch; Mousse never edits the agent's files. Off is the default for agents Mousse sets up, the agent's own setting for the user's own CLIs. Mousse itself collects no usage data.
- **Agent:** a model working in a thread, including any subagents it starts.
- **Subagent:** a thread the main thread of a conversation starts to do part of its work. It has its own thread and history, runs with its own model and workspace, and reports its result back to the thread that started it (its parent).
- **Lineage:** the section of the thread side card that lists the subagents a thread started, with their status and model. A subagent does not appear in thread lists (the sidebar, search, the CLI, channels); the desktop app shows it under its parent, and a parent row shows what its subagents are doing.
- **Subagent card:** the entry in a thread's conversation for one task it gave a subagent. It shows the subagent's name, state, model and last result, stays after the task ends, and opens the subagent's thread. A call that failed or started nothing keeps its ordinary tool row.
- **Delegation:** one task handed to a subagent, with its own ID and result. Giving the same subagent a second task is a second delegation on the same thread. A delegation ends as done, failed, stopped or interrupted, and that outcome does not change once the result is read. While the subagent is still waiting on its own subagents or on a delivery, the delegation is waiting on subagents and has no result yet; it ends once the subagent has nothing left to wait for.
- **Subagent title:** the short name a thread gives a subagent when it starts it, such as "API reviewer". It is unique among that thread's subagents and is how the thread later continues, reads or cancels that subagent.
- **Continue (a subagent):** send a follow-up to a subagent that already exists, by its title. It carries on in the same thread with what it already read, as a new delegation, instead of a new subagent starting from nothing. A message a person types in a subagent's thread is also a follow-up, and its parent hears the result.
- **Background work:** agents and shells a provider started that keep running after the turn that started them ended. Claude keeps one live process per thread so they survive. While a thread has background work it shows Waiting, and a subagent's task waits too.
- **Continuation run:** a run of a thread that records a turn the provider started on its own, because background work finished and the provider wants to read the report. It opens with a short note and ends at the provider's result.
- **Workflow:** a published sequence of steps that can run from the canvas, chat, CLI, channels, or schedules.
- **Bot:** an agent a person sets up once to do one job on its own, within permissions they approved. A personal bot runs only for its owner, on the owner's own providers.
- **Space bot:** a bot a member adds to a Space, which answers in the Space's chat. Its code lives in `bots/space/`, apart from personal bots.
- **Grant:** what a bot's owner approved: the tools, folders (read-only or writable), skills and MCP tools the bot may use, and its limits. The bot works inside its grant without asking.
- **Wall:** the point where a bot needs something its grant does not cover, such as another tool, another folder or more time. Its dispatch ends, and the bot waits for its owner's answer.
- **Escalation:** a bot asking its owner for something outside its grant on its own initiative. The owner answers it like a wall.
- **Activation:** one run of a bot, from its trigger (by hand, a schedule or a channel message) to its end. It starts on a fresh thread and may take several dispatches.
- **Dispatch:** one turn an activation sends to a provider. A wall ends a dispatch; the owner's answer starts the next one on the same thread.
- **Context thread:** a thread a bot keeps across activations and consults for background, such as notes on a project. The bot's main thread asks it questions; it never acts by itself.
- **Owner identity:** the account a bot's owner confirmed on a channel, so the bot answers its owner there and nobody else.
- **Scratch folder:** a private folder Mousse makes for each activation, outside the bot's folders, where its commands run and keep temporary files. Mousse deletes it when the activation ends.
- **Channel:** an outside chat connection, such as Telegram, Discord, or a webhook, that sends messages to Mousse and gets replies.
- **Mousse Net:** networking between Mousse installations. It covers Bridge and Spaces.
- **Bridge:** one person controlling agents on several of their own machines from one place.
- **Remote thread:** a thread that runs on another of the user's computers through Bridge; the target computer owns it. It is listed, opened and worked on like a local thread: the only differences are the computer's name and whether that computer is online. The editor button opens the thread's folder in an editor on this computer over SSH, when this computer has an SSH route to that computer. Features that need that computer's own screen (the live agent browser, deleting permanently, starting a workflow) say where they run.
- **Works on threads:** the signed permission (the `settings` capability in a device's delegation) that lets one of the user's computers act on threads that run on another of their computers. Only computers get it; phones never do, and a phone keeps the smaller phone API.
- **Let my other computers work on this computer's threads:** the switch on the computer that runs a thread (Settings, Devices, or `mousse-cli bridge threads on|off`). It is on by default, and a computer still needs Works on threads, and stays within its highest permission mode and its terminal switch. While it is off, that computer answers none of the thread actions that other computers send it, whoever holds Works on threads.
- **Qualified id:** the name of a thread or project on another of the user's computers, `<nodeId>:<id>`. A thread or project on this computer keeps its plain id.
- **Merged lists:** this computer's threads, projects and statuses together with those of the user's other computers, as one list for the windows on this computer (behind the routing flag). A row of another computer carries `node`, and its project says `sameAs` the project of this computer with the same Git history. The CLI and phones get this computer's lists alone.
- **Project group:** one entry in the sidebar's Projects view. A project of this computer and the projects of other computers that hold the same repository (they share a Git remote, so `sameAs` names the project here) are one group, with all their threads, each thread row still naming its computer. A project that exists on another computer only, or matches only by its first commit (`similarTo`: forks, templates), is a group of its own, named with its computer. A group stays, with offline rows, while a computer is out of reach.
- **Block (a device):** a setting on one computer that refuses every Bridge call, stream and request from one other device, at once. It is kept on that computer only, needs no authority, and is undone with Unblock.
- **Highest permission mode (for a device):** the most permissive permission mode a person on another computer can run a turn or create an "Always" rule in on this computer. A new computer starts at Auto-accept edits.
- **Editor connections from this device:** the per-device switch on the computer that runs a thread that lets one other computer open its editor on this computer's folders: its `ssh` signs in to this computer's own SSH server, carried inside Mousse Net, and always ends there (the other computer never names a host or a port). It is off by default and separate from "Terminals from this device". It ends at once when the device is blocked, the switch (or "Let my other computers work on this computer's threads") goes off, the device loses "Works on threads" or is revoked, or Net is turned off. It is the same as shell access for the user on that computer, and this computer needs an SSH server running.
- **Ask for editor connections:** when "Editor connections from this device" is off for a computer on another computer, its editor button becomes "Ask <computer>". The other computer shows "Let <computer>'s editor connect to this computer?" and "Gives shell access." with Allow and Not now, in the window and as a desktop notice. Only Allow turns the switch on, and only there. Not now is recorded, and the same computer is told so without anyone being asked for 30 minutes; at most three asks an hour reach a person. Each ask and answer is in that computer's audit.
- **Terminals from this device:** the per-device switch on the computer that runs a thread that lets one other computer open, type into and stop a terminal there. It is off by default. A terminal opened this way starts in the thread's own folder, in that computer's default shell, and ends at once when the device is blocked, the switch goes off or Net is turned off, and after 10 minutes with no connection from the device. It is the same as shell access for the user on that computer.
- **Activity (of a device):** what another of the user's computers did on this one, shown under its row in Settings, Devices: a line of plain words for the last 7 days, the recent actions with links to their threads, what it read in the last day, and the "Always" rules a person on it made, with Clear. It is read from this computer's own audit and is not sent anywhere. A turn it sent is marked "from <computer>" in the transcript.
- **Space:** a group chat for a project. Members add their own bots, which run on the owner's machine with the owner's keys.
- **Mousse ID:** the optional account service. Signing in lets a person reach their computers from a phone and relays connections without seeing their content. It was called Mousse Plus; code and wire names such as `net.plus.*` and `plus-relay` keep the old name. There are no paid plans. The hosted service is maintained separately; this repository holds only its MIT client in `src/mms/net/plus/`, which core Net reaches through `src/mms/net/hosted.ts`. Builds without `MOUSSE_ID_ORIGIN` show no Mousse ID UI.
- **Leaf node:** a device, such as a phone, that joins a user's devices but cannot invite or revoke others.
- **Nightly:** a prerelease build of `master`, published once a day when there are new commits and every check passes, with a version such as `0.1.2-nightly.20261022.17`. See `docs/releases.md`.
- **Contract version:** the version of a protocol, saved format or schema that other builds rely on, such as the daemon protocol or the Run Engine database. Bumped only on incompatible changes; listed in `src/mms/contractVersions.ts`.
- **Primary checkout:** the first entry in `git worktree list`, normally the copy the user runs and reads.
