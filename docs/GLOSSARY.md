# Glossary

Use these terms in issues, PRs, comments, and docs. If you need a term that is not here, explain it the first time it appears or use plain words instead. Add a term only when people will keep using it.

- **Daemon (MMS):** the background process (`mousse-cli service run`) that runs the Mousse Main Service. It owns agents, queues, and the scheduler, and keeps running when clients quit.
- **Client:** the Electron GUI or the CLI. Clients talk to the daemon over a local socket and never run agents themselves.
- **Profile:** one person's threads, projects, schedules, and settings inside an installation. Provider credentials and the model catalog are shared by all profiles.
- **Project:** a workspace directory registered in a profile.
- **Thread:** a conversation and its work history. A thread that changes a Git repository gets its own branch and worktree. Deleting a thread deletes the thread only: its worktree, branch, uncommitted changes and snapshots stay until the person removes them. Deleting a thread never happens on its own: only a person deletes one, from Archived.
- **Archived:** a thread put away from the sidebar's main list (Archive). It keeps its history, worktree and branch, an archived thread is unpinned and runs nothing, and Unarchive brings it back. Expiry archives a thread too. In code, storage and the API it is `archivedAt`, `archiveThread` and `threads.archive`; never call it settled. (Older Mousse versions called it settled: `settledAt` and `threads.settle` are still read from them.)
- **Turn:** one user message and the agent work it starts.
- **Thread database (`thread.db`):** where a thread keeps its history: one SQLite database in the thread's folder, with every message stored once as a row, and images and large outputs in the folder's `blobs/`. Deleting the thread's folder deletes it. Threads made before it are imported from their JSON files in the background, and those files are kept unchanged as a backup. See `docs/thread-storage.md`.
- **Snapshot:** a record of every file in a thread's worktree at one moment, kept as a Git commit under `refs/mousse/` that belongs to no branch. Each turn is recorded as a snapshot before and after, so the agent's own branches, commits and pushes never collide with Undo. See `docs/workspace-snapshots.md`.
- **Publish:** puts a thread's latest snapshot into the primary checkout as one commit on the branch it is on, made with your own Git identity. Uncommitted files are published too; the thread's own branch is not merged. It never writes over an ignored file in the primary checkout; it refuses with the file names instead.
- **Retired worktree:** a thread's or subagent's worktree that storage cleanup took off disk. It first waits in Mousse's trash, moved there whole, and comes back as it was when the thread is used. After an hour with no change in it, the trash keeps a snapshot of its files and deletes the folder; using the thread then rebuilds it from that snapshot.
- **Subagent result:** what a subagent (or a workflow agent) left when it finished, reported to its parent: where it worked, the files it started from and finished with (kept as snapshots), and its branch and commits. Mousse never merges it; the parent agent brings the work in with Git.
- **Run:** the saved record of a turn in the Run Engine, with its own ID. Stop, Steer, and Undo act on a run.
- **Steer:** a message sent to a turn that is still running, to change its direction.
- **Note:** a message one agent sends another thread with `thread_send` intent `note`: information that grants nothing. It arrives labelled with the sender, never as the user's words, and never answers a question or approval.
- **Chain:** the agent messages that follow from one run a person or a schedule started: every message, settle notice, wake and delegation it led to carries the chain's id. A chain may send 12 counted messages (work, a first message, a note that asks for attention) before a person decides whether it goes on; a person's message in the thread gives it a new budget.
- **Held message:** an agent's message past its chain's budget. It is kept, not dropped, until the person chooses Continue (it is sent, in order) or Stop (it is dropped and its sender told).
- **Stop:** ends what a thread is doing and everything its subagents are doing, at every depth. The Stop button, the CLI, Nest's Stop and Stop all, `task_cancel`, deleting a thread and archiving it are all the same Stop. A subagent's result that is already waiting to be read is kept.
- **Provider:** the agent backend a thread uses, such as Claude or Codex. Each provider has an adapter that translates its protocol.
- **Provider instance (instance):** one configured provider a profile can pick, with a stable id such as `claude`, `codex`, `pi:openai` or `claude:work`. Every caller chooses an agent by instance id and model. Settings → Providers shows each instance as an entry.
- **Private home:** the folder of its own (`<profile>/harness/<id>/home`) an instance of Claude Code, Codex or Grok runs in, so it signs in to its own account and never reads the user's `~/.claude`, `~/.codex` or `~/.grok`. An instance without one runs on the user's own setup.
- **Signed out in Mousse:** an instance on the user's own setup that was signed out on its card. Mousse stops using it and keeps it signed out across restarts, while the agent's own sign-in (in a terminal) is unchanged.
- **Known problem:** an agent version listed as not working with Mousse in the compatibility table (`docs/providers/compatibility.md`). Nothing runs on it until it is updated or the user runs that version anyway.
- **Setup matrix:** the table of which agent setups (operating system, where the agent comes from, how it signs in) were tested, and why the others are not: `docs/providers/setup-matrix.md`, generated from `setup-matrix.json`.
- **Agent telemetry:** an agent's own usage and error reports to the company that makes it. Each provider's Telemetry setting (Off or Agent's own setting) decides whether Mousse starts it with the agent's documented switch; Mousse never edits the agent's files. Off is the default for agents Mousse sets up, the agent's own setting for the user's own CLIs. Mousse itself collects no usage data.
- **MCP relay:** the second MCP server Mousse gives an agent, `mousse-relay`, through which Claude Code, Codex, Cursor, ACP agents, Antigravity and Grok use the MCP servers set up in Mousse. It is on for every one of them by default and can be turned off per agent in Settings, Skills & MCP. Claude Code and ACP agents use their own approvals for relayed tools; on Codex and Cursor, Mousse asks in the thread unless it is in Full access. Mousse still refuses a relayed tool for a bot and for a read-only subagent. The Mousse agent (model APIs) calls the servers directly and has no relay.
- **Agent:** a model working in a thread, including any subagents it starts.
- **Subagent:** a thread the main thread of a conversation starts to do part of its work. It has its own thread and history, runs with its own model and workspace, and reports its result back to the thread that started it (its parent).
- **Nest** (formerly Lineage): the section of the thread side card that lists the subagents a thread started, with their status and model. A subagent does not appear in thread lists (the sidebar, search, the CLI); the desktop app shows it under its parent, and a parent row shows what its subagents are doing.
- **Side chat:** a fork of a thread, with the thread's conversation so far, opened from the thread's Side chats panel to ask something on the side. It lives only in that panel: no thread list or search shows it, and nothing said in it reaches the thread. It works in the thread's checkout, on the thread's model unless changed. Archiving the thread ends its side chats; deleting it deletes them.
- **Subagent card:** the entry in a thread's conversation for one task it gave a subagent. It shows the subagent's name, state, model and last result, stays after the task ends, and opens the subagent's thread. A call that failed or started nothing keeps its ordinary tool row.
- **Delegation:** one task handed to a subagent, with its own ID and result. Giving the same subagent a second task is a second delegation on the same thread. A delegation ends as done, failed, stopped or interrupted, and that outcome does not change once the result is read. While the subagent is still waiting on its own subagents or on a delivery, the delegation is waiting on subagents and has no result yet; it ends once the subagent has nothing left to wait for.
- **Settle notice:** what Mousse tells a thread's agent about work it started in another thread with `notify` (`thread_send`, or `thread_create` with a first message): once if the work waits for a person, and once when it ends. Mousse writes it, not either agent; the chat shows it as a notice row that opens the other thread. It starts a turn when the thread is idle and waits in its queue otherwise.
- **Subagent title:** the short name a thread gives a subagent when it starts it, such as "API reviewer". It is unique among that thread's subagents and is how the thread later continues, reads or cancels that subagent.
- **Continue (a subagent):** send a follow-up to a subagent that already exists, by its title. It carries on in the same thread with what it already read, as a new delegation, instead of a new subagent starting from nothing. A message a person types in a subagent's thread is also a follow-up, and its parent hears the result.
- **Remote subagent:** a subagent an agent starts on another of the user's computers (`delegate_task` with `computer`). That computer runs it as an ordinary thread, under its own agents and accounts, in its project that holds the same repository, and its questions are answered there. Its parent continues, reads and stops it like any subagent; its result names the branch its work is on there. Agents may start one only when "Let agents work on your other devices" is on in Settings → Agents → Agent access (off at first), and only on the computers turned on under it. It runs no looser than its parent and within the highest permission mode that computer set for this one, which can be Full access.
- **Background work:** agents and shells a provider started that keep running after the turn that started them ended. Claude keeps one live process per thread so they survive. While a thread has background work it shows Waiting, and a subagent's task waits too.
- **Wake-up:** a thread agent's or bot's note to carry on later in its own thread without the person writing (`wake`): at a time, when another thread finishes its turn, or when a pull request merges, its checks settle or it gets a review. It is kept across restarts and sleep, grants nothing, and waits while the thread waits on the person's answer. A thread's pending wake-ups show with its background work; Stop, archive and delete cancel them. Subagents set none.
- **Continuation run:** a run of a thread that records a turn the provider started on its own, because background work finished and the provider wants to read the report. It opens with a short note and ends at the provider's result.
- **Workflow:** a published sequence of steps that can run from chat (its slash command), the CLI, or an automation.
- **Automation:** work that runs on its own. A trigger (a time, a request, a pull request's checks, reviews or comments, a `mousse-cli automation run` call, or Run now) starts a run: its Who (an agent, or one of the person's bots) does what it says in its project, usually on a thread of its own. A bot's schedules are automations with the bot as Who. **Tell me** sets the lowest report level that notifies, on an automation or on a bot for its unattended work reports and wake replies: Needs you, Worth a look (the default), FYI too or Every run; a failed run always does. The code calls an automation a scheduled job (`ScheduledJob`); the CLI is `mousse-cli automation`, with `schedule` as an alias.
- **Draft (automation):** an automation that is saved but never on and never runs, shown as a card with what each run is asked to do, When, Who, Project and May. A draft an agent wrote in a chat may do no more than that chat's mode. The Automation manager, a bot with the automation tools, or an agent in any chat (`automation_draft_save`) makes one. Turn on makes it the person's own automation, within their permissions; a bot allowed to "create and turn on automations" may turn on the drafts it wrote (`automation_enable`). Discard deletes it. The Inbox lists drafts under Drafts.
- **Automation manager:** the agent that turns what a person types in the Automations composer into a draft, asking a question first when it needs to. It is the default agent on one hidden thread per profile, reused for every request, and works in the project picked in the composer (or in a folder of its own).
- **Inbox:** the Automations page: every run of every automation, in the Chats sidebar's place. Runs still going sit on top, then Needs you, Worth a look, FYI, and Quiet runs folded. A run opens beside the list as its own thread, under a strip with its level, its pull request, its usage, Too noisy, Should have told me and Resolve. Manage lists the automations themselves, to turn on or off, edit or delete.
- **Needs you:** the Inbox's queue of what an automation is waiting on: a run that reported Needs you, a run that failed, and an approval or question on a run's thread. An item stays until it is resolved (Resolve, or answering the approval or question where it was asked); opening the run never resolves it. Items for an automation whose Who is a bot are assigned to that bot and folded under Assigned to bots.
- **Tuning note:** a dated note on an automation, written by Too noisy or Should have told me on one of its runs. Its newest five reach every later run, so its agent learns what is worth reporting. Manage lists them, with Remove.
- **Bot:** an agent a person makes from a look and one sentence to do one job on its own, within permissions they approved. It lives in the Chats tab, where its owner talks to it in its bot chat; it runs when asked there and on its own schedules. A personal bot runs only for its owner, on this computer and the owner's own providers. Its models are named only on Runs on (in About and New bot), beside its name at the top of About (its Talk model), in one chat line when a model picked there can't run, and on the line of one piece of work the owner asked to run on another model, and in the owner's own `/model` lines in the bot chat. See `docs/bots.md`.
- **Bound secret:** a secret the owner gave a bot for one HTTPS service. Mousse keeps the value and adds it only to that service's fixed authentication header through a GET or HEAD read. Known services also fix the allowed path segments and version headers. Commands outside a sandbox can still read the owner's secret-store files.
- **Space bot:** a bot a member adds to a Space, which answers in the Space's chat. Its code lives in `bots/space/`, apart from personal bots.
- **Grant:** what a bot's owner approved: the tools the bot may use beyond what every bot has, and its limits. The bot works inside its grant without asking. Every bot also has, without a grant, the profiler, Mousse's look, scheduled jobs, secrets the owner gives and quick actions, and, unless switched off in About, every MCP server set up in Mousse, every skill and the automation tools.
- **Use your threads:** the bot permission, off by default, to read, search and act on its owner's reachable threads. Work and scheduled runs, their subagents, and chat turns started by creation, an owner message or tap, a wake, a question or a job may act under the grant. A turn from another bot's message is read-only. A thread it starts runs under the starting device's limit (Full access on this computer); a message uses the target's mode. Answering an approval also requires the computer's “Agents may answer approvals on other threads” setting, except in a thread the bot started: there it answers that thread's own questions and approvals, whoever started the turn, and they don't ping the owner. Private threads and other bots' threads stay out of reach. The owner can switch the permission off in About. See `docs/bots.md`.
- **Create and turn on automations:** the bot permission, off by default, to turn on automation drafts the bot wrote, or write one and turn it on at once (`automation_enable`), as if the owner pressed Turn on. Without it a bot only writes drafts. It is asked for like any tool, refused on a turn another bot's message started, and goes with the automation tools' switch in About. See `docs/bots.md`.
- **Wall:** the point where a bot needs something its grant does not cover, such as another tool or more time, while its owner is chatting with it. Its dispatch ends, the bot's reply carries an ask, and the answer continues the turn. In a run, a missing permission is no wall: the call is refused and the run carries on. Work the owner asked for that runs out of time or turns posts what it has and waits for an ask for more, and Allow carries it on; a scheduled run that runs out ends, with an ask for more.
- **Escalation:** a bot asking its owner for something outside its grant on its own initiative (the `escalate` tool). The owner answers it like any other ask. The code calls every ask an escalation (`bot_escalations`).
- **Activation:** one piece of a bot's work, from its trigger to its end, in one of two lanes. A chat activation answers the owner's message on the bot's home thread; a run activation (by hand or a schedule) works on a fresh thread of its own. A bot has one chat activation at a time and no count on concurrent run activations, and an activation may take several dispatches.
- **Dispatch:** one turn an activation sends to a provider. A wall ends a dispatch; the owner's answer starts the next one on the same thread. A detached supervisor process ends a dispatch that runs past its time, even if the daemon is gone.
- **Bot subagent:** a helper a bot's work starts for one part of its job, on the work's model or one it picks, on a hidden thread of its own. It can do only what the bot can, is never held less tightly than its work (on another provider entry it runs without what that entry would hold less tightly), never asks the owner anything, returns its result to the work, and ends with the work's turn. See `docs/bots.md`.
- **Context thread:** a thread a bot keeps across activations and consults for background, such as notes on a project. The bot's main thread asks it questions; it never acts by itself.
- **Scratch folder:** a private folder Mousse makes for each activation, outside the bot's folders, where a bot on Pi works and keeps temporary files (on Claude Code and Codex it works in its files folder). Mousse deletes it when the activation ends. A bot's chat turns reuse one, emptied between them.
- **Bot chat:** a bot's conversation with its owner, in the Chats tab. It shows the owner's messages, the bot's replies (drawn as a thread's, with their applets and pictures) with their activity chips, its run reports, its asks and its errors, and never tool rows or model names. It is read from `bots.db`, not from the bot's threads.
- **Fixed line:** words Mousse posts without a model run: a service line such as a nudge, or the exact text saved as say on a schedule.
- **Active (owner):** Mousse observed owner input or a focused, non-idle app window within the last 15 minutes. Bot output and tool calls never count.
- **Telling:** a bot message's banner and possible sound, kept and decided in the service separately from the chat record. Read messages tell nothing; nearby reports fold into one banner.
- **Bot work:** something a bot does beside its bot chat, so the chat stays free while it works. The chat hands work off (anything in the browser, with commands, or with several steps; a quick web search, page or MCP call it makes itself), work runs on a thread of its own, with all its pieces able to run beside each other, and its report answers the message that asked for it. While it runs, the owner can ask how it's going, add to it or stop it. Scheduled runs share the same line. See `docs/bots.md`.
- **Reminder (bot):** a one-off time a bot keeps for its owner ("in 20 minutes", "at 9 tomorrow"). It says its text at that time, with no model run, or starts work then. For 24 hours after it is said, a text reminder can be snoozed with quick replies for 10 minutes, 1 hour or tomorrow at 09:00 on this computer. Snoozing creates a new reminder without a model run. Repeating ones are schedules.
- **Ask:** a bot's request for a permission, shown as a card in its bot chat with Allow and Not now. In a chat turn it is a wall; in a run, the bot carries on without the permission and later runs skip that step until the owner answers. A bot has one open ask per permission, and asks never expire or run out. After Not now, a run may ask again only after 24 hours, and no turn asks for it again until the owner writes or what the grant gives changes. Allowed permissions are listed in About, with Remove; what every bot has by default (MCP and each server, skills, automation tools) is listed with a switch only.
- **Allow everything:** a bot's Full access, switched on in About after a dialog: every tool and permission a bot can be given, without asking. About lists each one it gives with its own switch. The owner's switches, Settings and Labs, what each kind of turn may do and asks first still apply. See `docs/bots.md`.
- **Asks first:** a tool permission that holds each call for the owner to review its complete masked arguments, then choose Send or Not now. On by default for MCP calls that send or change things, decided from the tool’s read-only hint and name at call time. Support can set `experimental.botAsksFirstOff: true` in the settings file; the old `botAsksFirst` key is ignored. About lists permissions per service; it has no “Always” choice.
- **Let alone:** permission for one bot automation to use one tool in one exact place without a card, while the tool, its server and the automation’s prompt are unchanged and its hourly and daily call limits have room. Its argument names stay the same; only string content and safe file names may vary. Text may repeat address-like tokens from the sent field, and a file name keeps its non-empty extension in a folder-like place. Other calls still ask.
- **Held call:** one exact tool call stored by Mousse while it waits for review: its work waits with it, while a chat turn that held one ends and its result comes back to the chat as a turn of its own. Send names that call and the arguments the card showed; Mousse executes the stored call once. Its card keeps the masked content and outcome afterwards.
- **Question (bot):** a bot's question to its owner with answers to tap: 2 to 5 short choices or yes/no, and "Other…" for an answer in their own words, shown as a bubble with quick replies under the bot's reply. A tap is the owner's reply, but not their own words: the turn it starts may act on their threads under its grant, but can't switch models. Any other message from the owner moves past it, and a later tap still answers it. It grants nothing; a permission is an ask. A bot may ask up to four at once, and take one back it no longer needs. Work the owner asked for, and a scheduled run, can ask too: it waits for the answer without keeping a provider turn running, shows as waiting on you, and goes on in its own thread once answered. If the owner doesn't answer, Mousse nudges them, or the bot goes with its default answer, as the bot chose when it asked. See `docs/bots.md`, Questions.
- **Nudge:** a fixed line Mousse posts under an unanswered bot question or held-call card (a card says “Wants to …”), "Still need your answer on this one.", with the question's buttons again; no model runs. At most two per question or card (a question’s first nudge comes when the bot said; a card’s comes one hour after the owner was told; the next comes about a day after the first was told), and at most one an hour and three a day per bot. Work that waits on the question or card keeps waiting. Held cards stop nudging after an answer or withdrawal, while accepted or settled, or with their switch off.
- **Card (bot):** a small block a bot attaches to its message: facts (keys and values), a checklist, progress, or a gallery of pictures from its files folder. The app draws each kind from its own components; the bot sends only text and numbers. Each also reads as plain text, for notifications, other devices and the bot's memory. See `docs/bots.md`, Cards.
- **Default answer:** the choice a bot names when it asks a question, for a minor choice that is easy to undo, and goes with if its owner hasn't answered in the time it gave (at least 15 minutes). The bot carries on and says so ("No answer, so I went with A."), and the question shows "No answer · went with A". It is the bot's own choice: never the owner's words and never a permission. The owner can still answer later, and the bot hears it.
- **Run report:** what a run of an automation or a bot reports when it ends: a level and a short summary for the person (the `run_report` tool; a second call replaces the first). The level is Quiet, FYI, Worth a look or Needs you; a run that ends without a report has none (No report) and counts as Worth a look. A bot's run report is also posted in its bot chat, and is its notification.
- **Look:** a bot's face: a clay mouse in one of 8 colours wearing one of 12 accessories. The owner picks it when making the bot and can change it from the bot's menu.
- **Depth:** how much time a bot takes: quick, normal (the default) or deep. Its work levels are the same three, called light, medium and hard: the bot gives each piece of work a level, and work that names none, scheduled runs and reminders use the bot's standing depth, which the owner changes by asking ("think harder", "be quicker").
- **Bot models (Talk and Work):** a bot's rows on Runs on (in About and New bot). Talk runs its chat; Work runs its work, and under Advanced each work level (Light, Medium, Hard work) has a row of its own. Each row is a model the owner picked on one provider entry, with its reasoning level, in the app's model picker; New bot needs Talk and Work. A pick runs only on that entry: at its usage limit work waits for the reset, and when it can't run for another reason the bot is stuck with Pick a model. Bots made before picks keep Mousse choosing until their owner picks. Under Advanced, an **Images** row picks the model the bot makes pictures with; it may stay None, and only a bot with a pick there can make pictures.
- **Bot journal:** Mousse's complete record of what a bot did and was told: every message, run report, ask, answer and tool call, kept in `bots.db`. A bot's memory, chat summary and search are built from it. See `docs/bot-memory.md`.
- **Bot memory:** the short, dated facts about its owner and notes a bot keeps and sees in every turn, within a fixed size. The owner manages it by asking the bot ("remember …", "forget …", "export your memory").
- **Bot tool catalogue:** how a bot reaches the tools beyond its core set (memory, replies, asks, work, reminders, thread basics). Its instructions name each group in one line; the bot reads a group with `tool_catalogue` when it first needs it, which also gives that group's guidance. On Claude Code every tool is listed and loaded on demand by its tool search; on Codex and Pi only the core set is listed, and the rest are called through one fixed `use_tool` entry. Every permission and refusal is the same either way. See `docs/plans/bot-context.md` §15.
- **Chat summary:** a short summary of a bot's older chat, kept in `bots.db` and given to every turn with the recent messages. Mousse folds the oldest messages into it without a model call.
- **Files folder:** the folder where a bot keeps the documents it makes and copies of the files its owner attaches (`<profile>/bots/files/<botId>/`). The bot may always write there; it is not memory, and none of its contents are read back into prompts: only its files' names and dates are. Its file tools reach no other folder but its scratch folder: "use files on this computer" was removed, and a grant an older build wrote with it keeps working without it.
- **Bot browser:** a bot's own browser, which it uses once its owner allowed "use the browser": a browser without a window, on a Chromium profile of that bot alone, apart from the owner's tabs and every thread's. Sites the owner signs in to there stay signed in for that bot. Its reply shows a live preview of it; Expand opens the split view, the browser beside the bot chat, where the owner can take it over and give it back. Both get pictures only while they are on screen, pushed as the page paints. See `docs/bots.md`.
- **Hold (of a bot browser):** what Take over gives one app window: the bot's browser is that window's until it gives it back or goes away for two minutes, and its input goes to the page in order, each input answered (applied, or refused with a reason). Another window sees it held elsewhere and takes it over only on purpose.
- **Browser grant:** what lets the agents of a task tree a person started use the browser. The person's run roots it; their subagents, the wakes that deliver results and the continuations join it while the tree still has work, and all use the root's browser. Each agent that acts drives a tab of its own; a read-only or Plan agent only reads pages. Schedules, webhooks, remote origins and other agents' messages get none. See `docs/agents-workflows-profiles-browser-architecture.md` §10.8.
- **Agent cursor:** the pointer Mousse draws over a browser tab where an agent is about to click, type or scroll, in a thread's in-app tab and in a bot browser's preview and split view. It is drawn above the page, never put into it, so pages and what agents observe never contain it, and it fades after a few idle seconds.
- **Mousse Net:** networking between Mousse installations. It covers Bridge and Spaces.
- **Bridge:** one person controlling agents on several of their own machines from one place.
- **Remote thread:** a thread that runs on another of the user's computers through Bridge; the target computer owns it. It is listed, opened and worked on like a local thread: the only differences are the computer's name and whether that computer is online. The editor button opens the thread's folder in an editor on this computer over SSH, when this computer has an SSH route to that computer. Features that need that computer's own screen (the live agent browser, deleting permanently, starting a workflow) say where they run.
- **Works on threads:** the signed permission (the `settings` capability in a device's delegation) that lets one of the user's computers act on threads that run on another of their computers. Only computers get it; phones never do, and a phone keeps the smaller phone API.
- **Let my other computers work on this computer's threads:** the switch on the computer that runs a thread (Settings, Devices, where its row reads "Let other computers work here" and the switch keeps the full name; or `mousse-cli bridge threads on|off`). It is on by default, and a computer still needs Works on threads, and stays within its highest permission mode and its terminal switch. While it is off, that computer answers none of the thread actions that other computers send it, whoever holds Works on threads.
- **Private thread:** a thread that stays on the computer that started it. It is never listed, searched, opened or run from the user's other computers or phones, even with Bridge on, and the Run on menu is locked to this computer. Everything it starts is private too: its subagents, threads its agents create, and workflow agents; its agents cannot start work on other computers or send to a thread that is not private, and agents in other threads do not see it. A thread is private from the moment it is created (the lock button in the new thread's toolbar, or New private thread) and stays that way. Its worktree branch keeps its temporary random name: its first message is never sent to name it. Its messages still go to the model provider like any other thread's. With its worktree off it works in the project's own folder, whose files and commits other computers can read through Git; a computer that browses the project's files can also see the Git records Mousse keeps for it, and one with terminal access reaches everything on this computer.
- **Expiry (of a thread):** the time a thread archives itself, set from the new thread's toolbar (the clock), the thread's menu (Archive after…) or the bar above it, where it can be changed or removed before then; a private thread can start with one set in Settings → General → Runs. At expiry the thread is archived, as Archive does, and its expiry is removed, so it can be unarchived and used again. Nothing is deleted. Its subagents on other computers expire with it: their computer is given the expiry and every change or removal of it. A run still going waits to end, unless the thread was set to stop it. A thread that expired while the computer was off is archived on the next start, and no turn starts in an expired thread meanwhile.
- **Qualified id:** the name of a thread or project on another of the user's computers, `<nodeId>:<id>`. A thread or project on this computer keeps its plain id.
- **Merged lists:** this computer's threads, projects and statuses together with those of the user's other computers, as one list for the windows on this computer (behind the routing flag). A row of another computer carries `node`, and its project says `sameAs` the project of this computer with the same Git history. The CLI and phones get this computer's lists alone.
- **Project group:** one entry in the sidebar's Projects view. A project of this computer and the projects of other computers that hold the same repository (they share a Git remote, so `sameAs` names the project here) are one group, with all their threads, each thread row still naming its computer. A project that exists on another computer only, or matches only by its first commit (`similarTo`: forks, templates), is a group of its own, named with its computer. A group stays, with offline rows, while a computer is out of reach.
- **Block (a device):** a setting on one computer that refuses every Bridge call, stream and request from one other device, at once. It is kept on that computer only, needs no authority, and is undone with Unblock.
- **Highest permission mode (for a device):** the most permissive permission mode a person on another computer can run a turn or create an "Always" rule in on this computer, and the most a remote subagent that computer's agents start here can run in. A new computer starts at Auto-accept edits.
- **Agent reach (for a device):** which threads of this computer another computer's agents may change (start, message, steer, stop), set beside its highest permission mode in Settings → Devices → Limits ("Agents on <device> may change"; or `mousse-cli bridge limits <node> --agent-reach`): Nothing, Threads they started (the default) or All threads. Reading follows the device's ordinary access. It is a rule for a computer that marks its agents' calls as it should, not a barrier: blocking the device and its highest permission mode are the controls for one that is not trusted.
- **Work on threads from this device:** the per-device switch on one computer (Settings → Devices → Limits, or `mousse-cli bridge limits <node> --work on|off`) that lets another device start, send to, steer, stop and change threads there, see its files and Git, and make or change bots. It is on by default. Off, the device still reads threads and chats with bots (within each bot's own permissions), and every other call from it, a person's or an agent's, is refused with the reason `work_off`. Which call is which is the access table, `src/shared/net/accessClasses.ts`.
- **Access from this device (presets):** three choices on a computer's row in Settings → Devices that set its switches at once: **View and chat** (reads threads and chats with bots; work, terminals and editor off), **Work on threads** (the defaults) and **Full control** (terminals and editor on, Full access, agents may change all threads). Switches that match none show as Custom. Phones have none. The presets are in `src/shared/net/accessPresets.ts`.
- **Share bots with other devices:** the switch on each computer (Settings, Devices; or `mousse-cli bridge bots on|off`) that lets the user's phones and other computers list this computer's personal bots and chat with them. It is on by default and stored on that computer. While it is off, the lists other devices read carry no bots and every `bots.*` call they make is refused (`forbidden`, reason `setting_off`).
- **Devices (of a bot):** which of the owner's devices reach one personal bot, set in its About on the computer that holds it: All my devices (the default), Only this computer, or Chosen devices. **Bots on this computer** is the switch per device in Settings, Devices that lets that device reach none of the bots there. A device that is left out finds no such bot: it is in none of its lists, and every call about it answers as for a bot that is not there. See `docs/bots.md`, Two layers.
- **Editor connections from this device:** the per-device switch on the computer that runs a thread that lets one other computer open its editor on this computer's folders: its `ssh` signs in to this computer, carried inside Mousse Net, and always ends there (the other computer never names a host or a port): at Mousse's own SSH server inside the daemon, which needs no SSH server, no key and no setup on this computer, or at the computer's own SSH server when its owner chose "Use this computer's SSH server". It is off by default and separate from "Terminals from this device". It ends at once when the device is blocked, the switch (or "Let my other computers work on this computer's threads") goes off, the device loses "Works on threads" or is revoked, or Net is turned off. It is the same as shell access for the user on that computer. A Windows computer uses its own OpenSSH server instead only when the endpoint's helper is missing or does not run.
- **Mousse's SSH endpoint:** the SSH server inside the daemon that answers another computer's editor connection itself, so a computer needs no SSH server, no key and no setup. It is reached only through the Mousse tunnel (it listens on no port), logs in the device that opened the tunnel, and stops everything that device started when it is blocked or switched off. It is the default for paired computers; a Windows computer whose endpoint helper is missing or does not run uses its own OpenSSH server, and so does a device that already had "Editor connections from this device" on when the endpoint arrived, until its switch is turned off.
- **Use this computer's SSH server:** a choice on one computer (`mousse-cli bridge editor-server system`, off by default) that sends its other computers' editor connections to this computer's own SSH server instead of Mousse's endpoint. It needs an SSH server running here and a login it accepts. A computer the person reaches with their own SSH (an approved address) is never affected.
- **Ask for editor connections:** when "Editor connections from this device" is off for a computer on another computer, its editor button becomes "Ask <computer>". The other computer shows "Let <computer>'s editor connect to this computer?" and "Gives shell access." with Allow and Not now, in the window and as a desktop notice. Only Allow turns the switch on, and only there. Not now is recorded, and the same computer is told so without anyone being asked for 30 minutes; at most three asks an hour reach a person. Each ask and answer is in that computer's audit.
- **Terminals from this device:** the per-device switch on the computer that runs a thread that lets one other computer open, type into and stop a terminal there. It is off by default. A terminal opened this way starts in the thread's own folder, in that computer's default shell, and ends at once when the device is blocked, the switch goes off or Net is turned off, and after 10 minutes with no connection from the device. It is the same as shell access for the user on that computer.
- **Activity (of a device):** what another of the user's computers did on this one, shown under its row in Settings, Devices: a line of plain words for the last 7 days, the recent actions with links to their threads, what it read in the last day, and the "Always" rules a person on it made, with Clear. It is read from this computer's own audit and is not sent anywhere. A turn it sent is marked "from <computer>" in the transcript.
- **Connect link:** one line of text (`ml1_…`) made on one computer (Settings → Devices → Add device → Make a link, or `mousse-cli bridge link`) and pasted on another (Paste a link, or `mousse-cli bridge paste`). Made on the computer that keeps the list, it adds a computer; made on any other device of the list, it only connects a device already in it. On a computer with no network identity, making one creates it, and that computer keeps the others connected. A link lasts 30 minutes and a new one stops the last; it is a secret. See `docs/net/protocol.md` §8.
- **Held (device):** a computer that came in by a connect link made here, or the one this computer joined through a link, until a person on this computer answers. Its sessions open but this computer serves it nothing else. Allow connects it here with Work on threads; Remove (on the computer that keeps the list) revokes it; Not now and restarts leave it held. Mousse ID's automatic connection never lifts a hold, but other computers signed in to Mousse ID connect the new device on their own.
- **Space:** a group chat for a project. Members add their own bots, which run on the owner's machine with the owner's keys.
- **Mousse ID:** the optional account service of Mousse Net v1, shown as "Mousse ID (legacy)" in Settings → Labs. Signing in lets a person reach their computers from a phone and relays connections without seeing their content. Code and wire names such as `net.plus.*` and `plus-relay` come from it. The hosted service is maintained separately; this repository holds only its MIT client in `src/mms/net/plus/`, which core Net reaches through `src/mms/net/hosted.ts`. Builds without `MOUSSE_ID_ORIGIN` show no Mousse ID UI.
- **Mousse Plus:** the paid service of the new networking, signed in to under Settings → Devices. Its hosted relay connects a person's computers when no direct route and no relay of their own reaches, without seeing their content, and the group shows the plan and what is left of it. Networking needs no account: the LAN, SSH, tunnels and a person's own relays work without it.
- **Leaf node:** a device, such as a phone, that joins a user's devices but cannot invite or revoke others.
- **Nightly:** a prerelease build of `master`, published once a day when there are new commits and every check passes, with a version such as `0.1.2-nightly.20261022.17`. See `docs/releases.md`.
- **Contract version:** the version of a protocol, saved format or schema that other builds rely on, such as the daemon protocol or the Run Engine database. Bumped only on incompatible changes; listed in `src/mms/contractVersions.ts`.
- **Primary checkout:** the first entry in `git worktree list`, normally the copy the user runs and reads.
