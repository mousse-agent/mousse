# Workflow slash ingress handoff

Root-owned chat ingress resolves published workflow commands through the same profile-owned resolver and run coordinator as structured CLI and the desktop Run panel. App chat, `mousse-cli chat "/name --field value"`, ordinary one-shot CLI chat and unknown interactive slash commands reach that resolver. Reserved local commands retain their existing handlers. `/workflow name` and `/skill name` disambiguate collisions; `//text` escapes command interpretation. Typed input validation and command tokenization happen without invoking a model or shell.

## Admission and recovery

`MmsWorkflowChatBridge` stores a bounded profile-owned receipt before a workflow can enter the durable message queue. The receipt pins the published revision, typed input, authenticated GUI/CLI source and thread. Caller-owned UUIDs identify logical invocations. An identical retry reads its receipt before resolving the current published head; changed arguments with the same identity fail. RPC clients cannot supply the host-only receipt reference. Preparation validates the workflow, inputs, owner thread/project and available adapters without starting effects.

An ordinary thread execution lease serializes receipt execution with other chat turns. The workflow graph is admitted durably before transcript acceptance. A subsequent retry reuses the coordinator's durable admission identity. The original slash message, internal context and assistant run reference are accepted in one transcript persistence operation; queue provenance therefore cannot become durable without its run reference. After admission, the graph continues in the profile's durable run service. This does not yet bind a graph's main-agent node to an inherited thread execution segment.

Queue serialization preserves host-owned invocation references, rejects malformed references instead of converting them to ordinary prompts, deduplicates the same invocation, and prohibits promoting a workflow command into steering input. Removing a queued invocation, including stop-and-clear, tombstones its receipt before deleting the queue entry. A lost removal acknowledgement cannot revive the invocation with the same request ID. A durable clear failure is surfaced instead of reporting a memory-only queue clear.

Receipts are UUID-addressed regular files below a checked profile directory. Reads have a 2 MiB limit, reject receipt-file and receipt-directory symlinks, detect a changed canonical receipt root, compare opened and final file identities, and validate version, owner, run parameters and metadata. A version-2 integrity digest binds the complete pinned receipt body, and execution compares recovered queue content with the receipt's original command before admitting a run. Command inputs retain the resolver's tighter tokenizer/schema bounds. Receipt retention/garbage collection remains a follow-up; cancellation tombstones must survive any replay retention window.

## Clients

The renderer and interactive CLI retain up to 32 failed-send identities under hashes of their request content and thread/profile context. Successful sends evict the entry; hashes avoid retaining complete messages or image payloads in the retry cache. Renderer continuations check the visible profile/thread before changing errors or loading state. GUI IPC forwards a caller UUID and creates one for legacy callers. Failed slash sends surface the resolver's structured error and restore text to an empty composer.

One-shot CLI slash execution prints the admitted run and uses the existing workflow wait/exit-code behavior, or returns with `--no-wait`. `--request-id` supports a retry after losing a reply. Slash invocations reject provider/model/API-key override flags before connecting; the run uses its configured definition. A busy thread currently reports queued acceptance and exits: following that queued receipt until it becomes a run remains open. Interactive chat returns after admission and displays subsequent thread events. Both command namespaces are documented in CLI help.

## Evidence and qualification limits

The fixture uses actual owned `MousseMainService`, authenticated framed GUI/CLI clients, durable profile storage and separate built CLI processes. It covers typed inputs, trusted source selection, foreign-profile rejection, forged receipts, repeated admission, publication changes while queued, queue removal and stop-and-clear, same-home host reconstruction, and an injected fault after graph admission but before transcript acceptance. An assertion at the real `mutateThreadData` boundary checks that workflow user-message provenance and its run reference persist together. Model and title calls are rejected by fixture spies for explicit workflow execution.

The initial five-file run passed 66 tests and full type checking. Later tests/builds encountered ENOSPC while browser fixtures retained copied Chrome installations and old oversized download payloads. Those interrupted/failed results are not passing evidence. A persistence-boundary assertion was also corrected to observe `mutateThreadData`, which the production profile service uses, instead of `saveThreadData`.

Final qualification after space recovery: `npm run build` passed for app and CLI, both TypeScript projects passed, and six files / 70 tests passed (`platformWorkflowCli`, `threadMessageQueue`, `cliSessionCommands`, `cliLaunch`, `protocolValidation`, `platformWorkflowInvocation`). The built CLI tests ran after the build finished, with no concurrent build-output mutation. The new stop-and-clear test proves that a delayed first admission is aborted, queued invocation receipts are tombstoned, retry is rejected, and no graph starts. The original provider catalog refresh in the headless queue fixture is now isolated so persistence verification makes no network catalog call.

Host reconstruction is not an OS-process kill test; the injected fault is an explicit admission boundary fault. Existing separately reviewed W02 fixtures provide workflow-engine process-kill evidence. No live model/provider/account/channel was used. Renderer code has build/typecheck coverage here, but this slice does not claim rendered chat interaction qualification.

Open work includes workflow completion/argument forms, interactive run cards and debugger navigation, queued CLI wait/cancellation lookup, full renderer retry/attachment behavior, receipt retention, workflow activity in thread deletion/settlement guards, main-agent workflow tools and execution segments, native/CLI/MCP/Skill/browser adapter composition, schedule/channel targets, and packaged app/CLI qualification. Independent Sol review is recorded in `docs/implementation/agent-platform/reviews/sol-workflow-cli-slash.md`. No release gate closes from this slice.
