# Blank chat workspace toolbar

I extracted the project and worktree toolbar from teammate PR #41 (`9e9136d`), retaining its themed floating project picker, No project and Open project choices, device label, branch toggle, keyboard navigation, and responsive layout. I apply it to the initial composer and unstarted project drafts; it disappears after the first prompt starts the chat.

I persist workspace choices with each draft in its profile-local workspace state. A worktree requires a selected project and uses the existing thread worktree opt-in API. The first send waits for creation or a draft's worktree update. Changing projects creates a new hidden draft instead of relocating an existing thread's transcript. I transfer staged text, rich references, browser attachments, files, and voice notes before selection/model calls so a service failure keeps the prompt recoverable.

I preserve the current default branch's structured send errors and microphone handling. I check the active profile and thread before applying a returned model update, and I prevent workspace preparation from starting after navigation. I integrate rich-reference attachments alongside the toolbar while keeping agent DM and Group creation separate. I retain its existing worktree protocol and portable Chromium fixture.

The focused checks are `tests/createComposerThread.test.ts`, `tests/threadWorktreeToggle.test.ts`, and `scripts/check-composer-workspace.mjs`. The Chromium fixture covers project/worktree selection, draft changes, keyboard and outside-click dismissal, pending navigation, creation/selection/model failure recovery, structured send rejection, rich-reference resolution/transfer/recovery, project-path loading, profile-local persistence, and narrow layouts. Its platform flags exercise the shared renderer; native platform behavior remains outside this fixture. I made its SVG resolution and screenshot output use native filesystem paths on Windows.

I keep unresolved project-path lookups separate from confirmed standalone threads, so switching project threads preserves the Files or Git view. Project pills and project-context file links resolve the referenced project’s own draft instead of falling back to the previously active project, and I cancel their renderer updates after navigation or profile changes.

## Run on another computer

With no other computer to pick, the computer item is plain text naming this computer (`appInfo.deviceName`, else "This computer"): there is no button, no menu and no hint. Once at least one other computer is connected and threads of other computers are routed (`net.status` shows `netBridge` and `netBridgeThreads`; `bridge.nodes` lists the devices; phones and a device from a daemon that predates `kind` are handled as below), it becomes a button that opens a "Run on" menu: this computer first, then each connected computer. Phones are left out, and a device with no `kind` counts as a computer. A connected computer that does not hold "Works on threads" is named but cannot be picked, and the row says to turn it on in Settings, Devices. The thread side card's menu uses the same rows (`sideCard/deviceMenu.ts`) and shows its Run on group under the same rule; only a new, empty thread can pick, and a started thread just names the computer it runs on. A draft that already names a computer keeps the menu, so a computer that dropped offline can be left.

The pick is `ComposerWorkspace.node` in the draft, saved with the other workspace choices. While a remote computer is picked:

- The project picker lists that computer's projects, which this computer already lists with its own (`projects` rows with `node`, under qualified ids `<node>:<id>`). Picking a computer carries the draft's project over only when that computer lists a project that is `sameAs` it, the same Git repository (worked out by the merged lists from root commits and remotes). A folder that is not a repository, or no match, gives No project (the worktree choice is cleared). The draft remembers its project from this computer (`localProjectId`), so picking this computer again restores it, and a move from one computer to another matches from that remembered project. Picking a different project on the other computer drops the remembered one.
- "Open project…" asks for a folder path on that computer, suggests its project paths, and calls `bridge.hub.openProject`. The computer's refusal ("That folder does not exist on this computer.") shows in the dialog. The project is then named as this computer lists it (qualified) and selected.
- The model picker lists that computer's models (`bridge.hub.composerOptions`) and starts at its default; the pick is stamped on the new thread with the ordinary `threads.setModel`. A thread that already runs on another computer shows its model, or that computer's default, from the same list.
- The worktree toggle is sent as `worktreeEnabled`.
- The first send is the same as for a local chat: `threads.create` names the computer (`node`) and the qualified project, the daemon sends it there, and the thread that comes back is activated, selected, given its model and then written to with the ordinary send. If the computer refuses (offline, "Works on threads" off, a limit), its own words show above the composer, the text stays, and nothing is sent; the draft stays on that computer.

Quick actions and file context always use this computer's workspace, so they ignore a remote draft (`localWorkspaceFor`).

The Chromium check also covers the static label, the Run on menu, the project carry-over and its return, Open project on another computer, and the first send (`scripts/check-composer-workspace.mjs`).
