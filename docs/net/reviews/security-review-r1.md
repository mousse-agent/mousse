## Findings

### R1 — Medium: Bot execution gate omits the Space's minimum protocol minor

**Primary location:** `src/mms/bots/admission/service.ts:459` (`usableMeta`). Related: `src/mms/bots/BotProfileService.ts:645`, `:547`, `:840`; `src/mms/bots/execution/service.ts:464`; `src/mms/spaces/host/meta.ts:867`; `src/shared/net/limits.ts:3`.

**Contract:** `docs/net/protocol.md:151` permits reads below `minProtoMinor` but forbids writes and execution. The binary's supported minor is currently zero. A known minor-zero `settings.changed` can validly raise `minProtoMinor` to one: the settings schema accepts an integer, and the transition checks authority and monotonicity, then updates settings without changing the meta status to `upgradeRequired` (`host/meta.ts:870–875`, `:161`). This is distinct from an unknown critical event, which correctly blocks the Space.

**Concrete attack/state:** A currently authorized member sends two recent, independently signed minor-zero mentions to an otherwise qualified chat bot before the administrator raises the minimum. Execution E1 is admitted and its exact `bot.run.accepted` receipt is committed and acknowledged under the old minimum, but E1 has not entered `execution.start()` yet; its final asynchronous head refresh is pending. The administrator's signed settings change is applied. Another pending mention from the same member prepares a fresh, valid `admission` identity proof at the new head (`SpaceCurrentIdentity.ts:131–141`, `:386–425`). E1's head refresh then completes against that same applied head and its start resumes. Its member, signature, placement, policy, budget and receipt remain valid. `usableMeta` checks frozen/upgrade status and confirmed-head freshness but never compares `settings.minProtoMinor` with the supported minor. E1 can enter `running` and dispatch the model below the new minimum.

The second mention/proof refresh is an important precondition: an old scoped identity proof by itself fails the independent exact-head freshness check at `SpaceCurrentIdentity.ts:438–457`. I do not claim that every settings update lets a waiting execution through. The independently refreshable proof establishes current identity; it does not establish protocol compatibility.

**Why existing checks do not stop this sequence:** `onMetaChanged` clears the confirmation and reconciles only executions already in the execution service's `active` map (`BotProfileService.ts:547–550`, `execution/service.ts:464–472`). E1 is still in the profile's waiting/starting path. `startWhenAcknowledged` obtains a new confirmation, checks the stored mention, and starts it (`BotProfileService.ts:866–874`). The stored acceptance was legitimately sent before the setting changed, so requiring a sent receipt does not reject it. Both `mentionForExecution` and the native runtime's per-effect callback ultimately use the same gate without a minimum-minor comparison (`admission/service.ts:291–314`, `BotProfileService.ts:229–230`). The host's append check at `host/service.ts:710` rejects later minor-zero receipts; that does not prevent the already accepted execution's first billable call.

**Impact:** A protocol compatibility restriction that should fence execution can be bypassed for accepted work awaiting dispatch. This permits model spend and, for a qualified reader under its existing tool policy, project reads after the restriction is known. I found no widening of the reader tool inventory or budget ceiling through this omission. Default unqualified adapters still fail closed.

**Suggested fix:** Add a supported/negotiated-minor check to the shared admission and per-effect execution gate, preserving the separately allowed read path. Fence accepted waiting starts as well as active runs when the minimum rises. A focused regression should pause E1 before start, apply the settings change, refresh the same member's scoped admission proof through a second pending mention, resume E1, and assert zero provider/tool dispatch. Also check admission and approval resumption with a fully fresh current proof and an incompatible minimum.

### R2 — Medium: Incremental private records bypass the epoch and writer authorization enforced during snapshots

**Primary location:** `src/mms/spaces/client/service.ts:649`. Related: `src/mms/spaces/private/service.ts:913`, `:1545`, `:1058`; `src/mms/net/sync/subscription.ts:53`, `:188`; `src/mms/net/sync/session.ts:1339`.

**Contract:** A private content event must be authorized by the applicable signed participant/key control, with its current key epoch and author writer prefix. Old keys allow historical local reads, not new writes after exclusion. The honest host enforces this in `private/service.ts:1209–1228`. Snapshot replay independently enforces the control's key epoch and author-node nonce prefix at `:1058–1073`.

**Concrete attack/state:** B was a private participant and legitimately received epoch-one key K1. B remains a Space member with a valid node delegation, but the controller removes B from the private audience and commits an independently signed epoch-two control excluding B. Honest recipient A applies that control. B retains K1, creates a new minor-zero `message.posted` for the same private stream with a fresh event ID, current Space `auth`, current timestamp, `sealed.keyEpoch = 1`, and a correctly authenticated body/AAD under K1, and signs the entire envelope with B's own node key. B supplies it to a malicious host. The host delivers it as the next dense stream position after the epoch-two control on A's existing authenticated subscription.

**Source result:** The client validates the exact signature for `history`, the stream and Space auth bound, and the node-versus-bot event type. For an ordinary human private content event the remaining requirement is just the presence of `sealed` (`client/service.ts:650–661`). It does not check the applicable control's key epoch, author participant/node entitlement, or nonce prefix. The subscription stores the next dense record and advances its cursor. `afterStored` invokes `private.applyStored`, which returns immediately for non-control known content (`private/service.ts:913–916`). The record is therefore durably accepted. `private.open` accepts any retained historical key epoch and decrypts this new K1 body (`:1560–1568`).

**Why existing checks do not stop it:** B signs only as B; no independent-member signature forgery or root compromise is needed. Possession of K1 and its original writer prefix is the documented old-key residual. The honest host's `canWrite` check would reject the event, but a malicious host can bypass its own local checks; receiver enforcement is the missing boundary. The signature and GCM AAD bind the malicious event accurately, but neither proves that epoch one is still writable at this new stream position. Snapshot validation rejects the same post-control epoch mismatch, but ordinary live/incremental replay never invokes that validator.

**Impact:** An excluded private writer and a malicious host can insert newly authored, decryptable records into recipients' accepted private history after exclusion. This is a private-stream integrity/authorization failure. It does not give B K2, reveal later private plaintext, or forge A's signature. The bot admission gate separately requires the trigger's current private key epoch (`admission/service.ts:418`), so this old-epoch payload does not by itself cause a bot run. I did not verify a GUI rendering consequence; the demonstrated source boundary is durable acceptance and successful domain decryption.

**Suggested fix:** Use one position-aware private content authorization validator for incremental commit and snapshot replay. Before publishing each record/cursor, derive the signed control effective at that position and check the epoch, author user/node entitlement, and assigned nonce prefix, plus type-specific bot/owner rules. Preserve legitimate earlier historical reads without treating any retained key as permission to append at a later position. Validate buffered records again when they become contiguous, because their preceding controls may arrive after their initial receipt-time check. A focused regression should apply the removal control, deliver B's freshly signed K1 event at the next position, and assert rejection with no record/cursor commit; then replay legitimate pre-removal history and require it still to work.

### R3 — Low: Bot presence accepts timestamps beyond the specified freshness tolerance

**Primary location:** `src/mms/bots/presence/receiver.ts:73`. Related: `:107–110`, `:170–177`; `src/mms/bridge/BridgeProfileService.ts:420–428`.

**Contract:** `docs/net/state-machines.md:328` fixes a ±60-second tolerance against offset-corrected subject time. The receiver instead accepts ±90 seconds against its uncorrected local wall clock.

**Concrete attack/state:** With synchronized clocks, a malicious current host delays an independently signed bot heartbeat for 75 seconds. Its counter is greater than A's persisted last-seen counter, the bot/host delegations and membership remain valid, and A can obtain fresh presence identity evidence. The host then relays the unchanged packet. The receiver's 90-second check passes and it records the current monotonic receipt time as fresh liveness, despite the packet exceeding the 60-second contract. It displays fresh activity for the next 45 seconds and reaches offline at 90 seconds after receipt.

**Why existing checks do not stop it:** The counter prevents a packet already accepted by this receiver from being replayed; it does not reject a withheld, previously unseen higher counter. Independent signature and current placement prove authorship, not freshness. The production preparation path calls this same receiver after scoped proof preparation and adds no stricter timestamp check. Clock correction is also absent at this gate, creating false rejections for honest skew as well as the expanded acceptance window.

**Impact:** The accepted delayed-heartbeat window is larger than the frozen contract and can extend stale display liveness. Presence is explicitly not execution authority; I found no authorization escalation from this discrepancy.

**Suggested fix:** Enforce the defined 60-second tolerance using qualified subject-clock evidence, including relayed subjects, and fail conservatively when that evidence is unavailable. If a different tolerance/clock rule is intended, resolve it explicitly in the protocol rather than implementing a different silent contract. Add focused 60-second boundary, delayed-unseen-counter, and direct/relayed clock-skew cases.
