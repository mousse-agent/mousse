## Findings

### R2-01 — Medium: Pending TLS handshakes escape aggregate admission accounting

**Primary location:** `src/mms/net/NetService.ts:584`.

**Supporting locations:** `src/mms/net/NetService.ts:588`, `:615`; `src/mms/net/transports/relay.ts:95`, `:158`, `:283`, `:295`, `:300`; `src/mms/net/transports/manager.ts:145`; `src/mms/net/transports/direct.ts:170`.

**Concrete attack and state.** A profile has Net enabled and uses a relay controlled by an attacker. For each listener WebSocket, the relay sends a well-formed `challenge`, receives the client's authentication response, sends `ready`, then sends `paired` with any syntactically valid node ID. For the listener role, the client does not require that advertised peer to match a previously chosen target (`relay.ts:228`). The relay then leaves that carrier open without completing inner TLS, and repeats the sequence on the client's next listener.

The relay client hands each paired byte stream to the daemon and immediately rearms another listener (`relay.ts:295–300`), before TLS or node authentication finishes. Its socket set and the manager's socket set have no local admission-count check. `NetService.accept` compares only established sessions and already-created enrollment gateways against 64. It reserves no slot before awaiting TLS; a gateway is added only after TLS resolves. With no established sessions or completed handshakes, each new attempt therefore sees the same zero count and proceeds. An attacker can accumulate more than the intended connection limit in the TLS phase without a delegated node key or successful inner handshake.

**Impact.** The daemon allocates carrier sockets, TLS state and handshake timers beyond a fixed local pre-authentication connection ceiling. This exposes daemon resource exhaustion, potentially affecting work beyond the attacked route. I did not measure exhaustion or CPU/memory cost. The contract specifies at most 32 total pre-authentication connections and four per address (`protocol.md`, section 9); the current 64-session/gateway check neither implements that total nor counts the earlier TLS phase.

**Why existing checks do not stop it.** The TLS deadline eventually closes an individual attempt, but it does not bound the number admitted during that deadline. The gateway's 16 KiB application budget and authentication deadline start after this omitted phase. The relay server's own endpoint/admission limits protect an honest relay, but cannot be relied upon against the compromised relay covered by SEC-044. Direct's lease accounting is local to each `DirectTransport` instance; Cloudflare and Tailscale instantiate their own Direct listeners. Those per-listener checks do not supply shared admission accounting across carriers. Inner TLS still prevents this relay from becoming an authenticated Bridge caller or reading application plaintext.

**Suggested fix.** Reserve a shared pre-authentication lease synchronously at carrier admission, before the TLS await, and count it through TLS and quarantine until successful authentication or close. Use that allocator for every carrier, including relay, and enforce the agreed total, applicable per-address/principal bounds, byte budgets and one complete authentication deadline. Release leases on every timeout, exception, cancellation and close. An untrusted relay's advertised peer identifier must not give it unlimited separate admission buckets. Keep Direct's HTTP/WebSocket-specific limits as additional bounds.

**Focused future verification.** With an authorized test setup, use a fake relay that repeatedly pairs streams and withholds TLS, and assert that live admitted sockets/handshakes never exceed the shared cap. Also admit simultaneous incomplete handshakes through different carrier listeners and check timeout/close slot reuse. I did not run these checks.

### R2-02 — Medium: Auxiliary RPC paths skip the Bridge feature gate

**Primary location:** `src/mms/net/sync/rpcDispatcher.ts:199`.

**Additional affected location:** `src/mms/bridge/artifacts.ts:93`.

**Supporting locations:** `src/mms/net/sync/rpcDispatcher.ts:59`, `:97`, `:132`, `:208`, `:234`; `src/mms/bridge/BridgeProfileService.ts:163`, `:176`, `:248`, `:273`; `src/mms/net/NetService.ts:203`, `:213`, `:653`, `:1260`; `src/mms/net/sync/session.ts:1105`.

**Concrete attack and state.** The stored, accepted configuration has `enabled: true`, `features.netBridge: false`, and `features.netSpaces: true`. These flags are independently validated; `assertEnabled` permits the profile when either feature remains enabled. Runtime composition still registers Bridge methods, supplies the RPC dispatcher to sessions, and advertises `rpc.v1`.

1. Before Bridge was disabled, a current, same-user node with `read` submitted a `thread.snapshot` or `threads.get` request that durably completed with a result small enough to remain inline (at most 63 KiB). The response need not have reached the caller; its caller/request alias and terminal result remain persisted on the target. After the target restarts with the above feature state, the node connects normally and sends `rpc.result.get` with its own original request ID. The session checks `rpc.v1` and same-user identity; `DurableRpcDispatcher.result` checks the current delegation/capability and caller-bound alias, but never invokes the registered method's `authorize` hook. It returns the retained Bridge result even though a fresh request for the same method would throw `disabled` in `BridgeProfileService`'s hook.
2. A current, same-user node with `write` can send a fresh, durably idempotent `bridge.artifacts.open` request with `{forRpcId: <valid new RPC ID>, forMethod: "bridge.dispatch"}`. The wrapper's capability selector correctly demands `write`. Its `authorize` and handler call `authorizedMethod`, however, which checks only identity/capability and returns the target method without running its `netBridge` hook. `ensure` then creates a new `node.artifact` descriptor/stream and artifact binding in the profile database (`artifacts.ts:422–450`) while Bridge is disabled.

**Impact.** An inbound network session can retrieve retained inline Bridge data or create Bridge artifact state across the intended feature boundary. This is a feature-policy bypass by an otherwise authorized same-user node, not a cross-user or cross-caller result disclosure. In particular, a Spaces session alone does not imply that Bridge is enabled.

**Why existing checks do not stop it.** `dispatch` invokes `method.authorize` before durable admission and before running the handler. `result`, `cancel`, and `authorizedMethod` invoke only the private identity/capability checker. The missing check is exactly where the feature policy is installed. The artifact wrapper checks that the target method is registered/upload-enabled, but not that its feature is enabled. Stream reads, blob fetches and uploads are separately gated in `NetService.makeSession`, so this trace uses an inline result and stream creation; it does not establish a disabled-feature blob upload, fresh agent run or Dispatch execution.

The same hook omission exists in `cancel` (`rpcDispatcher.ts:208`); I did not establish an independent running-work exploit from that path, since disabling all Net performs teardown. I did not find an IPC method for independently toggling these two flags. The finding is conditional on the independently-disabled state explicitly supported by configuration loading. `net.disable` disables both features and tears down endpoints; this attack does not bypass that complete shutdown.

**Suggested fix.** Apply a common current method/family authorization policy to requests, result lookups, cancellation and artifact-open. Feature checks must run independently of handler execution. For retained results, use a policy callable from the persisted method/capability context rather than blindly invoking hooks that require unavailable original parameters. For artifact-open, evaluate the bound upload method's feature policy as well as its capability. Retain caller binding and allow Spaces sessions to keep working when only Bridge is disabled.

**Focused future verification.** With an authorized test setup, complete an inline Bridge result, reopen the target with Bridge false/Spaces true, and assert that both result lookup and fresh dispatch artifact-open fail with `disabled`; confirm that a normal Spaces operation still succeeds. I did not run this check.

- I did not execute supported restore/move paths or the unsupported foreign-private-controller/native-provider histories. I traced their guards and restrictions rather than claiming universal archive compatibility or safe operational retirement of an old host.
- I did not race profile removal/archive/restoration against live IPC binding, network operations, uploads, agent providers or noncooperating child processes. Captured-service ownership and draining fences are present; the complete SEC-052 stale-handle invariant still needs its runtime evidence.
- Already delivered results/keys/plaintext, the owner's intentionally authorized agent execution and Git configuration, a compromised OS owner, and an isolated unretired/pre-freeze host remain outside the protections claimed by the traced gates.
