# Bot runtime and admission contract (v1)

Status: P0 normative consumer contract for P1 storage/identity and P6 bots. This document specifies required behavior; it does not qualify an existing runtime. `MUST` denotes an implementation/conformance requirement. See [protocol](protocol.md), [state machines](state-machines.md), [compartments](compartments.md) and [the plan](PLAN.md) §4.8.

## Qualification and enforcement hooks

I inspected `src/shared/agents/types.ts`, `src/mms/agentDefinitions/runtimePolicy.ts`, `src/mms/execution/SandboxAdapter.ts`, `src/mms/orchestrator/LlmClient.ts`, `PiCodingTools.ts`, `toolPathSafety.ts`, and the installed Pi tools during P0. The adapter IDs below are the repository's runtime kinds. There is no network `BotRuntimeAdapter` implementation at this checkpoint. Consequently `supports(profile)` MUST return false for every profile until its adapter's qualification record proves all applicable requirements below. Selecting a profile in a definition or passing an ordinary runtime test does not supply that evidence.

|---|---|---|---|

P6 MUST retain a record per adapter version, provider/model billing configuration and profile: effective tool inventory; context/session bindings; enforcement hooks; cancellation behavior; bounded spend evidence; targeted negative-test results on the actual execution path. Changed runner/tool versions or provider accounting invalidate the affected record. Unknown adapters/profiles fail `profile_unsupported`. The UI offers only qualified combinations. A transport/crypto spike does not qualify any bot profile.

The immutable run policy is the intersection of the owner definition's grants, the bot profile, and the admitted scope. A fallback model, child, delegated task, resumed session, plugin or tool MUST use that same or narrower policy. v1 bots disable child delegation until an adapter proves inheritance. Runtime tool discovery MUST NOT widen the admitted inventory. The policy must be checked both before advertising tools to the model and immediately before dispatch, including model-invented tool names and aliases.

| Profile | Mandatory behavior |
|---|---|
| `chat` | Register zero tools, including skills loaders, ask-user, memory retrieval, delegation, browser, MCP, shell and provider built-in tools. Build context only from the bound compartment and permitted public history. No project-file, global memory, host environment, resource or unrelated-thread context injection. |
| `reader` | Allow only bounded read/list/search operations through a qualified host-controlled filesystem backend in one bound canonical project root. Deny all writes, shell/process tools, git commands, browser, web/network tools, MCP, plugins, skills loaders, delegation and global-memory access. Search traversal must enforce the same boundary for every result it opens. |
| `operator` | Use the owner's ordinary tool/approval settings. Steer policy MUST be `owner`; role/everyone policies are invalid even when the owner is an admin. Display “runs with your full access”. No filesystem, network or compartment isolation is claimed. Still enforce identity, placement, visibility routing, cancellation, deduplication and budget admission. |

`reader` path checks cover absolute paths, `..`, alternate OS path syntax, symlinks/junctions, root changes and races between validation and open. The backend must read the validated object through a safe handle, or otherwise demonstrate equivalent race containment; a preflight `realpath` followed by an unchecked read is insufficient. It must exclude the profile's stores, credentials, other compartments and provider session caches even when a chosen project root overlaps those paths; an overlapping root that cannot be safely restricted is rejected. Read sizes, traversal depth, result counts and elapsed time are bounded. Restricted runs must not spawn a child with inherited `process.env`; trusted provider credentials may be consumed by the daemon's model connection but never inserted into context/tool results. Existing files in an ordinary project are visible to a reader, including changes made during private operator runs (see compartments).

## Admission decision and timing

Only an ordinary stored `message.posted` envelope explicitly mentioning the bot can trigger work. Snapshot projections, edits, deletes, receipts, ephemeral messages and bot-authored messages never trigger work. The execution key is `(space, bot, event.id)`; two bots mentioned in one event have separate keys, reservations, receipts and backing threads. `payloadHash` is lowercase SHA-256 hex of the exact signed envelope bytes; it is never a hash of parsed/re-serialized JSON, prompt text or a host-modified projection.

The executor MUST run these gates without model calls or tools:

1. Verify the bot's current delegation places it on this node, its roster is conflict-free, its placement is active and its delegation is unexpired/non-revoked.
2. Obtain a host-confirmed meta head for the descriptor's current epoch. Apply the verified meta replica through that head; require a confirmation at most 30,000 ms old on the monotonic clock. The event's `auth.metaEpoch` must match and `metaSeq` must not be ahead. Unknown critical events, a frozen space, stale/conflicting identity or unreadable required private keys suspend admission.
3. Verify the exact envelope signature and author delegation against the pinned root. The author MUST be a current human member, with a current author epoch and matching node; bots cannot trigger work. Check current steer rights, mention target and stream visibility. A `reader`/`chat` approval cannot grant an out-of-profile tool. An `operator` mention from another member is always forbidden.
4. Look up the execution key. A matching hash returns the existing outcome without a new receipt, reservation, rate charge or model call, even if the original mention is now too old. A different hash is `conflict`. Expired and uncertain rows also guard duplicates. This lookup does not authorize new work for an author whose rights have since been removed.
5. Check authenticated clock measurement per the protocol: a correlated pong at most 30,000 ms old, monotonic round trip at most 5,000 ms, and wall elapsed versus monotonic elapsed difference at most 1,000 ms. A hello alone is unqualified. Define `hostNow = localWallNow + hostOffsetMs`. Require `abs(hostOffsetMs) <= 60,000`, `0 <= hostNow - recvTs <= 30,000`, and `0 <= recvTs - envelope.ts <= 120,000`. Exact upper boundaries pass; negative/future values do not. A stale/invalid offset fails `clock_skew`; never clamp future timestamps or extend the window by measurement uncertainty. Live delivery and replay use identical rules. Host receive metadata is not author-signed; a malicious host can falsify/delay it, which is a stated trust limitation.
6. Reject a trigger received by the host before this placement's activation watermark. Reserve capacity/budget and commit admission atomically below. Revalidate the meta/roster/policy revisions used for authorization inside the admission serialization boundary; a concurrent revoke/policy change must not slip between check and commit.

After authorization, a genuinely old delivery (`hostNow - recvTs > 30,000` or `recvTs - ts > 120,000`) calls `ExecutionLedger.expire` to commit an `expired` execution dedup row and one `bot.run.expired` outbox marker atomically; it reserves no money, concurrency or rate slot and invokes no model. Its callback receives the execution record and uses the same transaction; duplicate expiry skips the callback, and conflicting bytes reject. Future times produce `clock_skew`, not an expired marker. An authorization/staleness failure never produces an acceptance receipt. Failed transient gates may be re-evaluated on the same stored event only while the delivery window remains open; they create no open-ended queue.

## Atomic admission and budgets

The admission transaction is on the executor's profile `net.db`; it MUST include all of these, or none:

- unique execution key, payload hash, generated execution ID and `accepted` state;
- reservation of the entire per-run ceiling against `(bot, space, UTC admission day)`;
- concurrent-run slot and the member's persisted hourly admission counter;
- immutable compartment/output-stream binding and planned local backing-thread/workspace IDs;
- exact signed `bot.run.accepted` envelope and its outbox row under one stable generated event ID.

`ExecutionLedger.admit` invokes `sideEffects(record)` with the generated execution ID inside the same SQLite connection/transaction as `BudgetLedger`/`Outbox`; unrelated commits in that callback violate the contract. `bindRun(record.id, binding)` persists the immutable `BotExecutionBinding` there; `CompartmentStore.bind` installs/verifies the stable audience binding without attaching a public compartment forever to one thread. Never call the model, create filesystem workspaces, upload blobs, send a receipt or await network I/O inside the transaction. Preallocate bounded non-execution IDs and receipt material before entering; generate/sign the bounded receipt using `record.id` before enqueue. Unique-key/capacity races are resolved inside the transaction. At most 500 affected rows / 1 MiB per transaction. A duplicate must skip `sideEffects`. Any reservation, quota, rate or outbox failure rolls back the execution and every associated charge. Defaults are two concurrent runs per bot and twenty admitted runs per requesting member per hour; a failed/duplicate/expired admission does not consume a counter.

v1 budget units are integer micro-US dollars (`1 USD = 1,000,000 units`), nonnegative JSON-safe integers. Daily configured budget and run ceiling are positive safe integers. Available funds subtract both settled spend and all outstanding reservations; the database checks sums for overflow. The reservation belongs to its admission day's UTC bucket and cannot be made free by midnight, restart or placement move. Settlement is idempotent, replaces that reservation with actual accounted spend, and frees unused funds. Zero-cost pre-model failure releases the reservation; unknown provider cost remains held at the full ceiling until reconciled. `uncertain` execution frees its concurrency slot only after the process/effects are quiesced; it keeps its unresolved spend reservation. Resetting a counter or dropping a reservation on restart is forbidden.

A ceiling is a hard bound for admitted automatic spend, not just a warning after a response. Before each billable model call, retries, fallback and compaction included, the adapter MUST know a conservative maximum charge (bounded input/output, all billed cache classes, provider overhead) and atomically debit it from the execution's remaining reserved allowance. `BotRunRequest.spend.authorizeCall(maximumUnits)` supplies a stable call ID; `settleCall(id, spentUnits)` reconciles it, and `remainingUnits()` reflects held calls as well as known spend. These ports wrap `BudgetLedger.authorizeCall/settleCall` for the admitted execution. It dispatches only if that maximum fits, then reconciles actual spend. No documented maximum price/usage, unbounded autonomous CLI billing, or unknown accounting => `profile_unsupported` at setup/admission. A token-limit abort after incurred cost does not establish the bound. Provider cost unexpectedly above the reserved maximum fails the run, retains accounting evidence, suspends that qualification and blocks further calls; it must not silently settle as zero or authorize an overdraw.

## Permission requests and approval expiry

Permission requests live in a private stream containing only the owner, the requester when applicable and the bot. They expire after 24 hours, with at most twenty pending requests per bot. `now >= expiresAt` is expired. Owner/root identity and current membership/placement are verified on grants. Pending approval is not a model run and reserves no new spend. No request summary/tool arguments leak into public activity or notifications.

Two actions are distinct:

- A denied mention may ask the owner to change steer policy. Granting does not execute that old mention: the owner publishes the policy change, and the requester sends a new mention satisfying the normal delivery window. No 24-hour request may revive a 30-second trigger. Operator remains owner-only.
- A running execution may wait for an action permitted by its profile but requiring the owner's normal approval. The request binds `space`, `bot`, `execution`, request event ID, profile/definition revision, compartment/output-stream binding, canonical tool name and argument digest. The owner grant references that exact request, has an `expiresAt` no later than the request's expiry, and is consumed once in the transaction that records action authorization. Changed arguments, definition, participant epoch, placement, revoked rights, expired grant, cancelled/uncertain execution or a reused grant rejects dispatch. Recheck immediately before the effect; approval does not override the profile or add new tools.

Wire bodies use the `BotPermissionRequest`/`BotPermissionGrant` discriminants in `src/shared/net/envelope.ts`. `requestHash` is base64url SHA-256 of the exact original signed request envelope bytes. `profileDigest`, `actionHash` and `argumentDigest` are base64url SHA-256 digests. Use the protocol's canonical JSON for local profile/action/argument digest inputs: the immutable effective run policy for profileDigest, exact tool argument object for argumentDigest, and `{execution,tool,argumentDigest,profileDigest,binding}` for actionHash. The argument digest includes every argument, not the public summary. `BotRunRequest.approvals.requestAction({tool,argumentDigest,actionHash})` is the bound owner callback; an `approved` result only supplies evidence. `consume(approval,actionHash)` atomically revalidates/consumes that evidence immediately before dispatch. Callback success or approval event presence alone is not permission to perform an effect.

While `waitingApproval`, the execution retains its reservation and concurrency slot. Denial or expiry cancels that execution, settles known spend and holds unknown spend for reconciliation. An elapsed timer is never approval. Restart converts waiting executions to `uncertain`; no saved approval resumes effects automatically. Emergency stop/revocation aborts the adapter signal, pending approvals and descendants; if cancellation cannot prove an effect stopped, expose `uncertain`. The 30-second trigger window gates admission only; an already admitted execution does not become an expired mention while waiting for approval. Current authority/profile/audience/placement/clock and stop conditions are still checked before resuming.

## Crash recovery and ledger loss

Only after admission commits may the adapter materialize the planned backing thread/workspace. Store its binding idempotently by execution ID. Persist `running` before the first billable/effectful action. A crash during backing-thread creation is reconciled by the planned ID; the existence of that thread never authorizes running the model. On restart, `accepted` becomes `failed` with “not started”; `running` and `waitingApproval` become `uncertain`. Receipt outbox replay uses the same signed bytes/event ID. A completed result not durably recorded before a crash is uncertain, even if a thread transcript suggests success. Never infer completion from text or automatically rerun an effect. The owner retry is a new mention and execution key.

Execution dedup rows MUST outlive the guarded event IDs (including retained event tombstones); terminal cleanup cannot re-enable retained triggers. Detect missing/quarantined/rolled-back ledger or an inconsistent backup before admitting runs. Stream resync alone does not restore proof that a tool never ran. Disable the affected bot, retain receipts and uncertain evidence, and restore a coherent profile/ledger backup or perform explicit owner recovery. Owner recovery creates a new placement epoch and activation watermark, treats all host-received events before activation as non-executable, preserves available dedup evidence, and warns that lost external effects cannot be reconstructed. A space export does not contain this ledger and cannot qualify bot activation.

## Placement stop-and-transfer

1. Old node durably fences new admissions, cancels pending requests and drains/stops the bot's effects. Any unresolved runs become `uncertain`; do not label them completed.
2. Transfer a bot-scoped, authenticated manifest with old/new nodes, bot, old placement epoch, event/hash dedup rows across all spaces, terminal/uncertain outcomes, unresolved budget reservations and admission-day accounting, and compartment/session bindings according to [compartments](compartments.md). No root key or unrelated bot/profile rows. Verify size/count bounds and manifest hash before import; large ledgers use bounded staging transactions and atomic activation.
3. New node stages/imports without executing, verifies dedup/accounting coverage and acknowledges durable installation. Old node signs its stop acknowledgement and remains fenced, including after restart. Root authority issues a higher bot delegation epoch only after that evidence. Bot signing/session secrets transfer through authenticated encrypted local/peer key handling; never a public stream/archive.
4. Activate the new placement with a persisted host-time watermark; reject mentions with `recvTs < activationHostTs`. Same-time triggers are eligible only under all other gates. Never reset dedup or daily budget on movement. Every old-key run/session is refused after the new placement is learned.

`ExecutionLedger.exportFor/importFor` transfer complete `ExecutionRecord` rows, including original IDs, outcome/result and per-run bindings. `BudgetLedger.exportFor/importFor` transfer the exact `BotBudgetTransfer`: `daily` buckets use `day = floor(admissionMs / 86,400,000)`; each contains budget and settled spend. Daily `spentUnits` is the aggregate of already settled executions only. Outstanding reservation ceilings remain separate from that aggregate; their known/unknown provider-call accounting is preserved under the original call IDs. A reservation with `settledUnits` is a settlement tombstone already included in the daily aggregate, not an additional charge. Unknown call spend stays inside its held execution ceiling. Import installs/verifies this exact bot state idempotently, never adds the same daily settled total or reservation again, and rejects missing coverage/conflicting rows. The scoped transfer manifest links budget execution IDs to the exported ledger and activation boundary; staging/import completion is not activation until both ledgers are durable.

An unreachable old node cannot supply a stop acknowledgement. Automatic activation waits until its old delegation expires (seven days), and requires explicit ledger-loss recovery if coverage is missing. An owner-forced move records the warning/force decision and duplicate-effect risk; it does not assert exactly-once execution or erase known rows. A partitioned old node can operate until expiry; protocol alone cannot fence a root-key holder. Forced movement is never a default retry mechanism.

## Conformance

`test-vectors/net/admission/cases.json` freezes bounded admission and failure decisions. P0 loader checks validate the fixture catalogue only; P1/P6 MUST execute those inputs against real modules, inject every transaction/crash boundary, and establish the expected row/receipt/model-call counts. Qualification additionally needs real runtime negative tests for forbidden tools, path traversal/symlink swap, context/session leakage, budget races, cancellation and provider accounting. P0's documents/fixtures do not claim those runtime tests pass.
