# Mousse Net threat model

This models the P0 contracts. Mitigations below are requirements for later implementations; a test ID names required coverage, not a passing test. [state-machines.md](state-machines.md) gives the normative guards, [protocol.md](protocol.md) freezes codecs, and [bot-runtime.md](bot-runtime.md) qualifies enforceable profiles. Frozen cases in `test-vectors/net/security/` are inputs/oracles for future tests. A parser/signature unit test does not prove executor containment or an end-to-end fix.

## Assets and trust boundaries

Assets are user/node/bot private keys and provider credentials, signed identity and authorization history, invite proof keys, private content and content keys, execution/deduplication ledgers, honest durable cursors, repository files/commits, spend reservations, profile separation and availability.

The OS and executing daemon are trusted to enforce their own user/profile isolation. Root private-key possession is user authority. A delegated node is a revocable machine, not the root identity. A space host is trusted for ordering/availability and sees public content; consumers independently verify speaker and authorization. Relays, tunnels, routes and the network are untrusted byte carriers even when an outer transport is encrypted. Private-stream recipients are trusted with received plaintext and cannot be made to forget it. A bot owner trusts their runtime/provider with allowed data; members' signed messages and tool output remain untrusted prompt input. Local IPC authentication is a separate boundary from loopback reachability. Execution ledger and runtime effect stores have a crash boundary: protocol idempotency cannot make an arbitrary external action exactly-once.

## Devices that work on threads, and blocking

Bridge lets the user's own devices act on each other. Two kinds of device exist, and the owner's computer can tell them apart because the difference is signed.

- **Works on threads.** The `settings` capability in a device's delegation is the grant for the thread API between computers. It goes only to a device the authority has recorded as a computer, and to the authority's own delegation (an authority from before the grant existed adds it to itself on activation and renewal, so the user's main computer is not refused by their other computers). The authority records a device's kind itself: `bridge.invite` (the default for "Add device -> Another computer", `mousse-cli bridge invite` and SSH setup) records a computer, the QR offer ("Add phone") records a phone, a Mousse ID approval records the kind the user approved, and `bridge.setKind` lets the owner say what a device is. A device with no recorded kind (enrolled before kinds existed, or approved by an earlier authority) is shown as an unknown device and is refused the grant until the owner says it is a computer. `bridge.setCaps` and every invite path refuse `settings` for anything else. The name `settings` is the one older peers and the hosted relay already accept in their closed capability list, so a delegation that carries it validates everywhere. `bridge.setCaps` re-signs a delegation with the same key epoch and lease. The new `issuedAt` is the previous row's plus one, never `now`, so an authority with a fast clock cannot date a row in the future and lock the device out.
- **Where the kind comes from.** Mousse ID relays the kind a requester gives, but that is only what the approval prompt shows. The grant follows the kind the authority records when the user approves, and the user can correct it. A hosted service or requester that lies about its kind can only mislead the person who approves; it cannot grant anything by itself.
- **Block (a device).** `net_node_policy` (in the Net database) is written only on the computer it protects and needs no authority. Any computer, including a headless one (`mousse-cli bridge block|unblock`), can refuse any other device, the authority included. A blocked device gets `forbidden` from every `bridge` and `routed` method on its next call, including a result lookup for an earlier request and the phone endpoint and WebRTC offer methods, and every Bridge stream (read, snapshot, blob fetch, append) is refused. Blocking also ends the device's live subscriptions and asks its running requests to stop. The connection itself stays, so Unblock needs no new handshake and the device list and roster are not affected. Revocation, which needs the authority, remains the way to remove a device from the user's set.
- **Per-device limits.** `maxPermissionMode` (default Auto-accept edits; Auto sits between Auto-accept edits and Full access) and `terminal` (default off) are stored with the block. `maxPermissionMode` is enforced on routed calls (below); `terminal` is checked for every routed terminal row (reading a terminal, opening, typing into, resizing and stopping one) and for the terminal output stream (see "Terminals" below).

- **Older computers and Auto.** `routed.threads.setPermissionMode` takes `auto` from version 2. A caller sends an owner at version 1 (a Mousse from before Auto) `accept_edits` instead, the mode Auto runs as on an agent without an auto mode, so the thread never gets more than was chosen. A thread mode or profile default an owner reports that the caller does not know reads as Ask before acting, and an unknown device limit is not shown (the owner still enforces it). A Mousse from before Auto that reads an `auto` thread from a newer owner shows it without a name and sends only the modes it knows. Its daemon reads a stored `auto` (a thread, a job, the profile default) as Ask before acting and a device limit of `auto` as the default, Auto-accept edits; it cannot open a profile whose run database already has the Auto migration (version 16), as with any newer schema.

What a paired computer can reach is a lot. A device with `chat` and a turn at Full access can run code on this computer, and one with `write` can edit files, so `terminal` does not mark the line between safe and unsafe. The controls are blocking, revocation, the permission-mode limit and the audit of what a device did.

Limits of a block:
- **Stolen authority.** A block is keyed by node id. A thief who holds the authority can invite a new device, which no computer has blocked, and can revoke or rename the user's other computers. Blocking the stolen authority on each computer stops that one device only. The remedy is recovery: `net.recovery.import` with `becomeAuthority` on another computer makes it the authority and revokes the stolen one. Approval of devices added after a date is a possible later control and is out of scope here.
- **Work already running.** A block is checked on each call. A durable request that is running is asked to stop, but a turn the device already started (for example by sending a message) keeps running at its mode until it ends, and at Full access it can reach this computer's daemon API, including unblocking. Stop that turn on this computer. Stopping turns and removing queued items on block belongs to the routed changes that start them. An in-flight request that has made its effect still ends `outcome_uncertain`.
- **Spaces.** Space streams are not covered by a block. A blocked device keeps its place in Spaces hosted on this computer, and bots there run here with the owner's keys. Remove the device from the Space or revoke it to stop that.

### The routed thread API

A computer that holds "Works on threads" can call the methods in `ROUTED_METHODS` (`src/shared/bridge/routed.ts`) on the computer that runs a thread. Each row is its own Net method `routed.<method>` with a fixed capability (`read`, `chat` or `write`) and runs the same protocol handler a Mousse window on the owner would. The table is the security boundary: a method that is not a row cannot be called, and every protocol and domain method is either a row or listed as local with a reason (`tests/net/bridge/routed/table.test.ts`). `threads.purge`, `files.writeDirect` and `files.root` are not rows, nor are settings, providers, accounts, scheduled jobs, channels, MCP or the browser. Terminals are rows (`pty.*`), behind the device's terminal switch and the rules in "Terminals" below.

A call is allowed only when every one of these holds, and each is read again on every call, so none of them needs the connection to be closed:
- The caller's signed delegation holds `settings`. A phone and an older device never do.
- This computer has not blocked the device.
- The owner's switch, "Let my other computers work on this computer's threads" (`mousse-cli bridge threads on|off`), is on. It is on by default, since a computer also needs the signed grant, and starts at the highest permission mode Auto-accept edits with terminals off; turning it off is a kill switch.
- For a terminal row, this device's terminal switch is on.

A refused call tells the caller which of `capability`, `blocked`, `setting_off` or `terminal_off` it was, as a fixed word in the cause slot of the wire error (older peers already accept that slot). It is the only detail of an error that crosses the wire. A blocked device therefore learns that it is blocked; the phone API keeps the bare `forbidden`.

What a call may touch is decided on the owner before a handler runs: exactly the row's keys (never `cwd`, `env`, `command`, `shellArgs`, `source`, `projectPath`, `profileId` or `expectedProfileId`), a thread or project that is in this profile (a file or Git call names a thread or a project, never both and never neither, so there is no home-folder fallback), no absolute path outside `projects.open`, and secondary ids (a question, run, workflow run, terminal) that belong to the named thread. The routed call runs with a connection of type `bridge`: a person, never a window of this computer, so nothing meant for the owner's own window (direct saves, the files panel's folder, the browser host) is open to it.

A person on a paired computer is a person. Its messages are sent as `gui`, with the computer kept in `sentFrom`, so agents are refused `person_turn` on them and a routed send does not narrow the thread's agent access. The device's `maxPermissionMode` bounds what it can do beyond a single decision: its turns, queued messages and steers that have to wait run at no more than that mode, the thread's mode can be set only up to it, and a standing "Always" rule is made only for an action the limit allows without asking. `chat` together with Full access is code execution on this computer; blocking, revocation, the limit and the audit are the controls, not the capability name.

Every change a routed call makes (and every one that ended `uncertain`) is a row in `bridge_audit`: time, computer, method, thread, project (a `projects.open` names the project it opened, or a short hash of the path it was refused), outcome. The audited device must not be able to erase its own trail, so budgets are per device and per kind: a change row is deleted only when it is older than 30 days and beyond the newest 20,000 changes of that device, and refusals of admitted writes have their own budget of 1,000. Reads, refused reads included, are only counted: calls and bytes per computer and hour in `bridge_audit_reads`, kept for 30 days, because what matters about a read is how much of it there was. A refused call before admission (not allowed, malformed) is not recorded, so a blocked device cannot fill the table.

The Devices screen reads this audit for each computer that works on threads and says it in plain words: what the device did in the last 7 days ("Started 3 turns, answered 2 approvals or questions, opened a terminal"), its recent actions with links to the threads they were about, and the read total of the last 24 hours. It also lists the "Always" rules a person on the device made (the rules whose approval was answered by that device) with Clear for each and for all; Clear removes them from the thread's rules like a rule the owner revokes, and reaches no rule the owner or another device made. The transcript of a thread marks a turn a person on another computer sent ("from <computer>"), read from the run's `run.sent_from` event; a steer into a turn that was already running is not marked. These requests (`bridge.activity`, `bridge.clearDeviceRules`, `bridge.messageSenders`) are local to this computer's windows and are not routed methods: a device cannot ask them, and a path of this computer is never in the answer.

The first time a device changes something on a thread here is also told to the owner, once for each device: a desktop notification in the windows of this computer ("<device> is working on this computer's threads. Open Settings, Devices to limit what it can do.") and a row `thread.first_use` in the audit. A headless computer has the row only. Because the owner's switch and the routing flag are on by default, this and the wording where a computer is paired or granted (what it will be able to do, in both directions) are how the owner learns what pairing opened.

Some limits of the device's mode limit are plain:
- A steer that the running turn reads joins that turn at its mode; a running turn cannot be narrowed. A steer the turn never reads, one that waits and one that names a run that has just ended become a turn of their own at no more than the limit.
- A limit is fixed when a message is queued. Lowering a device's limit does not reach messages and turns already admitted. Blocking a device removes the messages it queued that have not started and the "Always" rules it made (see below), and the Devices screen lists those rules for a device that is not blocked, with Clear.
- A workflow's steps run under the workflow's own policy, not under a turn's permission mode, so the limit cannot bind them. A `/workflow` command from another computer is refused until workflows have a permission mode; approving or answering an existing workflow run is allowed (a decision on what the person sees).
- The owner cannot tell a person from an agent on the calling computer. Everything above treats a routed call as a person. An agent with Full access on a paired computer can use that computer's node key (readable unless the key store is passphrase-protected) or drive its daemon, and then act on this computer as "the person": answer approvals without `person_turn`, make "Always" rules within the limit, send `gui` turns. Agents not reaching across computers is enforced by the caller's router, not here. Protect the key store with a passphrase on computers where agents run, and keep the device limit low for computers you trust less.

A refusal the owner's handler makes on purpose (`thread_not_found`, `queue_conflict`, `permission_mode_above_ceiling`...) is a completed result `{ ok: false, error }`, recorded as completed in the ledger and never `outcome_uncertain`. Only an unexpected failure after the handler started is. Durable results are kept in the ledger up to 16 KiB and by hash beyond that, and the lists a local handler returns beside its result (`threads`, `all`, `projects`) are dropped from routed results.

#### Streams, large results and large inputs

Each computer that works on this computer's threads reads through streams of its own, so what one computer sees is not what a phone or another computer sees:
- `routed.stream.open` opens a thread stream, a lists stream, a channel stream (a Git action's progress, for the computer that started it) or a stream for one terminal. The stream is a display stream like a phone's, stored under a key that names the computer, and only that computer reads it. The check is in the stream authority (`nodeAuthority.ts`): the reader is the bound node, and still holds `read` and `settings`. The network layer adds the owner's switch (read on every record) and, for a terminal, the device's terminal switch. A request for a private stream the device may not read is answered on that stream with `forbidden`, and the connection stays up.
- A thread stream carries "Always for this thread" on an approval card only where the device's limit allows that rule (the same test `canAnswerApproval` applies when the rule is asked for), so a card never offers what would be refused. A phone's stream never carries it. The private stream also carries what a window of this computer hears about a thread: subagent, agent, task, pull request, save and workspace changes, as display-only notes that are never stored or replayed. The lists stream keeps the subagent rows and each thread's `lineage`, and reports Waiting and Paused; a phone's lists keep neither.
- Terminal output is its own stream, one record per chunk in order, never merged with another, and never on a thread stream. Git progress is only on the channel stream of the computer that started the action.
- Streams are bounded: a computer holds at most 16 thread streams, one lists stream, one channel stream and 4 terminal streams, and the computers together hold 32 thread streams (96 streams of every kind). They are counted apart from the streams phones and hubs open, so neither crowds out the other. A stream no one reads and no turn runs on is released after 10 minutes. A closed or released private stream is never reopened because something looked it up: only `routed.stream.open`, with its checks, opens it, and until then nothing reads it. Blocking a device closes its streams and ends its subscriptions at once, switching off a device's terminal ends its terminal streams, and turning the owner's switch off or taking the grant back (or revoking the device) lets go of everything held for it: its streams, the results it waits to fetch and the values it staged.
- At rest: a private stream's records are stored in the Net database like a phone's display stream: the newest 16 MiB of a transcript for a thread stream, and up to 8 MiB of recent output for a terminal stream. They stay until the stream is released and its records are truncated, so output of a terminal and text of a thread sit on the owner's disk for as long as the stream is open or until it is dropped as stale (7 days unopened).
- A thread stream is given the newest 16 MiB of a long transcript, and says where the older messages begin; `thread.messages` pages them, 8 MiB at most at a time. Images older than the newest 8 MiB, and queued images, carry no data until `thread.messageImage` fetches one.

A routed read larger than one RPC reply (63 KiB) is held in memory on the owner for a minute and fetched in 45 KiB pages with `routed.page` (a page travels as base64, so 48 KiB would not fit a reply). A computer holds four such results and 32 MiB at a time, and a newer one pushes out its oldest; the page results themselves are never written to disk (the stream records above are). A computer may have two of the reads that build such results under way at once (a snapshot, a page of messages, an image, a file, a diff); a third is refused `rate_limited`. The caller checks the length and the SHA-256 of what it reassembles. A durable result over 63 KiB goes through the artifact publisher as before.

A value too large to send inline (a long message, images, a file's content) is staged first. The caller uploads it as a request artifact of `routed.stage`; the owner keeps it in the blob store, up to 25 MiB per value, 64 MiB per computer and 256 MiB in all, for an hour, and answers an id that the call names in `stagedValues`. The row's own checks (its keys, the thread, the ids it names) run on the call as it was sent; the owner then puts the staged values back and the handler checks them exactly as it checks an inline value (only a row's content-like keys can be staged: `content`, `images`, `text`). A row-level check of a value's content added later has to look at staged values too. A value is used by one call: it is claimed when the call starts, a second call that names it meanwhile is refused `stage_in_use`, and a refused call gives it back. Expired values are looked for when the service starts and every minute, not only when someone stages. Staged values and held results go with a device that is blocked, or that loses the grant. The uploaded bytes stay in the blob store until the stream that carried them is emptied and the blob store collects them, which can be later than the hour.

#### Files, Git, review and Undo stay inside the thread's folder

A file, Git, review, Undo or pull request call from another computer works in the thread's folder (or a project's) and nowhere else. A window of this computer, and every other local caller, keeps today's rules (the path must stay inside the folder as it is spelled, and a link the user made is followed); the checks below are for `bridge` connections only (`RoutedGuard`, `src/mms/files/routedGuard.ts`).
- **Real paths.** A path is allowed when what it names on disk lies inside the folder's real path, once links, junctions, `subst` drives, short (8.3) names and differences of case are resolved. The two real paths are compared exactly, not with case folded, because a volume that tells `Proj` from `proj` would otherwise take a sibling for the folder. This covers `files.list`, `read`, `readAsset` (every piece of a preview), `stat` and `write`. Search and grep already skip a file whose real path is outside the folder. A file that is read or written is opened at its real path. The `..` test is for a step up, not a name that starts with two dots (`..cache`).
- **Refused outright:** an absolute path, a drive or share path (`C:\`, `\\host\share`), a `\\?\` or `\\.\` path, a NUL byte, and on Windows a device name (`NUL`, `CON.txt`), a stream (`file:name`) and a name with a trailing dot or space. A link that leads nowhere is refused for a save, since writing through it would create what it points at. A thread or project the daemon does not know, and a thread without a folder, are refused (`thread_not_found`, `project_not_found`, `thread_has_no_folder`); there is no home-folder fallback.
- **Credentials folders, in a project too.** A path whose real location is inside a folder of the credentials table (below) is refused for reading, listing, `stat` and saving (`path_protected`), also in a project the owner registered earlier, such as the home folder, and also through a link that is inside the project (`~/.aws` pointing into a dotfiles folder is the real folder's own path). `projects.open` is not the only way in.
- **Git and the review.** A path given to `git.diff` or `review.file`, or a pathspec given to `git.stage`, `unstage` or `discard`, must have its folders inside for real. A link at the end of the path is read as a link (the review shows the link's text, Git stores the link) and is never followed, so a committed link to a place outside is still listed and staged. `discard` deletes untracked paths, and Git for Windows follows junctions, which is why those paths are checked.
- **What a save may not change, at any limit** (`path_protected`):
  - Git's own folder: `.git` at any depth in any case, on Windows also `GIT~1` and its other spellings, and a worktree's `.git` file. Its hooks and config run programs on the next commit.
  - Every folder `core.hooksPath` names, in the folder's repository and in any repository nested in it. The setting is read with Git (asynchronously, never blocking the daemon) and kept for 10 seconds; relative paths are taken from the top of the working tree.
  - Every file Git reads as configuration besides the repository's own: the targets of `include.path` and `includeIf.*.path`, whether they apply now or could after a change of folder or branch. A `core.hooksPath` or `core.fsmonitor` in one runs a program on the owner's next `git status` or commit, with no one acting, so refusing these files also ends the order "hook file first, setting second". Targets of includes inside an included file that does not apply yet are not followed (they can only come from a file that is already refused).
  - Mousse's control files (`.mousse/task-progress.json`, `.mousse/materialized-inputs.exclude`).
  - A file that has other names (a hard link), which could be one of those under another name.
  If the settings cannot be read, the save is refused. Git operations themselves (stage, commit, push, fetch, branches) are not restricted, and run the repository's hooks as they do for the owner.
- **What a save may not change below Full access** (`path_needs_full_access`). The device's limit decides, as it does for turns: a device may change a file that starts programs by itself only when its limit already lets it run commands. These are the settings an agent harness loads from a project, which a device starts itself with `chat` (the next turn), and the runners Git calls on a commit, which it starts itself with a routed `git.commit`: `.claude/settings.json`, `.claude/settings.local.json`, `.claude/hooks/`, `.mcp.json`, `.cursor/{mcp,hooks,cli,environment}.json`, `.codex/{config.toml,hooks.json}`, `opencode.json`, `.opencode/opencode.json`, `.mousse/workflows/`, `.husky/`, `.lefthook/`, `lefthook*.{yml,yaml,json,toml}` and `.pre-commit-config.yaml`, in any folder and any case (`startsPrograms`, `src/mms/files/routedGuard.ts`; the harness files are the ones `data/paths.ts` and the Claude Code and Cursor drivers load). A device at Full access may change them. They stay readable.
- **Allowed, and why.** `package.json` scripts, `Makefile`, `.vscode/tasks.json`, `.envrc`, CI files and source code run only when a person on the owner runs them, or behind the tool's own prompt (VS Code's workspace trust, `direnv allow` after every change), and CI runs on the remote. Refusing them would block ordinary editing.
- **What the limit does not cover.** Below Full access a device can still ask the agent to write the same files with `orchestrator.send`; whether the agent may is then up to the thread's permission mode and the harness's own rules, which the device's limit already bounds (`maxPermissionMode`) but this check does not repeat. The list above is the files Mousse loads as settings; a prompt-level file (`CLAUDE.md`, slash commands, skills) is not on it.
- **How a save is made.** The guard resolves the path once, before anything is recorded, so a refused save leaves no action behind. The file is then opened and checked to be the file the guard resolved (not a link put there since, with one name) before a byte is changed. A new file is written beside its name and renamed onto it, because creating a file at a name that is a link follows the link on Windows and a rename does not. The folders above the file are checked once and not held: a folder swapped for a link between the check and the open is not caught. That needs a process on the owner that can already change the folder (an agent in the thread), which a thread at Full access can do directly.
- **Size and memory.** An editor save from another computer is staged and may be as large as one staged value (25 MiB). Every other caller of `files.write` keeps 512 KiB. A computer saves one staged (large) file at a time; a second is refused `rate_limited` until the first is written. Lines changed are counted exactly up to 2 MiB; above that only the difference in the number of lines is counted, by scanning, so a save does not hold two line lists of the old and new file.
- **Reads under `.git/`.** `files.read` of `.git/config` from another computer is allowed. It can show a token inside a remote URL. The person's own repository is the person's own, and the plan names writes only; the credentials table is where a secret folder is closed.
- **`projects.open`.** The owner refuses a folder that holds credentials or personal settings, lies inside one, or contains one, which includes the home folder, the folders above it and a drive root. Network and device paths and the Mousse data folders (and any folder holding them) are refused as before. The list is one table (`sensitiveFolders`, `src/mms/files/sensitiveFolders.ts`), compared by real path and as spelled, so a link, a junction, a short name or another case does not get around it:
  - sign-ins of coding agents (`~/.codex` or `CODEX_HOME`, `~/.claude` or `CLAUDE_CONFIG_DIR`, `~/.gemini`, `~/.cursor`, `github-copilot`);
  - SSH, GnuPG (`~/.gnupg`, `GNUPGHOME`, `%APPDATA%\gnupg`), AWS, Azure, Kubernetes, Docker, the GitHub CLI and Google Cloud folders, a password store, `1Password` and `sops` age keys, and the certificate database (`~/.pki/nssdb`);
  - package and build tools (`~/.cargo`, `~/.m2`, `~/.gradle`, `~/.terraform.d`);
  - the system keychain and key stores (macOS `Keychains`, Windows `Credentials`, `Protect`, `Vault`, `Crypto` and `SystemCertificates`, Linux keyrings and KWallet);
  - the folders browsers keep sign-ins in (Chrome, Chromium, Edge, Brave, Vivaldi, Opera, Arc, Firefox, Safari, Flatpak and snap browsers).
  Where an environment variable moves a tool's folder, both the variable's folder and the default are on the list. A refusal is `project_refused` with the reason, audited as refused with a hash of the path (never the path). Opening a folder is audited like any change. The first folder a device registers is also told to the owner, once for each device: a desktop notification ("<device> opened a folder (<project>) as a project on this computer") and a row `project.first_open`; it takes the place of the first-change notice when both are due. The Devices screen lists a refused open as "a folder" and never shows the hash.
- **Nested repositories** have their own hooks folder and included configuration checked, as above. The rule for a file in a nested repository that is not Git-related is the same as anywhere else.

#### Terminals

**A terminal from another computer is equivalent to shell access on this computer, as the user.** A device that may open one has full trust of the user account here for as long as it can reach a shell, and after that for as long as anything it left behind runs. The terminal switch is its own, per device, and off until the owner turns it on (Devices, "Terminals from this device"; `mousse-cli bridge limits`), because `write` and `chat` are not this. The switch, blocking and revoking decide who gets a shell and when it ends. They do not limit what a shell can do once it runs, and the audit is only as good as the computer's own account of it: a device with a shell can do all of the following, so after a device with a terminal has misbehaved, neither the block list, the audit, nor the owner's settings on this computer can be trusted until the account's files are checked (and, for a device that held the authority, recovery is the remedy, see "Limits of a block").
- It can edit this computer's own settings and records: `net_node_policy` (unblock itself, switch its terminal back on, raise its limit), `bridge_audit` (erase its rows), the owner's switch (`workOnThreads`), and the key store when it is not passphrase-protected.
- It can drive this computer's daemon as a local client (`mousse-cli`, or the local socket), which no routing rule applies to.
- It can leave processes and files that outlive a block, a revoke and the end of its terminal (a login item, a scheduled task, a changed shell profile, a copied key).
- It can read every file the user can, including the credentials folders that `projects.open` and the file calls refuse.

The shell is the owner's shell: it is started in the owner's default shell with the daemon's whole environment, exactly as a terminal opened in a window of this computer is. Mousse puts no secrets in that environment itself (it sets only `MOUSSE_HOME` and `MOUSSE_VERSION`), but whatever the owner started Mousse with reaches the shell, for example a provider key or a chat bot token given as an environment variable. Stripping some of them would be defence in depth at best, since a shell can read the same values elsewhere.

What is limited, and why it still matters:
- **Where it starts.** `pty.create` names a thread and nothing else. The owner starts the shell in the folder the thread works in (its worktree or checkout), or, for a thread with no folder, in the thread's own terminal workspace, in the default shell and environment. A call that carries `cwd`, `command`, `env`, `shellArgs`, `projectPath`, `source` or a profile id is refused `bad_request`, and so is one for an agent that is not a project shell (`__project-shell__`), which keeps a device from naming an agent of the owner. A terminal is never opened for a thread that is not in this profile, and never unbound. The first folder is not a sandbox: a shell leaves it with its first command.
- **Whose it is.** A device reads (list, status, scrollback, output, the stream), types into, resizes and stops only the terminals it opened. Another's, including one a window of this computer opened in the same thread, is `pty_not_found`, and a list shows a device only its own. At most four terminals per device are open at once (`terminal_limit`); the slot is taken before the shell starts. A thread has one terminal at a time, as for a window of this computer: a terminal holds the thread's writer lease, so a second one for the same thread says the writer is busy.
- **While it starts.** A device that is blocked, switched off, or loses its grant while its shell is starting has the shell stopped the moment it exists: the call is refused (`terminal_ended`), the end is audited (`blocked`, `terminal_off`...), and unblocking gives it nothing back. A shell whose call failed after it started (so the device was never told its id) is stopped and audited as `create_failed`.
- **Input.** Typing and resizing are numbered calls (`routed.pty.write`, `routed.pty.resize`) in a request class of their own, `sequenced`: they keep no ledger row and no result, take no idempotency key (a key is refused), and the handler applies each `(device, terminal, number)` once. The numbers are the terminal's own count, not a clock: they start at 0 for a terminal opened here, and at the owner's `lastSeq` for one found later (`pty.isAlive`, `pty.lookup` and `pty.list` say where it is). The caller sends calls without waiting for the replies, and the owner puts them back in number order (a call waits a moment for the one before it, at most 250 ms) and applies them one at a time. A resend of a number already applied is answered `{ ok, duplicate, lastSeq }` and not typed again, which is how a lost reply is handled; a caller whose count is behind the owner's (nothing of its was ever accepted) takes the answer as "behind", moves to `lastSeq` and sends the call again. Input is held to a steady rate (about 256 KiB a second and 100 calls a second, with a burst of 512 KiB and 200 calls) by making it wait, up to 3 seconds, so a paste stays whole and in order; a wait that would be longer is refused `rate_limited` and that call's number is used up. A paste above 512 KiB is refused whole by the caller (`paste_too_large`) before any of it is sent. An input the shell cannot take (it is stopping) is `pty_unavailable` with fixed words: what the shell said, which can name paths of this computer, stays in the owner's log.
- **Output.** The terminal's output is its own private stream, one record per chunk with the terminal's own sequence number, never merged and never on a thread stream (see "Streams" above). A chunk larger than a record is in pieces that share its number. The stream stores a burst a few milliseconds after it arrives, in batches of up to 32 records in one transaction: the roster and this computer's delegation are checked once per batch, and each record is still signed on its own and still its own record, so `pty.outputSince` (which fills a gap by sequence number) and the stream's own resume see exactly what they saw before. Output that is not a chunk (the end of the shell, a fresh snapshot) is stored behind what is waiting. On the caller, a piece already delivered is not delivered again, output missed while the link was down is fetched with `pty.outputSince` and delivered before anything newer (if the owner no longer holds it all, the terminal is cleared and its scrollback is written again), and what the shell printed before the stream was attached is shown once the window has mounted the terminal.
- **What ends a device's terminals.** At once, with no further call: the device being blocked, its terminal switch going off, the owner's switch going off, the device losing "Works on threads" or being revoked, and **Net or Bridge being turned off or the profile closing** (the shells are stopped and waited for, so each end is audited as `net_off`, the thread's writer lease is released, and the count starts again from a true zero when Net comes back). A device that has had **no session with this computer for 10 minutes** has its terminals ended (`device_away`), checked every 30 seconds: a shell holds the thread's writer lease, so a device that went away with a terminal open would otherwise freeze that thread's turns here with no one to stop it. A drop shorter than that (a lid, a link that comes back) keeps them, and the device reads them again. Unblocking, or switching the terminal on again, gives nothing back: the shells are gone.
- **What the owner sees.** The first terminal a device ever opens is a desktop notification in the windows of this computer ("<device> opened a terminal on this computer, in <thread>") and a row in the audit (`pty.first_open`); a computer with no window (a headless daemon) has the row only. While a device holds a terminal on a thread, the owner's terminal panel for that thread says so ("<device> has a terminal open on this thread") with a Stop button (`pty.list` names the holder to the owner's own windows; Stop is `pty.kill` from the window, audited as `owner_stopped`). The Devices screen lists the device's terminals in its activity (opened, closed and how each ended).
- **What is audited.** Each open and each stop is a row (`pty.create`, `pty.kill`), and each end is a row (`pty.close`) with the reason (`exited`, `killed`, `owner_stopped`, `blocked`, `terminal_off`, `setting_off`, `access_lost`, `net_off`, `device_away`, `create_failed`) and the bytes that went in and came out; what came out is also counted as read volume. Key presses are not rows. A shell that outlives its device's ability to be audited (see above) is not covered by any of it.

The owner's switch stays off until the UI lands.

#### Editor connections

**An editor connection from another computer is shell access on this computer, as the user.** It is an SSH login on this computer, answered by Mousse's own SSH server inside the daemon (the endpoint, below) or, where the owner chose it (and on a Windows computer whose helper cannot run), by this computer's own SSH server, carried inside the Net session (`src/mms/net/editor/tunnel.ts`, wire in `protocol.md` §13), so everything said under "Terminals" about what a shell can do, and about how far the block list, the audit and the owner's settings can be trusted after a device with a shell has misbehaved, applies here too. An editor starts in the thread's folder, but the folder is not a boundary: the login, its port forwards and the editor's own server on this computer can read what the user can read.

- **An upgrade changes nothing for a device that already had the switch on.** Before the endpoint, its connections ended at this computer's own SSH server and needed a key that server accepted. When Net first starts with the endpoint, every device whose switch is on is recorded (`editorSystemSshNodes` in the stored configuration) and keeps ending at the system's SSH server, so the upgrade grants it nothing new: it neither reaches more nor signs in differently. A device leaves that list when its switch is turned off, and a switch turned on again, and every device that gets the switch later, is the endpoint's (shell access with no key). The record is made once and is empty for a new profile.
- **The switch.** "Editor connections from this device" (`net_node_policy.editor`; Devices, "Limits"; `mousse-cli bridge limits --editor on|off`) is off until the owner turns it on, per device, on this computer. It is a switch of its own and not part of "Terminals from this device": an editor connection is long-lived, reconnects and is not tied to a thread (a terminal is, and ends after 10 minutes away), it opens a protocol endpoint of the operating system and not a shell Mousse mediates, and an owner may reasonably allow one and not the other. The device also needs "Works on threads", must not be blocked, and this computer's "Let my other computers work on this computer's threads" must be on, with Net and Bridge on. Existing databases gain the column with every device off (a migration that adds the column and leaves `user_version` alone, so an older build still opens the file). The switch is only ever set on this computer by a person there; a request from the other computer ("Ask", below) can only ask.
- **Where it ends: fixed.** The far end is one of two, and this computer chooses, never the caller. By default it is Mousse's own SSH endpoint, which the tunnel hands the stream of the connection and which listens on no port. It is this computer's own SSH server on loopback port 22 (127.0.0.1, then ::1) when the owner chose "Use this computer's SSH server" (`mousse-cli bridge editor-server system`, per computer, off by default) and on a Windows computer whose endpoint helper (below) is missing or does not run; a tunnel that is open keeps the server it was opened to. A system SSH server is reached by IP literal, so no name is looked up. `tunnel.open` has no field for a host or a port, a message with an extra field is not valid and ends the session, and the service that carries the tunnel accepts loopback addresses only even when configured, so a device cannot use a tunnel to reach another host or another port. Bytes inside the tunnel are SSH's and decide nothing: they are written to the one far end and never read as addresses. The SSH server sees the connection come from 127.0.0.1, like any local login: rules that name that address apply to the device and to this computer's own local logins together, and login throttles that count failures by address (fail2ban and similar tools usually ignore 127.0.0.1) will not ban a device that guesses passwords through a tunnel. What bounds guessing is the 30 opens a minute per device and the SSH server's own limit on tries for each connection.
- **Who logs in, with the endpoint.** The tunnel does. The device that opened the tunnel is proven by Net and allowed by the owner's switch, so the endpoint adds no second check of its own: it accepts the login on the client's first try of any method (OpenSSH tries `none` first, and a client that does not never has to ask for a password or a key) when the user name is this computer's login, and refuses every other name (six tries, then the connection ends). The login is bound to the device of the tunnel, never to anything the client sends: a key, a password or a name sent in SSH identifies nobody. Each login is a row (`editor.login` with the method), and a refused name is a row at most once a minute per device. This adds no trust beyond the tunnel, and no key, no password and no setup is needed on this computer, which is also why a program of the user on **this** computer that can run `mousse-cli` can reach the other computer's endpoint with no key (see "What the alias gives a local process"): the owner's switch, a block and the audit are the controls.
- **Who logs in, with the system's SSH server.** The SSH server does: the device needs a key the user has put in `authorized_keys` here (or whatever the server accepts). Mousse writes no key, no `authorized_keys` line and no server setting, and never will for this. So the switch gives network reach to the SSH server, not a login by itself; it is described as shell access because a device that can also authenticate gets one, and because the owner cannot tell from the switch whether it can.
- **Host identity.** With the endpoint it is proven twice too, by the Net session's pinned TLS and by the SSH host key the endpoint keeps in the key store, and nothing has to be checked about a server on a port: there is none, and what answers is the daemon itself, so no other account can stand in for it. The rest of this paragraph is about the system's SSH server, which an owner who chose it, and a Windows computer without a working helper, use. On macOS and Linux it is proven twice: by the Net session's pinned TLS, and by the SSH host key, which this computer vouches for over Net and the other computer pins in Mousse's own `known_hosts` under its alias (checked strictly, so the editor never asks). On those systems the port needs root (Linux) or the key files belong to root (macOS: another account may bind port 22, but cannot show the real key, so the connection fails). **On Windows the second proof needs a check, because any account can listen on port 22 when the SSH server does not, and, when the OpenSSH Server is not installed, any account can create `C:\ProgramData\ssh` and write `ssh_host_*_key.pub` in it; Mousse would then vouch for that account's server and its key, and the editor would connect to it with no prompt.** So on Windows the open is refused `host_untrusted` (and nothing is read) unless: the `sshd` service is running and its process is the only one that listens on port 22 here; and the folder and each public key file are owned by SYSTEM, Administrators or TrustedInstaller, are not links, and no other account can write them, delete them or change their permissions (`src/mms/net/editor/hostTrust.ts`; the facts are read in one PowerShell run as security descriptors, which name accounts by id and so do not depend on the system's language). Anything that cannot be read counts as a no. This costs a Windows owner a server that runs under another service name or has its keys elsewhere, which is refused rather than guessed. The keys are read from the SSH server's public files, `ssh_host_*_key.pub` in `/etc/ssh` (on Windows `%ProgramData%\ssh`), read only: plain files of at most 16 KiB, of a known key type, at most eight. A private key, a certificate or any other file is never opened. A key file that is a link, a server with its host key somewhere else (`HostKey` in its settings, Homebrew's `/opt/homebrew/etc/ssh`, a read-only system that links `/etc/ssh`) is not found, and the open is refused `no_host_key` (the person is told, and nothing is guessed). Not checked: that what answers on port 22 is the server these keys belong to (a second SSH server on the port, such as one forwarded from a Linux subsystem, makes the editor report a changed host key and refuse). The key is replaced when it changes, on the owner's word; a computer that is not who it says it is would already have failed the Net session.
- **What ends a tunnel, at once.** Every check above is made again for every live tunnel on every change, from the live policy and roster (`reconcile`), and a check that fails counts as a no. A **block**, the device's **switch going off**, this computer's **switch for other computers going off**, the device **losing "Works on threads"** or being **revoked**, and **Net or Bridge being turned off by the person** end all of the device's tunnels: the far end's connection is closed, the device is told why where the session can still carry it, and each end is audited. With the endpoint they also **stop everything the device started on this computer**, including a server that left its session and a device that has no session or connection left (below), and the stop does not wait: the lists are read and the signals are sent between turns of the event loop. **Closing the daemon is not one of these:** a quit, an update or a restart of Mousse ends the tunnels as an ordinary disconnect (below), so the servers an editor started keep running, as they do when an SSH server restarts. The sweep at the next start stops whatever has no right by then. A tunnel also ends with its session; there is no grace period, because the SSH connection cannot outlive its carrier. A tunnel that is being opened when one of these happens is refused, and the far end is let go. **An ordinary end is not a forced one.** An editor that closes, or a session that is lost, ends the connection the way `sshd` does: a terminal is hung up, the pipes of a program are closed, and a server the program started keeps running, because VS Code and Zed rely on their servers outliving a dropped connection (a reconnection finds them). Only the ends above stop everything. **How everything is found** (`endpoint/scope.ts`): every program started for a device has `MOUSSE_EDITOR_SCOPE=<token>` in its environment, where the token is the prefix of this profile's own key and a keyed hash of the device's id (so it is the same after the daemon restarts, and another profile's programs are never taken for this one's); a program keeps it across `fork`, `setsid` and daemonizing. Nothing the daemon keeps in memory is needed to find them. **The sweep** reads the environment of the user's processes (`/proc/<pid>/environ` on Linux, `ps -E` on macOS) and stops every program that carries a marker of this profile whose device is not one of the devices that may have an editor connection now (the roster's devices that pass every check above), with everything below it, looking again until nothing is left. So a block, a switch going off, a revoke (a revoked device is no longer on the roster, so it is not in the allowed list) and Net being turned off reach a server whose starting command exited long ago and whose window closed, with no connection or session of the device left; and they reach one that an earlier run of the daemon started. The sweep runs on every change of a right, when Net is turned off, and once when Net starts. If the key store cannot be read (locked), or the roster cannot, the sweep stops nothing, because it could not tell a device that has the right from one that has not. A connection ended by a block also stops that device's scope at once (its session programs, their process groups, and anything with the marker). The daemon's own process and everything it started are never stopped, even if the daemon was started from an editor's terminal and so carries a marker itself; the marker is removed from the daemon's own environment at start-up, so what it starts later does not carry it. **What this cannot find:** a program that cleared its own environment, left its process group and lost its parent. Linux has cgroup scopes and sub-reapers for that, which Node cannot ask for (it has no `prctl`, and `systemd-run` cannot start a shell with `-` as its first argument), and macOS has nothing; the macOS reading of the environment was not run, it is by analysis, and the macOS manual check in the pull request that added the endpoint gates a release to macOS owners. With the system's SSH server, an editor's own server on this computer (VS Code's detaches with `setsid`) and anything else the login started keeps running until its own idle timeout, as it does on any SSH host; nothing can reach it through Mousse once the tunnel is gone, but it is not stopped.
- **On Windows** (`endpoint/windowsHost.ts`, `native/sshd-helper`). Every session runs under a small helper named `sshd.exe`, shipped in the app's resources (unsigned, like the rest of the Windows build for now), because VS Code's Windows server script refuses to run without an ancestor process of that name and exits when it goes. The helper runs the command line it is given the way Win32-OpenSSH's sshd builds it: `cmd.exe /c "<command>"`, or the owner's OpenSSH `DefaultShell`. It checks that its parent is the process id it was given and takes only job names of Mousse's own form; that is a check against misuse, not a guard, since any program of the user could start it, and it never has more rights than what started it. The program gets the environment a fresh logon of the user gets, which the helper builds from the registry (machine variables, the user's, then the per-logon ones) and never from the daemon's own, plus sshd's session variables and the marker. **The program runs with a copy of the daemon's own token**, checked to be the same user at no higher integrity: the same rights as the daemon, a Mousse terminal or a local terminal (Credential Manager, DPAPI, mapped drives; elevated only if Mousse itself runs elevated), and no privilege is used to start it. This matters because Windows gives any program named `sshd.exe` a redirection guard (an Image File Execution Options entry names the image; it is there with OpenSSH Server installed, and was not checked on a computer without it), and a program started with the helper's own token would inherit it and could not follow a junction a user made (fnm, Scoop, a pnpm `node_modules`); with the daemon's token it can, and the helper is still its parent. **How everything is found and ended:** every program of a device is in one Job object of the device, named `Local\MousseEditor-<marker>`, with `KILL_ON_JOB_CLOSE` and without either breakaway limit, so no program in it can start one outside it (a `Start-Process` server stays in). Node puts every child it starts in a job of its own that ends with the daemon; the helper makes the program outside that job, suspended, puts it in the device's job and only then lets it run. A named job lasts only while a handle to it is open, so a keeper process for each device (the helper's `keep` mode, about 0.6 MB, started detached so it is outside Node's job) holds it while the daemon runs and, after the daemon ends, until nothing is left in the job. So a quit, an update or a restart of Mousse is an ordinary end on Windows as elsewhere, and a daemon that starts again reaches the job by its name (a test kills a separate daemon process and then blocks from a new one). The keepers and helpers run from a copy of the helper in the profile's own folder, versioned by its hash and checked against the packaged file before each use, because the installer of an update stops every program under the install folder, and a keeper stopped that way would end its device's job. The sweep lists the device jobs that exist in the user's logon session and ends those whose device has no right, one asynchronous call each. An ordinary end ends only the session's helper, as sshd's session process goes. A job of Mousse's name is used only when the user (or the user's default owner) owns it and its integrity label is not below medium, so another account or a lower-integrity program cannot hand the daemon a job of its own; to join it the job must also have the limits above, while ending it does not ask for them. A job that holds the calling daemon (one started from an editor's terminal) is not ended. **What this cannot find or prevent:** a program started for the device by a service outside the job (WMI, the Task Scheduler, an out-of-process COM server); a program of the device that changes its own job's limits and leaves it, since the job, like the user's other objects, is the user's to change (the job stops editors and servers that behave, not a device that means to stay, which has many other ways to persist with a login); and another Mousse daemon (another profile, or a development build) that was started from that device's terminal, which is inside the device's job and ends with it. If a keeper is killed by hand while nothing else holds its job, Windows ends the job's programs itself.
- **Limits.** At most four tunnels per device (`limit`) and sixteen on this computer. An id is held from the moment the open is read, before anything is awaited, and an open with an id that is in use or on its way is dropped, so any number of opens made at once, with one id or with many, give at most the tunnels the limits allow, and every one of them is found by a block. The slot is taken before the far end is reached. At most 30 opens a minute per device (`rate_limited`), decided first, before the roster or the policy is read and before anything is written, so a device that keeps asking costs this computer a counter and a reply. Refusals are written to the audit at most once of each kind per device a minute. Each tunnel has a window of 256 KiB per direction in pieces of 32 KiB, with credit given back only after the bytes were written to the local stream, so a slow reader holds a bounded amount and a fast sender is paused; more than the credit is `protocol` and ends the tunnel. The bytes travel on a lane of their own that takes turns with bulk, so an editor cannot starve thread sync and a snapshot cannot starve an editor. A `tunnel.close` is never refused for want of room in the control queue (the mux keeps room for it and sends it ahead of what waits), so a block reaches the other computer even on a busy session. There is no cap on the bytes of a tunnel (an editor's first connection installs its server, which is megabytes, and a remote session is as large as the work in it): every byte is counted in the audit, and what the far end sent counts as read.
- **Relay traffic.** Allowed, and counted against the relay quota. A tunnel is part of the session, so over a Mousse relay (`relay`, `plus-relay`) its bytes are bytes of the session that the relay counts for the principal like any other (1 GiB per hour by default on a self-hosted relay), and a large transfer can use the hour's quota that the rest of the session needs too. The computer that opens the tunnel is told which path is in use (`direct`, or `relay` with the transport named), so its screen can say "through Mousse relay". The editor's first download of its server goes from the owner to the internet directly, not through the relay. Nothing in a tunnel is readable by the relay: it is inside the session's TLS. The relay operator does see the sizes and timing of the session, and a tunnel makes them easy to read (a credit goes back every 64 KiB, so the rate of a transfer is visible).
- **What is audited.** A row for each open (`editor.open`: the path and the transport) and for each end (`editor.close`: the reason, the path, the bytes that went to the SSH server and the bytes it sent back, and the seconds). With the endpoint the `editor.close` row also says how many `exec` and `shell` requests, SFTP sessions and forwards the connection had (counts only), a login is a row (`editor.login`, with the method), and what the endpoint refused is a row of its own (`editor.refused`: `direct-tcpip`, `tcpip-forward`, `streamlocal`, `agent`, `x11`, `subsystem`, `terminal`, `channel_limit`; a refused user name is an `editor.login` row). A refusal that tells the owner something is a row of its own kind (`refused`: `editor_off`, `no_ssh_server`, `no_host_key`, `limit`); refusals for a blocked device, a lost grant, the owner's switch and Net being off are not rows, so a device cannot fill the audit. The first tunnel a device ever opens is also a desktop notification in the windows of this computer ("<device> opened an editor connection to this computer. It is the same as shell access..."), through the same `ui.notify` event as a terminal, with the `editor.open` row for a computer with no window. SSH's content is opaque to Mousse: no command, file name or key press is recorded, and a device with a login can change this computer's own settings and records as under "Terminals".
- **What the endpoint is.** An SSH server (`ssh2` 1.17.0, pinned, no native add-ons) with one instance for each tunnel and no listener, in the daemon's own process (`src/mms/net/editor/endpoint/`). It serves `exec`, `shell` (a login shell on Linux and macOS: argument 0 is `-bash`, and `$SHELL -c` for an exec, as sshd runs them), terminals (a pseudo-terminal with window changes and signals), the `sftp` subsystem (its own SFTP version 3 with OpenSSH's `posix-rename`, `statvfs`, `limits`, `expand-path`, `home-directory` and `hardlink`), and port forwards. It refuses agent forwarding, X11, every other subsystem and every unix-socket forward, in both directions, and the refusals are rows (`editor.refused`, one of each kind a minute per device, no address or name in it). A client's `env` requests are taken only for `LANG`, `LC_*`, `LANGUAGE`, `COLORTERM` and `TERM_PROGRAM*`.
- **What a program of the endpoint gets.** What a login of the user gets under OpenSSH's `sshd`, built from nothing: `USER`, `LOGNAME`, `HOME`, `SHELL`, a standard `PATH` (on Linux the one in `/etc/environment`), `MAIL`, `SSH_CLIENT` and `SSH_CONNECTION` (127.0.0.1), the time zone, the runtime folder (`XDG_RUNTIME_DIR`) and on macOS the per-user temp folder. **Never the daemon's own environment**, which can hold provider keys and Mousse's own variables; a test plants five such variables and checks they are absent. The user's profile then runs on top, as under `sshd`, so what the user keeps in their own shell files is there too. The program runs with the rights of the user the daemon runs as, in that user's session, which is **more than an `sshd` login gets**: on macOS the unlocked login keychain and the privacy permissions of Mousse (reading Documents, Desktop or Downloads may raise a prompt on this computer's screen, named for Mousse, or be refused when nobody is there), on Linux the session's own sockets, and git credential helpers just work. It is the same grant as a Mousse terminal: "same as shell access". The program starts in the user's home folder, not in the thread's folder; the folder is not a boundary.
- **What a forward reaches.** Only this computer's loopback: `direct-tcpip` (`-L`, `-D`, `-W`, and what the editors use) to 127.0.0.0/8, `::1`, `::ffff:127.x` and the word `localhost`, decided on the text of the address before anything is connected, and the word is mapped here, never looked up. Anything else is refused. `-R` binds the loopback only (an empty address, `localhost`, `127.x` and `::1`; `0.0.0.0`, `*` and every other address are refused), as sshd does with `GatewayPorts no`. The consequence is the one a shell has: **every service on this computer's loopback is reachable by the device** (a database, a dev server, Mousse's own local listeners), because a shell could reach them anyway.
- **Files.** SFTP is the whole file system as the user, the same as OpenSSH's `sftp-server`; the thread's folder is where a session starts and no boundary. What the audit says is counts (`exec`, `sftp` and `fwd` in the `editor.close` row), not names.
- **The host key.** One ed25519 key, made the first time it is needed and kept in the Mousse key store (encrypted at rest with the node's other secrets), never in `~/.ssh` or `/etc/ssh`. This computer vouches for its public half in `tunnel.opened` and the other computer pins it under the alias in Mousse's own `known_hosts`, so there is no trust on first use. A key that cannot be read back is replaced, and the other computer takes the replacement on this computer's word over Net. Switching between the endpoint and the system's SSH server changes the key the same way.
- **The library.** `ssh2` has one maintainer. Its release 1.17.0 (2025) is pinned exactly and upgrades are reviewed by hand; its optional native add-ons are neither built nor shipped, so Node's own crypto runs the ciphers. A past advisory (CVE-2020-26301, command injection in client methods on Windows) concerns client use of the library and is fixed before 1.17.0; Terrapin (CVE-2023-48795) is answered by the strict key exchange it has had since 1.15.0. It has no post-quantum key exchange, so OpenSSH 10.1 and later print a notice that the key exchange is not post-quantum; the bytes travel inside the Net session's TLS 1.3, so nothing reads them off the wire. Mousse's config file does not hide the notice: the only options that could (`IgnoreUnknown WarnWeakCrypto` with `WarnWeakCrypto no`) would have to sit outside every `Host` block, where they replace the `IgnoreUnknown` of the user's own file (the first one read wins), and inside a `Host` block they stop an older `ssh` from reading the file at all (it reports a bad option for every host that does not match).
- **Where it runs.** In the daemon's own process. The SSH crypto runs on its thread; the event-loop delay measured while a 96 MiB transfer ran each way through the whole path is in the pull request that added it, and the endpoint moves into a utility process only if that delay is too long.
- **Old computers.** `tunnel.v1` is a session capability, and lane 2 is never used on a session that did not negotiate it (an older build would close the connection on it). The caller of an older computer is told `unsupported`.
- **The calling computer.** On the computer that opens the tunnel, anything that can reach the local daemon can ask for one, as for the router below: it is not a boundary against code that runs as the user there. The owner's switch is the control. The program an editor's `ssh` starts, `mousse-cli net ssh-proxy`, is such a caller: it holds the owner token of the local daemon like every other `mousse-cli` command, asks for a tunnel to one named computer through four local methods (`net.editor.tunnel.open|read|write|close`, `docs/net/editor-ssh-config.md`), and names no host and no port. A tunnel belongs to the local connection that opened it, so a second program cannot read or write it, and it ends with that connection, with its profile binding, after two minutes with nobody reading or writing it, and with Net being turned off. The methods are local owner IPC only: a routed call from another computer is refused `forbidden`. The proxy reads the daemon's owner file and prints one line on stderr when it fails; it holds no key and starts nothing. The methods accept the `cli` client type on purpose: the proxy is a CLI, and the router's `gui`-only rule is for calls that act on another computer's threads.
- **What the alias gives a local process.** Once the `Include` line exists, any process of the user on this computer, an agent's shell included, can run `ssh mousse-<name>` and reach the other computer's SSH server through the tunnel, with no tooling beyond `ssh`. While the far end is the owner's own SSH server, that still needs a login the owner's server accepts (the user's key or agent, which such a process can usually read anyway). With the Mousse SSH endpoint, which authenticates by the device that opened the tunnel, **no key is needed**: the controls are only the owner's per-device switch "Editor connections from this device" (off by default), a block, and the audit, and the audit cannot tell an editor from a script. That has been so since the endpoint became the default. The boundary is still open: it could be narrowed by keeping the Mousse home out of a sandboxed agent's reach, and the endpoint does not do that.
- **Ask.** A computer whose editor connections are off here can ask for them, with the routed row `editor.ask` (`shared/bridge/editorAsk.ts`, `mms/bridge/routed/editorAsks.ts`). It is the least a routed call can be: a read of this computer that takes no key and needs only the grant every routed call needs (Works on threads, not blocked, and this computer's switch for other computers on), so a blocked computer, a phone and a computer that lost its grant are refused before anything runs, and a computer that cannot be asked is told why. It changes no setting. A person here sees "Let <computer>'s editor connect to this computer?" and "Gives shell access." with Allow and Not now (Allow is disabled for the first second the prompt shows), in the window and as a desktop notice (a computer with no window has the audit row, and `mousse-cli bridge limits <node> --editor on`). Only Allow turns the switch on, here, through the code of `bridge.policy` (which checks the device is on the roster) after checking again that the device still has Works on threads; Not now is recorded. One ask per device waits at a time and runs out after ten minutes; a device that is blocked or whose switch goes on meanwhile loses it. Asking again while it waits bothers nobody, after Not now the same computer is told "not now" for 30 minutes, and at most three asks an hour reach a person (`rate_limited`), so a device cannot turn the notice into a stream of prompts. The counters are kept per device and filled in after a restart from the audit by method and time, not from its last rows, so a busy device cannot push its asks out of view. The name shown is cleaned (no control or direction characters, at most 64 characters) and carries the last characters of the device id when another device has the same name; a device that is revoked or loses Works on threads loses its waiting ask. Audited: `editor.ask` for each ask that reached a person, `editor.ask.allowed` and `editor.ask.declined` for the answer, and one `refused` row a minute at most for a repeated ask that was not passed on. The ask carries no folder, command or name; what the owner shows is the name it already holds for the device.
- **The check before an editor opens.** The computer that opens a folder first asks the other computer what an open would meet (`net.editor.probe`, which sends `tunnel.open` with `kind: ssh.check`), so the person is told in words the fixed reasons above (`editor_off`, `no_ssh_server`, `host_untrusted`, `no_host_key`, offline...), instead of an editor window that waits. A check is not an open: the carrier keeps no tunnel, writes no `editor.open` or `editor.close` row (one `editor.check` row says what it found), raises no first-open notice and counts it against a limit of its own, so one click is one open and the open limits are untouched. It passes every check an open passes and reaches the SSH server only with a connection that says nothing. It runs on every open, which is cheap. Mousse's `Include` line in `~/.ssh/config` is added only after it passed, so a refused open leaves that file as it was. Afterwards, once for each computer in a run of the app, `ssh -o BatchMode=yes <name> exit` runs against Mousse's own file of names, in the environment the editor will start with. It is advice only: it cannot tell a computer that takes a password, a passphrase or a touch from one that cannot be signed in to, so it never stops the editor; a refused key becomes a hint after the editor started. It is never run for an address the person approved (a sign-in proved it when it was approved).

#### The caller side: the router

A window of one computer reaches a thread on another computer through a router in its own daemon (`src/mms/bridge/routed/ThreadRouter.ts`). It is behind the `netBridgeThreads` flag, which is on by default and has an effect only while Bridge is on. The window lists the other computers' threads with its own and opens them in the ordinary thread view; a user who turns Bridge on and pairs a computer sees them once that computer holds "Works on threads".

- A thread or project on another computer is named `<nodeId>:<id>` here; the owner's own ids are rewritten to that form in every result, refusal and event (`src/shared/bridge/routedIds.ts` lists the fields), and back in what a window sends. An id is found in any field of a call whose name ends in `Id` or `Ids`, at any depth and inside lists, so a qualified id cannot go unnoticed by being somewhere unexpected; free text is never read for ids. A call that names two computers, or one and this one, is refused.
- Only a connection that says it is a `gui` routes. A CLI connection, a phone's backend and any other kind of connection that names a qualified id gets `forbidden`, and the events of a thread on another computer (its messages, queue and questions with "Always") are not sent to a connection that is not a `gui`. This keeps Mousse's own tools and the CLI from acting on other computers' threads. **It is not a boundary against code that runs as the user.** A connection says what it is in its `hello`; the only secret is the daemon's owner token, which the CLI reads from the Mousse home, and any process of the user can read it, an agent's shell included. Such a process can connect as a `gui` and route through the daemon's unlocked keys. A secret that only the window holds cannot be kept from a process of the same user: the daemon is started detached and outlives the app, and whatever the app can read, that process can read. The controls that hold are the owner's: the switch for other computers, the block, the highest permission mode for the device and the audit, and, on this computer, a passphrase on the key store and a sandbox that hides the Mousse home from the agent's commands. The owner cannot tell a person from an agent on the calling computer, so this rule is the caller's alone.
- A method that is not a row of the routed table is never sent. A call that names a thread on another computer with such a method (permanent delete, for one) is refused with `not_available_remotely`.
- The router sends only the keys the owner's version of the row knows (`net.info` lists the versions). An action the owner lacks is refused with `computer_outdated`, and the rest of that computer keeps working.
- A write is sent with the request id of the window as its idempotency key (`clientRequestId`, or for a send or a queued message the `requestId` the window made). If the link is lost before the reply arrives, the router waits for the link, asks for the result of the same request id, and only sends the request again, with the same id and key, if the owner never saw it. A write that cannot be confirmed is reported as `outcome_uncertain`, never as done and never as failed. A call whose window supplies no request id gets one of its own for that call: a retry by the window after `outcome_uncertain` is a second request, which is why the window refreshes before it offers one. A call has a total time (its own deadline and the wait for a link that went), ends when its window closes, and a read on a connected computer that did not answer in time is not sent again.
- A thread a window keeps in view holds a lease; two windows share one stream, and a thread nobody has in view stays attached for ten minutes. At most 16 threads per computer and 32 in all are attached; a new one lets the oldest go, and tells the owner so its room is free. The transcript of an attached thread is the view the stream feeds, not a second read, so a snapshot and the stream's records cannot disagree. A computer that is offline answers from the copy of the stream kept on disk, marked offline.
- A device the owner blocks loses what it left behind, not only its access: the messages it queued that no turn has started, the "Always for this thread" rules a person on it made, and the turns it caused that are still running. A turn is the device's when its run records the computer (`run.sent_from`): a message sent from it, a queued message of its that has drained into a turn, the continuation after an approval it answered, and a steer of its that became a turn. The clean-up runs when the block is made and again when Bridge starts, so a block made while Bridge was off or cut short by a restart is finished; it removes only what is still there, so running it twice does no harm. A turn that began before a computer was recorded on its run (before this change) is not found; the owner stops it with Stop.

#### Lists of other computers

With the routing flag on, a window's lists (threads, projects, statuses, search, Recently deleted) include the threads of the user's other computers (`src/mms/bridge/routed/mergedLists.ts`).

- **Which computers.** The devices of the roster that are not this one, not revoked, not blocked here, and not phones. The kind the authority recorded wins (a phone never is one); a device of unknown kind counts only if its signed delegation holds "Works on threads", which only computers are given. A phone is never asked for lists, searched, or named as "not searched".
- **What is read.** Each online computer's private lists stream (a stream only this computer may read, opened with `routed.stream.open`) and, for search and Recently deleted, the routed `threads.search` and `threads.inventory` rows with a two-second deadline per computer. A computer that cannot be reached, or does not answer in time, is named as not searched; it never holds a list up. A search from a window ends only the older search of that window, never a Recently deleted read; a search that was replaced says it covered no computer. A routed search reads the transcripts of the newest 100 threads only, so a search typed on one computer is bounded work on the others. An older computer without the lists stream is read through the API a phone uses, at most 64 KiB of it.
- **What is kept on this computer.** In the Net database (a file with no encryption of its own, readable by the user only), per computer: the last lists it sent (thread names, project names and the owner's project folders; at most 2 MiB, with no statuses, so no turn error text), which of its projects were the same repository as one of this computer's (project ids only; it keeps the sidebar groups together while the computer is out of reach, and is asked again when it is back), the place of each of its threads among the rows here (thread ids and numbers), and when each thread was last opened here (for 7 days). The copy is written at most every 30 s and only when it changed, and when a computer is let go of.
- **When it is cleared.** The copies go when the routing flag is turned off, and everything kept for a computer goes when it leaves the roster or is blocked here (checked at every look, and again at the next start), so a computer that left while its stream was being opened is not written back. When another computer blocks this one or turns sharing off, its rows stay in this session marked "not shared" (not "offline"), searches name it as "stopped sharing threads", and its copy on disk is deleted. The places and opening times stay while the flag is off: they are ids and numbers, and keep the order when it is turned on again. Nothing is sent anywhere. The owner's folders are shown as the owner wrote them and are never parsed with this computer's path rules; a record in Recently deleted comes without its folders.
- **What reaches whom.** The merged rows are added only to the lists and events a `gui` connection receives. A CLI, a phone's backend or any other connection gets the lists of this computer alone, and never an event that names a thread of another computer. Storage settings read this computer's trash alone.
- **Size.** A computer's lists are one document that grows with its threads. Above 256 KiB, threads archived more than 30 days ago (and the subagents under them) are left out of the stream. The lists of another computer may have up to 262,144 JSON nodes where the wire parser allows 16,384; the byte bound (32 MiB) and the depth bound are unchanged, and the document is assembled from verified records of a computer of the same user. The shared lists a phone reads keep the wire bound: nothing is known to say a phone's parser takes more.
- **Projects that are the same repository.** A match needs a root commit in common and, where both sides have a remote, one remote in common: a fork, or a project made from the same template, is not the same repository. A match that rests on the root commit alone (one side has no remote) is marked weak and is not used to group: the sidebar makes one group of a project of this computer and the projects of other computers that match it strongly, and nothing else, so a match never changes which computer an action goes to. Matching reads each repository from its top folder, one at a time, shares its answers across callers, stops the Git calls of a slow one, and asks the other computer again only for a repository it has not asked about, or a minute after a failure.
- **Notifications.** A status change of a thread on another computer notifies only if this computer started the thread, sent a message in it, or opened it in the last 7 days, or if the person turned on "All threads on my other computers". A subagent counts as the thread it works for. A first look at a computer's lists, a reconnect and a restart never notify.

## Explicit limits and review evidence

Host signatures prove what a host said, not that its recvTs, meta head or presence delivery is honest. A host may censor, delay a signed removal indefinitely, fork delivery, refuse history and fabricate invite redemption under an issuer-authorized bearer grant. Meta replay catches unauthorized role changes it receives; it is not Byzantine consensus or a global freshness oracle. Honest-host delay windows are policy, not proof of adversarial real-time ordering.

Public channels are readable by the host. Private streams hide plaintext from nonparticipant hosts but expose participants, timing, sizes, control/key epochs and encrypted attachment identifiers. Already delivered data and keys cannot be revoked. Operator bots have the owner's full access; files on disk are shared across audiences. Even a contained reader may read an operator's privately produced project edit. Provider processing/privacy is outside the wire encryption claim.

A stolen root key or decrypted recovery file confers full user authority. Passphrase encryption helps only while the file remains encrypted and the passphrase is safe. ## Host principal limitation

**P0 decision:** v1 trusts a node with its own user's delegated privileges; there is no independent human-intent signature. A compromised space host belonging to the owner can sign as that owner's delegated node, use the owner's direct administrative path, steer that owner's owner-only bots within its capabilities, and forge that owner's presence. Invite evidence does not constrain this direct-owner path. The host cannot sign as an independently keyed member or steer that member's owner-only bot. Threat rows promising non-forgery apply to independent principals, not the host's own user. A separate controller/root authorization scheme would be a new protocol feature, not an unstated protection in v1. Owner-host key compromise and authority-root co-location therefore widen the compromise boundary. Teammate security review remains required before merge.
